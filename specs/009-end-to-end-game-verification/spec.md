## Problem

The mod can build (`dotnet build` passes) and pass internal tests (1447 passed / 0 failed on `dev` @ `0e7b468`), but `In-game runs: 0`. The Phase 2 growth hook (`ApplySoilGrowthModifier()`) reads real soil health data but has never been confirmed to change `Crop.newDay()` behavior in a live SMAPI session. The verification gap blocks `verified` status (Constitution v2.0.0 Gate 3) and prevents confident merge of 19 remaining roadmap features (`ROADMAP.md`).

### Session 2026-10-25 — Clarify (Agent Analysis, Round 3)

- Q: Direção do efeito de crescimento (±1 em `dayOfCurrentPhase`)? → A (autônomo, evidência decompilada): `dayOfCurrentPhase` é contador de progresso na fase; incrementar acelera, decrementar atrasa (vanilla `Crop.newDay` incrementa +1 e avança fase ao atingir `phaseDays[currentPhase]`). O código atual faz `+1` para solo pobre e `−1` para solo saudável — **invertido** (pobre acelera, saudável atrasa), contrariando comentário, agronomia e Gate 3. Correção: solo pobre (`health < 34`) → `−1` (atrasa); solo saudável (`health >= 67`) → `+1` (acelera). Sinais da passagem reversos em todo o spec (ver abaixo). Nota: esta correção assume a abordagem ingênua ±1; se a abordagem multiplicativa de `phaseDays` for adotada (Questão pendente abaixo), o critério muda.
- Q: Escopo de localização do hook de crescimento? → A (autônomo, padrão existente): `ApplySoilGrowthModifier()` hoje escaneia apenas `Game1.currentLocation`, de modo que em jogada normal (host acorda em `FarmHouse`) cultivos da `Farm`/`Greenhouse` nunca são processados. Refatorar para assinatura `ApplySoilGrowthModifier(string locationName)`, resolver via `ILocationProvider.GetLocationByName`, e chamar dentro do loop `foreach (var locationName in farmLocationNames)` de `OnDayStarted` (ao lado de `ProcessDayStart`), removendo a chamada pós-loop. `ILocationProvider` já existe em `ModEntry.cs:90` e deve ser injetado em `ModController` (`ModEntry.cs:127`).
- Q: Guarda de host e idempotência do hook de crescimento? → A (autônomo, Constituição VI + pesquisa SMAPI): `DayStarted` dispara após `newDayAfterFade` (vanilla já avançou +1) **e** após save/load, e dispara em farmhands também. Obrigatório: (i) guarda `if (!Context.IsMainPlayer) return;` no topo de `OnDayStarted` (host-autoritativo; single-player é caso degenerado); (ii) idempotência por chave de dia (`season:dayOfMonth:year`) para evitar reprocessamento em save/load; (iii) guards por localização como em `SoilDecayService._lastProcessedDayByLocation`. Sem (i)/(ii) o fix de localização reintroduziria regressões de dupla entrega proibidas pela Constituição VI.
- Q: Ordenação de `DayStarted` vs. crescimento vanilla? → A (autônomo, pesquisa SMAPI): `DayStarted` dispara **após** `Game1.newDayAfterFade()` e `Crop.newDay` (progresso vanilla já aplicado). Portanto o ±1 ingênuo compõe: solo saudável `+1` → net `+2` (aceleração); solo pobre `−1` → net `0` (sem progresso naquele dia). Documentar como limitação da abordagem ingênua; ver Questão pendente abaixo sobre abordagem multiplicativa.

## Functional Requirements

### FR-001 — Verification Protocol Documented (Scripted Local Primary — A, Clarified 2026-10-25; 4 Components In Scope as Local Script)
- **FR-001a**: Pipeline scriptado local (build → deploy → launch sob Xvfb → cenário → diff de save + reflexão + log → thresholds → quit) como **primário** (`Q10→A`, refinado Clarify 2026-10-25); checklist manual como fallback documentado; 4 componentes (`FR-001a`) em escopo como script local (não framework genérico): (1) `SoilHealthState` save-file comparator; (2) live `Crop` reflection/export helper; (3) structured SMAPI event-capture logger (per-tile); (4) scripted session runner (`STARDEW_GAME_PATH`, `GamePath`) — diferidos para CI-hosted até barreira de DLLs resolvida (`Regra dos Três` / `Constitution` V; `decision.md` 25–28; `AGENTS.md` 124). `ApplySoilGrowthModifier()` executa via `DayStarted` (`ModController.cs` 1767 — não `DryStarted`). Qualidade de colheita FORA do escopo de `verified` desta feature (diferida — `ComputeHarvestQualityRoll` não implementado).
- **FR-001b**: Save-file comparison method: compare `modData/soil_health_data_{saveId}` before/after scripted session; observe `Crop.currentPhase` / `dayOfCurrentPhase` delta via reflection (primary signal per clarification Q3→C); capture SMAPI console log; visual/overlay optional (not required for `verified`).
- **FR-001c**: Define evidence artifacts: `test.md` updated to `verified` only when scripted session produces (i) `SoilHealthState` JSON delta, (ii) crop-phase reflection delta meeting threshold rules (oposicao direcional: tile pobre +1 E tile saudavel -1, nas fronteiras 34/67; a regra anterior Delta +-1 isolado e superseded), and (iii) SMAPI log confirming event execution. Single-source evidence insufficient. Evidence bundle format (Round 2 Clarify 2026-10-25): MIRROR-style directory `evidence-bundle-<run-id>/` with `manifest.json` (schema version, run id, timestamp ISO 8601, tool/game/mod versions, environment) carrying SHA-256 per file; `claims.json` (claim → evidence pointer, risk, safe wording); `artifacts/` (screenshots, SMAPI logs, save-deltas before/after, reflection outputs); JUnit XML (CI integration) and Allure JSON (rich report); honesty levels W (launch/connect) / R (runtime evidence collected) / E (human judgment, never auto-assigned). Offline verifier recomputes digests and validates schema; structural pass ≠ truth. Failure handling (Round 2 Clarify 2026-10-25): 4-state model `pass`/`fail`/`errored`/`partial`/`skipped`; crash → `errored` with attached artifacts; incomplete signal set → `partial` (never auto-promoted to pass); retry only transient/environmental failures with bounded attempts and per-attempt logging; confirmed flakies quarantined with owner and time-box.
