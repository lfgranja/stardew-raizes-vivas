## Execution Rules (user-mandated)

1. **Scaffold/template first** — before hand-writing a file:
   - `Directory.Build.props` MUST be created with `dotnet new buildprops`.
   - `dotnet-tools.json` MUST be updated with `dotnet tool install` (not hand-edited).
   - `packages.lock.json` files MUST be generated with `dotnet restore --use-lock-file`.
   - coverage/duplication baselines MUST be generated by ReportGenerator/jscpd, never typed from memory.
   - GitHub Actions and the Python package have no official scaffold; these are the only documented exceptions. Start them from the contract table and the repo's existing workflow style.
2. **TDD RED gate** — Phase 2 writes every test first. `T018` is a hard blocking checkpoint. No gate implementation file (`scripts/quality-gate/quality_gate/*.py` beyond `__init__.py`, or `.github/workflows/quality-gate.yml`) may be created before `T018` is committed green-as-RED. T001–T008 scaffolding (tool manifest, requirement files, package markers, `.gitignore`, environment/build logs) is test infrastructure and is exempt.
3. **Property-based testing** — pure gate logic (thresholds, baseline IO, ratchet, severity filtering) MUST use Hypothesis property tests (`@given`) for invariants, not only example tests. The gate scripts are Python, so Hypothesis is used instead of the game-side FsCheck stack; the mod assembly stays free of CI tooling.
4. **Parallel waves** — `[P]` tasks are executed with subagent-driven development. Tasks sharing a file are owned by one subagent to avoid conflicting edits (see “Subagent Waves” below).
5. **Verification last** — only Phase 7 tasks attest to success or completeness. An implementation task may record logs, but MUST NOT claim the feature is complete.
6. **Atomic conventional commit after every file edit** — run:
   ```bash
   bash .specify/scripts/atomic-commit-hook.sh <file> "<summary>" "<why>"
   ```
   Every task below is complete only when its edited file(s) are committed and `git status --porcelain` is empty for those files.

## Implementation Strategy

### MVP First

The MVP is **US1** (reliability gate): analyzers enabled, warnings-as-errors, the 155 pre-existing diagnostics remediated or justifiably suppressed, and a clean build. Because the user required all tests first, the MVP still requires the full Phase 2 RED gate; it does not require US2/US3 implementation.

Suggested delivery slices:
1. **Slice 1** — Phase 1 + Phase 2 + US1 (T001–T026).
2. **Slice 2** — US2 (T027–T036).
3. **Slice 3** — US3 (T037–T048).
4. **Slice 4** — Polish (T049–T055).
5. **Slice 5** — Verification (T056–T071); only now may the feature be called complete.

### Incremental Delivery

- Each slice ends with its independent test criterion satisfied, but no completion claim is made until Phase 7.
- If a slice is blocked (for example, `BUILDDEPS_TOKEN` unavailable), record BLOCKED in the relevant log and continue only with tasks that do not depend on it.
- Do not remove SonarCloud in this feature. The removal is a separate follow-up after the 2–4 week parallel-run window.

### Notes

- The quality gate is CI/tooling only; no gameplay, domain, or persistence code changes.
- `LivingRoots.Verification/` and `LivingRoots.Verification.Runner/` contain only build artifacts and are not part of the solution; do not add them to the quality gate.
- The existing `Build and Test` workflow remains unchanged; it is gated by `vars.BUILDDEPS_ENABLED` and has recorded green runs. The new gate reuses its build-deps materialisation pattern but is a separate workflow/check.
- Do not add either the new gate or `Check Formatting` alone to `required_status_checks` until the new gate has at least one genuinely green CI run; the repo’s false-green history is explicit about this.
