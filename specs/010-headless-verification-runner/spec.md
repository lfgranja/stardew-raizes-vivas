## Clarifications

### Session 2026-10-26

- Q: What format should scenario definitions use? → A: **JSON** (validated against a JSON Schema) as the canonical machine format, with an optional human-facing Markdown companion checklist. JSON has no parser dependency in .NET (`System.Text.Json` is built-in); YAML is not used anywhere in the stack and would add a dependency (YAGNI). Thresholds reference `ModConstants` values by name and numeric value.
- Q: How should `Crop.currentPhase`/`dayOfCurrentPhase` be captured unattended? → A: **In-process dump** (verification mod writes JSON at `DayEnding` after `ApplySoilGrowthModifier`, atomic temp-file+rename, "done" sentinel) as the primary oracle; **save-file inspection** of serialized Crop data as an independent cross-check (divergence is diagnostic). Screenshots/OCR are supporting evidence only.
- Q: What mechanism should the runner use to inject scenarios? → A: **SMAPI macros** (`debug runmacro <file>`) for deterministic batch command execution (sleep, warp, item give) + **save file seeding** (StarDojo pattern) for reproducible initial conditions + **custom mod console commands** (e.g., `lr_dump_crop_phase`) for mod-specific state capture. Input simulation (xdotool) is excluded (fragile, non-deterministic). No verification bot mod needed — macros + seeding + custom commands provide sufficient determinism with lower effort and risk. Prior art: StarDojo (arXiv:2507.07445, ECCV 2026).
- Q: How should the runner acquire game files? → A: **Private repository download via GitHub API** using a secret token (`BUILDDEPS_TOKEN`), following the same pattern already used by the dormant `Build and Test` workflow (`.github/workflows/build-and-test.yml`). The user's legally purchased game files are uploaded to a private repo; the runner downloads, verifies checksum, and extracts. This eliminates SteamCMD, Steam Guard, and interactive authentication entirely. The runner fails fast if the token is missing or the repo is inaccessible. No proprietary assemblies are distributed in the public repo.
- Q: Should the Crop-phase dump hook be shipped as a separate verification mod or embedded in LivingRoots? → A: **Separate, dev/CI-only verification mod** (`LivingRoots.Verification`), not embedded in the main mod and not in production builds. SMAPI has no access control on console commands (any `Helper.ConsoleCommands.Add` entry is callable by anyone and shows in `help`); shipping dump code in the production binary leaves it present-but-disabled (CWE-489). The verification mod depends on LivingRoots via manifest `Dependencies`, is built from the same commit, and is excluded from the release zip; main mod exposes only a production-safe ordering signal (event raised after `ApplySoilGrowthModifier` in `OnDayEnding`) so the dump happens deterministically after the modifier. Runtime-gated debug code in the main mod is rejected (CWE-489 / OWASP ASVS 14.3.2). Aligns with FR-004/FR-009 references to "the verification mod."
- Q: How is the reproducible initial save created and maintained? → A: **Hybrid (StarDojo two-phase)**: (1) **milestone saves** — a small set (≤ ~5) of curated binary save folders stored in the **private builddeps repo** (FR-002/NFR-002), each with a JSON save manifest (game version, SMAPI version, save name/id, SHA-256, documented contents); never in the public repo; (2) **per-scenario `init_commands`** — SMAPI macros (`debug runmacro <file>`) + custom commands (`lr_dump_crop_phase`, plus seeding commands) that place the compost bin, insert waste, set crop phases, and set soil health, keeping the mod-specific delta (sidecars `soil_health_data_{saveId}.json` / `composting_bins_{saveId}.json`) **generated, reviewable, and version-stable** rather than opaque binary. Each runner instance copies the milestone save into a temp `XDG_CONFIG_HOME` (FR-018), runs macros, captures the 3 signals, then restores and asserts byte-identical (SC-005). Version bumps are regeneration events. Aligns with FR-006/FR-018.
- Q: What is the download endpoint, retry, and integrity policy for the game archive? → A: **GitHub Releases assets** (`GET /repos/{owner}/{repo}/releases/assets/{asset_id}` with `Accept: application/octet-stream`), fetched via `gh release download` or `curl -L` with `Authorization: Bearer ${BUILDDEPS_TOKEN}` — NOT the Contents API (1,000-entry cap, base64 overhead, 5-min URL expiry) and NOT auto-generated source archives (unstable hashes). **Checksum mandatory**: publish `gamepath.zip.sha256` alongside the asset; verify with `sha256sum -c` before extraction; fail fast on mismatch (treat as security event). **Auth fail-fast**: probe repo/release access first; 401/403/404 are terminal (no retry). **Retry**: exponential backoff with full jitter, 3–5 attempts, only on transient errors (5xx, 429 honoring `Retry-After`, network timeout/reset/DNS); cap total elapsed time (~5 min). **Partial download**: best-effort resume only (CDN `Range` support not guaranteed by GitHub); always verify final SHA-256; on mismatch delete `.part` and restart from byte 0. **Token**: fine-grained PAT scoped to the single private repo with `Contents: read` + `Metadata: read`, stored as `BUILDDEPS_TOKEN` repository secret, shortest viable expiry; upgrade to a GitHub App installation token (15k/hr, 1-hr expiry) for production. **Extraction**: temp dir + atomic swap + 6-assembly preflight; reject partial `.gamepath`. Aligns with FR-002/NFR-002.
- Q: What concrete retry, flakiness, and quarantine parameters should the runner use? → A: **2 retries (3 total attempts) for classified transient classes only** (reuse smoke-validation exit codes: Xvfb/display=10, launch timeout=4, lock contention=6, process conflict=7, save I/O, macro timeout; NOT retryable: threshold violation, crash, incomplete signals, version mismatch, missing dependency=9, host-guard breach); fixed 5 s cooldown (not exponential) between attempts, with mandatory per-attempt artifacts (`attempts/<n>/attempt.json`, stdout/stderr, intermediate verdict, signals). A run is **`flaky`** iff attempt 1 fails with a retryable class AND a later attempt passes. A scenario is **quarantined** only after 2 flaky runs within a rolling 14-day window (or 2 of the last 3 runs), for a 14-day time-box with one 14-day extension (28 days total) then escalate (auto-re-enable + GitHub issue). Owner via resolution chain: `--quarantine-owner` → `QUARANTINE_OWNER` env → git identity → repo owner (lfgranja), recorded in a committed `quarantine.json` registry; CODEOWNERS as future scale-up hook. Quarantined scenarios report as `skipped` in JUnit/Allure. No auto-promotion to `verified` for flaky/quarantined scenarios (FR-016). Constants: `RunnerMaxTransientRetries=2`, `RunnerRetryCooldownMs=5000`, `RunnerFlakyObservationWindowDays=14`, `RunnerFlakyQuarantineTriggerCount=2`, `RunnerQuarantineTimeBoxDays=14`, `RunnerQuarantineExtendedTimeBoxDays=28`. Aligns with FR-011/FR-016/FR-020.
- Q: What is the supported Stardew Valley / SMAPI version matrix and mismatch policy? → A: **Single pinned stable line** — latest Stardew Valley 1.6.x and matching SMAPI release — documented in a version-controlled `compat-matrix.json`; **hard-fail** (exit code 2, abort before Xvfb launch) if game/SMAPI/mod is outside the supported set or below the mod's `MinimumApiVersion`/`MinimumGameVersion`; **warn** (proceed + record deviation in evidence bundle) for newer-than-pinned (forward compat assumed) or unverified-but-in-range combinations; **info** (proceed, log only) for exact matrix match. Detection is file-based before launch (parse `Stardew Valley.dll`, `StardewModdingAPI.dll`, `manifest.json`; mod self-check; matrix classification). Version comparisons use SMAPI's `SemanticVersion` (never `string.Compare`; handle non-standard `1.11` < `1.2` and `-unofficial.*` channel). Mod manifest changes: add `"MinimumGameVersion": "1.6.14"` and bump `"MinimumApiVersion"` from `4.0.0` to `4.4.0` (or `4.5.0`). Mod at `0.x` is best-effort until `1.0.0`. Evidence bundle gains a `compatibility` block (observed/minimum/maximum/tier per component, modSelfCheck, deviation). SMAPI's null `MaximumGameVersion` is recorded as an upper-bound deviation → warn, not info, when observed game exceeds matrix maximum. Aligns with FR-001/FR-002/NFR-001.
- Q: How should a tile with no SoilHealthState entry (missing key) be treated in threshold evaluation? → A: **Non-participant (skipped, no change)** — not health 0 / not Poor. Missing keys and health `<= 0` are non-participants in growth threshold evaluation (FR-010); only strictly positive stored health `< 34` counts as Poor. Missing keys are treated as `0` **only** inside `SaveComparator` (persistence-layer diff, FR-012) and must not be conflated with runtime health (`GetSoilHealth`: missing → NaN → skip → vanilla). Aligns with `ApplySoilGrowthModifier` (`health <= 0f` skip) and spec 009 CHK032.
- Q: Is the automated runner required to support Windows/macOS hosts, or Linux (Xvfb) only? → A: **Linux (Xvfb) hosts only** for the automated runner. NFR-001 narrowed accordingly; the mod remains cross-platform, and Windows/macOS use build + unit tests plus the manual fallback (FR-021 / `VERIFICATION_PROTOCOL.md`). Xvfb has no admin-free, driver-free equivalent on Windows/macOS; CI stays `ubuntu-latest`.
- Q: What observable signal indicates a "host-guard breach" so the runner can classify it as non-retryable? → A: In a scenario tagged as a **farmhand (non-host)** session, a breach is indicated when execution evidence is present (the `Soil growth modifier elapsed: … ms` trace line, or a `phaseDays` mutation in the Crop-phase dump/save) **without** the `Soil growth modifier skipped: not main player.` skip line. Scenario definitions MUST declare the expected player role (host vs. farmhand). Non-retryable (FR-011); never quarantined or auto-promoted.
- Q: For the 5 ms performance gate (FR-013), should the runner hard-fail on a single per-location elapsed-ms trace line > 5 ms, or require p95 over ≥10 warm runs? → A: **Single-shot after a discarded warmup run, with Gen0 collection-count attribution** (middle ground). One warmup invocation is discarded before the measured run; the single per-location elapsed-ms trace line is compared against 5 ms; the Gen0 collection-count delta is recorded in the evidence bundle and, when > 0, the failure is tagged `gc-attributed` (diagnostic; still a fail). Avoids cold-JIT false failures without the harness complexity of a full p95 statistical gate. Aligns with FR-013/FR-014.
- Q: Who should own/distribute the offline evidence-bundle verifier (FR-015) — in-repo script or independent open-source tool? → A: **Independent open-source tool, with an in-repo script as the stepping stone.** Phase 1 (now): in-repo `scripts/verify-evidence-bundle.sh` (stepping stone A) validates the bundle format, verifier logic, and refusal-site behavior while requirements are still emerging. Phase 2 (promotion trigger, per FR-017, once 2+ features/mods reuse the loop): extract to an independently maintained open-source tool (B) with user-supplied trust anchors, documented bounded claims, and refusal-site liveness testing. Aligns with SLSA/in-toto producer→consumer separation and the Regra dos Três (no full external framework before 2+ reuses).
- Q: What public contract should the main mod expose so the dev/CI-only `LivingRoots.Verification` mod can dump Crop phase deterministically after `ApplySoilGrowthModifier` (FR-009/FR-004)? → A: **SMAPI mod-provided API** — override `ModEntry.GetApi()` to return an `ILivingRootsModApi` (SMAPI-free, in `Domain/Interfaces/`) carrying `event EventHandler<SoilGrowthModifierCompletedEventArgs> SoilGrowthModifierCompleted`, raised **synchronously on the game thread at the tail of `OnDayEnding`**, after the `ApplySoilGrowthModifier` loop completes for all locations (success or caught exception), before the day transition; `EventArgs` carry `DayKey`, `IsMainPlayer`, `LocationsProcessed`, `ElapsedMilliseconds`, `Success`, `Error`. The verification mod subscribes via `helper.ModRegistry.GetApi<ILivingRootsModApi>("lfgranja.LivingRoots")` in `GameLoop.GameLaunched`. Subscriber exceptions are isolated. This converts the implicit cross-mod handler-ordering assumption into a deterministic contract and keeps the production binary free of CWE-489 debug code (CWE-489 / OWASP ASVS 14.3.2). Aligns with the existing `ISoilHealthService.OnTileHealthChanged` event template and SMAPI's canonical Integrations API. Prior art: StarDojo (arXiv:2507.07445).
- Q: When the in-process Crop-phase dump and the save-file cross-check disagree, what is the verdict (FR-009/FR-016)? → A: **`partial` (signals disagree), recorded as an Anomaly Report entry; never auto-promoted to `pass`.** The in-process dump remains the primary oracle for Crop behavior and the save-file inspection remains the independent cross-check; divergence is diagnostic/informative (it may expose the documented Phase-2 gap where the hook writes state but `Crop.newDay()` ignores it) and is the most valuable output of the run, not noise — but it still blocks `verified` because the mandatory 3-signal agreement is not satisfied. Resolution requires a new full triad run (all 3 mandatory signals, clean session, frozen+hashed contract) that independently passes; re-running until green is selection bias, not verification. Auto-promotion to `verified` requires all three signals agreeing on a fresh `pass` (FR-016). Aligns with Barr et al. (IEEE TSE 2015) pseudo-oracle formalism and the existing 4-state verdict model.
- Q: What JSON Schema dialect/tooling/location should the Scenario Definition use (FR-007/FR-008/FR-022)? → A: **Draft 2020-12** (`$schema: https://json-schema.org/draft/2020-12/schema`), strict `additionalProperties: false`, absolute `$id` mirroring the file path, `$defs` for reusable fragments, `schemaVersion: const 1` for payload versioning. Location: `specs/010-headless-verification-runner/contracts/scenario.schema.json` (documentation contract) with machine-readable copies under `schemas/scenarios/v1/` once the Rule of Three (≥3 features reusing) justifies extraction. Validation: `JsonSchema.Net` (json-everything, MIT, .NET 6-compatible, System.Text.Json-friendly) in the runner/.NET side; `check-jsonschema`/`ajv-cli` in CI/pre-commit. Bundled `$ref`s at build time (no network at runtime). `System.Text.Json` itself cannot validate (dotnet/runtime #29887). Aligns with the existing `save-data-schema.md` strictness idiom and the evidence-bundle contract.
- Q: How should the runner create a farmhand (non-host) session to test the host-guard path (FR-011/SC-009 criterion 5)? → A: **Split-screen via `debug split` as the default automated path for guard presence**, with manual protocol / Roadmap D1 as the fallback for transport-level claims, and a two-instance host+client launch only when Roadmap D1 is funded. `debug split` sets `ScreenId != 0`, which makes `Context.IsMainPlayer` false, exercising the actual guard branch under test without a second process; the guard itself only checks `Context.IsMainPlayer`, so transport is not under test. The runner MUST document such runs as "host-authority guard exercised, transport not" (honesty level W/R only; E never auto-assigned) to avoid overclaiming. Aligns with the honesty-level discipline and `Invariants/SingleMultiplayerParityInvariantsTests.cs` (live 2-player proof owed to D1).
- Q: Where should the runner locate and update the per-feature `test.md` and the `COMPLETION_SUMMARY.md` / `ROADMAP.md` Gate 3 status on a `pass` verdict (FR-016/FR-017)? → A: **Feature `test.md` under `specs/<NNN-slug>/test.md`** (co-located with the spec), with a `testMdPath` field in the Scenario Definition JSON (fail-fast validated in FR-008) making the target explicit and eliminating slug-resolution ambiguity; root-doc updates via **marker-based injection** using HTML comment anchors (`<!-- GATE3:BEGIN -->` / `<!-- GATE3:END -->`) added to `ROADMAP.md` and `COMPLETION_SUMMARY.md` before the runner touches them, with surgical replacement, idempotency check before write, and a `--check` CI gate. Timestamps update only on actual state change. Aligns with the only existing convention (bug slug-resolution) being insufficient for features, and with the deterministic/idempotent/diff-minimal requirement.
- Q: Should the runner re-download game files on every invocation even when `STARDEW_GAME_PATH` already points to a valid, version-matching install, or skip download and reuse the existing install (cache/idempotent acquisition)? → A: **Cache-first with version+checksum verification.** The runner MUST reuse `STARDEW_GAME_PATH` when (a) all 6 required assemblies are present, (b) game/SMAPI versions classify as INFO or WARN (not HARD-FAIL) against `compat-matrix.json`, and (c) the pinned SHA-256 of the install matches; it MUST acquire from the private repo (FR-002) only on a cache miss (missing/invalid install, version-incompatible, or checksum mismatch). `--force-refresh` bypasses the cache and re-acquires. A cached install MUST still pass the full version-matrix gate and checksum verification before reuse (treat mismatch as a security event). Assumptions A1/A2/A13 are narrowed: download is the fallback/CI path, not the default. Aligns with `research/resilient-github-download.md` §9.2.5 ("skip download if `gamepath.zip` exists and checksum matches") and the project's sparse-cache / temp-swap idiom.
- Q: How does the runner detect and allocate a free Xvfb display number and a disposable save copy for concurrent instances (FR-020) without collision? → A: **Reuse Xvfb `-displayfd` + per-instance `mktemp` temp root.** Each instance starts its own Xvfb with `-displayfd <fd>`; the X server atomically allocates a free display number and writes it back to the fd (no `/tmp/.X*-lock` probe, no TOCTOU race). Save isolation uses a per-instance `temp_root="$(mktemp -d)"` (absolute path) with `XDG_CONFIG_HOME="${temp_root}/xdg"` and the milestone save copied into `${XDG_CONFIG_HOME}/StardewValley/Saves/`; distinct temp roots guarantee distinct save copies and sidecars. The run-wide `flock` from smoke validation is NOT reused as a whole-run gate (only short-lived locks around shared cache/build resources); `preflight_process_conflict` is scoped to the instance's own game process. The original save is hashed before and after and asserted byte-identical (SC-005). Aligns with `scripts/smoke-validation.sh` `display_start()` and `research-report-reproducible-saves.md` §6.
- Q: Should the headless verification runner be delivered as a Docker container image, a bash orchestrator, or a .NET console application — and how is it invoked locally vs. in CI? → A: **Bash orchestrator (extending the `smoke-validation.sh` substrate)** as the delivery form. The runner ships as `scripts/verify-scenario.sh` (or equivalent) that reuses the proven Xvfb `-displayfd` lifecycle, process-group/signal discipline, run log under XDG state, and exit-code taxonomy from spec 008; it downloads game files on cache miss (FR-001/FR-002), deploys the mod + `LivingRoots.Verification` mod, injects via SMAPI macros + save seeding, captures the 3 signals, evaluates thresholds, and writes the MIRROR evidence bundle. Invoked identically locally and in CI mode (`--ci`/non-interactive flag or env detection) per FR-023; in CI it emits JUnit XML + Allure JSON (FR-014) and exits per the exit-code contract (see NFR-003/exit-code table). Docker is deferred until 2+ mods reuse the loop (Regra dos Três), consistent with FR-015's two-phase verifier and A8's aspirational cross-mod reuse. Aligns with the spec's own "orchestration script (Xvfb + SMAPI + macros)" wording (`docs/verification-hook-shipping-report.md`) and the private-repo-download model (no game files to bundle).
- Q: What exit-code contract should the runner use for CI verdict and failure classes? → A: **Full contract (one distinct code per verdict/failure class)**, starting at 18 per the spec 008 allocation rule, reusing smoke codes where they already apply (4 timeout, 6 lock contention, 7 process conflict, 9 missing dependency, 10 display unavailable). Table: `0=PASS`, `18=FAIL` (threshold violation / assertion failure), `19=ERRORED` (crash or incomplete signal set, incl. version mismatch), `20=NO_TESTS` (no scenario discovered / all skipped, quarantined), `21=THRESHOLD` (policy/quality-gate violation), `22=reserved` (future). `ABORTED`/`USAGE`/`CRASH` are covered by inherited smoke codes (4 timeout, 14 usage error, 13 internal error) and are not redefined. `flaky` is metadata (`flaky: true` in JUnit/Allure), never a distinct code; a flaky run exits `18` (FAIL) but is flagged. `skipped` (quarantined) exits `20` (NO_TESTS) with a JUnit `<skipped>` element and is not a failure. `--ignore-exit-code` demotes codes to 0. Aligns with pytest/MTP/TestNG gold-standard class distinction and spec 008 FR-013 (exit code as sole machine-readable signal).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Maintainer runs full verification unattended (Priority: P1) 🎯 MVP

As the maintainer, I want to invoke a single command that builds, deploys, launches Stardew Valley headless under SMAPI, injects the compost→growth scenario, captures all three signals, evaluates thresholds, and produces a pass/fail verdict plus an evidence bundle — without me opening the game, building a farm, planting, watering, or waiting days — so that Gate 3 verification becomes a repeatable, reliable, non-manual process.

**Why this priority**: This is the core value: eliminating the manual gameplay loop that currently blocks `verified` status and makes every feature's verification error-prone and non-reproducible.

**Independent Test**: On a host with `STARDEW_GAME_PATH` configured and a licensed Steam account, running the runner against feature 004's scenario completes unattended and produces (a) a pass/fail verdict, (b) an evidence bundle with all three signals, and (c) an updated `test.md` status — with zero human gameplay input.

**Acceptance Scenarios**:

1. **Given** a clean host with `STARDEW_GAME_PATH` set, Steam credentials configured, and the mod built, **When** the maintainer runs the runner for feature 004, **Then** the runner downloads/verifies game files via SteamCMD, launches Stardew under Xvfb + SMAPI, loads the verification mod, executes the compost→growth scenario, captures all three signals, evaluates thresholds, and exits with a pass/fail verdict — all without human gameplay input.
2. **Given** the runner completes a scenario, **When** the pass/fail verdict is `pass`, **Then** an evidence bundle (MIRROR-style: `manifest.json` with SHA-256 per file, `claims.json`, `artifacts/`, JUnit XML, Allure JSON) is written and `test.md` is updated from `partial` to `verified` with file paths to all three signals.
3. **Given** the runner detects a threshold violation (e.g., poor soil did not slow growth), **When** evaluation completes, **Then** the verdict is `fail` with a diagnostic naming the violated threshold and the observed vs. expected values, and `test.md` is NOT auto-promoted to `verified`.
4. **Given** the runner encounters a crash or incomplete signal set, **When** evaluation completes, **Then** the verdict is `errored` or `partial` (never auto-promoted to `pass`), with attached artifacts and per-attempt logs.

### User Story 2 - Contributor reuses the runner for another feature (Priority: P2)

As a contributor, I want to define a new scenario (checklist + thresholds) for my feature and run the same runner against it, so that Gate 3 verification is reproducible without inventing steps and the same harness serves all 19 roadmap features.

**Why this priority**: Reusability is the stated goal ("para reutilizar para as outras features implementadas, do objetivo, do roadmap e em outros mods"). Without a scenario contract, each feature reinvents verification.

**Independent Test**: A contributor can add a scenario definition for a second feature and run the runner against it without modifying the runner's core, producing a pass/fail verdict and evidence bundle.

**Acceptance Scenarios**:

1. **Given** a contributor has added a scenario definition (checklist + thresholds) for their feature, **When** they invoke the runner with that scenario, **Then** the runner executes it unattended and produces a verdict + evidence bundle identical in structure to US1.
2. **Given** a scenario definition is missing or malformed, **When** the runner starts, **Then** it fails fast with a clear error naming the missing/invalid field, before launching the game.

### User Story 3 - CI runs verification on a self-hosted runner (Priority: P3)

As CI infrastructure, I want the runner to be invocable from a self-hosted runner (with access to the private builddeps repository via `BUILDDEPS_TOKEN`), so that verification can be triggered automatically on push/PR without a human, while public CI remains dormant.

**Why this priority**: Tertiary — the runner must first work locally; CI integration is a follow-on. Public CI (`Build and Test`) stays dormant due to proprietary-DLL barriers.

**Independent Test**: On a self-hosted runner with `STARDEW_GAME_PATH` set and Steam credentials available, the runner executes a scenario and reports pass/fail to CI (JUnit XML + Allure JSON) without human intervention.

**Acceptance Scenarios**:

1. **Given** a self-hosted runner with access to the private builddeps repository via `BUILDDEPS_TOKEN`, **When** the runner is invoked in CI mode, **Then** it downloads game files, runs headless, produces JUnit XML + Allure JSON, and exits with a non-zero code on `fail`/`errored`/`partial`.
2. **Given** the public (GitHub-hosted) CI, **When** a PR is opened, **Then** the runner is NOT invoked (public CI has no game files); the manual/local runner remains the verification path.

### Edge Cases

- What happens when the private builddeps repository is inaccessible or the token is missing/invalid? The runner must fail fast with a clear error naming the missing token or repository, before attempting any download.
- What happens when the game version or SMAPI version mismatches the mod's expected version? The runner MUST detect and report the mismatch **before scenario execution** (before Xvfb launch) using a file-based pre-launch gate: parse `Stardew Valley.dll` (game), `StardewModdingAPI.dll` (SMAPI, using SMAPI's `SemanticVersion` — never `string.Compare`; handle non-standard `1.11` < `1.2` and `-unofficial.*`), and `manifest.json` (mod version, `MinimumApiVersion`, `MinimumGameVersion`); perform mod self-check; classify against a version-controlled `compat-matrix.json` using the 3-tier policy (HARD-FAIL exit code 2 / WARN proceed+record deviation / INFO proceed+log); hard-fail if outside the supported set or below minimums, warn if newer-than-pinned or unverified-but-in-range, info on exact match. Mod manifest must declare `"MinimumGameVersion": "1.6.14"` and bump `"MinimumApiVersion"` to `4.4.0` (or `4.5.0`). Mod at `0.x` is best-effort until `1.0.0`. Evidence bundle gains a `compatibility` block (observed/minimum/maximum/tier per component, modSelfCheck, deviation). SMAPI's null `MaximumGameVersion` is recorded as an upper-bound deviation → warn when observed game exceeds matrix maximum.- What happens when a scenario step times out (e.g., crop does not grow within expected days)? The runner must abort with `errored`/`partial` and attach artifacts.
- What happens when the save file is corrupted or missing after the session? The runner must report `errored` with the before/after state, not crash.
- What happens when `STARDEW_GAME_PATH` is unset or points to an invalid path? The runner must fail fast with a clear error before attempting SteamCMD/game download.
- What happens when Xvfb fails to start or the display is unavailable? The runner must detect and report, not silently proceed.
- How does the runner handle a flaky scenario (passes on retry)? A run is `flaky` iff attempt 1 fails with a retryable class AND a later attempt passes. Flakies are quarantined (with owner and time-box) only after 2 flaky runs within a rolling 14-day window (or 2 of the last 3 runs), for a 14-day time-box with one 14-day extension then escalate; quarantined scenarios report as `skipped` in JUnit/Allure and are never auto-promoted to `verified`. Retry is limited to transient/environmental failures (classified via smoke-validation exit codes) with mandatory per-attempt logging; threshold violations, crashes, incomplete signals, version mismatches, missing dependencies, and host-guard breaches are NOT retried.- What happens when two runner instances run concurrently on the same host? They must use distinct save copies and distinct display numbers to avoid collision.

## Requirements *(mandatory)*

### Functional Requirements

#### Host & Environment

- **FR-001**: The runner MUST verify that `STARDEW_GAME_PATH` is set and points to a valid Stardew Valley + SMAPI installation before any other step; if not, it MUST fail fast with a clear, actionable error. Acquisition is **cache-first**: if `STARDEW_GAME_PATH` already contains a valid install whose game/SMAPI versions classify as INFO or WARN (not HARD-FAIL) against `compat-matrix.json` and whose pinned SHA-256 matches, the runner MUST reuse it without network access (no token required for a cache hit); it MUST acquire from the private repo (FR-002) only when the install is missing, invalid, version-incompatible (HARD-FAIL), or checksum-mismatched. `--force-refresh` bypasses the cache and re-acquires. A cached install MUST still pass the full version-matrix gate and checksum verification before reuse (treat mismatch as a security event).
- **FR-002**: On a cache miss or `--force-refresh` (see FR-001), the runner MUST acquire game files from a **private repository** (e.g., `lfgranja/stardew-raizes-vivas-builddeps` or equivalent) via the GitHub **Releases assets** endpoint (`GET /repos/{owner}/{repo}/releases/assets/{asset_id}`, `Accept: application/octet-stream`), authenticated with a secret token (`BUILDDEPS_TOKEN` or equivalent), following the same pattern already used by the dormant `Build and Test` workflow (`.github/workflows/build-and-test.yml`) but extended with the resilience layer below. The runner MUST NOT use the Contents API (1,000-entry cap, base64 overhead, 5-min URL expiry) or auto-generated source archives (unstable hashes). The runner MUST verify the token is present and valid (probe repo/release access) before attempting download; if the token is missing or the repository is inaccessible, it MUST fail fast with a clear, actionable error. The runner MUST NOT use SteamCMD or interactive Steam authentication — the private-repo pattern eliminates the Steam Guard barrier entirely. The downloaded archive MUST be verified (SHA-256, published as `gamepath.zip.sha256` alongside the asset) before extraction; on mismatch the runner MUST fail fast and treat it as a security event. The runner MUST retry transient failures (5xx, 429 honoring `Retry-After`, network timeout/reset/DNS) with exponential backoff + full jitter (3–5 attempts, capped total elapsed time); 401/403/404 are terminal (no retry). Partial-download recovery is best-effort only (CDN `Range` support is not guaranteed by GitHub): always verify the final SHA-256 and restart from byte 0 on mismatch, using a `.part` temp file + atomic rename. The token MUST be a fine-grained PAT scoped to the single private repo (`Contents: read` + `Metadata: read`), stored as `BUILDDEPS_TOKEN`, shortest viable expiry; upgrade to a GitHub App installation token for production.

- **FR-003**: The runner MUST start a virtual display (Xvfb) and verify it is available before launching the game; if Xvfb fails to start, the runner MUST abort with a clear error.
- **FR-004**: The runner MUST deploy the mod (and the verification mod) into the game's `Mods/` folder and verify deployment succeeded before launch.

#### Launch & Scenario Injection

- **FR-005**: The runner MUST launch Stardew Valley under SMAPI headlessly and wait for the game to reach a ready state (mod loaded, save available) before injecting the scenario.
- **FR-006**: The runner MUST inject the scenario into the game without human input using **SMAPI macros** (`debug runmacro <file>`) for deterministic batch command execution (sleep, warp, item give, etc.) combined with **save file seeding** (StarDojo two-phase pattern) for reproducible initial conditions, plus **custom mod console commands** (e.g., `lr_dump_crop_phase`) for mod-specific state capture. Save seeding is **hybrid**: (i) **milestone saves** (≤ ~5 curated binary save folders) stored in the private builddeps repo with a JSON save manifest (game/SMAPI version, save name/id, SHA-256, documented contents) provide coarse progression; (ii) **per-scenario `init_commands`** (SMAPI macros + custom commands) place the compost bin, insert waste, set crop phases, and set soil health, so mod sidecars (`soil_health_data_{saveId}.json`, `composting_bins_{saveId}.json`) are **generated, reviewable, and version-stable** rather than checked in as opaque binary. The injection mechanism MUST be documented and reproducible. Input simulation (xdotool) is explicitly excluded (fragile, non-deterministic). A verification bot mod is NOT required for *injection* — SMAPI macros + save seeding + custom commands provide sufficient determinism with lower effort and risk. The Crop-phase dump hook itself lives in a separate dev/CI-only verification mod (see Clarifications, Session 2026-10-26), not in the production binary.

- **FR-007**: The runner MUST support a scenario definition (checklist + thresholds) as input, so that different features can be verified without modifying the runner's core. The scenario definition MUST be authored as **JSON** (validated against a JSON Schema), with an optional human-facing **Markdown** companion checklist for contributor readability. JSON is the canonical machine format (no parser dependency in .NET — `System.Text.Json` is built-in; YAML is not used anywhere in the stack and would add a dependency, violating YAGNI). Thresholds in the scenario MUST reference `ModConstants` values by name and numeric value. **Schema contract (clarified):** validated against a **JSON Schema Draft 2020-12** (`$schema: https://json-schema.org/draft/2020-12/schema`), strict (`additionalProperties: false`), absolute `$id` mirroring the file path, `schemaVersion: const 1` for payload versioning, `$defs` for reusable fragments. Contract location: `specs/010-headless-verification-runner/contracts/scenario.schema.json` (documentation) with machine-readable copies under `schemas/scenarios/v1/` once the Rule of Three (≥3 features reusing) justifies extraction. Validation: `JsonSchema.Net` (json-everything, MIT, .NET 6-compatible) on the runner/.NET side; `check-jsonschema`/`ajv-cli` in CI/pre-commit; `$ref`s bundled at build time. Note: `System.Text.Json` cannot validate against JSON Schema (dotnet/runtime #29887). **Required scenario fields (clarified):** a `testMdPath` field (path to `specs/<NNN-slug>/test.md`) is required so the runner knows which file to update on `pass` (FR-016) without guessing; validated fail-fast (FR-008).
- **FR-008**: The runner MUST validate the scenario definition before launch (required fields, valid thresholds, valid boundaries); if invalid, it MUST fail fast with a field-level error.

#### Signal Capture & Evaluation

- **FR-009**: The runner MUST capture all three signals for every run: (i) `SoilHealthState` JSON delta (before/after `modData/soil_health_data_{saveId}.json`), (ii) `Crop.currentPhase` / `dayOfCurrentPhase` delta captured via **in-process dump** (the dev/CI-only `LivingRoots.Verification` mod writes a JSON dump at `DayEnding` *after* `ApplySoilGrowthModifier` has completed, using a production-safe ordering signal exposed by the main mod — not cross-mod handler ordering — with before/after pairs, atomic temp-file+rename, and a "done" sentinel) as the primary oracle, with **save-file inspection** of serialized `Crop` data as an independent cross-check (divergence between dump and save is diagnostic, not noise), and (iii) SMAPI console log excerpt confirming event execution and elapsed ms. **Ordering signal (clarified):** the main mod exposes the timing via an SMAPI mod-provided API (`ModEntry.GetApi()` → `ILivingRootsModApi`, SMAPI-free, in `Domain/Interfaces/`) carrying `event EventHandler<SoilGrowthModifierCompletedEventArgs> SoilGrowthModifierCompleted`, raised **synchronously on the game thread at the tail of `OnDayEnding`**, after the `ApplySoilGrowthModifier` loop completes for all locations (success or caught exception) and before the day transition; the verification mod subscribes via `helper.ModRegistry.GetApi<ILivingRootsModApi>("lfgranja.LivingRoots")` in `GameLoop.GameLaunched`. Subscriber exceptions are isolated. **Divergence policy (clarified):** when the in-process dump and the save-file cross-check disagree, the verdict is `partial` (signals disagree), recorded as an Anomaly Report entry; the dump remains the primary oracle for Crop behavior and the save remains the independent cross-check, and the run is never auto-promoted to `pass` (FR-016); resolution requires a new full triad run that independently passes.

- **FR-010**: The runner MUST apply the threshold rules: poor soil (health < 34) MUST slow growth (1.15× on `phaseDays`), healthy soil (health ≥ 67) MUST accelerate growth (0.85×), moderate [34, 67) MUST be unchanged (1.00×); `phaseDays` MUST never go below 1 and the 99999 sentinel MUST never be touched. Tiles with NaN health MUST be skipped (no change). Tiles with **no SoilHealthState entry (missing key)** and tiles with health `<= 0` MUST be treated as **non-participants (skipped, no change)** — never as Poor soil; only strictly positive stored health `< 34` counts as Poor. (Missing keys are treated as `0` only inside `SaveComparator`, per FR-012, at the persistence layer.)
- **FR-011**: The runner MUST compute a pass/fail/errored/partial/skipped/flaky verdict using the 4-state model plus flaky: crash → `errored` with attached artifacts; incomplete signal set → `partial` (never auto-promoted to `pass`); transient/environmental failure → retry with **bounded attempts** (`RunnerMaxTransientRetries = 2`, i.e. 3 total attempts) for **classified transient classes only** (reuse smoke-validation exit codes: Xvfb/display=10, launch timeout=4, lock contention=6, process conflict=7, save I/O error, macro timeout; NOT retryable: threshold violation, crash, incomplete signals, version mismatch, missing dependency=9, host-guard breach), with a fixed `RunnerRetryCooldownMs = 5000` cooldown and **mandatory per-attempt artifacts** (`attempts/<n>/attempt.json`, stdout/stderr, intermediate verdict, signals); a run is **`flaky`** iff attempt 1 fails with a retryable class AND a later attempt passes. **Confirmed flaky → quarantine** with owner and time-box only after 2 flaky runs within a rolling 14-day window (or 2 of the last 3 runs), for `RunnerQuarantineTimeBoxDays = 14` with one 14-day extension (`RunnerQuarantineExtendedTimeBoxDays = 28`) then escalate (auto-re-enable + GitHub issue); owner via `--quarantine-owner` → `QUARANTINE_OWNER` env → git identity → repo owner (lfgranja), recorded in a committed `quarantine.json` registry. Quarantined scenarios report as `skipped` in JUnit/Allure. No auto-promotion to `verified` for flaky/quarantined scenarios (FR-016). Constants: `RunnerMaxTransientRetries=2`, `RunnerRetryCooldownMs=5000`, `RunnerFlakyObservationWindowDays=14`, `RunnerFlakyQuarantineTriggerCount=2`, `RunnerQuarantineTimeBoxDays=14`, `RunnerQuarantineExtendedTimeBoxDays=28`. **Host-guard breach detection:** in a scenario tagged as a farmhand (non-host) session, a breach is detected when execution evidence is present (the `Soil growth modifier elapsed: … ms` trace line, or a `phaseDays` mutation in the Crop-phase dump/save) without the `Soil growth modifier skipped: not main player.` skip line; scenario definitions MUST declare the expected player role (host vs. farmhand). **Farmhand mechanism (clarified):** the runner uses **split-screen via `debug split`** as the default automated path to flip `Context.IsMainPlayer` to false (exercising the guard branch) without a second process; runs are documented as "host-authority guard exercised, transport not" (honesty levels W/R only; E never auto-assigned). Manual protocol / Roadmap D1 remain the fallback for transport-level claims; a two-instance host+client launch is used only when Roadmap D1 is funded.- **FR-012**: The runner MUST use the `SaveComparator` (0.0001f float tolerance, missing keys treated as 0, NaN tiles ignored) for the SoilHealthState delta, producing `added`/`removed`/`changed` entries. **Layer note:** missing keys are treated as `0` only at the persistence/diff layer (sparse cache); this differs from runtime `GetSoilHealth` (missing → NaN → skip → vanilla) and must not be conflated with threshold evaluation (FR-010), where missing keys are non-participants.
- **FR-013**: The runner MUST parse the SMAPI log for the elapsed-ms trace line and, **after one discarded warmup invocation**, hard-fail if the (single) per-location elapsed-ms value exceeds 5 ms (SC-009 criterion 6). The Gen0 collection-count delta for the measured invocation MUST be recorded in the evidence bundle; when it is > 0 the failure is tagged `gc-attributed` (diagnostic only — still a fail). The elapsed value is per location (up to 3 lines per day); each is evaluated independently.

#### Evidence & Output

- **FR-014**: The runner MUST produce a MIRROR-style evidence bundle: `manifest.json` (schema version, run id, timestamp ISO 8601, tool/game/mod versions, environment, SHA-256 per file), `claims.json` (claim → evidence pointer, risk, safe wording), `artifacts/` (screenshots, SMAPI logs, save-deltas before/after, reflection outputs), JUnit XML (CI), and Allure JSON (rich report). Honesty levels: W (launch/connect) / R (runtime evidence collected) / E (human judgment, never auto-assigned).
- **FR-015**: The runner MUST produce an offline-verifiable bundle: a verifier recomputes digests and validates schema; structural pass ≠ truth. **Verifier ownership (two-phase):** Phase 1 (stepping stone) — an in-repo `scripts/verify-evidence-bundle.sh` is maintained with the mod to validate bundle format, verifier logic, and refusal-site behavior while requirements emerge. Phase 2 (promotion trigger, per FR-017, once 2+ features/mods reuse the loop) — extract to an independently maintained open-source tool with user-supplied trust anchors, documented bounded claims, and refusal-site liveness testing. The bundle producer is never the sole trust anchor in Phase 2.
- **FR-016**: The runner MUST update `test.md` from `partial` to `verified` only when all three signals agree and the verdict is `pass`; on `fail`/`errored`/`partial`, it MUST NOT auto-promote. **Location (clarified):** the target is `specs/<NNN-slug>/test.md` (co-located with the spec), identified via a `testMdPath` field in the Scenario Definition JSON (fail-fast validated in FR-008); the runner MUST NOT guess or use slug-resolution.
- **FR-017**: The runner MUST update `COMPLETION_SUMMARY.md` and `ROADMAP.md` Gate 3 status on a `pass` verdict, recording the promotion trigger for deferred components (reflector/logger/runner promoted only after 2+ features reuse the loop). **Mechanism (clarified):** updates use marker-based injection via HTML comment anchors (`<!-- GATE3:BEGIN -->` / `<!-- GATE3:END -->`) that MUST be added to `ROADMAP.md` and `COMPLETION_SUMMARY.md` before the runner touches them; surgical replacement with an idempotency check before write and a `--check` CI gate; timestamps update only on actual state change.

#### Process & Lifecycle

- **FR-018**: The runner MUST always run against a disposable copy of the save (never the player's real save); it MUST back up/restore `Saves/<Name>/` and sidecars, using `XDG_CONFIG_HOME` pointing to a temp dir; the original save MUST be byte-identical at the end.
- **FR-019**: The runner MUST quit the game cleanly after scenario completion and capture all artifacts before exit.
- **FR-020**: The runner MUST support concurrent instances on the same host using distinct save copies and distinct display numbers. Display numbers are allocated by Xvfb via `-displayfd` (each instance starts its own Xvfb; the server atomically picks a free number; no `/tmp/.X*-lock` probe, no TOCTOU race). Save isolation uses a per-instance `temp_root="$(mktemp -d)"` (absolute path) with `XDG_CONFIG_HOME="${temp_root}/xdg"` and the milestone save copied into `${XDG_CONFIG_HOME}/StardewValley/Saves/`; distinct temp roots guarantee distinct save copies and sidecars. The run-wide `flock` from smoke validation is NOT reused as a whole-run gate (only short-lived locks around shared cache/build resources); `preflight_process_conflict` is scoped to the instance's own game process. The original save is hashed before and after and asserted byte-identical (SC-005).
- **FR-021**: The runner MUST preserve the manual SC-009 protocol as a documented fallback (`VERIFICATION_PROTOCOL.md` §3, `gate3-verification-contract.md`) for hosts where the runner cannot execute.

#### Reusability

- **FR-022**: The runner MUST expose a scenario contract so that a feature can define its own scenario (steps + thresholds) without modifying the runner's core.
- **FR-023**: The runner MUST be invocable both locally (interactive) and in CI mode (non-interactive, machine-readable output).

### Key Entities

- **Scenario Definition**: A declarative description of a verification scenario — steps (place bin, insert waste, sleep N days, harvest, apply compost, observe), expected signals, and threshold rules. Provided by a feature; consumed by the runner.
- **Evidence Bundle**: A directory (`evidence-bundle-<run-id>/`) containing `manifest.json`, `claims.json`, `artifacts/`, JUnit XML, and Allure JSON. Produced by every run.
- **Run Verdict**: One of `pass` / `fail` / `errored` / `partial` / `skipped`, with attached diagnostics and artifact paths.
- **Signal Set**: The three required signals (SoilHealthState delta, Crop phase delta, SMAPI log) plus optional visual evidence.

### Non-Functional Requirements

- **NFR-001**: The runner MUST be reproducible on any **Linux** host with `STARDEW_GAME_PATH` set and a licensed Steam account (Xvfb + software GL); it MUST NOT require changes to the mod's source code. Windows/macOS hosts use build + unit tests plus the manual fallback (FR-021).
- **NFR-002**: The runner MUST NOT distribute or embed proprietary game assemblies in the public repository; it MUST acquire them from a private repository via authenticated API (secret token). The runner relies on a pre-configured host with access to the private repo.
- **NFR-003**: The runner MUST produce a non-zero exit code on `fail`/`errored`/`partial` for CI integration, per the exit-code contract in the table below (full contract, one distinct code per verdict/failure class). Flaky runs exit `1` (FAIL) but are flagged via metadata; `skipped` (quarantined) exits `5` (NO_TESTS) with a JUnit `<skipped>` element. The runner MUST support `--ignore-exit-code` to demote codes to 0 without altering behavior, and MUST publish the enum as a public, semver-governed contract (spec 008 FR-013: exit code is the sole machine-readable signal).
- **NFR-004**: The runner MUST log each step with timestamps for debugging; on failure, it MUST attach all available artifacts.

#### Exit Codes (CI contract)

The runner publishes the following exit-code contract (public, semver-governed; spec 008 FR-013 makes the exit code the sole machine-readable signal). Infrastructure failure classes are **inherited unchanged** from the spec 008 smoke taxonomy (codes 1–17, with 8 retired and never reused); the runner's own verdict/failure classes are allocated **starting at 18** per the spec 008 allocation rule ("new categories take the next value above the highest published code"), so no published code is ever re-assigned. Reserved ranges (64–78, 100–254, 126, 127, ≥128) are never used.

| Code | Class | Meaning |
|------|-------|---------|
| 0 | PASS | All selected tests ran and passed (warnings allowed) |
| 1–17 | (inherited) | Smoke infrastructure codes, unchanged (spec 008 taxonomy): 1 game not found, 2 SMAPI not found, 3 graphics unusable, 4 timeout, 5 mod load failure, 6 lock contention, 7 process conflict, 9 missing dependency, 10 display unavailable, 11 steam prereq, 12 build artifact, 13 internal error, 14 usage error, 15 no log produced, 16 manifest invalid, 17 resolution aborted; 8 retired (never reused) |
| 18 | FAIL | Threshold violation / assertion failure (verdict `fail`) |
| 19 | ERRORED | Crash or incomplete signal set (verdict `errored`/`partial`), incl. version mismatch |
| 20 | NO_TESTS | No scenario discovered / all skipped (quarantined) (verdict `skipped`) |
| 21 | THRESHOLD | Policy / quality-gate violation (e.g. minimum-expected-tests, coverage threshold) |
| 22 | reserved | Future use (flaky-only or partial-success); unused |

`flaky` is reported as metadata (`flaky: true` in JUnit/Allure), never a distinct code; a flaky run exits `18` (FAIL) but is flagged. `skipped` (quarantined) exits `20` (NO_TESTS) with a JUnit `<skipped>` element and is not a failure. Version mismatch classifies as `ERRORED` (19). `ABORTED`/`USAGE`/`CRASH` are covered by the inherited smoke codes (4 timeout, 14 usage error, 13 internal error) and are not redefined. `--ignore-exit-code` demotes codes to 0 without altering behavior. The enum is published as a public, semver-governed contract.

Docker is deferred until 2+ mods reuse the loop (Regra dos Três); no Dockerfile/registry exists today. Aligns with the spec's "orchestration script (Xvfb + SMAPI + macros)" wording and the private-repo-download model (no game files to bundle).
