## Plain-Language Summary

The runner is a single command a maintainer can run on a Linux machine to prove that a gameplay feature actually works, without opening the game or playing it by hand. It starts a hidden display, launches Stardew Valley through SMAPI, loads a reproducible save, performs a short scripted scenario, and records three independent kinds of evidence: the mod's saved soil-health data, the crop's growth state, and the SMAPI log. It then compares the evidence with the feature's expected thresholds and writes a pass/fail report plus a tamper-evident evidence bundle. On a clean pass it updates the feature's Gate 3 record; on any doubt it refuses to promote the feature.

**Who this is for**: maintainers who need trustworthy Gate 3 evidence; contributors who want to add a scenario for their feature without changing the runner; CI operators who need a machine-readable verdict. This is a **layered specification**: the Plain-Language Summary, User Scenarios, and Success Criteria are written to be restated by a non-specialist; the normative FR/NFR sections use the precise technical vocabulary implementers need and are exempt from lay-readability. Every claim in the summary maps to a requirement ID, and the normative technical details live in the FR/NFR sections and the linked contracts under `contracts/`.

**Glossary**

| Term | Meaning |
|------|---------|
| **Runner** | The orchestration entry point that acquires/validates the game, launches it headlessly, injects a scenario, captures signals, evaluates thresholds, and writes evidence. |
| **Scenario** | A declarative JSON description of one verification: setup, ordered steps, expected signals, thresholds, and the `test.md` target. |
| **Signal** | One observation channel: persisted soil-health delta, crop-phase delta (in-process dump plus save cross-check), or SMAPI log excerpt. |
| **Verdict** | One of five base outcomes: `pass`, `fail`, `errored`, `partial`, `skipped`; `flaky` is derived metadata, not a sixth verdict. |
| **Evidence bundle** | The run directory containing `manifest.json`, `claims.json`, artifacts, per-attempt records, and CI reports. |
| **Gate 3 / GATE3 block** | The project's end-to-end verification gate and the marker-delimited block in `specs/<NNN-slug>/test.md` that records its status. |
| **Honesty level** | W (launch/connect only), R (runtime evidence collected), E (human judgment). `verified` status requires R; E is a separate human attestation and is never auto-assigned. |
| **Quarantine** | A human-approved, time-boxed removal of a persistently flaky scenario from the blocking gate; it never means the scenario passed. |
| **Milestone save** | A curated, versioned save folder in the private builddeps repository used as the reproducible starting point. |

## Scope and Implementation-Detail Boundary

**In scope (Phase 1)**: Linux/Xvfb unattended execution; private-repository game-file acquisition with cache-first reuse; scenario JSON contract; three-signal capture; threshold evaluation; verdict/exit-code contract; evidence bundle and offline verification; retry/flaky/quarantine handling; concurrent local instances; save preservation; CI-mode invocation; the dev/CI-only verification mod and the production-safe ordering API it consumes.

**Out of scope (Phase 1)**: Windows/macOS automated execution (manual fallback applies); Docker/container delivery; interactive game-store authentication; distribution of proprietary assemblies; public GitHub-hosted CI execution with game files; a second runtime implementation; Sigstore/DSSE signing; external SIEM integration; multi-mod packaging/distribution. Deferred items and their promotion triggers are listed in the Assumptions and `GOVERNANCE-ANNEX.md`.

**Implementation-detail policy**: Functional requirements state observable behaviour, contracts, and safety invariants. Names of external systems the runner must interoperate with (Stardew Valley, SMAPI, Xvfb, GitHub Releases, the game's save format) are in scope because they are the feature's subject. Programming-language, library, test-framework, and packaging choices are implementation decisions and live in `plan.md`, not in the FRs. Where a requirement needs a precise mechanism to be testable (for example atomic-write ordering), the mechanism is delegated to a named contract (`CONCURRENCY.md`, `contracts/scenario.schema.json`, `contracts/exit-codes.md`) and the FR states the required observable outcome.

## Clarifications

### Session 2026-10-26

- Q: What format should scenario definitions use? → A: **JSON** (validated against a JSON Schema) as the canonical machine format, with an optional human-facing Markdown companion checklist. JSON has no parser dependency in .NET (`System.Text.Json` is built-in); YAML is not used anywhere in the stack and would add a dependency (YAGNI). Thresholds reference `ModConstants` values by name and numeric value.
- Q: How should `Crop.currentPhase`/`dayOfCurrentPhase` be captured unattended? → A: **In-process dump** (verification mod writes JSON at `DayEnding` after `ApplySoilGrowthModifier`, atomic temp-file+rename, "done" sentinel) as the primary oracle; **save-file inspection** of serialized Crop data as an independent cross-check (divergence is diagnostic). Screenshots/OCR are supporting evidence only.
- Q: What mechanism should the runner use to inject scenarios? → A: **SMAPI macros** (`debug runmacro <file>`) for deterministic batch command execution (sleep, warp, item give) + **save file seeding** (StarDojo pattern) for reproducible initial conditions + **custom mod console commands** (e.g., `lr_dump_crop_phase`) for mod-specific state capture. Input simulation (xdotool) is excluded (fragile, non-deterministic). No verification bot mod needed — macros + seeding + custom commands provide sufficient determinism with lower effort and risk. Prior art: StarDojo (arXiv:2507.07445, ECCV 2026).
- Q: How should the runner acquire game files? → A: **Private repository download via GitHub API** using a secret token (`BUILDDEPS_TOKEN`), following the same pattern already used by the dormant `Build and Test` workflow (`.github/workflows/build_and_test.yml`). The user's legally purchased game files are uploaded to a private repo; the runner downloads, verifies checksum, and extracts. This eliminates interactive game-store authentication entirely. The runner fails fast if the token is missing or the repo is inaccessible. No proprietary assemblies are distributed in the public repo.
- Q: Should the Crop-phase dump hook be shipped as a separate verification mod or embedded in LivingRoots? → A: **Separate, dev/CI-only verification mod** (`LivingRoots.Verification`), not embedded in the main mod and not in production builds. SMAPI has no access control on console commands (any `Helper.ConsoleCommands.Add` entry is callable by anyone and shows in `help`); shipping dump code in the production binary leaves it present-but-disabled (CWE-489). The verification mod depends on LivingRoots via manifest `Dependencies`, is built from the same commit, and is excluded from the release zip; main mod exposes only a production-safe ordering signal (event raised after `ApplySoilGrowthModifier` in `OnDayEnding`) so the dump happens deterministically after the modifier. Runtime-gated debug code in the main mod is rejected (CWE-489 / OWASP ASVS 14.3.2). Aligns with FR-004/FR-009 references to "the verification mod."
- Q: How is the reproducible initial save created and maintained? → A: **Hybrid (StarDojo two-phase)**: (1) **milestone saves** — a small set (≤ ~5) of curated binary save folders stored in the **private builddeps repo** (FR-002/NFR-002), each with a JSON save manifest (game version, SMAPI version, save name/id, SHA-256, documented contents); never in the public repo; (2) **per-scenario `initCommands`** — SMAPI macros (`debug runmacro <file>`) + custom commands (`lr_dump_crop_phase`, plus seeding commands) that place the compost bin, insert waste, set crop phases, and set soil health, keeping the mod-specific delta (sidecars `soil_health_data_{saveId}.json` / `composting_bins_{saveId}.json`) **generated, reviewable, and version-stable** rather than opaque binary. Each runner instance copies the milestone save into a temp `XDG_CONFIG_HOME` (FR-018), runs macros, captures the 3 signals, then restores and asserts byte-identical (SC-005). Version bumps are regeneration events. Aligns with FR-006/FR-018.
- Q: What is the download endpoint, retry, and integrity policy for the game archive? → A: **GitHub Releases assets** (`GET /repos/{owner}/{repo}/releases/assets/{asset_id}` with `Accept: application/octet-stream`), fetched via `gh release download` or `curl -L` with `Authorization: Bearer ${BUILDDEPS_TOKEN}` — NOT the Contents API (1,000-entry cap, base64 overhead, 5-min URL expiry) and NOT auto-generated source archives (unstable hashes). **Checksum mandatory**: the authoritative SHA-256 is pinned in the reviewed `gamepath.lock.json` (updated only by reviewed PR); the release's `gamepath.zip.sha256` is advisory and may be compared but never trusted alone. Verify with `sha256sum -c` against the pinned digest before extraction; fail fast on mismatch (treat as security event). **Auth fail-fast**: probe repo/release access first; 401/403/404 are terminal (no retry). **Retry**: exponential backoff with full jitter, 3–5 attempts, only on transient errors (5xx, 429 honoring `Retry-After`, network timeout/reset/DNS); cap total elapsed time (~5 min). **Partial download**: best-effort resume only (CDN `Range` support not guaranteed by GitHub); always verify final SHA-256; on mismatch delete `.part` and restart from byte 0. **Token**: fine-grained PAT scoped to the single private repo with `Contents: read` + `Metadata: read`, stored as `BUILDDEPS_TOKEN` repository secret, shortest viable expiry; upgrade to a GitHub App installation token (15k/hr, 1-hr expiry) for production. **Extraction**: temp dir + atomic swap + 6-assembly preflight; reject partial `.gamepath`. Aligns with FR-002/NFR-002.
- Q: What concrete retry, flakiness, and quarantine parameters should the runner use? → A: **2 retries (3 total attempts) for classified transient classes only** (reuse smoke-validation exit codes: Xvfb/display=10, launch timeout=4, lock contention=6, process conflict=7, save I/O, macro timeout; NOT retryable: threshold violation, crash, incomplete signals, version mismatch, missing dependency=9, host-guard breach); fixed 5 s cooldown (not exponential) between attempts, with mandatory per-attempt artifacts (`attempts/<n>/attempt.json`, stdout/stderr, intermediate verdict, signals). A run is **`flaky`** iff attempt 1 fails with a retryable class AND a later attempt passes; a flaky run exits `0` (PASS) with `flaky: true` and is never counted as a failure. A scenario is **quarantined** only after 2 flaky runs within a rolling 14-day window (or 2 of the last 3 runs), for a 14-day time-box with one 14-day extension (28-day hard cap, no second extension) then escalate (auto-disable + GitHub issue). Owner via resolution chain: `--quarantine-owner` → `QUARANTINE_OWNER` env → git identity → repo owner (lfgranja), recorded in a committed `quarantine.json` registry; CODEOWNERS as future scale-up hook. Quarantined scenarios report as `skipped` in JUnit/Allure. No auto-promotion to `verified` for flaky/quarantined scenarios (FR-016). Constants: `RunnerMaxTransientRetries=2`, `RunnerRetryCooldownMs=5000`, `RunnerFlakyObservationWindowDays=14`, `RunnerFlakyQuarantineTriggerCount=2`, `RunnerQuarantineTimeBoxDays=14`, `RunnerQuarantineExtendedTimeBoxDays=28`. Aligns with FR-011/FR-016/FR-020.
- Q: What is the supported Stardew Valley / SMAPI version matrix and mismatch policy? → A: **Single pinned stable line** — latest Stardew Valley 1.6.x and matching SMAPI release — documented in a version-controlled `compat-matrix.json`; **hard-fail** (exit code 19, abort before Xvfb launch) if game/SMAPI/mod is outside the supported set or below the mod's `MinimumApiVersion`/`MinimumGameVersion`; **warn** (proceed + record deviation in evidence bundle) for newer-than-pinned (forward compat assumed) or unverified-but-in-range combinations; **info** (proceed, log only) for exact matrix match. Detection is file-based before launch (parse `Stardew Valley.dll`, `StardewModdingAPI.dll`, `manifest.json`; mod self-check; matrix classification). Version comparisons use SMAPI's `SemanticVersion` (never `string.Compare`; handle non-standard `1.11` < `1.2` and `-unofficial.*` channel). Mod manifest changes: add `"MinimumGameVersion": "1.6.14"` and bump `"MinimumApiVersion"` from `4.0.0` to `4.4.0` (or `4.5.0`). Mod at `0.x` is best-effort until `1.0.0`. Evidence bundle gains a `compatibility` block (observed/minimum/maximum/tier per component, modSelfCheck, deviation). SMAPI's null `MaximumGameVersion` is recorded as an upper-bound deviation → warn, not info, when observed game exceeds matrix maximum. Aligns with FR-001/FR-002/NFR-001.
- Q: How should a tile with no SoilHealthState entry (missing key) be treated in threshold evaluation? → A: **Non-participant (skipped, no change)** — not health 0 / not Poor. Missing keys and health `<= 0` are non-participants in growth threshold evaluation (FR-010); only strictly positive stored health `< 34` counts as Poor. Missing keys are treated as `0` **only** inside `SaveComparator` (persistence-layer diff, FR-012) and must not be conflated with runtime health (`GetSoilHealth`: missing → NaN → skip → vanilla). Aligns with `ApplySoilGrowthModifier` (`health <= 0f` skip) and spec 009 CHK032.
- Q: Is the automated runner required to support Windows/macOS hosts, or Linux (Xvfb) only? → A: **Linux (Xvfb) hosts only** for the automated runner. NFR-001 narrowed accordingly; the mod remains cross-platform, and Windows/macOS use build + unit tests plus the manual fallback (FR-021 / `VERIFICATION_PROTOCOL.md`). Xvfb has no admin-free, driver-free equivalent on Windows/macOS; CI stays `ubuntu-latest`.
- Q: What observable signal indicates a "host-guard breach" so the runner can classify it as non-retryable? → A: In a scenario tagged as a **farmhand (non-host)** session, a breach is indicated when execution evidence is present (the `Soil growth modifier elapsed: … ms` trace line, or a `phaseDays` mutation in the Crop-phase dump/save) **without** the `Soil growth modifier skipped: not main player.` skip line. Scenario definitions MUST declare the expected player role (host vs. farmhand). Non-retryable (FR-011); never quarantined or auto-promoted.
- Q: For the 5 ms performance gate (FR-013), should the runner hard-fail on a single per-location elapsed-ms trace line > 5 ms, or require p95 over ≥10 warm runs? → A: **Single-shot after a discarded warmup run, with Gen0 collection-count attribution** (middle ground). One warmup invocation is discarded before the measured run; the single per-location elapsed-ms trace line is compared against 5 ms; the Gen0 collection-count delta is recorded in the evidence bundle and, when > 0, the failure is tagged `gc-attributed` (diagnostic; still a fail). Avoids cold-JIT false failures without the harness complexity of a full p95 statistical gate. Aligns with FR-013/FR-014.
- Q: Who should own/distribute the offline evidence-bundle verifier (FR-015) — in-repo script or independent open-source tool? → A: **Independent open-source tool, with an in-repo script as the stepping stone.** Phase 1 (now): in-repo `scripts/verify-evidence-bundle.sh` (stepping stone A) validates the bundle format, verifier logic, and refusal-site behavior while requirements are still emerging. Phase 2 (promotion trigger, per FR-017, once 2+ features/mods reuse the loop): extract to an independently maintained open-source tool (B) with user-supplied trust anchors, documented bounded claims, and refusal-site liveness testing. Aligns with SLSA/in-toto producer→consumer separation and the Regra dos Três (no full external framework before 2+ reuses).
- Q: What public contract should the main mod expose so the dev/CI-only `LivingRoots.Verification` mod can dump Crop phase deterministically after `ApplySoilGrowthModifier` (FR-009/FR-004)? → A: **SMAPI mod-provided API** — override `ModEntry.GetApi()` to return an `ILivingRootsModApi` (SMAPI-free, in `Domain/Interfaces/`) carrying `event EventHandler<SoilGrowthModifierCompletedEventArgs> SoilGrowthModifierCompleted`, raised **synchronously on the game thread at the tail of `OnDayEnding`**, after the `ApplySoilGrowthModifier` loop completes for all locations (success or caught exception), before the day transition; `EventArgs` carry `DayKey`, `IsMainPlayer`, `LocationsProcessed`, `ElapsedMilliseconds`, `Success`, `Error`. The verification mod subscribes via `helper.ModRegistry.GetApi<ILivingRootsModApi>("lfgranja.LivingRoots")` in `GameLoop.GameLaunched`. Subscriber exceptions are isolated. This converts the implicit cross-mod handler-ordering assumption into a deterministic contract and keeps the production binary free of CWE-489 debug code (CWE-489 / OWASP ASVS 14.3.2). Aligns with the existing `ISoilHealthService.OnTileHealthChanged` event template and SMAPI's canonical Integrations API. Prior art: StarDojo (arXiv:2507.07445).
- Q: When the in-process Crop-phase dump and the save-file cross-check disagree, what is the verdict (FR-009/FR-016)? → A: **`partial` (signals disagree), recorded as an Anomaly Report entry; never auto-promoted to `pass`.** The in-process dump remains the primary oracle for Crop behavior and the save-file inspection remains the independent cross-check; divergence is diagnostic/informative (it may expose the documented Phase-2 gap where the hook writes state but `Crop.newDay()` ignores it) and is the most valuable output of the run, not noise — but it still blocks `verified` because the mandatory 3-signal agreement is not satisfied. Resolution requires a new full triad run (all 3 mandatory signals, clean session, frozen+hashed contract) that independently passes; re-running until green is selection bias, not verification. Auto-promotion to `verified` requires all three signals agreeing on a fresh `pass` (FR-016). Aligns with Barr et al. (IEEE TSE 2015) pseudo-oracle formalism and the existing five-base-verdict model.
- Q: What JSON Schema dialect/tooling/location should the Scenario Definition use (FR-007/FR-008/FR-022)? → A: **Draft 2020-12** (`$schema: https://json-schema.org/draft/2020-12/schema`), strict `additionalProperties: false`, a versioned logical `$id` (`urn:lfgranja:livingroots:scenario:v2`) that is not a file-path mirror, `$defs` for reusable fragments, `schemaVersion: const 2` for payload versioning (v2 makes the structured `thresholds[].predicate` the machine oracle; `condition` is optional v1 migration provenance, never the oracle). Location: `specs/010-headless-verification-runner/contracts/scenario.schema.json` (documentation contract) with machine-readable copies under `schemas/scenarios/v2/` once the Rule of Three (≥3 features reusing) justifies extraction. Validation: `JsonSchema.Net` (json-everything, MIT, .NET 6-compatible, System.Text.Json-friendly) in the runner/.NET side; `check-jsonschema`/`ajv-cli` in CI/pre-commit. Bundled `$ref`s at build time (no network at runtime). `System.Text.Json` itself cannot validate (dotnet/runtime #29887). Aligns with the existing `save-data-schema.md` strictness idiom and the evidence-bundle contract.
- Q: How should the runner create a farmhand (non-host) session to test the host-guard path (FR-011/SC-009 criterion 5)? → A: **Split-screen via `debug split` as the default automated path for guard presence**, with manual protocol / Roadmap D1 as the fallback for transport-level claims, and a two-instance host+client launch only when Roadmap D1 is funded. `debug split` sets `ScreenId != 0`, which makes `Context.IsMainPlayer` false, exercising the actual guard branch under test without a second process; the guard itself only checks `Context.IsMainPlayer`, so transport is not under test. The runner MUST document such runs as "host-authority guard exercised, transport not" (honesty level W/R only; E never auto-assigned) to avoid overclaiming. Aligns with the honesty-level discipline and `Invariants/SingleMultiplayerParityInvariantsTests.cs` (live 2-player proof owed to D1).
- Q: Where should the runner locate and update the per-feature `test.md` and the `COMPLETION_SUMMARY.md` / `ROADMAP.md` Gate 3 status on a `pass` verdict (FR-016/FR-017)? → A: **Feature `test.md` under `specs/<NNN-slug>/test.md`** (co-located with the spec), with a `testMdPath` field in the Scenario Definition JSON (fail-fast validated in FR-008) making the target explicit and eliminating slug-resolution ambiguity; root-doc updates via **marker-based injection** using HTML comment anchors (`<!-- GATE3:BEGIN -->` / `<!-- GATE3:END -->`) added to `ROADMAP.md` and `COMPLETION_SUMMARY.md` before the runner touches them, with surgical replacement, idempotency check before write, and a `--check-docs` CI gate. Timestamps update only on actual state change. Aligns with the only existing convention (bug slug-resolution) being insufficient for features, and with the deterministic/idempotent/diff-minimal requirement.
- Q: Should the runner re-download game files on every invocation even when `STARDEW_GAME_PATH` already points to a valid, version-matching install, or skip download and reuse the existing install (cache/idempotent acquisition)? → A: **Cache-first with version+checksum verification.** The runner MUST reuse `STARDEW_GAME_PATH` when (a) all 6 required assemblies are present, (b) game/SMAPI versions classify as INFO or WARN (not HARD-FAIL) against `compat-matrix.json`, and (c) the pinned SHA-256 of the install matches; it MUST acquire from the private repo (FR-002) only on a cache miss (missing/invalid install, version-incompatible, or checksum mismatch). `--force-refresh` bypasses the cache and re-acquires. A cached install MUST still pass the full version-matrix gate and checksum verification before reuse (treat mismatch as a security event). Assumptions A1/A2/A13 are narrowed: download is the fallback/CI path, not the default. Aligns with `research/resilient-github-download.md` §9.2.5 ("skip download if `gamepath.zip` exists and checksum matches") and the project's sparse-cache / temp-swap idiom.
- Q: How does the runner detect and allocate a free Xvfb display number and a disposable save copy for concurrent instances (FR-020) without collision? → A: **Reuse Xvfb `-displayfd` + per-instance `mktemp` temp root.** Each instance starts its own Xvfb with `-displayfd <fd>`; the X server atomically allocates a free display number and writes it back to the fd (no `/tmp/.X*-lock` probe, no TOCTOU race). Save isolation uses a per-instance `temp_root="$(mktemp -d)"` (absolute path) with `XDG_CONFIG_HOME="${temp_root}/xdg"` and the milestone save copied into `${XDG_CONFIG_HOME}/StardewValley/Saves/`; distinct temp roots guarantee distinct save copies and sidecars. The run-wide `flock` from smoke validation is NOT reused as a whole-run gate (only short-lived locks around shared cache/build resources); `preflight_process_conflict` is scoped to the instance's own game process. The original save is hashed before and after and asserted byte-identical (SC-005). Aligns with `scripts/smoke-validation.sh` `display_start()` and `research-report-reproducible-saves.md` §6.
- Q: Should the headless verification runner be delivered as a Docker container image, a bash orchestrator, or a .NET console application — and how is it invoked locally vs. in CI? → A: **Bash orchestrator (extending the `smoke-validation.sh` substrate)** as the delivery form. The runner ships as `scripts/verify-scenario.sh` (or equivalent) that reuses the proven Xvfb `-displayfd` lifecycle, process-group/signal discipline, run log under XDG state, and exit-code taxonomy from spec 008; it downloads game files on cache miss (FR-001/FR-002), deploys the mod + `LivingRoots.Verification` mod, injects via SMAPI macros + save seeding, captures the 3 signals, evaluates thresholds, and writes the MIRROR evidence bundle. Invoked identically locally and in CI mode (`--ci`/non-interactive flag or env detection) per FR-023; in CI it emits JUnit XML + Allure JSON (FR-014) and exits per the exit-code contract (see NFR-003/exit-code table). Docker is deferred until 2+ mods reuse the loop (Regra dos Três), consistent with FR-015's two-phase verifier and A8's aspirational cross-mod reuse. Aligns with the spec's own "orchestration script (Xvfb + SMAPI + macros)" wording (`docs/verification-hook-shipping-report.md`) and the private-repo-download model (no game files to bundle).
- Q: What exit-code contract should the runner use for CI verdict and failure classes? → A: **Full contract (one distinct code per verdict/failure class)**, starting at 18 per the spec 008 allocation rule, reusing smoke codes where they already apply (4 timeout, 6 lock contention, 7 process conflict, 9 missing dependency, 10 display unavailable). Table: `0=PASS`, `18=FAIL` (threshold violation / assertion failure), `19=ERRORED` (crash or incomplete signal set, incl. version mismatch), `20=NO_TESTS` (no scenario discovered / all skipped, quarantined), `21=THRESHOLD` (policy/quality-gate violation), `22=reserved` (future). `ABORTED`/`USAGE`/`CRASH` are covered by inherited smoke codes (4 timeout, 14 usage error, 13 internal error) and are not redefined. `flaky` is metadata (`flaky: true` in JUnit/Allure), never a distinct code; a flaky run exits `0` (PASS) with `flaky: true` and is never counted as a failure. `skipped` (quarantined) exits `20` (NO_TESTS) with a JUnit `<skipped>` element and is not a failure. `--ignore-exit-code` demotes codes to 0. Aligns with pytest/MTP/TestNG gold-standard class distinction and spec 008 FR-013 (exit code as sole machine-readable signal).

### Session 2026-10-27

- Q: What format should the evidence-bundle run id use? → A: **Timestamp-based `run-<UTC compact>-<4 hex>`** (e.g. `run-20261027T123456Z-a3f1`), where `<UTC compact>` is `YYYYMMDDTHHMMSSZ` and `<4 hex>` is 4 lowercase hex digits from a CSPRNG. Directory name `evidence-bundle-<runId>/`. Chosen for chronological sortability and human auditability of MIRROR-style bundles; UUID v4/v7 rejected for opacity. Collision-resistant under concurrent instances (C-CON-10). Published as a public, semver-governed contract alongside the exit-code enum (NFR-003). See C-BND-02.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Maintainer runs full verification unattended (Priority: P1) 🎯 MVP

As the maintainer, I want to invoke a single command that builds, deploys, launches Stardew Valley headless under SMAPI, injects the compost→growth scenario, captures all three signals, evaluates thresholds, and produces a pass/fail verdict plus an evidence bundle — without me opening the game, building a farm, planting, watering, or waiting days — so that Gate 3 verification becomes a repeatable, reliable, non-manual process.

**Why this priority**: This is the core value: eliminating the manual gameplay loop that currently blocks `verified` status and makes every feature's verification error-prone and non-reproducible.

**Independent Test**: On a host with `STARDEW_GAME_PATH` configured and access to the private builddeps repository (or a valid cached install), running the runner against feature 004's scenario completes unattended and produces (a) a pass/fail verdict, (b) an evidence bundle with all three signals, and (c) an updated `test.md` status — with zero human gameplay input.

**Acceptance Scenarios**:

1. **Given** a clean host with `STARDEW_GAME_PATH` set, `BUILDDEPS_TOKEN` configured (or a valid cached install), and the mod built, **When** the maintainer runs the runner for feature 004, **Then** the runner acquires/verifies game files from the private builddeps repository (or reuses the cache), launches Stardew under Xvfb + SMAPI, loads the verification mod, executes the compost→growth scenario, captures all three signals, evaluates thresholds, and exits with a pass/fail verdict — all without human gameplay input.
2. **Given** the runner completes a scenario, **When** the verdict is a clean non-flaky `pass` with all three signals agreeing and honesty level ≥ R, **Then** an evidence bundle (MIRROR-style: `manifest.json` with SHA-256 per file plus a detached `manifest.sha256`, `claims.json`, `artifacts/`, JUnit XML, Allure JSON) is written and `test.md` is updated from `partial` to `verified` with file paths to all three signals. A `pass` that is flaky, signal-incomplete, or below R does not promote.
3. **Given** the runner detects a threshold violation (e.g., poor soil did not slow growth), **When** evaluation completes, **Then** the verdict is `fail` with a diagnostic naming the violated threshold and the observed vs. expected values, and `test.md` is NOT auto-promoted to `verified`.
4. **Given** the runner encounters a crash or incomplete signal set, **When** evaluation completes, **Then** the verdict is `errored` or `partial` (never auto-promoted to `pass`), with attached artifacts and per-attempt logs.
5. **Given** attempt 1 fails with a classified transient failure and a later attempt passes on the same commit, seed, and environment, **When** the run finalizes, **Then** the verdict is `pass` with `flaky: true`, the exit code is `0`, and `test.md` remains at `partial` until a later clean non-flaky pass.

**Why this priority**: Reusability is the stated goal ("para reutilizar para as outras features implementadas, do objetivo, do roadmap e em outros mods"). Without a scenario contract, each feature reinvents verification.

**Acceptance Scenarios**:

### User Story 3 - CI runs verification on a self-hosted runner (Priority: P3)

As CI infrastructure, I want the runner to be invocable from a self-hosted runner (with access to the private builddeps repository via `BUILDDEPS_TOKEN`), so that verification can be triggered automatically on push/PR without a human, while public CI remains dormant.

2. **Given** a valid cached game install and no network access, **When** the runner is invoked with `--no-acquire`, **Then** it reuses the cache, runs the scenario, and never contacts the private repository; a cache miss exits `9` with an actionable message.

### Edge Cases

- What happens when the private builddeps repository is inaccessible or the token is missing/invalid? The runner must fail fast with a clear error naming the missing environment variable (`BUILDDEPS_TOKEN`) or repository identifier (never the credential value) before attempting any download.
- What happens when the game version or SMAPI version mismatches the mod's expected version? The runner MUST detect and report the mismatch **before scenario execution** (before Xvfb launch) using a file-based pre-launch gate: parse `Stardew Valley.dll` (game), `StardewModdingAPI.dll` (SMAPI, using SMAPI's `SemanticVersion` — never `string.Compare`; handle non-standard `1.11` < `1.2` and `-unofficial.*`), and `manifest.json` (mod version, `MinimumApiVersion`, `MinimumGameVersion`); perform mod self-check; classify against a version-controlled `compat-matrix.json` using the 3-tier policy (HARD-FAIL exit code 19 / WARN proceed+record deviation / INFO proceed+log); hard-fail if outside the supported set or below minimums, warn if newer-than-pinned or unverified-but-in-range, info on exact match. Mod manifest must declare `"MinimumGameVersion": "1.6.14"` and bump `"MinimumApiVersion"` to `4.4.0` (or `4.5.0`). Mod at `0.x` is best-effort until `1.0.0`. Evidence bundle gains a `compatibility` block (observed/minimum/maximum/tier per component, modSelfCheck, deviation). SMAPI's null `MaximumGameVersion` is recorded as an upper-bound deviation → warn when observed game exceeds matrix maximum.
- What happens when a scenario step times out (e.g., crop does not grow within expected days)? The runner must abort with `errored`/`partial` and attach artifacts.
- What happens when the save file is corrupted or missing after the session? The runner must report `errored` with the before/after state, not crash.
- What happens when `STARDEW_GAME_PATH` is unset versus set-but-invalid? **Unset/empty** fails fast with a usage error (exit `14`) and does not attempt acquisition, because there is no install directory to populate. **Set but invalid** (missing assemblies, unreadable layout, or failed version/checksum validation) is a cache miss: the runner acquires from the private repo when a token is available, and otherwise fails with exit `9` naming the normalized invalid path and that the token is absent, never its value (FR-001, C-SEC-04).
- What happens when Xvfb fails to start or the display is unavailable? The runner must detect and report, not silently proceed.
- How does the runner handle a flaky scenario (passes on retry)? A run is `flaky` iff attempt 1 fails with a retryable class AND a later attempt passes; a flaky run exits `0` (PASS) with `flaky: true` and is never counted as a failure. Flakies are quarantined (with owner and time-box) only after 2 flaky runs within a rolling 14-day window (or 2 of the last 3 runs), for a 14-day time-box with one 14-day extension (28-day hard cap) then auto-disable; quarantined scenarios report as `skipped` in JUnit/Allure and are never auto-promoted to `verified`. Retry is limited to transient/environmental failures (classified via smoke-validation exit codes) with mandatory per-attempt logging; threshold violations, crashes, incomplete signals, version mismatches, missing dependencies, and host-guard breaches are NOT retried.
- What happens when two runner instances run concurrently on the same host? They must use distinct save copies and distinct display numbers to avoid collision.

## Requirements *(mandatory)*

### Functional Requirements

#### Host & Environment

- **FR-001**: The runner MUST distinguish three host states before doing anything else. **(a) Unset** — `STARDEW_GAME_PATH` is absent or empty: fail fast with a usage error (exit 14) and an actionable message; do not attempt network acquisition, because there is no install directory to populate. **(b) Set but invalid** — the path exists but is missing required assemblies, has an unreadable layout, or fails version/checksum validation: treat it as a **cache miss** and acquire from the private repo (FR-002) when a token is available; if no token is available, fail fast with exit 9 (missing dependency) and a message that names the normalized invalid path, the `STARDEW_GAME_PATH` variable, and that `BUILDDEPS_TOKEN` is absent (never the token value). **(c) Valid cache** — all required assemblies are present, game/SMAPI versions classify as INFO or WARN (not HARD-FAIL) against `compat-matrix.json`, and the pinned digest matches `gamepath.lock.json`: reuse without network access (no token required). `--force-refresh` bypasses (c) and re-acquires. A cached install MUST still pass the full version-matrix gate and checksum verification before reuse; a checksum mismatch is a security event and is never reused. `--no-acquire` disables network acquisition entirely (hermetic/offline runs): a valid cache proceeds, a cache miss exits `9` with an actionable message, and combining `--no-acquire` with `--force-refresh` is a usage error (exit `14`). The player's real save directory is never opened or modified by this check.
- **FR-002**: On a cache miss or `--force-refresh` (see FR-001), the runner MUST acquire game files from a **private repository** (e.g., `lfgranja/stardew-raizes-vivas-builddeps` or equivalent) via the GitHub **Releases assets** endpoint (`GET /repos/{owner}/{repo}/releases/assets/{asset_id}`, `Accept: application/octet-stream`), authenticated with a secret token (`BUILDDEPS_TOKEN` or equivalent), following the same pattern already used by the dormant `Build and Test` workflow (`.github/workflows/build_and_test.yml`) but extended with the resilience layer below. The runner MUST NOT use the Contents API (1,000-entry cap, base64 overhead, 5-min URL expiry) or auto-generated source archives (unstable hashes). The runner MUST verify the token is present and valid (probe repo/release access) before attempting download; if the token is missing or the repository is inaccessible, it MUST fail fast with a clear, actionable error. The runner MUST NOT use interactive game-store authentication — the private-repo pattern eliminates that barrier entirely. **Immutable asset pinning**: `gamepath.lock.json` MUST pin the release ID, asset ID, asset name, archive SHA-256, and a per-file digest map for the extracted tree; the runner MUST reject a mutable `latest` release, an asset whose ID/name does not match the lock, and any redirect or URL whose scheme is not HTTPS or whose host is not an allowed GitHub host. The token MUST NOT be sent to a non-GitHub host. The downloaded archive MUST be verified against the authoritative SHA-256 pinned in `gamepath.lock.json` (updated only by reviewed PR); the release's `gamepath.zip.sha256` is advisory and may be compared but never trusted alone. On mismatch the runner MUST fail fast and treat it as a security event. The runner MUST retry transient failures (5xx, 429 honoring `Retry-After`, network timeout/reset/DNS) with exponential backoff + full jitter (3–5 attempts, capped total elapsed time); 401/403/404 are terminal (no retry). Partial-download recovery is best-effort only (CDN `Range` support is not guaranteed by GitHub): always verify the final SHA-256 and restart from byte 0 on mismatch, using a `.part` temp file + atomic rename. **Token phases**: Phase 1 uses a fine-grained PAT scoped to the single private repo (`Contents: read` + `Metadata: read`), stored as `BUILDDEPS_TOKEN`, maximum 90-day lifetime and 30-day rotation; Phase 2 upgrades to a GitHub App installation token (1-hour expiry) when the runner moves to shared/self-hosted CI; Phase 3 may use OIDC-issued ephemeral tokens when the hosting platform supports them. The phase in use is recorded in the evidence bundle.

- **FR-003**: The runner MUST start a virtual display (Xvfb) and verify it is available before launching the game; if Xvfb fails to start, the runner MUST abort with a clear error.
- **FR-004**: The runner MUST deploy the mod (and the verification mod) into the game's `Mods/` folder and verify deployment succeeded before launch.

#### Launch & Scenario Injection

- **FR-005**: The runner MUST launch Stardew Valley under SMAPI headlessly and wait for an observable ready state before injecting the scenario. Ready means: a fresh `Log started at … UTC` sentinel exists with an inode-change assertion; `Loaded N mods:` appears after that sentinel; the target mod is not in `Skipped mods`; and, when the scenario requires a loaded world, the verification mod's `GameLaunched` marker is present. Save-load completion is not externally observable and MUST NOT be used as a ready condition; scenarios drive load completion through macros and custom commands (C-LCH-01).
- **FR-006**: The runner MUST inject the scenario into the game without human input using **SMAPI macros** (`debug runmacro <file>`) for deterministic batch command execution (sleep, warp, item give, etc.) combined with **save file seeding** (StarDojo two-phase pattern) for reproducible initial conditions, plus **custom mod console commands** (e.g., `lr_dump_crop_phase`) for mod-specific state capture. Save seeding is **hybrid**: (i) **milestone saves** (≤ ~5 curated binary save folders) stored in the private builddeps repo with a JSON save manifest (game/SMAPI version, save name/id, SHA-256, documented contents) provide coarse progression; (ii) **per-scenario `initCommands`** (typed `{kind: "macro", file}` or `{kind: "console", command}` entries) place the compost bin, insert waste, set crop phases, and set soil health, so mod sidecars (`soil_health_data_{saveId}.json`, `composting_bins_{saveId}.json`) are **generated, reviewable, and version-stable** rather than checked in as opaque binary. The injection mechanism MUST be documented and reproducible. Input simulation (xdotool) is explicitly excluded (fragile, non-deterministic). A verification bot mod is NOT required for *injection* — SMAPI macros + save seeding + custom commands provide sufficient determinism with lower effort and risk. The Crop-phase dump hook itself lives in a separate dev/CI-only verification mod (see Clarifications, Session 2026-10-26), not in the production binary.

- **FR-007**: The runner MUST support a scenario definition (checklist + thresholds) as input, so that different features can be verified without modifying the runner's core. The scenario definition MUST be authored as **JSON** (validated against a JSON Schema), with an optional human-facing **Markdown** companion checklist for contributor readability. JSON is the canonical machine format; YAML is not used anywhere in the stack and would add a dependency (YAGNI). Thresholds MAY reference `ModConstants` values by name; when they do, the numeric value in the structured predicate remains authoritative. **Schema contract (clarified):** validated against **JSON Schema Draft 2020-12** (`$schema: https://json-schema.org/draft/2020-12/schema`), strict (`additionalProperties: false` at every object level), a versioned logical `$id` (`urn:lfgranja:livingroots:scenario:v2`, not a file-path mirror), `schemaVersion: const 2` for payload versioning (v2 makes the structured `thresholds[].predicate` the machine oracle; `condition` is optional v1 migration provenance, never the oracle), and `$defs` for reusable fragments. Contract location: `specs/010-headless-verification-runner/contracts/scenario.schema.json` (documentation) with machine-readable copies under `schemas/scenarios/v2/` once the Rule of Three (≥3 features reusing) justifies extraction. Validator selection, `$ref` bundling, and CI/pre-commit tooling are implementation decisions recorded in `plan.md`; the contract requires that the selected validator implements Draft 2020-12 and that the same fixtures produce identical outcomes in at least two independent validators (C-SCN-38). **Versioning policy:** `schemaVersion` is an integer major version. Because the schema is strict, any field addition, removal, rename, type change, or constraint tightening is a major bump and a new immutable file; there are no minor/patch schema versions (SemVer is N/A for this contract). **Required scenario fields (clarified):** a `testMdPath` field (repo-relative path to `specs/<NNN-slug>/test.md`) is required so the runner knows which file to update on `pass` (FR-016) without guessing; it MUST resolve to an existing regular file, end with `test.md`, and contain exactly one `<!-- GATE3:BEGIN -->` … `<!-- GATE3:END -->` block. Validation is fail-fast before launch (FR-008, exit 14). The schema also requires `environment` (game/SMAPI/mod/save/config), requires `minimumGameVersion`, requires `determinism`, requires `scenarioKind`, defaults `timeoutSeconds` to `300`, and requires `hostGuard` when `playerRole` is `farmhand`; `expectedVerdict` is optional and defaults to `pass` for `positive` scenarios; it is **mandatory** for `boundary` scenarios (restricted to `pass`/`fail`) and for `negative` scenarios (restricted to the non-pass base verdicts `fail`, `errored`, `partial`, `skipped`). Every optional field MUST document either a default applied on omission or explicit absence semantics; a JSON Schema `default` keyword is used only where a value is actually applied.
- **FR-008**: The runner MUST validate the scenario definition before launch (required fields, valid thresholds, valid boundaries, `testMdPath` existence and marker block); if invalid, it MUST fail fast with a field-level error (exit 14). `--scenario` accepts a single scenario file or a directory; directory discovery and suite aggregation follow C-SCN-34. **Environment overrides (clarified):** the runner MUST accept repeatable `--override <dotted.key>=<value>` flags for declared environment values (`environment.gameVersion`, `environment.smapiVersion`, `environment.modVersion`, `environment.saveId`, `environment.config.*`) and `--milestone-save <name>` for the milestone source. Overrides are applied after schema validation, are re-validated against the version matrix, are recorded in `manifest.json` under `environmentOverrides`, and MUST NOT override `testMdPath`, `expectedSignals`, `thresholds`, `playerRole`, or `hostGuard`. An unknown override key is a usage error (exit 14).

#### Signal Capture & Evaluation

- **FR-009**: The runner MUST capture all three signals for every **host** run: (i) `SoilHealthState` JSON delta (before/after `modData/soil_health_data_{saveId}.json`), (ii) `Crop.currentPhase` / `dayOfCurrentPhase` delta captured via **in-process dump** (the dev/CI-only `LivingRoots.Verification` mod writes a JSON dump at `DayEnding` *after* `ApplySoilGrowthModifier` has completed, using a production-safe ordering signal exposed by the main mod — not cross-mod handler ordering — with before/after pairs, atomic temp-file+rename, and a "done" sentinel) as the primary oracle, with **save-file inspection** of serialized `Crop` data as an independent cross-check (divergence between dump and save is diagnostic, not noise), and (iii) SMAPI console log excerpt confirming event execution and elapsed ms. **Ordering signal (clarified):** the main mod exposes the timing via an SMAPI mod-provided API (`ModEntry.GetApi()` → `ILivingRootsModApi`, SMAPI-free, in `Domain/Interfaces/`) carrying `event EventHandler<SoilGrowthModifierCompletedEventArgs> SoilGrowthModifierCompleted`, raised **synchronously on the game thread at the tail of `OnDayEnding`**, after the `ApplySoilGrowthModifier` loop completes for all locations (success or caught exception) and before the day transition; the verification mod subscribes via `helper.ModRegistry.GetApi<ILivingRootsModApi>("lfgranja.LivingRoots")` in `GameLoop.GameLaunched`. Subscriber exceptions are isolated. **Divergence policy (clarified):** when the in-process dump and the save-file cross-check disagree, the verdict is `partial` (signals disagree), recorded as an Anomaly Report entry; the dump remains the primary oracle for Crop behavior and the save remains the independent cross-check, and the run is never auto-promoted to `pass` (FR-016); resolution requires a new full triad run that independently passes. **Farmhand runs:** the same three capture channels are used, but the crop-phase channel asserts absence of mutation and the SMAPI channel asserts the host-guard skip line. This is an expected-absence signal, not an incomplete signal set; a farmhand run with the skip line and no mutation can be `pass`, while execution evidence without the skip line is a host-guard breach (`fail`, exit 18, non-retryable, never quarantined).

- **FR-010**: The runner MUST apply the threshold rules: poor soil (`0 < health < 34`) MUST slow growth (1.15× on `phaseDays`), healthy soil (health ≥ 67) MUST accelerate growth (0.85×), moderate [34, 67) MUST be unchanged (1.00×); `phaseDays` MUST never go below 1 and the 99999 sentinel MUST never be touched. Tiles with NaN health MUST be skipped (no change). Tiles with **no SoilHealthState entry (missing key)** and tiles with health `<= 0` MUST be treated as **non-participants (skipped, no change)** — never as Poor growth participants; only strictly positive stored health `< 34` counts as Poor. The verification dump classifies the same tiles as `healthTier`: `unknown` (missing key or stored NaN, unmeasured), `nonParticipant` (measured `<= 0`), `poor` (`0 < health < 34`), `moderate` `[34, 67)`, `healthy` `>= 67`. A measured zero may still render as the game's Poor visualization category; that is a visualization concern, separate from growth participation. (Missing keys are treated as `0` only inside `SaveComparator`, per FR-012, at the persistence layer.)
- **FR-011**: The runner MUST compute one of five base verdicts `{pass, fail, errored, partial, skipped}` plus the derived mark `flaky` (never a sixth base verdict): crash → `errored` with attached artifacts; incomplete signal set → `partial` (never auto-promoted to `pass`); transient/environmental failure → retry with **bounded attempts** (`RunnerMaxTransientRetries = 2`, i.e. 3 total attempts) for **classified transient classes only** (reuse smoke-validation exit codes: Xvfb/display=10, launch timeout=4, lock contention=6, process conflict=7, save I/O error, macro timeout; NOT retryable: threshold violation, crash, incomplete signals, version mismatch, missing dependency=9, host-guard breach), with a fixed `RunnerRetryCooldownMs = 5000` cooldown and **mandatory per-attempt artifacts** (`attempts/<n>/attempt.json`, stdout/stderr, intermediate verdict, signals). Save I/O errors and macro timeouts are transient subclasses of `errored`/`partial`: the attempt records that intermediate verdict, and the final verdict follows the retry outcome. Incomplete signals are not retryable on their own; they are retryable only when the incompleteness is caused by one of the classified transient classes (for example, a save I/O error that prevented an artifact from being written). **Run-level `flaky`:** a run is `flaky` iff attempt 1 fails with a retryable class AND a later attempt passes on the same commit, seed, and environment; a flaky run exits `0` (PASS) with `flaky: true`, is never counted as a failure, and **MUST NOT auto-promote `test.md` to `verified`** (FR-016). **Quarantine candidate:** a scenario becomes a quarantine candidate after 2 flaky runs within a rolling 14-day window (or 2 of the last 3 runs); automation proposes, a human approves (C-REL-10/C-REL-26), and the approved entry carries an owner and time-box in a committed `quarantine.json`. **Confirmed flaky:** a distinct statistical status requiring N ≥ 30 runs and a Wilson 95% score interval computed from the observed failure proportion; confirmed-flaky requires the interval's upper bound < 1.0 (it excludes 100%) and a point failure rate ≥ 30% (C-REL-07/C-REL-26); below N the status is `insufficient-data`. Confirmed-flaky status is **not** a prerequisite for quarantine, and neither status may be assigned manually from a single run. Quarantine time-box is `RunnerQuarantineTimeBoxDays = 14` with one 14-day extension (`RunnerQuarantineExtendedTimeBoxDays = 28`, hard cap, no second extension); at the cap the scenario is **auto-disabled** and a GitHub issue is opened (C-REL-21/C-REL-27). The suite-level rerun cap `RunnerMaxSuiteReruns = 4` counts retries across all scenarios in one suite invocation, resets per invocation, and is recorded as `suiteRerunCount`/`suiteRerunCapHit` in the evidence bundle (C-REL-22). Deletion or retirement of a quarantined scenario requires human approval; auto-disable at the cap is automatic and terminal. Owner resolution: `--quarantine-owner` → `QUARANTINE_OWNER` env → git identity → repo owner (lfgranja). Quarantined scenarios report as `skipped` in JUnit/Allure. **Host-guard breach:** in a scenario tagged as a farmhand (non-host) session, a breach is execution evidence (the `Soil growth modifier elapsed: … ms` trace line, or a `phaseDays` mutation in the Crop-phase dump/save) without the `Soil growth modifier skipped: not main player.` skip line; the verdict is `fail` (exit 18), non-retryable, never quarantined, never auto-promoted. Scenario definitions MUST declare the expected player role (host vs. farmhand). **Expected-verdict semantics:** a `negative` scenario MAY declare any non-pass `expectedVerdict` (`fail`, `errored`, `partial`, or `skipped`); `positive` scenarios are restricted to `pass`, and `boundary` scenarios to `pass`/`fail`. A matched expected verdict is preserved as the actual verdict and exits with that verdict's normal code (`fail` → `18`; `errored`/`partial` → `19`; `skipped` → `20`, or `0` in a mixed suite with at least one `pass`), and is never rewritten to `pass`. A mismatch — including an unexpected pass — is `errored`/exit `19` and recorded as `expected-verdict-mismatch`. Expected-failure lanes opt into `--ignore-exit-code 18` explicitly for matched `fail`; they MUST NOT change the recorded verdict. Constants: `RunnerMaxTransientRetries=2`, `RunnerRetryCooldownMs=5000`, `RunnerFlakyObservationWindowDays=14`, `RunnerFlakyQuarantineTriggerCount=2`, `RunnerQuarantineTimeBoxDays=14`, `RunnerQuarantineExtendedTimeBoxDays=28`. **Farmhand mechanism (clarified):** the runner uses **split-screen via `debug split`** as the default automated path to flip `Context.IsMainPlayer` to false (exercising the guard branch) without a second process; runs are documented as "host-authority guard exercised, transport not" (honesty levels W/R only; E never auto-assigned). Manual protocol / Roadmap D1 remain the fallback for transport-level claims; a two-instance host+client launch is used only when Roadmap D1 is funded.
- **FR-012**: The runner MUST use the `SaveComparator` (0.0001f float tolerance, missing keys treated as 0, NaN tiles ignored) for the SoilHealthState delta, producing `added`/`removed`/`changed` entries. **Layer note:** missing keys are treated as `0` only at the persistence/diff layer (sparse cache); this differs from runtime `GetSoilHealth` (missing → NaN → skip → vanilla) and must not be conflated with threshold evaluation (FR-010), where missing keys are non-participants.
- **FR-013**: The runner MUST parse the SMAPI log for the elapsed-ms trace line and, **after exactly one discarded warmup invocation per scenario**, hard-fail if the single measured per-location elapsed-ms value exceeds 5 ms. The warmup uses the same seed, milestone save, and state-reset procedure as the measured run; its artifacts are retained under `attempts/warmup/` but it is not counted as an attempt, is never eligible for `flaky`, and cannot satisfy `pass` on its own. The measured run is a fresh launch after the warmup, not a retry. The Gen0 collection-count delta for the measured invocation MUST be recorded in the evidence bundle; when it is > 0 the failure is tagged `gc-attributed` (diagnostic only — still a fail). The elapsed value is per location (up to 3 lines per day); each is evaluated independently. The 5 ms threshold and criterion 6 come from **spec 009's SC-009 (per-criterion manual verification protocol), criterion 6 (performance)**, not from spec 010's own success criteria.

#### Evidence & Output

- **FR-014**: The runner MUST produce a MIRROR-style evidence bundle: `manifest.json` (schema version, run id, timestamp ISO 8601, tool/game/mod versions, environment, `subject` array with SHA-256 per file), a **mandatory** detached `manifest.sha256` anchor, `claims.json` (claim → evidence pointer, risk, safe wording), `artifacts/` (screenshots, SMAPI logs, save-deltas before/after, reflection outputs), JUnit XML (CI), and Allure JSON (rich report). Honesty levels: W (launch/connect) / R (runtime evidence collected) / E (human judgment, never auto-assigned). The detached anchor is written after `manifest.json` is finalized and is the trust root the offline verifier compares against; `files` is a deprecated alias for `subject` for one schema major.
- **FR-015**: The runner MUST produce an offline-verifiable bundle: a verifier recomputes digests and validates schema; structural pass ≠ truth. The verifier MUST be invocable as `scripts/verify-evidence-bundle.sh <bundle-dir>` and as `scripts/verify-scenario.sh --verify-bundle <bundle-dir>`; neither form launches the game. The verifier MUST fail closed: a missing mandatory artifact (manifest, the detached `manifest.sha256` anchor, `claims.json`, any of the three signal artifacts, `commands`/`materials`/≥1 seed for R/E, or an unresolvable digest) exits `19`; a claim whose `safeWording`/`honestyLevel` overstates the evidence exits `21`; only a fully valid bundle exits `0`. **Phase-1 independence:** the verifier runs as a separate process/job from the producer, reads only the finalized bundle (never producer memory, logs, or workspace state), recomputes every digest itself, and is exercised with negative fixtures for each refusal site. The producer cannot mark its own bundle valid, and the runner's `pass` verdict is not accepted as verifier output. **Verifier ownership (two-phase):** Phase 1 (stepping stone) — an in-repo `scripts/verify-evidence-bundle.sh` is maintained with the mod to validate bundle format, verifier logic, and refusal-site behavior while requirements emerge. Phase 2 (promotion trigger, per FR-017, once 2+ features/mods reuse the loop) — extract to an independently maintained open-source tool with user-supplied trust anchors, documented bounded claims, and refusal-site liveness testing. The bundle producer is never the sole trust anchor in Phase 2.
- **FR-016**: The runner MUST update `test.md` from `partial` to `verified` only when all three signals agree, the verdict is `pass`, the run is **not flaky**, and the honesty level is at least R. `verified` is an R-level machine-evidence status; E is a separate human attestation that the runner never auto-assigns. On `fail`/`errored`/`partial`, or on a flaky `pass`, the runner MUST NOT auto-promote: a flaky pass leaves `test.md` at `partial` and records `flaky: true` in the bundle and the GATE3 block until a later clean non-flaky pass. **Location (clarified):** the target is `specs/<NNN-slug>/test.md` (co-located with the spec), identified via a `testMdPath` field in the Scenario Definition JSON (fail-fast validated in FR-008); the runner MUST NOT guess or use slug-resolution. The runner updates only the content between `<!-- GATE3:BEGIN -->` and `<!-- GATE3:END -->`, preserving everything outside the block byte-for-byte; a missing, duplicated, or inverted marker block is a fail-fast validation error (exit 14) before launch.
- **FR-017**: The runner MUST update `COMPLETION_SUMMARY.md` and `ROADMAP.md` Gate 3 status on a clean non-flaky `pass` verdict, recording the promotion trigger for deferred components (reflector/logger/runner promoted only after 2+ features reuse the loop). **Mechanism (clarified):** updates use marker-based injection via HTML comment anchors (`<!-- GATE3:BEGIN -->` / `<!-- GATE3:END -->`) that MUST already exist in `ROADMAP.md` and `COMPLETION_SUMMARY.md`; if a required marker block is absent, duplicated, or inverted, the runner MUST fail fast with exit 14 before launch and MUST NOT create or guess a block. Surgical replacement is followed by an idempotency check before write; timestamps update only on actual state change. `--check-docs` compares the committed GATE3 blocks against the latest bundle verdict and exits `21` on drift, `0` when no update is pending, and `14` when a marker block is missing or malformed. Root-doc updates are never performed on a flaky pass.

#### Process & Lifecycle

- **FR-018**: The runner MUST always run against a disposable copy of the **source milestone save** — the read-only curated save folder selected by `--milestone-save` or the scenario's `environment.saveId` — and never against the player's real save directory, which it MUST NOT open, copy, or modify. It MUST back up the copied `Saves/<Name>/` folder and the mod sidecars before mutation, using `XDG_CONFIG_HOME` pointing to a per-instance temp dir. The source milestone save MUST remain byte-identical throughout (hash-before/hash-after over the source folder). The working copy is mutated during play, then restored from the backup; after restore it MUST hash to the same digest as the source. A mismatch on either the source or the restored copy is `errored` (exit 19).
- **FR-019**: The runner MUST quit the game cleanly after scenario completion and capture all artifacts before exit.
- **FR-020**: The runner MUST support concurrent instances on the same host using distinct save copies and distinct display numbers. Display numbers are allocated by Xvfb via `-displayfd` (each instance starts its own Xvfb; the server atomically picks a free number; no `/tmp/.X*-lock` probe, no TOCTOU race). Save isolation uses a per-instance `temp_root="$(mktemp -d)"` (absolute path) with `XDG_CONFIG_HOME="${temp_root}/xdg"` and the milestone save copied into `${XDG_CONFIG_HOME}/StardewValley/Saves/`; distinct temp roots guarantee distinct save copies and sidecars. The run-wide `flock` from smoke validation is NOT reused as a whole-run gate (only short-lived locks around shared cache/build resources); `preflight_process_conflict` is scoped to the instance's own game process. The original save is hashed before and after and asserted byte-identical (SC-005).
- **FR-021**: The runner MUST preserve the manual SC-009 protocol as a documented fallback (`VERIFICATION_PROTOCOL.md` §3, `gate3-verification-contract.md`) for hosts where the runner cannot execute.

#### Security & Supply-Chain Addendum (research-backed, Session 2026-10-26)

- **FR-024**: On any integrity failure (checksum mismatch, archive-member validation failure, extraction integrity failure), the runner MUST produce a **tamper-evident record** `integrity-failure.json` in the evidence bundle before finalization, containing: `failureClass` (enum: `checksum-mismatch`, `archive-member`, `extraction`, `token-invalid`, `partial-download`), `verificationMode` (`checksum` | `signature`), `phase` (`pre-extraction` | `post-extraction` | `cache-reuse`), `releaseId`, `assetId`, `observedDigest`, `expectedDigest`, `artifactPath`, `perFileDigestMismatches[]`, `timestamp` (ISO 8601 UTC), `runnerVersion`, and `attemptNumber`. The bundle's `manifest.json` MUST cover `integrity-failure.json` through its `subject` array (append-only semantics: the failure record is never overwritten or deleted on retry; each attempt gets its own entry under `attempts/<n>/`). The offline verifier (FR-015) MUST validate that, when a non-zero integrity exit code occurred, the bundle contains a valid `integrity-failure.json` matching the recorded failure class, mode, and phase. The record MUST be retained for ≥ 365 days (FR-027). Aligns with SLSA v1.2 VSA (`verificationResult: FAILED`) and OWASP CICD-SEC-9/10. Closes CHK014.

- **FR-025**: Archive extraction MUST be performed **in-process**, without shelling out to external archive utilities, with explicit member validation (extends FR-002): reject any member whose resolved path escapes the destination (`..`, absolute paths, drive letters, symlink/hardlink escapes, NUL bytes, overlong names); enforce `ModConstants.RunnerMaxArchiveMembers`, `RunnerMaxArchiveBytes`, `RunnerMaxCompressionRatio` (default 100:1) against actual decompressed bytes (not declared sizes, which are forgeable); reject duplicate member paths; reject entries whose type is not a regular file or directory; verify each extracted file's SHA-256 against the **mandatory** per-file digest map pinned in `gamepath.lock.json`. If the per-file digest map is absent or incomplete, the runner MUST fail closed with `errored` (exit 19) and MUST NOT execute the extracted tree. Abort with `errored` (exit 19) on any violation, leaving the target untouched (C-CON-04 atomic replace). Closes CHK024.

- **FR-026**: The runner MUST execute under a **non-root, least-privilege account** in CI: the runner process and any child (game, Xvfb) MUST NOT run as root/admin; self-hosted runners MUST be split into a **high-privilege group** (may hold `BUILDDEPS_TOKEN` and write the game cache) and a **low-privilege group** (runs untrusted pull-request code; no token, no game-cache write access, no shared workspace), each scoped to the repository (or organization) with no cross-repo access. A job MUST NOT span both groups. `GITHUB_TOKEN` defaults to `permissions: contents: read` in all workflow files (deny-by-default); runner hosts SHOULD be ephemeral where feasible. Code-level enforcement: a startup guard fails fast if `EUID == 0` (or equivalent). Infrastructure-level items (runner-group creation, host OS hardening, firewall rules) are documented in `GOVERNANCE-ANNEX.md` and are not enforced by code. Closes CHK037/CHK038/CHK039.

- **FR-027**: Audit and evidence artifacts MUST follow a defined **retention and immutability** policy: audit logs (access, downloads, integrity events, overrides) retained ≥ 1 year (365 days) with append-only/tamper-evident storage (hash chain or WORM); evidence bundles retained ≥ 1 year, content-addressed via the `manifest.json` `subject` array plus a detached `manifest.sha256` anchor stored alongside the bundle and recorded in the audit log; application/step-level logs retained ≥ 30 days; logs containing a leaked secret are retained indefinitely with the secret purged and the incident recorded. Evidence storage MUST be append-only/WORM for the retention period; deletion before expiry requires documented human approval plus an audit event and is never performed automatically. GitHub Actions' default 90-day artifact retention is insufficient for the 1-year requirement; bundles MUST be exported to durable storage. Retention periods are recorded here and reviewed annually. Closes CHK049.

### Clarified Requirements-Quality Contracts (Session 2026-10-26)

The following clauses close the requirements-quality gaps identified by the four checklists under `checklists/`. Each clause is a normative addition to the FRs above; checklist items it satisfies are cited in brackets. Items not covered here are recorded in `GOVERNANCE-ANNEX.md` (ownership, review cadence, R/A/C/I) or were resolved in the final clarification batch.

#### Concurrency & Save-Preservation Contract [concurrency.md]

- **C-CON-01 (CHK004/005/026)**: The runner MUST NOT create, probe, signal, or remove `/tmp/.X{n}-lock` or `/tmp/.X11-unix/X{n}` for displays it did not allocate. An **owned display** is one allocated by this instance through `-displayfd`, with its Xvfb PID and start-time identity token recorded in the instance namespace. Under `-displayfd`, Xvfb sets `nolock = TRUE` and writes no lock file. On cleanup the runner MUST SIGTERM (escalate SIGKILL) the Xvfb process group it spawned; the server removes its own socket. **Orphaned displays** (sockets whose owning PID is dead or whose identity token does not match) MUST be detected via an `xdpyinfo` handshake and reported in an append-only `orphaned-displays.json` registry inside the evidence bundle as informational only — never signalled or deleted. Only a display whose identity token matches this instance may be force-unlinked (C-CON-22); unknown ownership is always report-only.
- **C-CON-02 (CHK008)**: Save preservation (byte-identical original) MUST be verified with SHA-256 (`sha256sum`) over the archived save folder. The `SaveComparator` persistence-layer diff MUST use a `0.0001f` absolute tolerance (matching game precision), with NaN tiles skipped (not mapped to 0) and missing sparse-cache keys treated as 0 at the persistence layer only.
- **C-CON-03 (CHK010)**: If the original save is not byte-identical after the run, the verdict MUST be `errored` (exit code 19) with before/after SHA-256 and diff attached; it MUST NOT be `fail` (18), because the isolation/safety contract was breached rather than a gameplay assertion failing. `errored` is non-retryable.
- **C-CON-04 (CHK011/040/043/044)**: All persisted artifacts (sidecars, dumps, evidence-bundle files, restore writes) MUST use atomic replace: create a temp file in the same directory, write, `fsync` the temp file, `rename` it over the target, then `fsync` the parent directory. Temp files use `mkstemp` (which supplies `O_EXCL` and mode 0600); lock files and any path that may be attacker-influenced use `open(O_CREAT|O_EXCL|O_NOFOLLOW|O_CLOEXEC, 0600)` because `mkstemp` does not accept `O_NOFOLLOW`. On any failure the target MUST remain untouched (torn-write prevention). Temp files MUST be unlinked on failure (idempotent cleanup).
- **C-CON-05 (CHK014)**: In addition to `XDG_CONFIG_HOME` (absolute path, per-instance temp dir), the runner MUST set `HOME` to a per-instance directory so any component ignoring XDG vars writes into the isolated tree. `XDG_DATA_HOME`, `XDG_STATE_HOME`, and `XDG_CACHE_HOME` SHOULD also be set explicitly for belt-and-braces.
- **C-CON-06 (CHK015/031)**: Per-instance temp dirs MUST be cleaned up via the runtime's exit/signal/finally cleanup hooks, registered immediately after creation, with an empty-path guard on recursive delete. Cleanup MUST preserve the original process exit code even when a later cleanup step fails. Cleanup failures MUST be recorded in the run log / evidence bundle (`cleanup_failed: true` + error), never silently swallowed.
- **C-CON-07 (CHK016/033)**: Runtime temp dirs MUST be created via `mktemp -d` (`mkdtemp`, mode 0700) with `umask 077` beforehand; temp files via `mkstemp` (mode 0600). Permissions MUST be enforced via the open file descriptor, not the path. The system-provided `XDG_RUNTIME_DIR` MUST NOT be chmod'd.
- **C-CON-08 (CHK018/019/020/021)**: Locks MUST be advisory only (`flock`/OFD locks, never mandatory locking). Non-blocking acquisition MUST use a poll loop with bounded timeout + backoff (no native timeout). Lock ordering MUST be documented as a global order `game-cache → build-output → shared-doc` to prevent deadlock; there is no whole-run lock. **Conflict predicate:** two lock requests conflict iff they name the same resource ID and at least one is exclusive. `shared-doc` covers the only shared writable artifacts (`test.md`, root docs, `quarantine.json`); its locks are short-lived (read → merge → atomic write) and never held across a game launch. OFD locks (`F_OFD_SETLK`) SHOULD be preferred over process-associated locks where thread safety across subprocesses is needed.
- **C-CON-09 (CHK023/024/029)**: Process-conflict check-and-claim MUST be atomic (`O_EXCL|O_CREAT|O_NOFOLLOW`, never check-then-create) in a **shared claim directory** (`${XDG_STATE_HOME:-$HOME/.local/state}/livingroots/claims/`) that holds only short-lived claim files and is an explicit exception to C-CON-10's no-shared-run-state rule. The claim key MUST be the resolved per-instance **working-copy save path** or a caller-forced `display:<N>`; the source `saveId`/`milestoneSave` are read-only shared inputs and MUST NOT be claim keys, so two instances of the same scenario do not conflict merely by sharing a scenario. PID liveness MUST be verified via a stored identity token (start-time + command-line hash), not `kill -0` alone (PID recycling). The runner MUST never signal a PID without an exact token match; unverified PIDs are left alone and recorded as informational. A stale claim may be removed only when the token mismatches and the recorded owner is confirmed dead; the `<claim>.reclaim` guard is itself stale only after 30 s **and** a dead owner token, otherwise the reclaimer exits `6` without unlinking.
- **C-CON-10 (CHK025/034/037)**: Each instance MUST have a unique instance ID and a per-instance writable namespace. There is **no shared writable run state** between instances; the only shared artifacts are `test.md`, the root docs, and `quarantine.json` (guarded by the short-lived `shared-doc` lock, C-CON-08, and updated by read-merge-atomic-write) plus the short-lived claim files in the C-CON-09 claim directory (coordination only, never run data). Concurrent instances MUST produce non-interleaved verdicts by writing per-instance verdict files and merging them under that lock.
- **C-CON-11 (CHK027/028)**: Child processes (game) MUST run in a new process group (`setsid`/`setpgid`). On shutdown the runner MUST forward SIGTERM/SIGINT to the process group, escalate to SIGKILL after a bounded grace period, and always `waitpid` to reap. Before signalling, it MUST re-verify the leader's PID + start-time token because a PGID can be reused after the leader exits; it MUST never signal an unverified PGID.
- **C-CON-12 (CHK032)**: Temp dirs MUST be created on a local filesystem only (not NFS), because NFS breaks `flock` and `O_EXCL` semantics.
- **C-CON-13 (CHK039/041)**: Restore MUST be write-temp-then-atomic-rename with fsync; any failure before rename leaves the original untouched. The operation MUST be idempotent.
- **C-CON-14 (CHK042)**: `O_EXCL` MUST be paired with `O_CREAT`; add `O_NOFOLLOW` for any path that may be attacker-influenced and `O_CLOEXEC` on every descriptor. `mkstemp`/`mkdtemp` are the sanctioned exception for private temp paths (they supply `O_EXCL` and 0600/0700 but not `O_NOFOLLOW`). Acquisition MUST handle `EINTR` (retry), `EEXIST` (re-poll or fail as conflict), and `EAGAIN` (backoff).
- **C-CON-15 (CHK045)**: Concurrency primitives MUST be documented in a dedicated `CONCURRENCY.md` with per-operation invariants, errno failure modes, retryability, and recovery.
- **C-CON-16 (CHK046)**: Concurrency behavior MUST be identical in local and CI modes (single test entry point; no mode-specific locking).
- **C-CON-17 (CHK048)**: A traceability matrix MUST link each concurrency requirement (CHK) → test case → code location.
- **C-CON-18 (CHK049)**: Concurrency requirements MUST be reviewed for TOCTOU (replace check-then-act with atomic primitives and `*at`/`O_NOFOLLOW`).

#### Verdict & Flakiness Contract [reliability.md]

- **C-REL-01 (CHK024)**: The verdict set is closed: `{pass, fail, errored, partial, skipped}` plus `flaky` as a derived state (not a base verdict). No additional states may be introduced without a major version bump.
- **C-REL-02 (CHK003)**: Retry eligibility is keyed primarily on verdict state, secondarily on failure class: `errored`/`partial` from a transient environmental cause → retryable; `fail` (threshold violation) → never retryable; `pass` → no retry. The failure-class taxonomy (exit codes) refines but does not override verdict-state eligibility.
- **C-REL-03 (CHK004)**: Retries MUST be gated by an idempotency check: hash of save + sidecars before retry; reset to seed state; unique attempt IDs; no double-apply of side effects.
- **C-REL-04 (CHK007)**: A suite-level retry cap (`RunnerMaxSuiteReruns`) MUST be defined in addition to the per-scenario cap, to prevent unbounded CI retry storms.
- **C-REL-05 (CHK008/009)**: The fixed 5 s cooldown (`RunnerRetryCooldownMs = 5000`) is retained (not exponential) because run retries are environmental, not network-bound; jitter of ±1 s MAY be added. Rationale: Xvfb/process teardown dominates; exponential backoff applies to download retries (FR-002) only.
- **C-REL-06 (CHK011)**: Retry classification MUST be tied to the version-controlled `compat-matrix.json` contract; a new SMAPI version is not supported until its failure classes are classified.
- **C-REL-07 (CHK013)**: A confirmation threshold (N = 30 runs, binomial CI) MUST be defined before promoting a **scenario** to confirmed-flaky status, distinct from both the per-run `flaky` mark (FR-011) and the quarantine-candidate rule. A single run's `flaky` mark never changes scenario status.
- **C-REL-08 (CHK014)**: Pass-rate tiers MUST be defined as monitoring signals: healthy ≥ 99 %, monitor 95–99 %, **alert < 95 %**; suite alarm if > 2–3 % of scenarios are flaky. A tier crossing opens an investigation issue and notifies the owner; it is **not** a quarantine trigger by itself. Quarantine requires the separate 2-flaky-run candidate rule plus human approval (C-REL-26/C-REL-27).
- **C-REL-09 (CHK015)**: RAFT (retry-aware flaky test) awareness MUST be documented: verdict separation for retried failures, plus resource-varied detection (vary Xvfb/CPU configs, χ² test) to distinguish order-dependent from resource-dependent flakiness.
- **C-REL-10 (CHK022)**: Human approval MUST be required for quarantine entry, extension, and retirement (not fully automated), with an audit trail. Retirement (permanent removal from the suite) is distinct from auto-disable (temporary, automatic, reversible only through the shadow-pass gate in C-REL-27).
- **C-REL-11 (CHK035/036/037/038/040)**: Honesty levels MUST be defined in FR-014: W = launch/connect verified with no runtime evidence (tooling only); R = runtime evidence collected and valid (artifacts present, digests recomputed); E = human judgment, never auto-assigned, requires W + R prerequisites. Assignment is strictly sequential W → R → E. `claims.json` MUST carry an `honestyLevel` field alongside risk and safe wording.
- **C-REL-12 (CHK041/044/045)**: Signal independence MUST be required: each of the three signals is captured by an independent path (persisted SoilHealthState JSON, in-process Crop dump plus save cross-check, SMAPI log) and MUST NOT share a single failure mode. A signal is **failed** when its capture path errors, **incomplete** when its artifact is missing, and **divergent** when two captured signals disagree. Failed or incomplete signals yield `partial` (exit 19) unless the failure is a classified transient (then retry); divergence yields `partial` (exit 19). If two signals share a failure mode (for example, both read the same file), the run is `errored` (19) rather than claiming independence. Single-source evidence is explicitly prohibited for `pass`. The necessary-but-not-sufficient asymmetry MUST be documented: failure of any signal → not `pass`; agreement of all three → eligibility only (not automatic `verified`).
- **C-REL-13 (CHK012 refinement)**: A run is `flaky` iff attempt 1 fails with a retryable class AND a later attempt passes, on the **same commit, same seed, and no code change**, within the observation window; a flaky status MUST expire if no recurrence within the window.
- **C-REL-14 (CHK018)**: Quarantine extensions are capped at **one 14-day extension** (28 days total), then the scenario is auto-disabled and a GitHub issue is opened (C-REL-27); no further extensions. Deletion requires human approval. The earlier "2 renewals" wording is superseded by C-REL-21/C-REL-27 and MUST NOT be used.
- **C-REL-15 (CHK033)**: The complete allowed auto-promotion set is closed and enumerated in `contracts/test-md-template.md`: (1) `partial` → `verified` only on a clean, non-flaky `pass` with three agreeing signals, honesty level ≥ R, and matching `expectedVerdict`; (2) `verified` → `verified` only to refresh `runId`/`date`/evidence pointers on another clean, non-flaky `pass`; (3) `verified` → `partial` on any later `fail`/`errored`/`partial`/`skipped` or flaky `pass`; (4) any → `partial` by manual demotion after evidence review. All other transitions are prohibited: no `partial` → `pass`, no auto-`E`, no promotion from flaky or quarantined runs, and no hand-editing a non-pass block to `verified`. Re-promotion after a failed run requires a new full triad run, never a re-run-until-green loop.
- **C-REL-16 (CHK039)**: Claim discipline MUST include refusal-site liveness: the offline verifier MUST test that refusal sites (missing evidence, digest mismatch) actually fail, not just that happy paths pass.
- **C-CON-19 (CHK047)**: Concurrency primitives MUST be validated before merge. Managed-side contracts use systematic interleaving exploration plus property-based invariant tests; orchestration-script contracts use behavioral tests, static analysis, and a stress harness for lock/cleanup races. The stress harness MUST run K ≥ 30 concurrent instances (and a 1,000-iteration lock/rename loop) with the C-CON-21 pass criteria.
- **C-REL-17 (CHK056)**: Flakiness requirements MUST be explicitly identical across local and CI modes (single test entry point; no mode-specific flakiness behavior).
- **C-REL-18 (CHK057)**: Verdict requirements MUST be covered by tests (verdict state machine unit + integration tests).
- **C-REL-19 (CHK058)**: A traceability link MUST exist from each verdict requirement to its test case.
- **C-REL-20 (CHK059)**: Reliability requirements are reviewed on the tiered cadence recorded in `GOVERNANCE-ANNEX.md` (trigger-based on reliability-relevant changes, quarterly lightweight, annual full); the annex is the authoritative review record.
- **C-SCN-17 (CHK006)**: The scenario schema MUST include an IEEE 829 §6.2 field mapping table (identifier, test items, inputs, outputs, environment, procedural requirements, intercase dependencies) or document justified omissions.
- **C-SCN-18 (CHK007)**: Conditional requirements MUST be encoded via `if/then/else` or `dependentRequired` (e.g., farmhand scenarios require host-guard fields).
- **C-SCN-19 (CHK014)**: The test suite MUST include boundary-value analysis cases (min-1, min, min+1, max-1, max, max+1, sentinel, NaN, missing key, 0).
- **C-SCN-20 (CHK015)**: Every step input MUST be an explicit field (no hidden global state, time, or RNG seed); `inputs`, `rngSeed`, and `time` fields MUST be declared.
- **C-SCN-21 (CHK016)**: Step order is given by the ordered array; `dependsOn` is NOT required — array order is the single source of truth (documented).
- **C-SCN-22 (CHK017)**: Expected outputs MUST be exact values or ranged values with an explicit `tolerance` field (defaulting to 0.0001f where applicable).
- **C-SCN-23 (CHK022)**: Test-double kind declaration is N/A for this e2e runner (uses the real game); explicitly marked not applicable.
- **C-SCN-24 (CHK023)**: Injection lifecycle (per-scenario setup/teardown) MUST be explicitly specified.

- **C-LCH-02 (clean quit)**: The runner MUST NOT rely on SIGTERM alone — SMAPI registers no signal handlers, so `OnExiting`/`Dispose` may be skipped, and Stardew does NOT auto-save. #### Batch 4 — Research-Resolved Contracts (Session 2026-10-27, /speckit.clarify)

- **C-CON-22 (CHK004)**: After Xvfb cleanup, the runner MUST verify within bounded timeouts: (a) process liveness — `kill -0 $XVFB_PID` returns ESRCH within 100 ms of `waitpid`; (b) socket absence — `stat /tmp/.X11-unix/X{N}` returns ENOENT, confirmed in **2 consecutive polls 50 ms apart (about 50 ms total, not 100 ms)** within 500 ms of `waitpid` (TOCTOU guard); (c) no connection — `connect()` to the socket returns ENOENT/ECONNREFUSED within 500 ms; (d) no zombie — `/proc/$PID/stat` state ≠ `Z` within 100 ms. Polling is at 50 ms intervals. If the socket persists beyond 500 ms after process exit, the runner MUST force `unlink()` **only when the display is owned by this instance and its recorded PID + start-time identity token match**; otherwise it MUST log `orphaned-socket`, append to `orphaned-displays.json`, and MUST NOT unlink. With `nolock=TRUE` (no lock file), the runner MUST track the Xvfb PID and start-time token itself and use `kill -0` as the primary liveness signal (socket absence alone is insufficient against a crashed-and-restarted Xvfb on the same display). Constants: `RunnerDisplayCleanupProcessTimeoutMs=100`, `RunnerDisplayCleanupSocketTimeoutMs=500`, `RunnerDisplayCleanupPollIntervalMs=50`, `RunnerDisplayCleanupConfirmPolls=2`.
- **C-CON-23 (CHK019)**: Non-blocking lock acquisition MUST use a bounded poll loop with exponential backoff + jitter: initial delay `RunnerLockInitialDelayMs=100`, multiplier `RunnerLockBackoffMultiplier=2`, per-step cap `RunnerLockMaxDelayMs=2000`, attempts `RunnerLockMaxRetries=8`, hard wall-clock `RunnerLockTotalTimeoutMs=10000`, jitter `RunnerLockJitterPercent=25` (±25% per step). Locks are advisory only (CHK018); OFD locks (`F_OFD_SETLK`) preferred over process-associated locks; acquisition on local filesystem only (CHK032); global lock order `game-cache → build-output → shared-doc` documented (CHK021); there is no whole-run lock. Timeout is authoritative; on expiry the attempt is classified as lock contention (exit 6, retryable).
- **C-REL-26 (CHK016)**: `flaky` MUST be a **derived** mark computed from verdict history on the same commit + seed + environment, never manually assigned. Flakiness has **three independent axes that MUST NOT be conflated**: (a) the **per-run mark** (`flaky: true`, no scenario status change); (b) the **scenario status** (candidate → quarantined → disabled, with confirmed-flaky as a separate statistical status); and (c) the **suite signal** (pass-rate tier and flaky fraction, monitoring only). A run mark never mutates scenario status by itself; a scenario status never rewrites a historical run; a suite signal never quarantines anything. Derivation rule: a run is `flaky` iff attempt 1 fails with a retryable class AND a later attempt passes, on the same commit/seed/environment within the observation window; the mark MUST expire if no recurrence within the window. **Stage names are distinct and MUST NOT be used interchangeably:** (1) **flaky run** — the per-run derived mark (`flaky: true`), no scenario status change; (2) **quarantine candidate** — 2 flaky runs in the rolling 14-day window (or 2 of the last 3); automation opens a pending entry in `quarantine.json`; (3) **quarantined** — a human approves the pending entry (CODEOWNERS-gated); the scenario reports `skipped` and is removed from the blocking gate for the time-box; (4) **disabled** — automatic terminal action at the 28-day cap. **Confirmed flaky** is a separate statistical status, not a quarantine stage and not a prerequisite for quarantine: N ≥ 30 runs, Wilson 95% CI excludes 100% AND failure rate ≥ 30%; below N → `insufficient-data`. Pass-rate tiers (C-REL-08) are monitoring signals only and never create a quarantine candidate. Benjamini–Hochberg (q ≤ 0.05) where rates are compared across configs (RAFT). No single run may set `flaky`. Manual annotations (`@pytest.mark.flaky`-style) are a quarantine input, not a detection mechanism.
- **C-REL-27 (CHK018/CHK019)**: Quarantine escalation at the 28-day cap is **auto-disable** (remove from the blocking gate / mark ineligible for change-based test selection), NOT auto-re-enable. Auto-disable is the only automatic terminal action and is non-silent: at day ~21 notify the owner (and backup maintainer, if one exists); at day 28 auto-disable, escalate the linked issue, and create/raise a GitHub issue if none exists. Extensions: at most **1 extension** (28 days total), requiring a written reason and resetting the clock; no second extension. Deletion or **retirement** (permanent removal from the active suite, distinct from temporary auto-disable) requires human approval; the runner never deletes a quarantined scenario automatically. Re-enablement is gated on **stability evidence**: ≥ 20 consecutive **shadow passes**, never on the calendar alone. A **shadow pass** is a full scenario run executed out-of-band from the blocking gate, on the same commit/seed/environment, with normal evidence capture and verdict evaluation, but not counted toward promotion, flakiness, or quarantine status; the run is recorded in `quarantine.json` and the audit log with `shadow: true`. "Consecutive" means no intervening `fail`/`errored`/`partial` in that shadow series; a break resets the count. This reconciles C-REL-14 and C-REL-21: the hard ceiling is one 14-day extension (28 days total); the "2 renewals" wording is superseded.
- **C-SCN-36 (CHK001)**: The authoritative required-field set — at the top level and at every nested object level — is declared in the `required` arrays of `contracts/scenario.schema.json`; `data-model.md` reproduces it for readability. FR-007 names in prose only fields whose required/optional status was a clarification decision (currently `testMdPath`, `environment`, `minimumGameVersion`, and conditional `hostGuard`). A CI consistency check (extending speckit-analyze) MUST assert that `data-model.md`'s required-field table equals the union of `required` arrays in `scenario.schema.json`. IEEE 829 §6.2 field completeness is satisfied by the schema + a documented mapping (C-SCN-17), not by prose enumeration. CHK001 is re-worded to: "Is the required field set explicitly declared in the schema's `required` arrays at every object level, and mirrored in data-model.md?"
- **C-SCN-37 (CHK035)**: Split semantics for missing sparse-cache keys is normative and preferred: (1) domain read returns `NaN` for a missing key (unmeasured, not 0% health); `0f` always means a measured floor of the Poor interval; (2) arithmetic baselines (`SoilDecayService`, `CompostApplicationService`, `UpdateHealth`) may coerce `NaN → 0f` locally, before the operation; (3) persistence diff (`SaveComparator`) treats missing as `0` only at the persistence layer, stored `NaN` is skipped never mapped to 0; (4) visualization passes `NaN` for missing tiles so they render `Unknown` (gray); (5) growth modifier treats missing keys as non-participants, never Poor; (6) no silent coercion elsewhere; (7) explicit `0` round-trips as `0f`/Poor and is never collapsed into Unknown by sparse omission. The clause-2 coercion SHOULD be centralized into one shared helper to eliminate the three inline copies.
- **C-SCN-38 (CHK044)**: CHK044 ("same contract drives ≥2 runtime implementations") is **evaluated at the contract-portability layer**, not as a second runtime: the runner does not claim two implementations. It is substantiated by a **cross-validator agreement test** (Bowtie pattern): the same ≥5 valid + ≥5 invalid scenario fixtures MUST be run through ≥2 independent validators (e.g., `JsonSchema.Net` + Python `jsonschema`/`ajv`) with identical outcomes, gated in CI. Local vs. CI modes (FR-023) are mode-parity, not distinct implementations; dump vs. save (FR-009) are triangulated signals, not implementations. A full second runtime implementation (e.g., Python reference runner) is **deferred** behind the existing promotion triggers (FR-015 Phase 2 / FR-017 / 2+ features reuse), consistent with YAGNI and the Rule of Three; re-evaluate when the .NET runner is stable across ≥2 features and a non-.NET consumer appears.
- **C-SEC-29 (CHK031)**: Commands executed and materials/seeds are **mandatory per-run evidence** for honesty level R/E, added to the bundle manifest (additive fields): (a) `commands` array (argv as array, workingDir, timestamps, exitCode, stdout/stderr refs) recorded before products are computed (Witness material-before-execute ordering); (b) `materials` array of ResourceDescriptor (uri, sha256 digest, name, mediaType, size, annotations.role) with roles `game-file`, `mod-manifest`, `tool`, `seed-save`, `dataset-instance`; seeds are materials with `annotations.role = "seed"` plus a mandatory-presence rule (≥1 seed material for R/E runs), carrying `seedId`, `source`, `baseCommit`/`baseSaveHash`; (c) completeness flags `commandsCompleteness`, `materialsCompleteness` (default false unless hermetic), `seedsCompleteness`. Every command/material/seed digest is listed in the manifest `subject` array and covered by the detached `manifest.sha256` anchor. Honesty gating: W allows absence; R requires commands + materials + ≥1 seed + claims + recomputed digests; E requires R + maintainer attestation over the enumerated commands/materials/seeds. Producer MUST be the runner, not the mod under test (SLSA non-falsifiability).
- **C-SEC-28 (CHK040)**: Fail-closed integrity, no fallback to unverified. Verification is three-valued (verified / failed / unverified); "cannot determine" is its own outcome, never collapsed into verified. (a) Checksum mismatch (Phase 1, active): quarantine the artifact, delete partial, write `integrity-failure.json`, non-zero exit, no downstream execution, no retry, no weaker substitution, no unverified-cache reuse; (b) Signature mismatch (Phase 2, deferred): identical fail-closed semantics when Sigstore/cosign activates, including no fallback from X.509 cert to raw public key (GHSA-fx35-mq7g-6g98 lesson); deferral is documented, auditable, non-weakening, recorded as `signatureVerification: deferred` in the bundle; (c) universal no-fallback: no skip on missing tool, no relaxed retry, no unverified cache reuse; (d) audit/tamper-evidence: `integrity-failure.json` carries `verificationMode` (`checksum` | `signature`) and `phase` (`pre-extraction` | `post-extraction` | `cache-reuse`); ≥365-day retention (FR-027). The offline verifier (FR-015) MUST test refusal-site liveness for both checksum and signature paths.

### Key Entities

- **Scenario Definition**: A declarative description of a verification scenario — steps (place bin, insert waste, sleep N days, harvest, apply compost, observe), expected signals, and threshold rules. Provided by a feature; consumed by the runner.
- **Evidence Bundle**: A directory (`evidence-bundle-<run-id>/`) containing `manifest.json`, the mandatory detached `manifest.sha256` anchor, `claims.json`, `artifacts/`, JUnit XML, and Allure JSON. Produced by every run.
- **Run Verdict**: One of `pass` / `fail` / `errored` / `partial` / `skipped`, with the derived `flaky` mark and attached diagnostics/artifact paths.
- **Signal Set**: The three required signals (SoilHealthState delta, Crop phase delta, SMAPI log) plus optional visual evidence.

- **SC-007**: The offline verifier recomputes every digest in `manifest.json` and rejects a bundle with any single tampered byte; tested with at least one tampered fixture per artifact class.
- **SC-008**: A maintainer on a clean Linux host follows `quickstart.md` and completes a run within 30 minutes of the first command, excluding one-time game acquisition, without editing any file. Measured by: timed dry run plus shell history.
- **SC-009**: A transient attempt-1 failure followed by a pass yields exit `0` and `flaky: true`; 2 flaky runs in 14 days create a quarantine candidate; no flaky or quarantined run is promoted to `verified`; 100% of cases match.
- **SC-010**: After one discarded warmup, each measured per-location elapsed value is ≤ 5 ms or the run fails; a young-generation garbage-collection delta is recorded in the bundle for 100% of measured runs.
- **SC-011**: K ≥ 30 concurrent instances produce K distinct display identities and K distinct save-copy paths, with 0 interleaved verdicts and 0 save-hash mismatches.
- **SC-012**: 100% of tampered archives (traversal member, oversized member, duplicate member, wrong digest) are rejected before game launch, with `integrity-failure.json` present and no retry.
- **SC-013**: 100% of sampled audit/evidence artifacts (sample ≥ 30 bundles per quarter) have a durable-store receipt, a valid digest, and a retention timestamp ≥ 365 days; an attempted deletion before expiry is denied and produces an audit event. Measured by: the quarterly durable-store audit query plus a deletion-drill log.
- **SC-014**: A second maintainer on a different Linux host reproduces the same verdict for the same commit, milestone save, and seed in 3 of 3 repetitions; any divergence produces an Anomaly Report naming owner, date, and root cause before the bundle is marked `verified`. Measured by: verdict equality 3/3 and the Anomaly Report path.

## Assumptions

- **A1**: A host with access to the private builddeps repository (via `BUILDDEPS_TOKEN` secret) is available; the runner downloads game files from there rather than from a game store **when acquisition is required (cache miss or `--force-refresh`)**. A valid cached install is reused without network or token (see FR-001 cache-first). The user's legally purchased game files are hosted in the private repo (same pattern as the dormant `Build and Test` workflow).
- **A2**: The private builddeps repository contains a complete, valid game + SMAPI installation archive (`gamepath.zip` or equivalent) with all 6 required assemblies; the runner verifies checksums before extraction.
- **A3**: Xvfb + MonoGame rendering is stable enough for unattended scenario execution on Linux (precedent: JunimoServer runs Stardew + SMAPI headless on Linux via Docker/Xvfb).
- **A4**: Scenario injection can be driven by the dev/CI-only `LivingRoots.Verification` mod plus SMAPI debug macros and console commands without human input (precedent: dedicated-server mods automate host behavior).
- **A5**: `Crop.currentPhase` / `dayOfCurrentPhase` can be captured unattended via in-process dump to file/log or save-file inspection of serialized Crop data.
- **A6**: The SMAPI console log reliably contains the elapsed-ms trace line and `DayEnding` event name in a parseable format (format may need version-pinning).
- **A7**: The spec 009 manual protocol (`VERIFICATION_PROTOCOL.md` §3, `gate3-verification-contract.md`, SC-009) remains a documented fallback for hosts where the runner cannot execute.
- **A8**: The runner is an internal reusable module first; "para outros mods" is aspirational and requires the scenario contract to be defined and proven (Regra dos Três).
- **A9**: The proprietary game assemblies in `.gamepath` are not distributed by the runner; the six required assemblies are checked by the preflight and the runner relies on a pre-configured host.
- **A10**: The 3-signal triangulation and threshold rules from spec 009 (34/67 boundaries, 1.15×/0.85× multipliers, never below 1, never touch 99999 sentinel, NaN tiles skipped) are the authoritative evaluation criteria for the runner.
- **A11**: The Crop-phase dump hook lives in a separate, dev/CI-only verification mod (`LivingRoots.Verification`), not in the production `LivingRoots` binary; the main mod exposes only a production-safe ordering signal after `ApplySoilGrowthModifier` (see Clarifications, Session 2026-10-26). The verification mod is excluded from the release zip and verified absent by CI.
- **A12**: Reproducible initial conditions use the StarDojo hybrid: milestone saves (≤ ~5 curated binary save folders) in the private builddeps repo + per-scenario `initCommands` (typed macro/console entries) in the public repo; mod sidecars are generated, not checked in (see Clarifications, Session 2026-10-26).
- **A13**: Game-archive acquisition uses GitHub Releases assets with the authoritative SHA-256 pinned in the reviewed `gamepath.lock.json` (release `.sha256` advisory only), fine-grained PAT (`BUILDDEPS_TOKEN`), exponential-backoff retry (3–5 attempts), and auth fail-fast; partial download is best-effort resume only (see Clarifications, Session 2026-10-26).
- **A14**: Flaky handling uses 2 retries (3 total attempts), 5 s fixed cooldown, 14-day observation window, quarantine candidate at 2 flaky runs with human approval before entry, 14-day time-box with one 14-day extension, owner resolution chain defaulting to repo owner (lfgranja), recorded in a committed `quarantine.json`; quarantined scenarios report as `skipped` and are never auto-promoted (see Clarifications, Session 2026-10-26).
- **A15**: Version compatibility uses a single pinned stable line (latest SV 1.6.x + matching SMAPI) in a version-controlled `compat-matrix.json`, 3-tier policy (HARD-FAIL/WARN/INFO), file-based pre-launch detection using SMAPI's `SemanticVersion`, manifest additions (`MinimumGameVersion: 1.6.14`, `MinimumApiVersion: 4.4.0`), mod at 0.x best-effort until 1.0.0, evidence bundle `compatibility` block (see Clarifications, Session 2026-10-26).
- **A16**: The runner is delivered as a **thin orchestration layer** extending the spec 008 smoke-validation substrate (Xvfb `-displayfd`, process-group/signal discipline, run log under XDG state, exit-code taxonomy), plus a **small helper process** invoked by the orchestrator for the operations the orchestration layer cannot perform safely in-process: JSON Schema validation, structured-predicate evaluation, and in-process archive extraction with member validation (FR-025). The helper is not a second runner: it has no orchestration, launch, or verdict authority, and it communicates via documented argv/stdin/stdout JSON. "Invoked identically locally and in CI mode" means the **same entry point, scenario file, validation path, and verdict semantics**; CI mode changes only non-interactivity and machine-readable output (JUnit/Allure), never the security or verdict behavior (C-CON-16, C-REL-17, C-SEC-10). Docker is deferred until 2+ mods reuse the loop (Regra dos Três); no Dockerfile/registry exists today.
