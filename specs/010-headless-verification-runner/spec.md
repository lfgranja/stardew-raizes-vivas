## Clarifications

### Session 2026-10-26

- Q: What format should scenario definitions use? → A: **JSON** (validated against a JSON Schema) as the canonical machine format, with an optional human-facing Markdown companion checklist. JSON has no parser dependency in .NET (`System.Text.Json` is built-in); YAML is not used anywhere in the stack and would add a dependency (YAGNI). Thresholds reference `ModConstants` values by name and numeric value.
- Q: How should `Crop.currentPhase`/`dayOfCurrentPhase` be captured unattended? → A: **In-process dump** (verification mod writes JSON at `DayEnding` after `ApplySoilGrowthModifier`, atomic temp-file+rename, "done" sentinel) as the primary oracle; **save-file inspection** of serialized Crop data as an independent cross-check (divergence is diagnostic). Screenshots/OCR are supporting evidence only.
- Q: What mechanism should the runner use to inject scenarios? → A: **SMAPI macros** (`debug runmacro <file>`) for deterministic batch command execution (sleep, warp, item give) + **save file seeding** (StarDojo pattern) for reproducible initial conditions + **custom mod console commands** (e.g., `lr_dump_crop_phase`) for mod-specific state capture. Input simulation (xdotool) is excluded (fragile, non-deterministic). No verification bot mod needed — macros + seeding + custom commands provide sufficient determinism with lower effort and risk. Prior art: StarDojo (arXiv:2507.07445, ECCV 2026).
- Q: How should the runner acquire game files? → A: **Private repository download via GitHub API** using a secret token (`BUILDDEPS_TOKEN`), following the same pattern already used by the dormant `Build and Test` workflow (`.github/workflows/build-and-test.yml`). The user's legally purchased game files are uploaded to a private repo; the runner downloads, verifies checksum, and extracts. This eliminates SteamCMD, Steam Guard, and interactive authentication entirely. The runner fails fast if the token is missing or the repo is inaccessible. No proprietary assemblies are distributed in the public repo.
- Q: Should the Crop-phase dump hook be shipped as a separate verification mod or embedded in LivingRoots? → A: **Separate, dev/CI-only verification mod** (`LivingRoots.Verification`), not embedded in the main mod and not in production builds. SMAPI has no access control on console commands (any `Helper.ConsoleCommands.Add` entry is callable by anyone and shows in `help`); shipping dump code in the production binary leaves it present-but-disabled (CWE-489). The verification mod depends on LivingRoots via manifest `Dependencies`, is built from the same commit, and is excluded from the release zip; main mod exposes only a production-safe ordering signal (event raised after `ApplySoilGrowthModifier` in `OnDayEnding`) so the dump happens deterministically after the modifier. Runtime-gated debug code in the main mod is rejected (CWE-489 / OWASP ASVS 14.3.2). Aligns with FR-004/FR-009 references to "the verification mod."
- Q: How is the reproducible initial save created and maintained? → A: **Hybrid (StarDojo two-phase)**: (1) **milestone saves** — a small set (≤ ~5) of curated binary save folders stored in the **private builddeps repo** (FR-002/NFR-002), each with a JSON save manifest (game version, SMAPI version, save name/id, SHA-256, documented contents); never in the public repo; (2) **per-scenario `init_commands`** — SMAPI macros (`debug runmacro <file>`) + custom commands (`lr_dump_crop_phase`, plus seeding commands) that place the compost bin, insert waste, set crop phases, and set soil health, keeping the mod-specific delta (sidecars `soil_health_data_{saveId}.json` / `composting_bins_{saveId}.json`) **generated, reviewable, and version-stable** rather than opaque binary. Each runner instance copies the milestone save into a temp `XDG_CONFIG_HOME` (FR-018), runs macros, captures the 3 signals, then restores and asserts byte-identical (SC-005). Version bumps are regeneration events. Aligns with FR-006/FR-018.
- Q: What is the download endpoint, retry, and integrity policy for the game archive? → A: **GitHub Releases assets** (`GET /repos/{owner}/{repo}/releases/assets/{asset_id}` with `Accept: application/octet-stream`), fetched via `gh release download` or `curl -L` with `Authorization: Bearer ${BUILDDEPS_TOKEN}` — NOT the Contents API (1,000-entry cap, base64 overhead, 5-min URL expiry) and NOT auto-generated source archives (unstable hashes). **Checksum mandatory**: publish `gamepath.zip.sha256` alongside the asset; verify with `sha256sum -c` before extraction; fail fast on mismatch (treat as security event). **Auth fail-fast**: probe repo/release access first; 401/403/404 are terminal (no retry). **Retry**: exponential backoff with full jitter, 3–5 attempts, only on transient errors (5xx, 429 honoring `Retry-After`, network timeout/reset/DNS); cap total elapsed time (~5 min). **Partial download**: best-effort resume only (CDN `Range` support not guaranteed by GitHub); always verify final SHA-256; on mismatch delete `.part` and restart from byte 0. **Token**: fine-grained PAT scoped to the single private repo with `Contents: read` + `Metadata: read`, stored as `BUILDDEPS_TOKEN` repository secret, shortest viable expiry; upgrade to a GitHub App installation token (15k/hr, 1-hr expiry) for production. **Extraction**: temp dir + atomic swap + 6-assembly preflight; reject partial `.gamepath`. Aligns with FR-002/NFR-002.
- Q: What concrete retry, flakiness, and quarantine parameters should the runner use? → A: **2 retries (3 total attempts) for classified transient classes only** (reuse smoke-validation exit codes: Xvfb/display=10, launch timeout=4, lock contention=6, process conflict=7, save I/O, macro timeout; NOT retryable: threshold violation, crash, incomplete signals, version mismatch, missing dependency=9, host-guard breach); fixed 5 s cooldown (not exponential) between attempts, with mandatory per-attempt artifacts (`attempts/<n>/attempt.json`, stdout/stderr, intermediate verdict, signals). A run is **`flaky`** iff attempt 1 fails with a retryable class AND a later attempt passes. A scenario is **quarantined** only after 2 flaky runs within a rolling 14-day window (or 2 of the last 3 runs), for a 14-day time-box with one 14-day extension (28 days total) then escalate (auto-re-enable + GitHub issue). Owner via resolution chain: `--quarantine-owner` → `QUARANTINE_OWNER` env → git identity → repo owner (lfgranja), recorded in a committed `quarantine.json` registry; CODEOWNERS as future scale-up hook. Quarantined scenarios report as `skipped` in JUnit/Allure. No auto-promotion to `verified` for flaky/quarantined scenarios (FR-016). Constants: `RunnerMaxTransientRetries=2`, `RunnerRetryCooldownMs=5000`, `RunnerFlakyObservationWindowDays=14`, `RunnerFlakyQuarantineTriggerCount=2`, `RunnerQuarantineTimeBoxDays=14`, `RunnerQuarantineExtendedTimeBoxDays=28`. Aligns with FR-011/FR-016/FR-020.
- Q: What is the supported Stardew Valley / SMAPI version matrix and mismatch policy? → A: **Single pinned stable line** — latest Stardew Valley 1.6.x and matching SMAPI release — documented in a version-controlled `compat-matrix.json`; **hard-fail** (exit code 2, abort before Xvfb launch) if game/SMAPI/mod is outside the supported set or below the mod's `MinimumApiVersion`/`MinimumGameVersion`; **warn** (proceed + record deviation in evidence bundle) for newer-than-pinned (forward compat assumed) or unverified-but-in-range combinations; **info** (proceed, log only) for exact matrix match. Detection is file-based before launch (parse `Stardew Valley.dll`, `StardewModdingAPI.dll`, `manifest.json`; mod self-check; matrix classification). Version comparisons use SMAPI's `SemanticVersion` (never `string.Compare`; handle non-standard `1.11` < `1.2` and `-unofficial.*` channel). Mod manifest changes: add `"MinimumGameVersion": "1.6.14"` and bump `"MinimumApiVersion"` from `4.0.0` to `4.4.0` (or `4.5.0`). Mod at `0.x` is best-effort until `1.0.0`. Evidence bundle gains a `compatibility` block (observed/minimum/maximum/tier per component, modSelfCheck, deviation). SMAPI's null `MaximumGameVersion` is recorded as an upper-bound deviation → warn, not info, when observed game exceeds matrix maximum. Aligns with FR-001/FR-002/NFR-001.
- Q: How should a tile with no SoilHealthState entry (missing key) be treated in threshold evaluation? → A: **Non-participant (skipped, no change)** — not health 0 / not Poor. Missing keys and health `<= 0` are non-participants in growth threshold evaluation (FR-010); only strictly positive stored health `< 34` counts as Poor. Missing keys are treated as `0` **only** inside `SaveComparator` (persistence-layer diff, FR-012) and must not be conflated with runtime health (`GetSoilHealth`: missing → NaN → skip → vanilla). Aligns with `ApplySoilGrowthModifier` (`health <= 0f` skip) and spec 009 CHK032.
- Q: Is the automated runner required to support Windows/macOS hosts, or Linux (Xvfb) only? → A: **Linux (Xvfb) hosts only** for the automated runner. NFR-001 narrowed accordingly; the mod remains cross-platform, and Windows/macOS use build + unit tests plus the manual fallback (FR-021 / `VERIFICATION_PROTOCOL.md`). Xvfb has no admin-free, driver-free equivalent on Windows/macOS; CI stays `ubuntu-latest`.
- Q: What observable signal indicates a "host-guard breach" so the runner can classify it as non-retryable? → A: In a scenario tagged as a **farmhand (non-host)** session, a breach is indicated when execution evidence is present (the `Soil growth modifier elapsed: … ms` trace line, or a `phaseDays` mutation in the Crop-phase dump/save) **without** the `Soil growth modifier skipped: not main player.` skip line. Scenario definitions MUST declare the expected player role (host vs. farmhand). Non-retryable (FR-011); never quarantined or auto-promoted.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Maintainer runs full verification unattended (Priority: P1) 🎯 MVP

As the maintainer, I want to invoke a single command that builds, deploys, launches Stardew Valley headless under SMAPI, injects the compost→growth scenario, captures all three signals, evaluates thresholds, and produces a pass/fail verdict plus an evidence bundle — without me opening the game, building a farm, planting, watering, or waiting days — so that Gate 3 verification becomes a repeatable, reliable, non-manual process.

**Why this priority**: This is the core value: eliminating the manual gameplay loop that currently blocks `verified` status and makes every feature's verification error-prone and non-reproducible.

**Independent Test**: On a host with `STARDEW_GAME_PATH` configured and a licensed Steam account, running the runner against feature 004's scenario completes unattended and produces (a) a pass/fail verdict, (b) an evidence bundle with all three signals, and (c) an updated `test.md` status — with zero human gameplay input.

**Acceptance Scenarios**:

1. **Given** a clean host with `STARDEW_GAME_PATH` set, Steam credentials configured, and the mod built, **When** the maintainer runs the runner for feature 004, **Then** the runner downloads/verifies game files via SteamCMD, launches Stardew under Xvfb + SMAPI, loads the verification mod, executes the compost→growth scenario, captures all three signals, evaluates thresholds, and exits with a pass/fail verdict — all without human gameplay input.
2. **Given** the runner completes a scenario, **When** the pass/fail verdict is `pass`, **Then** an evidence bundle (MIRROR-style: `manifest.json` with SHA-256 per file, `claims.json`, `artifacts/`, JUnit XML, Allure JSON) is written and `test.md` is updated from `partial` to `verified` with file paths to all three signals.
3. **Given** the runner detects a threshold violation (e.g., poor soil did not slow growth), **When** evaluation completes, **Then** the verdict is `fail` with a diagnostic naming the violated threshold and the observed vs. expected values, and `test.md` is NOT auto-promoted to `verified`.
4. **Given** the runner encounters a crash or incomplete signal set, **When** evaluation completes, **Then** the verdict is `errored` or `partial` (never auto-promoted to `pass`), with attached artifacts and per-attempt logs.

### User Story 2 - Contributor reuses the runner for another feature (Priority: P2)

As a contributor, I want to define a new scenario (checklist + thresholds) for my feature and run the same runner against it, so that Gate 3 verification is reproducible without inventing steps and the same harness serves all 19 roadmap features.

**Why this priority**: Reusability is the stated goal ("para reutilizar para as outras features implementadas, do objetivo, do roadmap e em outros mods"). Without a scenario contract, each feature reinvents verification.

**Independent Test**: A contributor can add a scenario definition for a second feature and run the runner against it without modifying the runner's core, producing a pass/fail verdict and evidence bundle.

**Acceptance Scenarios**:

1. **Given** a contributor has added a scenario definition (checklist + thresholds) for their feature, **When** they invoke the runner with that scenario, **Then** the runner executes it unattended and produces a verdict + evidence bundle identical in structure to US1.
2. **Given** a scenario definition is missing or malformed, **When** the runner starts, **Then** it fails fast with a clear error naming the missing/invalid field, before launching the game.

### User Story 3 - CI runs verification on a self-hosted runner (Priority: P3)

As CI infrastructure, I want the runner to be invocable from a self-hosted runner (with access to the private builddeps repository via `BUILDDEPS_TOKEN`), so that verification can be triggered automatically on push/PR without a human, while public CI remains dormant.

**Why this priority**: Tertiary — the runner must first work locally; CI integration is a follow-on. Public CI (`Build and Test`) stays dormant due to proprietary-DLL barriers.

**Independent Test**: On a self-hosted runner with `STARDEW_GAME_PATH` set and Steam credentials available, the runner executes a scenario and reports pass/fail to CI (JUnit XML + Allure JSON) without human intervention.

**Acceptance Scenarios**:

1. **Given** a self-hosted runner with access to the private builddeps repository via `BUILDDEPS_TOKEN`, **When** the runner is invoked in CI mode, **Then** it downloads game files, runs headless, produces JUnit XML + Allure JSON, and exits with a non-zero code on `fail`/`errored`/`partial`.
2. **Given** the public (GitHub-hosted) CI, **When** a PR is opened, **Then** the runner is NOT invoked (public CI has no game files); the manual/local runner remains the verification path.

### Edge Cases

- What happens when the private builddeps repository is inaccessible or the token is missing/invalid? The runner must fail fast with a clear error naming the missing token or repository, before attempting any download.
- What happens when the game version or SMAPI version mismatches the mod's expected version? The runner MUST detect and report the mismatch **before scenario execution** (before Xvfb launch) using a file-based pre-launch gate: parse `Stardew Valley.dll` (game), `StardewModdingAPI.dll` (SMAPI, using SMAPI's `SemanticVersion` — never `string.Compare`; handle non-standard `1.11` < `1.2` and `-unofficial.*`), and `manifest.json` (mod version, `MinimumApiVersion`, `MinimumGameVersion`); perform mod self-check; classify against a version-controlled `compat-matrix.json` using the 3-tier policy (HARD-FAIL exit code 2 / WARN proceed+record deviation / INFO proceed+log); hard-fail if outside the supported set or below minimums, warn if newer-than-pinned or unverified-but-in-range, info on exact match. Mod manifest must declare `"MinimumGameVersion": "1.6.14"` and bump `"MinimumApiVersion"` to `4.4.0` (or `4.5.0`). Mod at `0.x` is best-effort until `1.0.0`. Evidence bundle gains a `compatibility` block (observed/minimum/maximum/tier per component, modSelfCheck, deviation). SMAPI's null `MaximumGameVersion` is recorded as an upper-bound deviation → warn when observed game exceeds matrix maximum.- What happens when a scenario step times out (e.g., crop does not grow within expected days)? The runner must abort with `errored`/`partial` and attach artifacts.
- What happens when the save file is corrupted or missing after the session? The runner must report `errored` with the before/after state, not crash.
- What happens when `STARDEW_GAME_PATH` is unset or points to an invalid path? The runner must fail fast with a clear error before attempting SteamCMD/game download.
- What happens when Xvfb fails to start or the display is unavailable? The runner must detect and report, not silently proceed.
- How does the runner handle a flaky scenario (passes on retry)? A run is `flaky` iff attempt 1 fails with a retryable class AND a later attempt passes. Flakies are quarantined (with owner and time-box) only after 2 flaky runs within a rolling 14-day window (or 2 of the last 3 runs), for a 14-day time-box with one 14-day extension then escalate; quarantined scenarios report as `skipped` in JUnit/Allure and are never auto-promoted to `verified`. Retry is limited to transient/environmental failures (classified via smoke-validation exit codes) with mandatory per-attempt logging; threshold violations, crashes, incomplete signals, version mismatches, missing dependencies, and host-guard breaches are NOT retried.- What happens when two runner instances run concurrently on the same host? They must use distinct save copies and distinct display numbers to avoid collision.

## Requirements *(mandatory)*

### Functional Requirements

#### Host & Environment

- **FR-001**: The runner MUST verify that `STARDEW_GAME_PATH` is set and points to a valid Stardew Valley + SMAPI installation before any other step; if not, it MUST fail fast with a clear, actionable error.
- **FR-002**: The runner MUST acquire game files from a **private repository** (e.g., `lfgranja/stardew-raizes-vivas-builddeps` or equivalent) via the GitHub **Releases assets** endpoint (`GET /repos/{owner}/{repo}/releases/assets/{asset_id}`, `Accept: application/octet-stream`), authenticated with a secret token (`BUILDDEPS_TOKEN` or equivalent), following the same pattern already used by the dormant `Build and Test` workflow (`.github/workflows/build-and-test.yml`) but extended with the resilience layer below. The runner MUST NOT use the Contents API (1,000-entry cap, base64 overhead, 5-min URL expiry) or auto-generated source archives (unstable hashes). The runner MUST verify the token is present and valid (probe repo/release access) before attempting download; if the token is missing or the repository is inaccessible, it MUST fail fast with a clear, actionable error. The runner MUST NOT use SteamCMD or interactive Steam authentication — the private-repo pattern eliminates the Steam Guard barrier entirely. The downloaded archive MUST be verified (SHA-256, published as `gamepath.zip.sha256` alongside the asset) before extraction; on mismatch the runner MUST fail fast and treat it as a security event. The runner MUST retry transient failures (5xx, 429 honoring `Retry-After`, network timeout/reset/DNS) with exponential backoff + full jitter (3–5 attempts, capped total elapsed time); 401/403/404 are terminal (no retry). Partial-download recovery is best-effort only (CDN `Range` support is not guaranteed by GitHub): always verify the final SHA-256 and restart from byte 0 on mismatch, using a `.part` temp file + atomic rename. The token MUST be a fine-grained PAT scoped to the single private repo (`Contents: read` + `Metadata: read`), stored as `BUILDDEPS_TOKEN`, shortest viable expiry; upgrade to a GitHub App installation token for production.

- **FR-003**: The runner MUST start a virtual display (Xvfb) and verify it is available before launching the game; if Xvfb fails to start, the runner MUST abort with a clear error.
- **FR-004**: The runner MUST deploy the mod (and the verification mod) into the game's `Mods/` folder and verify deployment succeeded before launch.

#### Launch & Scenario Injection

- **FR-005**: The runner MUST launch Stardew Valley under SMAPI headlessly and wait for the game to reach a ready state (mod loaded, save available) before injecting the scenario.
- **FR-006**: The runner MUST inject the scenario into the game without human input using **SMAPI macros** (`debug runmacro <file>`) for deterministic batch command execution (sleep, warp, item give, etc.) combined with **save file seeding** (StarDojo two-phase pattern) for reproducible initial conditions, plus **custom mod console commands** (e.g., `lr_dump_crop_phase`) for mod-specific state capture. Save seeding is **hybrid**: (i) **milestone saves** (≤ ~5 curated binary save folders) stored in the private builddeps repo with a JSON save manifest (game/SMAPI version, save name/id, SHA-256, documented contents) provide coarse progression; (ii) **per-scenario `init_commands`** (SMAPI macros + custom commands) place the compost bin, insert waste, set crop phases, and set soil health, so mod sidecars (`soil_health_data_{saveId}.json`, `composting_bins_{saveId}.json`) are **generated, reviewable, and version-stable** rather than checked in as opaque binary. The injection mechanism MUST be documented and reproducible. Input simulation (xdotool) is explicitly excluded (fragile, non-deterministic). A verification bot mod is NOT required for *injection* — SMAPI macros + save seeding + custom commands provide sufficient determinism with lower effort and risk. The Crop-phase dump hook itself lives in a separate dev/CI-only verification mod (see Clarifications, Session 2026-10-26), not in the production binary.

- **FR-007**: The runner MUST support a scenario definition (checklist + thresholds) as input, so that different features can be verified without modifying the runner's core. The scenario definition MUST be authored as **JSON** (validated against a JSON Schema), with an optional human-facing **Markdown** companion checklist for contributor readability. JSON is the canonical machine format (no parser dependency in .NET — `System.Text.Json` is built-in; YAML is not used anywhere in the stack and would add a dependency, violating YAGNI). Thresholds in the scenario MUST reference `ModConstants` values by name and numeric value.
- **FR-008**: The runner MUST validate the scenario definition before launch (required fields, valid thresholds, valid boundaries); if invalid, it MUST fail fast with a field-level error.

#### Signal Capture & Evaluation

- **FR-009**: The runner MUST capture all three signals for every run: (i) `SoilHealthState` JSON delta (before/after `modData/soil_health_data_{saveId}.json`), (ii) `Crop.currentPhase` / `dayOfCurrentPhase` delta captured via **in-process dump** (the dev/CI-only `LivingRoots.Verification` mod writes a JSON dump at `DayEnding` *after* `ApplySoilGrowthModifier` has completed, using a production-safe ordering signal exposed by the main mod — not cross-mod handler ordering — with before/after pairs, atomic temp-file+rename, and a "done" sentinel) as the primary oracle, with **save-file inspection** of serialized `Crop` data as an independent cross-check (divergence between dump and save is diagnostic, not noise), and (iii) SMAPI console log excerpt confirming event execution and elapsed ms.

- **FR-010**: The runner MUST apply the threshold rules: poor soil (health < 34) MUST slow growth (1.15× on `phaseDays`), healthy soil (health ≥ 67) MUST accelerate growth (0.85×), moderate [34, 67) MUST be unchanged (1.00×); `phaseDays` MUST never go below 1 and the 99999 sentinel MUST never be touched. Tiles with NaN health MUST be skipped (no change). Tiles with **no SoilHealthState entry (missing key)** and tiles with health `<= 0` MUST be treated as **non-participants (skipped, no change)** — never as Poor soil; only strictly positive stored health `< 34` counts as Poor. (Missing keys are treated as `0` only inside `SaveComparator`, per FR-012, at the persistence layer.)
- **FR-011**: The runner MUST compute a pass/fail/errored/partial/skipped/flaky verdict using the 4-state model plus flaky: crash → `errored` with attached artifacts; incomplete signal set → `partial` (never auto-promoted to `pass`); transient/environmental failure → retry with **bounded attempts** (`RunnerMaxTransientRetries = 2`, i.e. 3 total attempts) for **classified transient classes only** (reuse smoke-validation exit codes: Xvfb/display=10, launch timeout=4, lock contention=6, process conflict=7, save I/O error, macro timeout; NOT retryable: threshold violation, crash, incomplete signals, version mismatch, missing dependency=9, host-guard breach), with a fixed `RunnerRetryCooldownMs = 5000` cooldown and **mandatory per-attempt artifacts** (`attempts/<n>/attempt.json`, stdout/stderr, intermediate verdict, signals); a run is **`flaky`** iff attempt 1 fails with a retryable class AND a later attempt passes. **Confirmed flaky → quarantine** with owner and time-box only after 2 flaky runs within a rolling 14-day window (or 2 of the last 3 runs), for `RunnerQuarantineTimeBoxDays = 14` with one 14-day extension (`RunnerQuarantineExtendedTimeBoxDays = 28`) then escalate (auto-re-enable + GitHub issue); owner via `--quarantine-owner` → `QUARANTINE_OWNER` env → git identity → repo owner (lfgranja), recorded in a committed `quarantine.json` registry. Quarantined scenarios report as `skipped` in JUnit/Allure. No auto-promotion to `verified` for flaky/quarantined scenarios (FR-016). Constants: `RunnerMaxTransientRetries=2`, `RunnerRetryCooldownMs=5000`, `RunnerFlakyObservationWindowDays=14`, `RunnerFlakyQuarantineTriggerCount=2`, `RunnerQuarantineTimeBoxDays=14`, `RunnerQuarantineExtendedTimeBoxDays=28`. **Host-guard breach detection:** in a scenario tagged as a farmhand (non-host) session, a breach is detected when execution evidence is present (the `Soil growth modifier elapsed: … ms` trace line, or a `phaseDays` mutation in the Crop-phase dump/save) without the `Soil growth modifier skipped: not main player.` skip line; scenario definitions MUST declare the expected player role (host vs. farmhand).- **FR-012**: The runner MUST use the `SaveComparator` (0.0001f float tolerance, missing keys treated as 0, NaN tiles ignored) for the SoilHealthState delta, producing `added`/`removed`/`changed` entries. **Layer note:** missing keys are treated as `0` only at the persistence/diff layer (sparse cache); this differs from runtime `GetSoilHealth` (missing → NaN → skip → vanilla) and must not be conflated with threshold evaluation (FR-010), where missing keys are non-participants.
- **FR-013**: The runner MUST parse the SMAPI log for the elapsed-ms trace line and hard-fail if elapsed > 5 ms for the run (SC-009 criterion 6).

#### Evidence & Output

- **FR-014**: The runner MUST produce a MIRROR-style evidence bundle: `manifest.json` (schema version, run id, timestamp ISO 8601, tool/game/mod versions, environment, SHA-256 per file), `claims.json` (claim → evidence pointer, risk, safe wording), `artifacts/` (screenshots, SMAPI logs, save-deltas before/after, reflection outputs), JUnit XML (CI), and Allure JSON (rich report). Honesty levels: W (launch/connect) / R (runtime evidence collected) / E (human judgment, never auto-assigned).
- **FR-015**: The runner MUST produce an offline-verifiable bundle: a verifier recomputes digests and validates schema; structural pass ≠ truth.
- **FR-016**: The runner MUST update `test.md` from `partial` to `verified` only when all three signals agree and the verdict is `pass`; on `fail`/`errored`/`partial`, it MUST NOT auto-promote.
- **FR-017**: The runner MUST update `COMPLETION_SUMMARY.md` and `ROADMAP.md` Gate 3 status on a `pass` verdict, recording the promotion trigger for deferred components (reflector/logger/runner promoted only after 2+ features reuse the loop).

#### Process & Lifecycle

- **FR-018**: The runner MUST always run against a disposable copy of the save (never the player's real save); it MUST back up/restore `Saves/<Name>/` and sidecars, using `XDG_CONFIG_HOME` pointing to a temp dir; the original save MUST be byte-identical at the end.
- **FR-019**: The runner MUST quit the game cleanly after scenario completion and capture all artifacts before exit.
- **FR-020**: The runner MUST support concurrent instances on the same host using distinct save copies and distinct display numbers.
- **FR-021**: The runner MUST preserve the manual SC-009 protocol as a documented fallback (`VERIFICATION_PROTOCOL.md` §3, `gate3-verification-contract.md`) for hosts where the runner cannot execute.

#### Reusability

- **FR-022**: The runner MUST expose a scenario contract so that a feature can define its own scenario (steps + thresholds) without modifying the runner's core.
- **FR-023**: The runner MUST be invocable both locally (interactive) and in CI mode (non-interactive, machine-readable output).

### Key Entities

- **Scenario Definition**: A declarative description of a verification scenario — steps (place bin, insert waste, sleep N days, harvest, apply compost, observe), expected signals, and threshold rules. Provided by a feature; consumed by the runner.
- **Evidence Bundle**: A directory (`evidence-bundle-<run-id>/`) containing `manifest.json`, `claims.json`, `artifacts/`, JUnit XML, and Allure JSON. Produced by every run.
- **Run Verdict**: One of `pass` / `fail` / `errored` / `partial` / `skipped`, with attached diagnostics and artifact paths.
- **Signal Set**: The three required signals (SoilHealthState delta, Crop phase delta, SMAPI log) plus optional visual evidence.

### Non-Functional Requirements

- **NFR-001**: The runner MUST be reproducible on any **Linux** host with `STARDEW_GAME_PATH` set and a licensed Steam account (Xvfb + software GL); it MUST NOT require changes to the mod's source code. Windows/macOS hosts use build + unit tests plus the manual fallback (FR-021).
- **NFR-002**: The runner MUST NOT distribute or embed proprietary game assemblies in the public repository; it MUST acquire them from a private repository via authenticated API (secret token). The runner relies on a pre-configured host with access to the private repo.
- **NFR-003**: The runner MUST produce a non-zero exit code on `fail`/`errored`/`partial` for CI integration.
- **NFR-004**: The runner MUST log each step with timestamps for debugging; on failure, it MUST attach all available artifacts.
