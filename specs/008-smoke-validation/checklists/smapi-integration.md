## 2. SMAPI Log File Detection

- [x] 2.1 Script reads log from `~/.config/StardewValley/ErrorLogs/SMAPI-latest.txt` (Linux convention) — upstream `Constants.LogDir` = `Path.Combine(Constants.DataPath, "ErrorLogs")` and `DataPath` = `ApplicationData` + `/StardewValley` (`Constants.cs:89`, `:92`), and `Constants.LogFilename` = `"SMAPI-latest"` with `LogExtension` = `"txt"` (`Constants.cs:145`, `:148`)
- [x] 2.2 Script checks for `SMAPI-crash.txt` first (presence indicates crash → immediate failure)
- [x] 2.3 If `SMAPI-crash.txt` is present, it overrides `SMAPI-latest.txt` as the failure source
- [x] 2.4 Script waits for the current run's `Log started at {UTC} UTC` sentinel before polling, and evaluates every signal only against log lines that follow it (SMAPI unlinks and recreates the log at launch, so the sentinel — not the file's existence — marks the run boundary; FR-002). The sentinel's exact form is `Log started at {DateTime.UtcNow:s} UTC` → `Log started at 2026-10-19T21:01:38 UTC` — it carries **no offset**, so the comparison against `T0` MUST treat it as UTC explicitly (append `Z` when parsing) rather than parsing it as local time. The sentinel is the **third** line of every log, after the version banner and the `Mods go here:` line, and it is a **TRACE**-level record with source `SMAPI` (`Monitor.Log` defaults to `LogLevel.Trace`), so a parser that reads only `INFO`-and-above records would never find the run boundary
- [x] 2.5 Log file path is configurable (not hardcoded) for non-standard installations
- [x] 2.6 Script handles the case where the log file never appears (timeout → failure) — and the case where the game exits with status `0` but produces no log (SMAPI's post-update dependency re-assertion, `Program.AssertDepsJson` → `Environment.Exit(0)` after printing "Please exit this window and re-launch SMAPI to play", `Program.cs:170-188`), which is also a failure (FR-002, exit `15`)
- [x] 2.7 Pre-launch cleanup removes a stale `SMAPI-latest.txt` and `SMAPI-crash.txt` from the SMAPI log directory **and both** of SMAPI's leftover **markers** — `StardewModdingAPI.crash.marker` **and** `StardewModdingAPI.update.marker` — from the **game** directory `<game-path>/smapi-internal/` (FR-002 "Pre-launch cleanup (MUST)"; FR-012 item 6). The **marker** is what gates SMAPI's `Console.ReadKey()` (`LogManager.HandleMarkerFiles()` tests for the marker's presence, `LogManager.cs:214`, and reads the key at `:219` **before** deleting the crash log and the marker at `:220-221`), so removing only the crash log leaves the marker in place and the launch still fails. The markers live beside the game's SMAPI assemblies, **not** in the log directory (`Constants.InternalFilesPath` = `<game-path>/smapi-internal`, `Constants.cs:37`; `Constants.cs:154`, `:157`) — the crash marker's read is unconditional, the update marker's is gated on `Constants.ApiVersion.IsPrerelease()` (`LogManager.cs:198`, `:207`). The pre-flight MUST also verify the SMAPI log directory is **writable** (FR-012 item 6)
- [x] 2.8 The log's inode is recorded before launch and verified to have changed once the log is recreated (belt-and-braces freshness assertion; FR-002 "Log freshness (MUST)"). The **order** is normative — the inode is recorded *before* the stale log is removed, or the baseline is "absent" and the assertion is vacuous. The check is what detects SMAPI's `SMAPI-latest.player-{n}.txt` fallback (`SCore.GetLogPath`, `SCore.cs:2538`, `:2550`), which happens when `PurgeNormalLogs` swallows the `IOException` from a log still in use

## 3. Log Format Parsing

- [x] 3.1 Log entries are parsed using the `[HH:mm:ss LEVEL SOURCE] message` format — the level token is **variable width**: SMAPI pads it with `PadRight(Monitor.MaxLevelLength)`, and `MaxLevelLength` = 5 (the longest **public** `LogLevel` name: `Trace`/`Debug`/`Error`/`Alert` = 5, `Monitor.cs:26`), so the six public levels render as `TRACE`, `DEBUG`, `INFO `, `WARN `, `ERROR`, `ALERT` — five characters each, `INFO`/`WARN` carrying a trailing pad space — while the internal `ConsoleLogLevel` enum also contains `Critical` and `Success`, and `PadRight(5)` is a **no-op** on them, so SMAPI core can render **`CRITICAL` (8 characters)** via `Monitor.LogFatal` and **shifts the source column by three**. The level MUST therefore be bound **by label, never by column** (FR-003 "The level token is variable width (MUST)"). A real mod-scoped line reads `[14:32:02 ERROR Stardew Valley - Living Roots] …` — the level lives **inside** the bracket group, so there is no `[ERROR]` token; the canonical upstream form is SMAPI's own `^\[(?<time>\d\d[:\.]\d\d[:\.]\d\d) (?<level>[a-z]+)(?: +screen_(?<screen>\d+))? +(?<modName>[^\]]+)\] ` (`src/SMAPI.Web/Framework/LogParsing/LogParser.cs:17`) — the level is matched as a **label**, the source is the remainder of the bracket group. The prefix is applied **once** to the whole message (`Monitor.LogImpl`: `fullMessage = $"{prefix} {message}"`, `Monitor.cs:159`), so the message's own leading whitespace sits **after** the prefix — the skipped-mods header appears on the wire as `[<ts> ERROR SMAPI]    Skipped mods`, and an anchor of the form `^   Skipped mods` matches **nothing**. Lines are CRLF-terminated (`LogFileManager.WriteLine`: `message + "\r\n"`) while newlines **inside** a message are bare LF, so the file is **mixed CRLF/LF**; before any matching the trailing `\r` MUST be stripped (`sed 's/\r$//'`), because GNU `grep` does not strip it and any pattern ending in `$` never matches a CRLF-terminated line
- [x] 3.2 Mod-specific entries are filtered by the manifest name `Stardew Valley - Living Roots` — the **source label**, i.e. the remainder of the bracket group (FR-003 "Source (MUST)"). SMAPI falls back to the mod's relative folder path when the manifest has no `Name`, and in split-screen mode a `screen_<n>` token precedes the source. Records whose source is `SMAPI` or `game` are **outside** the mod-scoped gate
- [x] 3.3 All 6 log levels are recognized: TRACE, DEBUG, INFO, WARN, ERROR, ALERT (the six **public** `LogLevel` names, `LogLevel.cs`; the internal `ConsoleLogLevel` also has `Critical` and `Success`, which are rendered but are neither of the two failure levels nor among the six public ones)
- [x] 3.4 Only ERROR and ALERT level entries are treated as failure markers — and the level is compared as a **label** taken from the bracket group, never as a literal `[ERROR]` substring and never as a fixed-width column slice (FR-003 "Failure markers (MUST)")
- [x] 3.5 WARN-level entries are logged but do NOT fail the smoke test
- [x] 3.6 TRACE-level entries are captured for diagnostics only and do NOT fail the test
- [x] 3.7 Parsing handles multi-line entries (stack traces following Error lines) — a record is one physical line with a prefix, optionally followed by **continuation lines that carry no prefix**; a continuation line inherits no level and no source and MUST NOT be treated as a new record (FR-003 "Continuation lines and line endings (MUST)"). SMAPI's own multi-line records include `Mod failed handling that command:\n{summary}` (`SCore.cs:694`)
- [x] 3.8 Parsing handles entries with special characters in messages (paths, exception names) — the gates read the level and source **labels** out of the bracket group and never match on the message text, so a path or an exception name in the message cannot disturb the parse

## 4b. Mod-Resolution Gate (authoritative success signal)

- [x] 4b.1 The script requires a `Loaded N mods:` block in the log — note that SMAPI writes `Loaded 0 mods.` (**period**, no colon) when zero mods load, because it composes the header as `"Loaded " + count + " mods" + (count > 0 ? ":" : ".")` (`LogManager.cs:303`), so the block must be matched as `Loaded [0-9]+ mods[.:]` rather than the colon form alone, or a "0 mods loaded" state is indistinguishable from "no block at all" (FR-003)
- [x] 4b.2 The mod's full manifest name (`Stardew Valley - Living Roots`) appears within one of that block's per-mod entry lines, matched as a **full-name substring** — SMAPI renders entries as `   <Name> <Version> by <Author>` with an optional ` | <Description>` suffix (`LogManager.cs:307-312`), and the name contains spaces, so a first-token comparison would silently fail
- [x] 4b.3 The mod does **not** appear in SMAPI's `Skipped mods` section; when it does, SMAPI's stated reason (e.g. "because it needs SMAPI 4.0.0 or later. Please update SMAPI to the latest version to use this mod.", `ModResolver.cs:139`) is surfaced in the failure report. The section header is the three-space literal `"   Skipped mods"` (`LogManager.cs:411`) and its entries the six-space literal `      - <Name> <Version> because <reason>` (`LogManager.cs:425`) — anchoring on the unpadded header would make this leg vacuously true and report a skipped mod as a pass (FR-003)
- [x] 4b.4 The log's `Mods go here: <path>` line confirms which mods directory SMAPI resolved — it is **tilde-anonymised** by SMAPI (`PathUtilities.AnonymizePathForDisplay` replaces `$HOME` with `~`, `LogManager.cs:244`), so the comparison is against the home-relative form, **and both sides MUST be `realpath`-canonicalised before the comparison**: SMAPI reports the *canonical* path while the script's default `--game-path` traverses the `~/.steam/steam` symlink (a real Steam install links `~/.steam/steam` → `~/.local/share/Steam`), so an un-canonicalised comparison silently never matches. Measured on the maintainer's machine, SMAPI logged `Mods go here: ~/.local/share/Steam/steamapps/common/Stardew Valley/Mods` while the script's default `--game-path` is `~/.steam/steam/steamapps/common/Stardew Valley` — the two strings differ, the two canonical paths do not. The line is **context only**: it precedes the run sentinel, so it is exempt from the "only after the sentinel" rule and never gates the verdict (FR-002 "Header region (MUST)")
- [x] 4b.5 The log's `SMAPI <version> with Stardew Valley <version> on <os>` banner reports the installed SMAPI version (`LogManager.cs:241`; measured: `SMAPI 4.5.2 with Stardew Valley 1.6.15 build 24356 on Unix 7.2.9.201`) — it too precedes the sentinel, so it is **context only** and never gates the verdict (FR-002 "Header region (MUST)")

## 5. Pass/Fail Logic (AND Conjunction)

- [x] 5.1 Pass requires ALL: the mod is listed in `Loaded N mods:`, is absent from `Skipped mods`, AND no Error/Alert entries from the mod exist (FR-006, verbatim)
- [x] 5.2 The mod absent from `Loaded N mods:` (or present in `Skipped mods`) → failure (detected load error or skip)
- [x] 5.3 Mod listed, not skipped, no Error/Alert entries → pass (clean load)
- [x] 5.4 Mod listed but Error/Alert entries also present → failure (errors override the load signal)
- [x] 5.5 No `Loaded N mods:` block at all → failure — but **not** a mod-load failure: a **missing** `Loaded` header indicates a foreign or truncated log and MUST be reported as `13`, whereas the `Loaded 0 mods.` form is a legitimate empty block and MUST be reported as a mod-load failure (`5`) (FR-003; FR-009)
- [x] 5.6 The AND conjunction eliminates false positives **only when each leg is evaluated against its own section** — an unscoped search for the manifest name across the whole log makes a *skipped* mod satisfy leg 1 (SMAPI's skip entry and the content-pack entry's ` | for <ModID>` suffix both contain the name), a demonstrated false pass (FR-003 "The manifest name MUST NOT be searched for across the whole log")
- [x] 5.7 Save check is deferred (FR-004) and does NOT gate success in current implementation
- [x] 5.8 Every **gating** signal is evaluated only against log lines after the current run's `Log started at` sentinel, so a stale log from an earlier successful run cannot produce a false pass (FR-002, SC-011). The header region — the version banner and the `Mods go here:` line — precedes the sentinel and is context only

## 6. SMAPI Mod Loading Lifecycle

- [x] 6.1 Script allows sufficient time for SMAPI to load all mods (polls, doesn't assume instant readiness) — FR-002 now defines a **two-phase wait**: the sentinel establishes readiness, and the script then continues polling **within the same deadline** (FR-009) for the mod-resolution header. This is necessary because the sentinel is written by `LogManager.LogIntro()` in the `SCore` **constructor**, while the block is written by `LogManager.LogModInfo()` from `LoadMods()`, which runs only from `InitializeBeforeFirstAssetLoaded()` — i.e. after the graphics device is created. Measured against the installed 4.5.2 apphost: the sentinel is the third line of the log ≈1 s after launch, and the block arrives ≈14 s later unloaded / 28–42 s later under host load
- [x] 6.2 Script detects when SMAPI has finished loading mods (the `Loaded N mods:` block appears) — FR-002's two-phase wait requires the script to keep polling for the mod-resolution header (`Loaded <N> mods:` or `Loaded 0 mods.`) within the same deadline, and FR-009 bounds that whole two-phase window. The upstream ordering is unambiguous — the sentinel is written in the `SCore` constructor (`SCore.cs:210`) and the block only from `InitializeBeforeFirstAssetLoaded()` (`SCore.cs:511`) — so evaluating the gate at the sentinel would have reported a missing header on every run. The header's *presence* is what distinguishes "SMAPI resolved the mods and ours was not among them" (`5`) from "SMAPI never got that far" (`4`)
- [x] 6.3 Script distinguishes between "mod failed to load" (Error entries) and "mod not found" (absent from the `Loaded N mods:` block) — the two are separate legs of the conjunction (FR-006)
- [x] 6.4 Script handles SMAPI's automatic error recovery (mod marked failed but game still launches) — **no special handling is required**: the AND-conjunction already fails the run on any mod-scoped ERROR/ALERT record, including a deferred-load failure (Clarifications, round 8)
- [x] 6.5 Script does not confuse SMAPI core messages with mod-specific messages — SMAPI core's "Oops! Steam achievements won't work because Steam isn't loaded." is an Error-level entry (`SGameLogger.cs:61`, `LogLevel.Error`) written by the **game** monitor, whose source label is `game` (`LogManager.cs:72`) — not the mod's name — so it is outside the mod-scoped gate
- [x] 6.6 Script distinguishes "mod skipped by SMAPI" from "mod crashed" via the `Skipped mods` section and its stated reason
- [x] 6.7 Script launches SMAPI's native apphost (`./StardewModdingAPI --no-terminal`) with the game directory as the working directory — a relocated launcher copy fails in one of **four** measured ways, all re-measured against the installed 4.5.2 apphost: **154** ("The application to execute does not exist" — no `.dll` beside the apphost), **131** ("You must install .NET to run this application" — no runtime), **135** ("Could not resolve CoreCLR path" — a partial runtime) and **134** (SIGABRT — the runtime is present but the game files are not, so SMAPI's `AssertGamePresent()` calls `PrintErrorAndExit()` → `PressAnyKeyToExit()` → `Console.ReadKey()`, which throws `InvalidOperationException` on the `/dev/null` stdin FR-005 mandates; the exception is caught by `Program.Main`, whose own `PressAnyKeyToExit` throws again and escapes as an unhandled exception → SIGABRT). FR-007's table maps `134`/`131`/`154` → `2` (SMAPI not functional) and `135` → `13`; the earlier claim that a relocated copy "does **not** abort with SIGABRT" and exits **137** was wrong — `137` was not reproducible. The rationale is corrected too: the apphost resolves its runtime relative to its **own path**, `Constants.GamePath` is the directory of `StardewModdingAPI.dll` (`Constants.cs:34`), and the log directory is `$XDG_CONFIG_HOME`/`~/.config` + `/StardewValley/ErrorLogs` — not relative to the game directory

## 7. Headless Game Testing via Xvfb

- [x] 7.1 Xvfb is started with `-displayfd`, so the **X server** allocates a free display and reports it back — the script neither chooses a display number nor manages `/tmp/.X{n}-lock` files (the server writes no lock under `-displayfd`). If Xvfb fails to start or reports no number, the run aborts with exit `10` (FR-012 item 5)
- [x] 7.2 `DISPLAY` environment variable is exported to the game process
- [x] 7.3 Xvfb readiness is confirmed before game launch (`xdpyinfo` exits `0` and its output contains the `GLX` and `RANDR` extensions — FR-012 item 4a)
- [x] 7.4 Software OpenGL rendering is genuinely usable — `xdpyinfo` reports the `GLX` and `RANDR` extensions, and `glxinfo -B` under `LIBGL_ALWAYS_SOFTWARE=1` exits successfully reporting a software renderer (`llvmpipe`/`softpipe`); the presence of `libGL.so` alone does NOT satisfy this check (FR-012 item 4). **The probe is layered and must assert the game-specific capability too**: the maintainer's actual failure is MonoGame's `PlatformNotSupportedException: MonoGame requires either ARB_framebuffer_object or EXT_framebuffer_object` (MonoGame 3.8.1, `GraphicsDevice.OpenGL.FramebufferHelper.cs:32-34`) — a context *was* created, it just lacked FBOs — and `glxinfo -B` prints **no extension list**, so it cannot detect that class. Full `glxinfo` (or `glxinfo -s`, which prints one extension per line) MUST additionally report `GL_ARB_framebuffer_object` or `GL_EXT_framebuffer_object`; MonoGame accepts GL ≥ 3.0 **or** either extension (`GraphicsCapabilities.OpenGL.cs:86-87`). Note also that `glxinfo` exits **255** on failure (not 1 — measured: `glxinfo -B` with no display exits `255`) and that `glxinfo -create` does not exist — it prints "Unknown option `-create'" to **stdout** (not stderr) and **exits 0**, i.e. it would always pass
- [x] 7.5 Game launch to log check completes within the configured timeout, and the measured figures are recorded — the spec commits only to the 120 s `--timeout` default measured **from the instant the game is launched** (FR-009), and the run log records the duration of every phase and the total wall time (FR-014). Measured against the installed 4.5.2 apphost: the sentinel lands ≈1 s after launch and the `Loaded N mods:` block ≈14 s later unloaded, 28–42 s later under host load (and later still when a leftover marker adds its ~20 s delay). The earlier "15-30 s" figure in this checklist was not conservative and appeared nowhere else in the artifacts
- [x] 7.6 Xvfb process is terminated during cleanup (same SIGTERM → SIGKILL pattern as game — FR-010 item 2)
- [x] 7.7 Only the **display socket** `/tmp/.X11-unix/X{n}` is removed during cleanup, and only for the display the script itself allocated — the `/tmp/.X{n}-lock` policy is **retired**: under `-displayfd` the server sets `nolock = TRUE` and `LockServer()` returns without writing a lock file, so the script MUST NOT create, probe or remove one (FR-010 item 3; FR-012 item 5)
- [x] 7.8 `SDL_VIDEODRIVER=x11` is exported (never `wayland`) — the game bundles `libSDL2-2.0.so.0` and Wayland cannot be used against an Xvfb display (FR-001, FR-015)
- [x] 7.9 `LIBGL_ALWAYS_SOFTWARE=1` and `GALLIUM_DRIVER=llvmpipe` are exported to force Mesa software rendering (FR-001, FR-015)
- [x] 7.10 No X11 lock file is probed, created or removed — the lock-liveness protocol (live-owner → exit `10`, dead-owner → reclaim) was **withdrawn in round 7/8**; exit `10` now means only "the virtual display could not be allocated or started" (FR-012 item 5; FR-010 item 3)

## 9. Mod-Specific Error Detection

- [x] 9.1 Script greps the log for the mod name `Stardew Valley - Living Roots` (case-sensitive exact match, per clarification) — but the search is **scoped per leg**: the name is looked up only inside the loaded-mods block for the "listed" leg and only inside the skipped-mods section for the "skipped" leg, never across the whole log (FR-003 "The manifest name MUST NOT be searched for across the whole log")
- [x] 9.2 Script searches for entries whose **level label** is `ERROR` or `ALERT` and whose **source label** is the mod — the log has **no `[ERROR]` token** (the level lives inside the bracket group, `[14:32:02 ERROR Stardew Valley - Living Roots]`), so a literal `grep -F '[ERROR]'` matches nothing, and because the level token is variable width (`CRITICAL` renders 8 characters wide) the level MUST be bound **by label, not by a fixed column**: the canonical upstream pattern is `^\[(?<time>\d\d[:\.]\d\d[:\.]\d\d) (?<level>[a-z]+)(?: +screen_(?<screen>\d+))? +(?<modName>[^\]]+)\] ` (`LogParser.cs:17`), from which the level and the source are extracted as labels
- [x] 9.3 Script checks for the mod being skipped or erroring — the real signals are SMAPI's `Skipped mods` section (`      - <Name> <Version> because <reason>`, `LogManager.cs:425`; e.g. "because it needs SMAPI 4.0.0 or later", `ModResolver.cs:139`) and mod-scoped Error entries (e.g. `Mod failed handling that command:`, `SCore.cs:694`; `Failed loading the per-mod API instance from …`, `ModRegistryHelper.cs:133`). SMAPI emits **no** literal `"failed to load"` string — the only occurrence of that phrase in the SMAPI sources is a code comment (`SCore.cs:2094`) — so that wording is corrected here and in the *Common Failure Modes* table below
- [x] 9.4 Script looks for exception stack traces mentioning mod types — the stack trace rides in the failure record's **continuation lines**, and the exception **type and HResult** come from the **mod's own** Trace records (e.g. `RegisterEvents exception type: System.InvalidOperationException (HResult: 0x80131509)`, `ModController.cs:378`), never from SMAPI (`ExceptionHelper.GetLogSummary` is `Exception.ToString()` and carries no HResult) (FR-003 "Trace diagnostics (MUST)")
- [x] 9.5 Failure reports include the relevant Trace lines following any Error entry — but **not** as a fixed `tail -N` window: a .NET stack trace is routinely 20–40 lines long, so a fixed window can consist entirely of stack frames while omitting the record that names the failure. FR-007 requires the matched record together with its continuation lines and every mod Trace record that follows it; the 30-record cap applies only to the "no record matched" fallback (FR-007 "Log context (MUST)")
- [x] 9.6 Script distinguishes mod errors from SMAPI core errors and other mods' errors — by the **source label** inside the bracket group; records whose source is `SMAPI` or `game` are outside the mod-scoped gate (FR-003 "Source (MUST)")

## 10. Crash Detection

- [x] 10.1 `SMAPI-crash.txt` existence is checked before parsing `SMAPI-latest.txt`
- [x] 10.2 If `SMAPI-crash.txt` is present, script parses it for exception details and stack trace — the crash log is a **copy of the log file** written at the moment of the crash (`LogManager.WriteCrashLog`, `LogManager.cs:168-179`), so it is parsed as the same normalised record stream and yields the same failure record plus its continuation lines
- [x] 10.3 Game crash during launch is detected via non-zero process exit code — every child status is translated into the FR-007 taxonomy before the script exits
- [x] 10.4 Crash time is compared with test run time to confirm relevance (N/A — the timestamp comparison is explicitly ruled out: spec.md:313 — "Should `SMAPI-crash.txt` timestamps be compared against the run window? → A: No. Stale-crash cleanup before launch (FR-012 item 6) already guarantees relevance; the timestamp comparison is N/A (smapi-integration 10.4)". - [x] 10.7 Removal of the stale crash **marker** (`<game-path>/smapi-internal/StardewModdingAPI.crash.marker`) prevents SMAPI's `Console.ReadKey()` in `LogManager.HandleMarkerFiles()` (`LogManager.cs:214-221`) from blocking the headless launch — the marker, not the crash log, gates the read. Measured, not inferred. The **update** marker must be removed too (FR-012 item 6)

## 11. Artifact Identity & Mods Path

- [x] 11.1 The script rebuilds the mod with `dotnet build --configuration Release --no-incremental` after removing the deploy target directory `<mods-path>/<ModFolderName>/`, and **pins the deploy target** with `-p:GameModsPath="<resolved mods path>"` so the build deploys into exactly the directory SMAPI loads from (FR-016 (b), (c)). The project is located via `--mod-project`, defaulting to `<repo-root>/LivingRoots/LivingRoots.csproj`, with `<repo-root>` derived from the script's own location (`SCRIPT_DIR/..`) (FR-016 (a))
- [x] 11.2 A build failure aborts the script with exit code `12` **before** the game is launched — a failed build that leaves the old DLL in place would otherwise produce a false pass (FR-016 (b))
- [x] 11.3 The deployed assembly's SHA-256 digest is compared with the freshly built assembly's (`<mod-project-dir>/bin/<EntryDll>` vs `<mods-path>/<ModFolderName>/<EntryDll>`); a mismatch, a missing file, or a file **strictly** older than the build aborts with exit `12` and names both digests (FR-016 (d), SC-012). The comparison is within the run only — cross-build digest equality is not asserted, because the compiler's content hash is a function of the absolute source path
- [x] 11.4 The manifest `Version` is **not** used as the freshness assertion — it is fixed at `0.0.1` and invariant across builds (`manifest.json`)
- [x] 11.5 The mods directory is resolved explicitly and passed to SMAPI via `--mods-path` / `SMAPI_MODS_PATH`, defaulting to `<game-path>/Mods` (FR-017). Upstream reads the argument first and consults the environment variable only when the argument is empty (`Program.cs:205-217`), and the default is `Constants.DefaultModsPath` = `Path.Combine(Constants.GamePath, "Mods")` (`Constants.cs:160`)
- [x] 11.6 The check that the resolved mods directory exists and contains the mod's `manifest.json` with a matching `UniqueID` runs **after** the build-and-verify step, not in the pre-flight — FR-016 removes and recreates the deploy target, so a check placed before the build would fail on a clean machine; a failure exits `16` (FR-017 "Verification of the mod folder (MUST)")
- [x] 11.7 A relative `--mods-path` is resolved against the game directory, matching SMAPI's own semantics (`Path.Combine(Constants.GamePath, rawModsPath)`, `Program.cs:226-228`); an absolute one is accepted as-is and is its own base (FR-012 item 7, FR-017)

## Common Failure Modes Detected

| Failure Mode | Detection Method | Log Indicator |
|--------------|------------------|---------------|
| Manifest validation error | Check the skipped-mods list | `      - <Name> <Version> because its <manifest error>` (`LogManager.cs:425`) — the mod is never loaded, so it emits no mod-scoped record of its own |
| Missing dependency | Check the skipped-mods list | `      - <Name> … because it requires mods which aren't installed (…)` (`ModResolver.cs:312`) — a skip, not a warning |
| Incompatible version | Version check | `because it needs SMAPI <ver> or later` (`ModResolver.cs:139`) or `because it needs Stardew Valley <ver> or later` (`ModResolver.cs:146`) |
| Assembly loading error | Load status | Mod-scoped Error entry, e.g. `Failed loading the per-mod API instance from …` (`ModRegistryHelper.cs:133`) |
| Mod crash during entry | Exception trace | Exception summary in the mod-scoped Error record, plus its continuation lines |
| Game version mismatch | Version check | SMAPI's own `AssertGameVersion` — a hard exit, not a warning (`Program.cs:128-149`) |
| SMAPI version mismatch | Version check | SMAPI's own `AssertSmapiVersions` — a hard exit, not a warning (`Program.cs:153-166`) |
| Corrupted save data | Save load errors | Save-related error messages (deferred — no save is loaded) |
| Mod skipped by SMAPI | `Skipped mods` section | "because it needs SMAPI X or later" |
| Stale deployed artifact | SHA-256 digest comparison (pre-launch) | n/a — detected before the game starts |
| Stale log from a previous run | `Log started at {UTC} UTC` sentinel | sentinel timestamp older than the launch time |
| Graphics device failure | `glxinfo` pre-flight probe **and** the log | n/a — the pre-flight catches it, but the classification MUST also come from the log and the observed exit status, never from the absence of the `Loaded N mods:` block alone (a graphics failure happens before mod resolution, so block-absence alone would yield a timeout `4`) |
| Clean exit with no log | process exited, no log produced | n/a — treated as failure (exit `15`) |

## Round-8 Verification Note

Every SMAPI-format claim in this checklist was re-verified against the upstream **4.5.2** sources (`/tmp/opencode/smapi-src/`, byte-identical to the `4.5.2` tag — the locally extracted `LogManager.cs` matches `src/SMAPI/Framework/Logging/LogManager.cs` by MD5) and, where it was cheap, against the **installed 4.5.2+821167e5…** build on the maintainer's machine.

**Measured on the installed build** (all runs with stdin redirected from `/dev/null`):

| Scenario | Result |
|----------|--------|
| Relocated apphost, no `StardewModdingAPI.dll` beside it | exit **154** — "The application to execute does not exist" |
| Relocated apphost, no runtime | exit **131** — "You must install .NET to run this application" |
| Relocated apphost, partial runtime | exit **135** — "Could not resolve CoreCLR path" |
| Relocated apphost, runtime present but game files absent | exit **134** — SIGABRT: `AssertGamePresent` → `PrintErrorAndExit` → `Console.ReadKey()` throws `InvalidOperationException`, is caught by `Program.Main`, whose own `PressAnyKeyToExit` throws again and escapes as an unhandled exception |
| Leftover `smapi-internal/StardewModdingAPI.crash.marker` present | exit **1**, silently: the `ReadKey()` exception propagates out of `RunInteractively()`, `SCore.Dispose()` runs `Dispose(isError: true)` → `Environment.Exit(1)` (`SCore.cs:346-349`, `:397`), so the process never reaches `Program.Main`'s catch. The log holds the sentinel, the three crash-marker lines and `Disposing...`, **no `Loaded N mods:` block**, and **the marker survives** |

**Log shape confirmed from a real run** (banner → `Mods go here:` → sentinel, all before mod resolution): `[23:20:59 INFO  SMAPI] …` — level padded to 5 with a trailing pad space on `INFO`/`WARN`, CRLF-terminated (`\r\n`), the sentinel at `[23:20:59 TRACE SMAPI] Log started at 2026-10-20T03:20:59 UTC` (TRACE level, source `SMAPI`, no UTC offset), and `Mods go here: ~/.local/share/Steam/steamapps/common/Stardew Valley/Mods` — the **canonical** path, `~`-anonymised, while the script's default `--game-path` is the `~/.steam/steam` symlink.

**New findings that are not covered by D2–D4** (raised for the maintainer, not resolved here):

1. **FR-002's readiness/verdict sequencing is not implementable as written.** The sentinel is written by `LogManager.LogIntro` in the `SCore` **constructor**; the `Loaded N mods:` block is written by `LogManager.LogModInfo` from `LoadMods`, reached only from `InitializeBeforeFirstAssetLoaded` — i.e. after the graphics device is created. FR-002 says "readiness is the sentinel alone" and the verdict is "evaluated immediately after the sentinel", and FR-009 bounds the wait to the sentinel only, so a conforming script would evaluate the gate **before** the block exists and always report a missing `Loaded` header (`13`). FR-003's own distinction between `Loaded 0 mods.` (`5`) and a missing header (`13`) only makes sense if the script waits for the mod-resolution output. Items 6.1 and 6.2 are left `[ ]` until the two clauses are reconciled (the natural fix: keep the sentinel as readiness, then wait for the `Loaded N mods:`/`Loaded 0 mods.` block — or the process's exit — inside the **same** deadline).
2. **Citation drift:** the skipped-mods **entry** literal is at `LogManager.cs:425` (and `:433` for the duplicate-mod variant), not `:428` as FR-003 and the round-8 clarification state. The header at `:411` and the `Loaded N mods:` composition at `:303` are correct.
3. **`research.md:48` carries a malformed "canonical anchored form"** — `^\[\d\d[:.]\d\d[:.]\d\d\] (?<level>[A-Z]+)…` places the level **outside** the bracket group, which no SMAPI log line has. The correct upstream form is `LogParser.cs:17` (level inside the bracket group, matched by label). `research.md` is non-normative, but the regex is quoted in FR-003-style discussions and should be corrected.
4. **`FR-012` item 6's "status `134`" for an unwritable log directory is unverified and probably wrong.** The same code path that produces the marker abort's `1` (an exception out of the `SCore` constructor) reaches `Program.Main`'s catch, where the second `Console.ReadKey()` throws and escapes as an unhandled exception — measured as **134** for the `AssertGamePresent` path, but the log-directory failure happens *after* `AssertGamePresent`, so the two paths differ; the status should be measured, not assumed.
