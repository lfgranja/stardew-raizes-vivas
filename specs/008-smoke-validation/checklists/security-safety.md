## 1. Path Traversal Prevention

- [x] 1.1 All filesystem paths constructed from external input are canonicalized with `realpath()` before use — FR-012 item 7 is now the normative hook ("**every path the script constructs is validated**: it MUST be canonicalized with `realpath` and MUST satisfy a **component-boundary** prefix test against the intended base"), reinforced by `plan.md`'s Constitution Compliance (Security-First: "The script handles filesystem paths … and must sanitize/validate all paths"). (Round-8 correction: the clause is no longer "not yet an FR" — FR-012 item 7 states it normatively.)
- [x] 1.2 Canonicalized paths are verified to start with the expected base directory prefix — the check applies **only to paths the script constructs**; the user-supplied roots (`--game-path`, `--mods-path`, `--smapi-log`) are their own bases and are resolved with `realpath -e` for existence but are **not** prefix-checked against the game directory, because an absolute `--mods-path` outside the game directory is legal (FR-012 item 7, FR-017). The prefix test is a **component-boundary** test (`case "$real" in "$base"/*)`), and the base is the canonicalized root — FR-012 item 7 resolves the user-supplied roots with `realpath -e`, and `realpath` output is canonical and carries no trailing slash, so the test matches only a genuine child of the base. (Residual, flagged in the round-8 note: the spec never states "the base MUST be canonical and slash-free" in so many words, and FR-016 (a)'s repository-root base and the XDG state base are not explicitly canonicalized — measured: a base with a trailing slash makes `case "$real" in "$base"/*)` never match.)
- [x] 1.3 Paths containing `../` sequences are handled by canonicalization: `realpath` resolves them away, so the residual check is a **component-boundary prefix test** (`case "$real" in "$base"/*)`), never a reject-on-`..` test — after canonicalization the string *cannot* contain `..`, so such a rule is dead code (FR-012 item 7). The percent-encoded variant is **not applicable**: the CLI surface is `--game-path`, `--mods-path`, `--smapi-log`, `--mod-project`, `--timeout`, `--grace-period`, `--build-timeout`, `--force` (plus `--help`/`--version`) — no URL or percent-decoding exists anywhere in the design (the round-7 decision withdrew the percent-decoding clause; `research-bash-security.md` §1.3 carries the supersession banner)
- [x] 1.4 Paths containing NUL bytes (`\0`, `%00`) are rejected — vacuously but unambiguously: bash's command substitution **drops** NUL bytes (measured on this host: `bash: command substitution: ignored null byte in input`), so a NUL cannot be carried into a path variable from any external source, and the CLI has no percent-decoding, so `%00` is a literal three-character string rather than an encoded NUL
- [ ] 1.5 Unicode-normalize all path components (NFC or NFKC) before comparison to prevent homoglyph bypasses — **the rule was withdrawn in round 7 and is now explicitly contradicted by the spec**: FR-012 item 7 states "**No Unicode normalization is performed and no normalizer dependency is required**" (NFC is a provable no-op for ASCII paths — UAX #15 — and is not a homoglyph defence, UTS #39), and the replacement control is the ASCII path allowlist `[A-Za-z0-9._/-]+`, whose scope is the open decision D1 (as written, the allowlist rejects the script's own default `--game-path`, `…/Stardew Valley/`). Left unchecked until D1 settles the replacement control. (The previous justification — "NFC via python3/uconv, required pre-flight dep — FR-012 item 7; fail closed if absent" — cited a clause that no longer exists: FR-012 item 8's required-tool set contains no normalizer.)
- [x] 1.6 Absolute paths are accepted, not rejected — every real input in this design is absolute by default (`--game-path` → `~/.steam/.../Stardew Valley/`, `--smapi-log` → `~/.config/.../SMAPI-latest.txt`) and FR-017 permits an absolute `--mods-path` (the quickstart's documented invocation is absolute — `--mods-path /path/to/mods` — and TC-14 exercises a non-default `--mods-path`). The rule that *is* normative is FR-017's: a **relative** `--mods-path` is resolved against the game directory. (Round-7 decision: the blanket rejection is withdrawn.)
- [x] 1.7 Symlink-safe file creation is provided by `mktemp` itself — measured on this host: `mktemp` creates the file with mode `0600` and the directory with `0700` **even under `umask 022`** (it sets the mode explicitly) and never reuses an existing name, so the `O_CREAT|O_EXCL` guarantee holds; the script opens the lock file `O_RDWR|O_CREAT` **without** `O_TRUNC` (FR-002 "Lock file (MUST)": `exec 9<>"$lockfile"`), so a planted symlink cannot destroy its target — measured: `exec 9<>` on a symlink left the target's size at 7 bytes, while the forbidden `exec 9>` truncated it to 0. No `O_NOFOLLOW` helper is required: bash exposes no `O_NOFOLLOW`, and the round-7 security posture places the script's files in private `0700` directories where there is no adversary (FR-002 "Lock file (MUST)", FR-014 "Run log permissions (MUST)"). (Residual, flagged in the round-8 note: FR-002's mode enforcement is the path-based `chmod 0600 "$lockfile"`, which follows a symlink — measured: the target's mode changed from `0644` to `0600` — so it can act on an inode other than the one `flock` holds; the spec does not pin the descriptor form `chmod 0600 /proc/self/fd/9`.)
- [x] 1.8 Game save directory paths are validated to resolve to the expected Stardew Valley save location (N/A — the save check is deferred (FR-004): the script never loads a save, so it never constructs a save path; `research-bash-security.md` §1.8 records the rule for the future implementation)
- [x] 1.9 Path sanitization failures are logged (without exposing the raw malicious input) for audit purposes — a failed validation is a run failure, so it is reported through FR-007's "What → Where → How to fix" pattern and captured in the run log (FR-014 "Run log (MUST)": the log MUST contain every line the script emits at any level); `plan.md`'s Constitution Compliance requires that error messages "must not leak sensitive system details", and `research-bash-security.md` §1.3 requires the failure to be logged generically, without echoing the raw payload
- [x] 1.10 The sanitization rigor of `ModDataService.SanitizePathSegments()` is **not** ported into the script — the save check is deferred (FR-004), so there is no save-id consumer and the port would be dead code, contradicting `plan.md`'s YAGNI constraint; `plan.md`'s Security-First paragraph and the supersession banner in `research-bash-security.md` both record the decision explicitly. Path validation is instead specified directly in FR-012 item 7 (canonicalise → component-boundary prefix test → ASCII allowlist). (The allowlist's *scope* is the open decision D1; the rule itself is stated as written in the spec.)

## 2. Process Management Security

- [x] 2.1 Process detection identifies the game by executable path, never by `ps | grep` piping (resolved by decision — a candidate PID qualifies only when `/proc/$PID/exe` resolves under the resolved game directory (`StardewModdingAPI` or `StardewValley`). `pgrep -x` MUST NOT be used for the apphost: the kernel's process name is truncated to 15 characters and `StardewModdingAPI` is 17, so an exact-name match can never succeed — re-measured on this host with procps-ng 4.0.6: `pgrep -x StardewModdingAPI` refuses the pattern outright ("pattern that searches for process name longer than 15 characters will result in zero matches") and exits `1`. `pidof` matches on the untruncated name and on `/proc/$PID/exe` and is the acceptable alternative (`/usr/bin/pidof` is present on this host) — FR-011, round-6 clarification)
- [x] 2.2 When killing by pattern, the most specific identifier possible is used (resolved by decision — identification is by `/proc/$PID/exe` restricted to the resolved game path, not by a command-line pattern, and the comparison MUST use the **canonicalized** game directory on **both** sides (FR-011: bash's `$PWD` is logical while `/proc` is physical, and `~/.steam/steam` is a symlink, so an un-canonicalised comparison silently never matches). `pgrep -f` over-matches deterministically: it was observed matching the invoking shell whose command line merely contained the target name — FR-011)
- [x] 2.3 After spawning the game, the actual PID is captured from `$!` and stored (FR-005: "`$!` is simultaneously the child's PID and its process-group ID"; `data-model.md` → Process State carries `game_pid` and `game_pgid`)
- [x] 2.4 Before sending any signal to a PID, process identity is verified via `/proc/$PID/exe` (resolved by decision — the rule now has FR backing and an explicit scope. Any PID **discovered by scanning the process table** MUST be verified before it is signalled; the script's own spawned PID needs no check, because an unreaped child stays a zombie and the kernel does not recycle a zombie PID (documented in `pidfd_open(2)` NOTES; GNU `timeout` relies on the same invariant). `/proc/$PID/comm` is no longer offered as an alternative — it is a 15-character truncated, process-writable name, not an identity token. The round-8 corollary is FR-012 item 10: an orphaned Xvfb is **detected and reported, never signalled**, because no foreign X server can satisfy this identity rule — FR-011, FR-012 item 10)
- [x] 2.5 SIGTERM → grace period (15-30s) → SIGKILL escalation is implemented with configurable timeout — the grace period is `--grace-period`, default **15 s** (FR-005); the "15-30s" range is a description of that default plus headroom, not a second fixed value
- [x] 2.6 SIGTERM/SIGINT traps forward the signal to child processes before exiting (FR-005 "Trap design (MUST)": the `INT`, `TERM` and `HUP` handlers MUST forward the signal to the child process groups and then **reset their own trap and re-raise** it (`trap - SIG; kill -SIG $$`), so the script dies *from* the signal and the caller observes `128+N` as a genuine signal death; `trap '' INT TERM` is prohibited because it makes the script un-killable and is inherited by later children)
- [x] 2.7 Process exit is verified using `kill -0 "$PID"` or `wait` after SIGKILL (FR-005 pins the primitive for the launch wait — both children MUST be waited on with `wait -f` — and the SIGKILL escalation is conditional: it is sent only "if the process is unresponsive"; the observed exit is logged (FR-014))
- [x] 2.8 The entire process group is killed, not just the parent PID (prevents orphaned children) (FR-010 items 1 and 2: the **game** and the **Xvfb** groups are both signalled by group, because both children are launched under `set -m` and therefore each has a process group whose ID equals its PID (FR-005); the same mandatory assertion — the group ID must differ from the script's own group ID and from `1` — precedes each group signal, and a failed assertion aborts with `13` rather than falling back to a single-PID signal)
- [x] 2.9 All process lifecycle events (spawn, signal, exit) are logged with timestamps (FR-014: spawn (game, Xvfb), every signal sent "including the PID and the signal", the grace period, the escalation to SIGKILL, and the observed exit, so that a failed run can be reconstructed from the run log alone)
- [x] 2.10 `kill -9` is never used as the first signal — graceful SIGTERM is always attempted first (FR-005 and FR-010 items 1–2 for the two children the script starts; FR-011 for the `--force` kill of a pre-existing instance, which is also SIGTERM → grace period → SIGKILL)

## 3. File Lock Security

- [x] 3.1 `flock` (kernel advisory lock) is used rather than PID files — eliminates stale lock problem (FR-002 "Lock file (MUST)"; `research.md` §4.1 lists "PID file + liveness check" as a rejected alternative — the kernel releases the lock on process death, even after SIGKILL)
- [x] 3.2 `flock -n` (non-blocking) is used to fail fast if another instance holds the lock (FR-002: "The lock MUST be acquired with `flock -n 9`"; contention is exit `6`, matched by SC-008 and TC-5)
- [x] 3.3 Lock file is stored in a directory with restrictive permissions (`chmod 0700`) at a **stable, per-user** path — `${XDG_RUNTIME_DIR}/livingroots-smoke.lock`, falling back to `${XDG_STATE_HOME:-$HOME/.local/state}/livingroots-smoke/` — and is **not** inside a per-run `mktemp -d` directory: a unique directory per run means two concurrent instances lock different inodes and mutual exclusion is zero, which would make SC-008, TC-5 and exit `6` unreachable. FR-002 "Lock file (MUST)" pins the path and the `0700` directory; "Lock file permissions (MUST)" additionally pins the lock file's own mode (`0600`, enforced with an explicit `chmod`, not by the umask alone)
- [x] 3.4 Lock file is opened with a dedicated file descriptor (`exec 9<>"$lockfile"`) held for script lifetime — read-write, create-if-absent; the `>` form is forbidden because it truncates and follows symlinks (measured on this host: `exec 9<>` on a symlink left the target's size at 7 bytes, `exec 9>` truncated it to 0). FR-002 "Lock file (MUST)"
- [x] 3.5 If PID files are used, stale lock detection verifies PID is alive AND `/proc/$PID/exe` matches expected binary (N/A — the script uses no PID file: mutual exclusion is `flock` on a dedicated lock file, auto-released by the kernel on process death (FR-002 "Lock file (MUST)"; FR-010 item 5; `research.md` §4.1 lists "PID file + liveness check" as a rejected alternative). The only PID-bearing file that ever existed in the design — Xorg's `/tmp/.X{n}-lock` — **no longer exists under `-displayfd`** (the server sets `nolock = TRUE`, so `LockServer()` writes no lock), and FR-012 item 5 forbids the script from probing, creating or removing it; FR-012 item 10 requires orphaned displays to be *detected and reported, never signalled*, so PID-reuse identity verification is inapplicable.)
- [x] 3.6 If PID files are used, they are created with `O_CREAT|O_EXCL` (or `set -o noclobber`) to prevent symlink following (N/A — no PID file is created: the only mutual-exclusion lock is `flock` on a dedicated lock file (FR-002; `research.md` §4.1), and the X11 lock file is out of scope entirely (FR-012 item 5, FR-010 item 3). Symlink-safe creation of the script's *own* files is `mktemp`'s `O_CREAT|O_EXCL` guarantee (FR-012 item 8 lists `mktemp` as a required tool; FR-010 item 4 removes the temp tree) and checklist 8.1 — note that the lock file is deliberately opened **without** `O_EXCL` (`exec 9<>`), so the next run can re-open the same inode.)
- [x] 3.7 Lock is tested under SIGKILL crash scenarios (kernel releases on process death) — the property the item asserts is guaranteed by `flock(2)` and is stated normatively: FR-010 item 5 ("the flock is auto-released by the kernel on process death"), FR-002, and `quickstart.md` R-4 ("the kernel releases the `flock` on process death, even after SIGKILL"). (Coverage note: no TC currently kills the *script* with SIGKILL — the property is asserted by kernel semantics rather than exercised by a test case.)
- [x] 3.8 `rm` of lock files after `flock` is avoided — kernel releases lock on process exit; removal creates race window (FR-002: "The lock file MUST **not** be removed at exit: … removing the file detaches the name from the locked inode and re-opens the race window that a second instance would exploit"; FR-010 item 5 repeats the rule; the Scope's declared side effects list the lock file as one that is "**left in place** afterwards")

## 4. Temporary File Security

- [x] 4.1 `mktemp` (or `mktemp -d` for directories) is used for all temporary files — never hardcoded paths (FR-012 item 8 lists `mktemp` in the required host-tool set; FR-010 item 4 requires the temp files/directories to be removed on exit; the Scope declares the `0700` temporary directory under `$TMPDIR` as a side effect)
- [x] 4.2 `mktemp` uses a template with identifiable prefix: `mktemp "${TMPDIR:-/tmp}/livingroots-smoke.XXXXXX"` (the exact template is not pinned in the spec — FR-012 item 8 only requires `mktemp` to be present and FR-010 item 4 requires the temporary resources to be removed — but the *prefix* and the location are anchored: the Scope declares "a `0700` temporary directory under `$TMPDIR`", and `quickstart.md` R-6 looks for the leftovers with `ls -d /tmp/livingroots-smoke.*`, i.e. the `livingroots-smoke.` prefix. Residual noted in the round-8 note: R-6 hard-codes `/tmp` while the spec says `$TMPDIR`.)
- [x] 4.3 Temp file/directory creation success is verified by **`mktemp`'s exit status**, not by testing the resulting path: `tmpfile=$(mktemp …) || { log_error "temp file creation failed"; exit 13; }` — `mktemp` already creates atomically with `O_CREAT|O_EXCL` and mode `0600`/`0700` (measured: `0600`/`0700` even under `umask 022`), so a `[[ -f "$tmpfile" ]]` test adds nothing (and is false for a `mktemp -d` directory). The old `|| exit 1` also collided with FR-007, where `1` means "game installation not found"; a temp-creation failure is an internal script error → `13`, which is FR-007's translation of any unmapped non-zero child status (`13` = "internal script error")
- [x] 4.4 `umask 077` is set at script start to ensure all created files are owner-only by default (FR-014 "Umask (MUST)": "The script MUST set `umask 077` before it creates any file or directory", and the umask is inherited by every child process). FR-014 is explicit that the umask is a **default, not a guarantee** — it does not change the mode of an already-existing file — so every artifact is additionally chmod-enforced (FR-002 "Lock file permissions (MUST)", FR-014 "Run log permissions (MUST)"). Measured: under `umask 022` a shell redirection creates `0644` and a directory `0755`; under `umask 077`, `0600`/`0700`.
- [x] 4.5 `trap cleanup EXIT` is defined BEFORE creating any temp files (the `EXIT` trap is the single cleanup path, registered exactly once in the top-level shell (FR-005 "Trap design (MUST)"), and FR-010 item 4 makes the temp tree its responsibility; registering the trap before the first `mktemp` is the only ordering consistent with both — the spec does not fix the ordering in so many words)
- [x] 4.6 Cleanup trap includes SIGTERM and SIGINT: the `EXIT` trap is registered **exactly once** in the top-level shell and is the single cleanup path; the INT/TERM/HUP handlers forward the signal to the child process groups and then **reset their own trap and re-raise** (`trap - SIG; kill -SIG $$`) so the script dies *from* the signal. A combined `trap 'rm -rf "$tmpdir"' EXIT INT TERM` is **forbidden**: its INT/TERM branch would swallow the signal, skip the forwarding, and exit `0` instead of `143`. FR-005 "Trap design (MUST)" — which also requires the cleanup to be idempotent (guarded by an `in_cleanup` flag) and time-bounded, and forbids `trap '' INT TERM`
- [x] 4.7 Temp files containing sensitive data are in `mktemp -d` directories with `chmod 0700` (the Scope declares "a `0700` temporary directory under `$TMPDIR`"; the only artefact the script writes that could carry sensitive content — the run log — is kept **outside** the temp tree, at `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/<run-id>.log`, in a `0700` directory with a `0600` file (FR-014 "Run log permissions (MUST)"))
- [x] 4.8 Fixed filenames in `/tmp` are never used for temporary files (vulnerable to symlink attacks) — the **lock file is the single documented exception**, and it is not in `/tmp` at all: FR-002 places it at `${XDG_RUNTIME_DIR}/livingroots-smoke.lock` or `${XDG_STATE_HOME:-$HOME/.local/state}/livingroots-smoke/livingroots-smoke.lock`. It must live at a stable, predictable path for mutual exclusion to work at all, and it is protected by living in a `0700` per-user directory (measured on this host: `/run/user/1000` is `0700`, `~/.local/state` is `0700`) and by being opened `O_RDWR|O_CREAT` **without** `O_TRUNC` (so a planted symlink cannot destroy its target). The one other `/tmp` artefact is the X11 socket `/tmp/.X11-unix/X{n}`, which the **X server** creates, not the script, and which the script removes only for the display it allocated (FR-010 item 3).
- [x] 4.9 Temp file paths passed between processes are validated to be within the expected temp directory — **N/A, vacuous by design**: no design element hands a temp path to another process (the only cross-process handoffs are the X11 socket and the SMAPI log path). It becomes live only if the deferred save check or a helper process is added.

## 5. Injection Prevention

- [x] 5.1 `set -euo pipefail` is at the top of the script (FR-014 "Shell options (MUST)": "The script MUST run under `set -Eeuo pipefail`" — the `-E` is load-bearing, because without `errtrace` the `ERR` trap is not inherited by shell functions and could not report the enclosing function name that FR-014 requires; `-e` supplies the automatic exit the trap's `13` contract relies on, `-u` forbids unset-variable reads, `-o pipefail` forbids a pipeline from reporting only its last element's status, and job control (`set -m`) is enabled separately and only around the launches (FR-005))
- [x] 5.2 Every variable expansion is quoted: `"$var"` — never bare `$var` or `${var}` in command position (no artifact permits an unquoted expansion, and every form the spec mandates is quoted: `case "$real" in "$base"/*)` (FR-012 item 7), `rm -rf -- "$target"` (FR-016 (b)), `exec 9<>"$lockfile"` (FR-002), `-p:GameModsPath="<resolved>"` (FR-016 (c)). The spec's own `kill -- -$!` is an argument, not a command position, and is safe because `$!` is a PID)
- [x] 5.3 `--` is used before any variable representing a filename or path: `rm -- "$file"`, `cd -- "$dir"` (FR-016 (b) pins the exact form `rm -rf -- "$target"` — with no trailing slash, because a trailing slash makes `rm` follow a symlinked final component and delete the target's contents; measured on this host: `rm -rf -- link/` deleted the symlink's target directory and its contents, while `rm -rf -- link` removed only the link)
- [ ] 5.4 External input is validated against an allowlist — **the allowlist's scope is the open decision D1**: FR-012 item 7 states "Path components MUST match the allowlist `[A-Za-z0-9._/-]+`", but that rule is unscoped: it rejects the script's own default `--game-path` (`…/Stardew Valley/`) and `Stardew Valley.dll` (~86 % of Steam titles contain a space), and it permits `..`, so it is a quoting proxy rather than a security control. The spec also pins no **test form** for it (measured: a positive `case` character class matches **every** path, so the allowlist only bites in its negated form `*[!A-Za-z0-9._/-]*`), and the numeric validation of `--timeout` / `--grace-period` that the previous justification asserted has no normative clause (FR-007's `14` = "malformed value" is the only hook). The save-directory-name allowlist remains withdrawn (FR-004 defers the save check). Left unchecked until D1 is decided.
- [x] 5.5 `eval` is never used with any input originating from outside the script (no artifact mentions `eval`; the design reaches child processes through arrays and environment variables (FR-001), and `research-bash-security.md` records the same posture)
- [ ] 5.6 Shell metacharacters are **not** rejected in user-supplied input — the round-7 decision withdrew a blanket metacharacter rejection, but FR-012 item 7's ASCII allowlist (`[A-Za-z0-9._/-]+`) **does** reject `&`, `(` and `)` in path components, so the two rules are in direct conflict: the maintainer's own `--game-path` may legitimately contain them and the allowlist would refuse it. The structural protections the item relies on are real (every expansion is quoted (5.2) and `--` precedes every path (5.3), so no value is ever re-parsed by a shell), but the normative text contradicts the item as written. Left unchecked until D1 settles the allowlist's scope.
- [x] 5.7 Command strings are not constructed by concatenation — use arrays (`cmd=(binary "${args[@]}")`) (no artifact builds a command string: the game is launched as `./StardewModdingAPI --no-terminal` (FR-001), the build is invoked with a quoted `-p:GameModsPath="<resolved>"` property (FR-016 (c)), and the log is read with `sed`/`awk`/`grep` over the normalised record stream (FR-003))
- [x] 5.8 `printf '%q'` is **not** used — the design invokes no shell-invoking command (no `bash -c`, no `sh -c`, no `eval`, no `xargs -0 sh`); values reach child processes through arrays (5.7) and environment variables (FR-001). The idiom has no call site, so requiring it would be dead code (round-7 decision).
- [x] 5.9 Game-generated data passed to other commands is validated for shell metacharacters (satisfied **structurally** rather than by a metacharacter filter: game-generated text — the SMAPI log — is only *matched* (FR-003's normalised record stream) and *printed* (FR-007's context, FR-014's run log); it is never expanded into a command position, so a metacharacter in the log can never be re-parsed by a shell)

## 6. Data Integrity During Termination

- [x] 6.1 SIGTERM (15) is always sent first — never SIGKILL (9) as the initial signal (FR-005: SIGTERM to the entire group first, SIGKILL only "if the process is unresponsive"; FR-010 items 1–2 for both children; FR-011 for the `--force` kill of a pre-existing instance)
- [x] 6.2 A grace period (15-30 seconds) is implemented after SIGTERM before escalating to SIGKILL (the grace period is `--grace-period`, default **15 s** (FR-005); the "15-30s" range is that default plus headroom, not a second fixed value, and the round-7 decision dropped the `timeout --kill-after=30` form — the escalation window is the grace period)
- [x] 6.3 After SIGTERM, process exit is polled using `kill -0 "$PID"` in a loop with sleep intervals (the grace period and the escalation rule are FR-005's — SIGKILL is sent only "if the process is unresponsive" — and the children MUST be waited on with `wait -f`; the spec does not fix the observation primitive used *during* the grace window, so either a `kill -0` poll or a bounded wait satisfies it)
- [x] 6.4 Process exit is verified (not just that the signal was sent) (FR-005: the children are waited on with `wait -f` and the SIGKILL escalation is conditional on the process still being unresponsive; FR-010 items 1–2 make the escalation mandatory rather than best-effort)
- [x] 6.5 After process exit, expected output files (SMAPI log) are verified to exist and have non-zero size — the log is removed pre-launch and recreated by SMAPI, so existence is checked against the current run's file, not a leftover; the sentinel requirement (a file that contains the `Log started at` line is non-empty) implies both existence and non-emptiness. The **normative** freshness criterion remains FR-002's: the stale log MUST be removed and its absence asserted immediately afterwards, the inode MUST be recorded *before* the removal and verified changed afterwards, and every gating signal MUST be evaluated only after the `Log started at {UTC} UTC` sentinel; size/non-emptiness is a secondary sanity check that may only be applied *after* the sentinel is seen
- [x] 6.6 A timeout prevents the script from hanging indefinitely if the game becomes unresponsive (FR-009: a 120-second default `--timeout` bounding the launch-to-sentinel window, enforced by a deadline poll loop that exits `4`; FR-016 (b) adds an independent `--build-timeout` (default 300 s) for the rebuild phase, so no phase can hang the run forever)
- [x] 6.7 SIGKILL usage is logged (indicates graceful shutdown failed — potential data corruption risk) (FR-014 requires "every signal sent (including the PID and the signal), the grace period, the escalation to SIGKILL, and the observed exit" to be recorded, so a failed graceful shutdown is visible from the run log alone)
- [ ] 6.8 `timeout --signal=TERM --kill-after=30s` is used as a safety net for unresponsive processes — **the form was dropped in round 7 and the spec forbids this use**: FR-009 says the `timeout` utility "MAY be used to bound the poll as a belt-and-braces wrapper, but it MUST **not** wrap the game launch", and the round-7 clarification states "The `--kill-after=30` form is dropped: the escalation window is `--grace-period` (15 s)". FR-005/FR-010 own the escalation (SIGTERM → grace period → SIGKILL on the process group); `timeout` is used, if at all, only to bound the log poll and the build (FR-016 (b)).
- [x] 6.9 Mod-specific save triggers that must be invoked before termination are documented (FR-005 documents that the mod emits no observable marker on `Saved` — "making it impossible to detect externally" — and that the script therefore does not wait for that event; the termination point is the title screen, where no save is loaded (FR-004), so no save trigger has to be invoked before the game is stopped)
- [ ] 6.10 An X11 lock file owned by a **live** process is never removed — the run aborts with exit code `10` instead; only a lock whose owning PID is dead is treated as stale and reclaimed (mirrors xorg-server's `LockServer()` ESRCH/EPERM semantics — verified against xorg-server 21.1.24 `os/utils.c`: `kill(l_pid, 0)` returning `ESRCH` means stale and the lock is unlinked, while `EPERM` or success means live and the server refuses to start leaving the lock intact; FR-012 item 5 now also pins the lock file's fixed 11-byte `"%10lu\n"` format, whose leading-space padding MUST be stripped, and treats a non-11-byte lock as bogus/stale. Resolved by decision: the EXIT-trap cleanup removes X locks **only for the display this script allocated** and, for the lock file, only when its owning PID is dead — FR-010 item 3, round-6 clarification) — **the whole lock-liveness protocol is retired**: under `Xvfb -displayfd` the server sets `nolock = TRUE` and `LockServer()` returns without writing any `/tmp/.X{n}-lock`, so there is no lock to probe, no PID to verify and no stale lock to reclaim; FR-012 item 5 forbids the script from probing, creating or removing lock files, and FR-010 item 3 removes only the **socket** of the display the script allocated. Exit `10` now means "the virtual display could not be allocated or started" (FR-007, `data-model.md`), not a lock conflict. The previous justification cited FR-012 item 5's 11-byte `"%10lu\n"` lock format, which no longer exists in the spec.

## 8. POSIX Filesystem Security

- [x] 8.1 `O_CREAT|O_EXCL` semantics are used for file creation: `mktemp` already provides them (measured on this host: `mktemp` creates the file `0600` and the directory `0700` **even under `umask 022`**, and it never reuses an existing name), and `set -o noclobber` is **not** an `O_EXCL` equivalent (it is a regular-file guard only and `>\|` bypasses it). The "shared directories" clause is vacuous for a single-user tool — the script's own temp dir and its `0700` state dir are private namespaces (FR-002 "Lock file (MUST)", FR-014 "Run log permissions (MUST)"). The lock file is the deliberate exception: it is opened `O_RDWR|O_CREAT` **without** `O_EXCL` (FR-002), so the next run can re-open the same inode.
- [ ] 8.2 `access()` or `stat()` is never used to *gate* an `open()` — this creates a TOCTOU window; the implementation opens directly and branches on the syscall result. Existence and readability checks MAY still be performed for **reporting** (a clearer error message), as long as they do not decide whether the open happens. CWE-367: "The most basic advice for TOCTOU vulnerabilities is to not perform a check before the use" — **the rule is not normatively pinned (open decision D5)**: it survives only in the round-7 security clarification ("Never stat before open is kept as the load-bearing rule") and in `research-bash-security.md` §8.2; no FR states it. CWE-367's own mitigation text says the advice "does not resolve the underlying issue … but it does help to limit the false sense of security given by the check", and Wheeler's guidance applies such a check "only when a user cannot affect the file or any directory along its path" — a condition the single-user threat model does not guarantee. Left unchecked until the rule is given a normative home (or explicitly retired).
- [x] 8.3 A symlink check (`[[ -L ]]`) MAY be performed immediately before operating on a file, and is used for **diagnosis** — with the residual race accepted (the source research concedes "lstat then open is still racy; mitigate with 0700 dirs + O_NOFOLLOW and by not re-checking"). It is **not** a security control: the atomic protection is the `O_CREAT|O_EXCL` open itself, not the preceding stat. The demotion to a diagnostic is a round-7 decision recorded in the spec's Clarifications ("the symlink check is demoted to a diagnostic, not a gate") and is a permissive rule that no artifact contradicts (the pre-flight's own existence and writability probes, e.g. FR-012 item 6's log-directory check, are diagnostics). This resolves the apparent conflict with item 8.2 — 8.2 forbids the check as a *gate*, 8.3 permits it as a *diagnostic*
- [x] 8.4 Directories used for lock/temp files have `0700` permissions (FR-002 "Lock file permissions (MUST)": the lock file's directory MUST be `0700` and owned by the current user — the `$XDG_RUNTIME_DIR` case is guaranteed by the XDG Base Directory Specification (measured on this host: `/run/user/1000` is `0700`, owned by the user), and the `${XDG_STATE_HOME:-$HOME/.local/state}/livingroots-smoke/` fallback MUST be created with `0700` **and** enforced with `chmod 0700`; FR-014 "Run log permissions (MUST)": **every** directory level of the run-log path below the XDG base — `living-roots-smoke/` and `runs/` — MUST be `0700`, because `mkdir -p -m 0700` applies the mode to the **final path component only** (measured: an intermediate level came out `0755` under `umask 022`); the Scope declares the temporary directory `0700`)
- [x] 8.5 On shared systems, `mktemp -d` creates a private working directory rather than writing to `/tmp` directly (the Scope declares a `0700` temporary directory under `$TMPDIR`, created and removed by the script (FR-010 item 4); FR-012 item 8 makes `mktemp` a required tool)
- [x] 8.6 Symlinks in the game and mod directories are **not** swept — the check is out of threat model for a single-user local tool (the only actor is the maintainer, who already owns every file in question) and had no assigned exit code; `research-bash-security.md` §8.6 records the recommendation and the file's supersession banner records its rejection. The real protection is that the script's own files live in private `0700` directories (FR-002, FR-014) and are created by `mktemp` with `O_CREAT|O_EXCL` — the lock file being the deliberate exception, opened `O_RDWR|O_CREAT` **without** `O_EXCL` (FR-002)
- [x] 8.7 File ownership and permissions are verified only for the files the script itself creates — the run-log directory and file (`0700`/`0600`, per FR-014) and the lock file (`0600`, in a `0700` directory, per FR-002). The game installation's ownership is **not** checked: a root-owned Steam install is normal, and the source research explicitly permits root-owned read-only game files (`research-bash-security.md` §8.7.4). (Precision: the spec mandates *enforcement* — `chmod 0700` / `chmod 0600` — rather than a separate ownership-and-mode verification step; the modes themselves are now normative in FR-002 and FR-014.)

## 9. Secrets & Sensitive Data

- [x] 9.1 API keys, tokens, and passwords never appear in logs, error messages, or script output (no credential is involved in the design: the script's environment set is enumerated in FR-015 — `SMAPI_NO_TERMINAL`, `SMAPI_DEVELOPER_MODE`, `LIBGL_ALWAYS_SOFTWARE`, `GALLIUM_DRIVER`, `SDL_VIDEODRIVER`, `SDL_AUDIODRIVER`, `ALSOFT_DRIVERS`, `DISPLAY` — and none is a secret; the run log records paths, PIDs, signals and timestamps (FR-014))
- [x] 9.2 SMAPI log excerpts in failure reports are truncated to relevant lines only — **paths are shown** (the "What → Where → How to fix" format FR-007 mandates requires a `Where:` field, and every worked example prints a full path), but **no credentials, tokens or environment secrets** are included. - [x] 9.3 Error messages do not expose sensitive system details — normatively grounded in `.specify/memory/constitution.md` **Principle II (Security-First Data Handling)** and `plan.md`'s Constitution Compliance ("Exit codes and error messages must not leak sensitive system details"), plus FR-007's "no subprocess-specific status may ever become the script's final code". *(The earlier attribution of the phrase "DO NOT expose raw exception messages to logs" to the constitution was a misattribution — that line lives in the project's `AGENTS.md` anti-pattern list, not in the constitution.)*
- [x] 9.4 No Xauthority/cookie material exists under the accepted minimal posture (spec.md Clarifications, "Session 2026-10-19 (checklist review)"), so there is no cookie to leak; the rule holds trivially if the posture is ever changed
- [x] 9.5 The run log directory is created with mode `0700` and the run log file inherits that restriction — it records paths, PIDs and signals but no secrets (FR-014) — corrected: a directory's mode is **not** inherited by the files inside it, so the file's `0600` mode is established explicitly. - [x] 9.6 The run log records the run ID and script `VERSION` only as correlation metadata; no credentials or tokens are ever written to it (FR-014 "Run ID and version (MUST)": the run ID is `<UTC timestamp>-<PID>` and `VERSION` is `0.1.0` for the first release, stamped on every log line and reported in the stdout summary; the log's remaining content is the lifecycle events FR-014 enumerates)

| 1 | `eval "$user_input"` | Arbitrary code execution | Never use `eval` with external input |

## Round-8 Verification Note

- **Result**: 82 items — **75 `[x]`**, **7 `[ ]`** (1.5, 5.4, 5.6, 6.8, 6.10, 7.6, 8.2). The seven failures are the D1-dependent items (1.5, 5.4, 5.6), the D5-dependent item (8.2), and three items whose requirement the current spec **contradicts**: 6.8 (the `timeout --kill-after=30s` form was dropped in round 7 and FR-009 forbids wrapping the launch), 6.10 (the whole X11 lock-liveness protocol is retired — under `-displayfd` the server writes no lock file) and 7.6 (the script no longer chooses a display number).
- **Gaps found while verifying (not covered by D1–D5)** — the spec does **not** contain the round-8 hardening this checklist was told about:
  1. FR-012 item 7 pins **no `realpath` mode** for the paths the script constructs. Measured: bare `realpath` (default `-E`) succeeds on a missing final component but **fails when the parent is missing**; `realpath -m` succeeds in both cases. A path the script is about to create therefore needs `-m`, and the spec does not say so.
  2. FR-012 item 7 does **not** require the prefix-test base to be canonicalized or slash-free, and does **not** forbid a positive `case` character class. Measured: `case "$p" in [A-Za-z0-9._/-]*)` matches **every** path (including `/etc/passwd` and paths with spaces or `;`), so the allowlist only bites in its negated form `*[!A-Za-z0-9._/-]*`; a base with a trailing slash makes `case "$real" in "$base"/*)` never match.
  3. FR-002's lock-file mode enforcement is the path-based `chmod 0600 "$lockfile"`, not the descriptor form `chmod 0600 /proc/self/fd/9`. Measured: a path-based `chmod` on a symlink changes the **target's** mode (`0644` → `0600`), so it can act on an inode other than the one `flock` holds; the `install -m 0600` ban and the "no write-and-replace" rule **are** present.
  4. FR-012 item 8 assigns **no exit code** to a path-validation failure (the D3 gap), and FR-012 item 7's allowlist remains unscoped (D1).
- **Minor inconsistencies noted**: `quickstart.md` R-6 hard-codes `/tmp` while the spec says `$TMPDIR`; the quickstart's exit-code index says the failure report carries "the last 20–30 log lines" where FR-007 specifies the trailing **records** capped at 30.
