## Summary

A bash script that launches Stardew Valley via SMAPI with the Living Roots mod installed under a headless Xvfb display, polls the SMAPI log for SMAPI's own mod-resolution output, and exits with a deterministic pass/fail result. The script is the project's first automated end-to-end validation tool — it transforms "does the mod load in the real game?" from a manual, error-prone task into a single command with a machine-readable exit code.

The script follows a strict lifecycle: **command-line parsing → host-tool sweep → defaults → run-log creation** → pre-flight validation (bash-version and Xvfb-runnability probes, own-literal validation, game/SMAPI probes, mods-directory check, Steam prerequisite, `--mod-project` resolution, crash-marker removal, orphan-display report) → virtual-display allocation + software-OpenGL probe → build & verify artifact → flock acquisition → existing-process detection → log baseline (stale-log removal) → game launch → two-phase log polling (the run sentinel, then the mod-resolution header) → result determination → game termination → cleanup. It uses SMAPI's officially supported automation environment variables and parses the SMAPI log for mod-specific entries only. The save-data persistence check is deferred (the mod is purely reactive and SMAPI has no CLI save selection).

**The host-tool sweep is NOT part of the pre-flight, and the order around it is load-bearing.** `main()` parses the command line **first**, then runs the sweep, then applies the defaults, and only then creates the run log (`scripts/smoke-validation.sh` → `main()`, lines 4123–4148; `parse_args()`, line 579; `preflight_tool_sweep()`, line 1764; `apply_defaults()`, line 708; `run_log_init()`, line 1117). Three consequences, each observable in the code:

- the **usage paths stay reachable on a host that is missing a tool** — `--help`, `--version` and the exit-`14` usage error are answered by `parse_args()` before the sweep runs, and the parser itself needs no external command (the help text and the version line are built from shell builtins), so the usage reference is available even on a host that has **none** of the swept tools (T101, FR-015);
- the **sweep precedes the run log's creation** because the log's own creation uses `date`, `mkdir` and `chmod` — a sweep that ran afterwards would report a missing `date` as the shell's own `127` and a missing `mkdir` as an internal error (`13`), when the mandated answer for a missing host tool is `9` (FR-012 item 8);
- the **bash-4 requirement check sits behind the parser**, inside the pre-flight's `preflight_tools()` (line 1804) — so the file stays *parseable* by bash 3 (`bash3 -n` exits 0) and the usage paths answer under bash 3, while a run that reaches the pipeline on such a host still fails closed with exit `9` (T169, FR-012 item 8). The file therefore declares **no bash-4-only construct at load time**: the tool→package table is the `case` function `tool_package_for()` (line 1717) and **not** an associative array, because `declare -A` fails on bash 3 — the file would die at the declaration, before the command line was ever parsed.

**Phase order vs. FR-012 (0) — reconciled, not papered over.** FR-012 (0) prescribes: "the build-and-verify step (FR-016) then runs, then the flock, then the existing-process check, then the log baseline, then the game launch". The shipped `main()` now follows exactly that order — `phase_preflight` → `phase_display` → `phase_build` → `phase_lock` → `phase_conflict_check` → `phase_log_baseline` → `phase_launch` — so this plan, the spec and the code agree. The named phases (`pre-flight`, `display`, `rebuild-and-verify`, `lock`, `process-conflict-check`, `log-baseline`, `launch`, `readiness wait`, `verdict`, `termination`, `cleanup`) are the ones the run log timestamps. **History, for the record:** an earlier revision of the script acquired the flock and ran the existing-process check and the log baseline **inside** the pre-flight — i.e. *before* the build-and-verify step — which contradicted FR-012 (0). Convergence task **T033** reconciled it; this plan records the reconciled order, and the reordered lifecycle has since been **executed end to end**: five retained run logs under `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/` (`20261021T022934Z-372155.log`, `20261021T035305Z-909174.log`, `20261021T035527Z-912170.log`, `20261021T035630Z-914932.log`, `20261021T035732Z-917347.log`) record the post-T033 phase order and the verdict `SUCCESS: Mod loaded without errors.`

## Technical Context

**Language/Version**: Bash 4+ (Linux), with standard POSIX utilities (grep, sed, awk, date) and no external language runtime — but the file itself must stay **parseable and runnable up to the pre-flight on bash 3**, so that `--help`, `--version` and the exit-`14` usage error remain reachable on an older host (see the Summary lifecycle below)

**Primary Dependencies**: Stardew Valley game installation, SMAPI 4.5.2 (Stardew Modding API), Xvfb (virtual framebuffer), `mesa-utils` (`glxinfo`, `xdpyinfo`) for the graphics probe, and the **.NET SDK** (`dotnet`) for the pre-run rebuild (FR-016) — the *game* needs no host .NET runtime. The host-tool set the sweep verifies is the **31 externals** of `REQUIRED_TOOLS` (`scripts/smoke-validation.sh`, line 1699) — `Xvfb`, `xdpyinfo`, `glxinfo`, `flock`, `timeout`, `mktemp`, `stat`, `realpath`, `sha256sum`, `date`, `grep`, `dotnet`, `ps`, `readlink`, `sed`, `awk`, `cut`, `head`, `tr`, `cp`, `cat`, `sort`, `touch`, `mkdir`, `chmod`, `rm`, `dirname`, `basename`, `tail`, `sleep`, `mkfifo` — **plus one alternative rule**: `pgrep` **or** `pidof`, *either* of which satisfies the sweep (line 1791). The list names **every** external the script invokes, not only the ones the happy path needs: a tool that is used but not verified is a tool whose absence is silently misclassified (a host without `sort` would report a healthy installation as "SMAPI not functional", exit `2`, instead of as a missing host tool, exit `9`). The tool→package mapping is the `case` function `tool_package_for()` (line 1717) — **one table, 31 entries and 31 arms**, so no tool can lack a remediation and no arm can name a package that does not ship the tool; it is a `case` and not an associative array so that the file stays parseable by bash 3. The **bash 4+ requirement is not a swept tool**: it is a separate runtime check in the pre-flight's `preflight_tools()` (line 1804), placed behind the command-line parser. **No Unicode normalizer is required** — the round-7 decision replaced NFC normalization with an explicit ASCII path allowlist, because NFC is a provable no-op for ASCII paths (UAX #15) and is not a homoglyph defence (UTS #39).

**Process-group mechanism**: **each** child — the game, the X server **and** the rebuild — is launched with bash job control (`set -m`) enabled for that launch only, so each child's process-group ID equals its PID and `kill -- -$!` signals exactly that group. There are therefore **three group-owning children**, and the **PGID assertion covers all three**: `assert_child_group_is_own()` (line 1375) is called for the X server (line 2519), for the rebuild (line 2940) and for the game (line 3557). The rebuild is included because `dotnet build` spawns MSBuild worker processes of its own: signalling only the muxer would leave those workers running, and they would keep writing into the shared build output and the deploy target after the script exited, which FR-016 (b) forbids. Two further properties of the three groups are load-bearing: the game's and the X server's groups are **published before their assertion** (lines 2517–2519 and 3555–3557), so the assertion's *own* failure path can still stop the child rather than orphaning it; and the rebuild's group is held in the **script-global** `build_pgid` (line 2939) — not in a phase-local variable — so the cleanup and the signal forwarder can stop an interrupted build, with the publication withdrawn as soon as the group is gone (a process-group id can be recycled by an unrelated process, and the cleanup must never signal such a stranger; lines 2960 and 2982–2984). No extra dependency (`setsid`) is introduced: `setsid` is excluded because it would add a dependency, not because it forks — measured on this host, `setsid sleep 30 &` does **not** fork (the background child of a non-interactive script is not already a process-group leader), so the earlier rationale was wrong. Every group signal is preceded by an assertion that the group ID differs from the script's own group ID and from `1` (FR-005), and the assertion applies to **all three** children: a child launched without `set -m` shares the script's group, so a group signal to it would either abort the run with `13` before the child is killed — leaving it orphaned — or terminate the script itself. `set -m` is deliberately **not** left enabled for the whole script: that would move the script out of the terminal's foreground process group, so a terminal-generated SIGINT would reach the poll loop's foreground `sleep` instead of the script, and the `INT` handler would never run (measured under a pty).

**Launch Invocation**: `./StardewModdingAPI --no-terminal --mods-path "<resolved mods path>"`, executed with the game installation directory as the working directory. The `--mods-path` argument is **normative** (FR-017): the script resolves the mods directory itself (default `<game-path>/Mods`) and passes it to SMAPI explicitly, so SMAPI never falls back to its own implicit default and the directory the game loads from is the same one the build deployed into. The launch is a subshell that `cd`s to the game directory and `exec`s the apphost, with `set -m` enabled **around the launch only**. SMAPI 4.x is a **self-contained .NET 6 `linux-x64`** deployment (`libcoreclr.so`, `libhostfxr.so`, `libhostpolicy.so` ship in the game folder), so **no system .NET runtime and no Mono runtime** is required to *launch* the game or probed by the pre-flight. (The .NET **SDK** is a separate requirement: FR-016 rebuilds the mod before each run, so `dotnet` must be on `PATH` — a missing SDK exits `9`.) The launcher must be run in place: a relocated copy fails in one of four measured ways — **154** (assembly missing), **131** (.NET runtime missing), **135** (partial runtime — "Could not resolve CoreCLR path") or **134** (SIGABRT: the runtime is present but the game files are not, so SMAPI's `AssertGamePresent()` calls `PressAnyKeyToExit()`, whose `Console.ReadKey()` throws on the `/dev/null` stdin FR-005 mandates). FR-007's translation table maps the first, second and fourth to `2` (SMAPI not functional) and the third to `13`.

**Launch environment**: the launch exports **seven** automation variables plus `DISPLAY` — `SMAPI_NO_TERMINAL=true`, `SMAPI_DEVELOPER_MODE=true`, `LIBGL_ALWAYS_SOFTWARE=1`, `GALLIUM_DRIVER=llvmpipe`, `SDL_VIDEODRIVER=x11`, `SDL_AUDIODRIVER=dummy`, `ALSOFT_DRIVERS=null` and `DISPLAY` (exported from the display number Xvfb reports through `-displayfd`). The two audio variables are load-bearing rather than cosmetic: Xvfb virtualizes the **display**, not the audio device, so without them the run would play sound on the host's speakers. FR-015 renders this set in the help's "Environment (set automatically)" section, stating that the variables are script-managed and not user-configurable.

**Display allocation**: Xvfb is started with `-displayfd`, so the **X server itself** binds the first free display and writes the number back; the script never chooses a display number and never touches `/tmp/.X{n}-lock` files (`-displayfd` disables the server lock entirely). The script records the reported number for the cleanup phase and exports `DISPLAY` from it.

**Artifact identity**: the build's deploy target is pinned to the resolved `--mods-path` via `-p:GameModsPath`, and the deployed assembly's SHA-256 digest is compared with the freshly built one **within the same run** — the standard deploy-effectiveness assertion (file-integrity monitoring / SLSA subject digest). The digest is never compared across runs, because the .NET compiler's deterministic content hash is a function of the absolute source path. The **deploy folder** is the project's **effective `ModFolderName`** property, and it is **read, not pinned**: `resolve_mod_folder_name()` (line 2678) asks MSBuild for the effective value (`dotnet msbuild -getProperty:ModFolderName`, bounded to 10 s), falls back to the project's own unconditional `<ModFolderName>` declaration, and finally to the ModBuildConfig default — the project *file's* base name, not the project's directory name. Pinning `-p:ModFolderName=` would override the project's own declaration with the script's reading of it, and the digest comparison would then compare the build against itself and could no longer detect a deploy that landed somewhere else.

**Storage**: No persistent data model of the script's own — it reads external artifacts (the SMAPI log, the mod build artifact, the mod data files) and produces a single exit code. What it **writes** is more than one thing, and the **exhaustive** list is `spec.md` → Scope → **Declared side effects**; the enumeration below is a **summary** of that list, not a substitute for it. The summary: the per-run diagnostic log at `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/<run-id>.log` (FR-014), the build output in `LivingRoots/bin/` and `LivingRoots/obj/` plus the NuGet cache (and the release archive the build emits into `LivingRoots/bin/`), the deployed mod tree under the resolved mods path, the lock file it leaves in place, the X11 socket it creates and removes, and the temp directory it creates and removes. The items the spec's exhaustive list adds beyond that summary are the **destructive** and **environmental** ones: the removal of the stale `SMAPI-latest.txt` and `SMAPI-crash.txt` from the SMAPI log directory and of SMAPI's crash/update **markers** from the *game* directory, the destruction of the user's previous SMAPI log, the creation of the SMAPI log directory when it is missing, the two transient **write probes** (one in the log directory, one beside the lock file), the creation of `$XDG_RUNTIME_DIR` (mode `0700`), the `--force` termination of a game the script did **not** start, and the indirect writes the launched game itself makes inside the game installation (`smapi-internal/blacklist-updated.json`, `save-backups/`).

**Testing**: An automated bash property-test suite under `scripts/tests/` — a shared harness, a runner and four suites — that drives the script against synthetic fixtures (a synthetic game installation, a controllable apphost stub, synthetic SMAPI logs, stub host tools) and, for the integration cases, against the real game installation and the real mod. Every assertion is checked by exit code and by report content. The suite's bash analogue of property-based testing is described under Constitution Check → **TDD** below.

**Target Platform**: Linux (maintainer's machine; Steam installation at `~/.steam/steam/steamapps/common/Stardew Valley/`)

**Project Type**: CLI tool / maintainer automation script

**Performance Goals**: The script's wall time is the sum of three **independently bounded** phases, each of which reports its measured duration in the run log (FR-014). Measured on the maintainer's machine (8 cores, .NET SDK 10.0.400):

| Phase | Measured | Bound |
|---|---|---|
| Pre-flight (tool sweep, path probes, display allocation, graphics probe) | ~1–3 s | not separately bounded; fails closed |
| Rebuild-and-verify (FR-016) | 6.6 s warm · 8.8–10.6 s from a clean tree (restore ~2 s) · **5.0–26.2 s under host load** | `--build-timeout`, default **300 s** |
| Launch-to-verdict (exec → SMAPI's loaded-mods block) | **~15 s unloaded · 29.6–41.8 s under host load** | `--timeout`, default **120 s** |
| Termination (SIGTERM → grace) | 0.3–1 s typical, 15 s worst | `--grace-period`, default 15 s |

Typical total **~25 s** in the earlier measurement campaign; the five retained post-reconciliation runs of 2026-10-21 measured **41 s, 45 s, 49 s, 49 s and 50 s** in total — in each of them the rebuild took 8–10 s and the readiness wait 26–34 s; worst observed **~85 s**. **The 120 s figure is a per-phase bound on the launch-to-verdict window, not a whole-script bound** — the whole script's duration is the sum of the phases and is *reported*, not enforced. A whole-script cap of 120 s would leave only ~1.4× headroom in the worst measured state and would manufacture the very flakiness the test is meant to detect (absolute-timing flakiness rises with test size).

**Constraints**: 
- Headless operation only (Xvfb + Mesa software rendering via `LIBGL_ALWAYS_SOFTWARE=1` / `GALLIUM_DRIVER=llvmpipe`)
- No save file loading (title screen is expected state)
- Local execution only (no CI integration in current scope) — but the exit-code contract is CI-interpretable by design
- No cross-process data locking in the mod (script-level flock + process detection required)
- Not a container entrypoint — PID 1 signal semantics are out of scope
- Configuration via CLI arguments with documented defaults (no config file, no env-var mechanism)
- No running Steam client required (`steam_appid.txt` ships with the game)
- **Environment-derived paths are unrestricted**: the game path, the mods path, the SMAPI log path and the mod project path may contain spaces and non-ASCII characters; no character allowlist is applied to them. Path safety rests on `realpath` canonicalization, a component-boundary prefix test, correct quoting (every path expanded as `"$var"` and passed after `--`), and the open-without-gating rule. The script's own authored path literals are constrained to `[A-Za-z0-9._-]+`. No Unicode normalization
- The script **mutates** the workspace and the game installation — it deletes and recreates `<mods-path>/LivingRoots/`, writes `LivingRoots/bin/`, removes stale SMAPI log artifacts, and creates a lock file it leaves in place (see spec.md → Scope → Declared side effects)

**Scale/Scope**: Single maintainer, single game instance, single mod. No scalability concerns.

**Design Decisions (from clarification)**:

| Decision | Resolution |
|----------|------------|
| Success signal | SMAPI's loaded-mods block / `   Skipped mods` section — the skipped-mods header carries **three** leading spaces and the loaded-mods header is `Loaded N mods:` or `Loaded 0 mods.`; the mod's own marker is reported but does not gate (FR-003) |
| Build provenance | Rebuild, remove deploy target first, compare SHA-256 digests (FR-016) |
| Mods directory | Resolved explicitly via `--mods-path`, default `<game-path>/Mods` (FR-017) |
| Log freshness | Evaluate only lines after SMAPI's `Log started at {UTC} UTC` sentinel, plus an inode-change assertion (FR-002) |
| Diagnostic output | Per-run XDG log file with a run ID; verdict on stdout, diagnostics on stderr (FR-014) |
| Exit-code taxonomy | One distinct code per failure category — a bespoke one-code-per-class scheme (**not** the `sysexits.h` numbering, which starts at 64 and is deprecated by FreeBSD and OpenBSD; the "sysexits-*style*" label is withdrawn too). Every child status is translated before the script exits. Round 7 added `14` (usage), `15` (no log produced) and `16` (mods path/manifest invalid), made `11` reachable via a `steam_appid.txt` check, and added `129` for SIGHUP. Round 8 added `17` (SMAPI aborted before mod resolution), allocated above the highest published code |
| Dependency failures | `9` = a required host tool is **absent**; `3` = the graphics stack is **present but unusable** |
| Process-group launch | bash job control (`set -m`) around **each** child launch — the game, the X server **and** the rebuild, i.e. **three group-owning children**; the PGID assertion (`assert_child_group_is_own`) covers **all three**, and the game's and the X server's groups are published **before** their assertion so the assertion's own failure path can still stop the child; the rebuild's group is a **script-global**, so the cleanup and the signal forwarder can stop an interrupted build (an MSBuild worker that outlived the muxer would keep writing into the shared build output). Mandatory PGID assertion before every group signal (a failed assertion exits `13`). `set -m` is scoped to the launches — leaving it on for the whole script would break the `INT` handler (FR-005) |
| Process identification | the game is discovered by a `/proc/<pid>/exe` scan restricted to the canonicalized game path — `pgrep`/`pidof` are consulted **only** by the orphan-Xvfb scan (either tool satisfies the sweep) — never `pgrep -x` on the 17-character apphost |
| Display allocation | `Xvfb -displayfd` — the X server binds the first free display atomically; the script neither chooses a number nor manages `/tmp/.X{n}-lock` files. Exit `10` = the display could not be allocated or started |
| Artifact identity | **Deploy effectiveness**: the build's deploy target is pinned to the resolved `--mods-path` (`-p:GameModsPath`) and the deployed assembly's digest is compared with the fresh build's **within the run**. No cross-build digest comparison, and no source-correspondence claim (the assembly carries no build identity) |
| Path validation | Canonicalize with `realpath` (`-e` where the path must exist, `-m` where it need not), then a component-boundary prefix test against the **canonicalized** base, on paths the script *constructs*; user-supplied roots are their own bases — **with exactly one exception: `--mod-project` is the one user-supplied root that is prefix-tested against a *foreign* base, the canonicalized repository root** (`preflight_mod_project()`, line 1993; the test itself at line 2012, against `REPO_ROOT`, line 96). FR-016 (a) requires it: a project that does not exist, or one that lives outside the repository, is rejected before the build — the rebuild's outputs are written into the project tree, so the project must be inside the repository. The resolved path is written back into `mod_project`, so the build receives the canonical path and not the spelling the caller typed. **No character allowlist on environment-derived names** (the game path legitimately contains a space); the script's own authored literals are constrained to `[A-Za-z0-9._-]+`, and every path expansion is quoted and passed after `--`. No Unicode normalization |
| Log freshness | Evaluate every gating signal only against lines after the `Log started at {UTC} UTC` sentinel; the **header region** (version banner, `Mods go here:`) precedes the sentinel and is context only. The `Mods go here:` path is `~`-anonymised |
| Trap design | One `EXIT` trap (registered exactly once) plus `INT`/`TERM`/`HUP` handlers that reset-and-re-raise; `trap '' INT TERM` is prohibited; cleanup is idempotent and time-bounded. The script runs under `set -Eeuo pipefail` — the `-E` is required so the `ERR` trap is inherited by shell functions and can report the enclosing function name (FR-014) |
| CLI surface | A single normative **Command-Line Options** table in `spec.md` owns the spelling, argument placeholder and default of every option; the requirements own the behaviour; `--help` and the quickstart are **renderings** of the table (the `help2man` relation). Long form only except `-h`, no abbreviation, `--opt=VALUE` accepted, `--` ends option processing, no positional arguments |

**Structure Decision**: The **shipped artifact** is a single-file bash script at `scripts/smoke-validation.sh`. The feature is a standalone maintainer tool with no external interfaces, no API surface, and no data persistence. A single file is the simplest structure that satisfies all requirements. The `scripts/` directory already exists in the repository for similar tooling (e.g., `scripts/check-protected-paths.sh`).

The **test harness** under `scripts/tests/` is deliberately a **separate tree**, not part of the artifact: it is validation infrastructure, it is never installed with the mod, and it exists only to exercise the script (per `tasks.md` → Notes: "The script is the feature; `scripts/tests/` is validation infrastructure and is NOT part of the shipped artifact"). The harness is *sourced* by each suite — it is never executed on its own — and `run-all.sh` is the single entry point that discovers and runs the suites. `lefthook.yml` is the only wiring between the two trees and the repository's hooks: it lints both, so a broken test file is caught at commit time just like a broken script, and the pre-push hook runs the launch-free suites, so a change that breaks the script's own cases cannot be pushed unverified.
