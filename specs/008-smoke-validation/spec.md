# Feature Specification: Smoke Validation Script

**Feature Branch**: `008-smoke-validation`

**Created**: 2026-10-19

**Status**: Draft

**Input**: Assessment `automate-ingame-testing` (intake + research + define + shape + decision, verdict: go, Option A)

## User Scenarios & Testing

### User Story 1 - Automated smoke validation of mod loading (Priority: P1)

As the maintainer, I want a script that launches the game with the mod installed and reports whether the mod loaded without errors, so that I can verify the mod works in the real game without manual play-through.

**Why this priority**: This is the immediate blocker — the mod has never been executed in the real game. Without this, no gameplay-affecting feature (spec 005 growth, quality, extra harvest) can be activated with confidence.

**Independent Test**: Can be fully tested by running the script and checking its exit code (0 = mod loaded without errors, non-zero = errors found). Delivers value by providing a repeatable, auditable signal that the mod loads correctly in the game. The save check (User Story 2) is deferred — see FR-004.

**Acceptance Scenarios**:

1. **Given** the game is installed and the mod is deployed in the mods folder, **When** the script runs, **Then** the script launches the game with SMAPI + mod, waits for initialization, checks the SMAPI log for errors, and exits with code 0 if no errors are found. The script terminates the game immediately after the log check passes (see FR-005).
2. **Given** the mod has a runtime error during load, **When** the script runs, **Then** the script detects the error in the SMAPI log and exits with a non-zero code and a descriptive message
3. **Given** the script has run successfully once, **When** the script runs again, **Then** it produces the same result (idempotent)
4. **Given** the assembly deployed into the mods directory is not the one produced by the current build, **When** the script runs, **Then** it fails before launching the game with a non-zero code and a message naming both SHA-256 digests (see FR-016)
5. **Given** a previous run left a `SMAPI-latest.txt` that already contains the mod's success marker, **When** the script runs, **Then** the stale content is not used to decide the verdict — only log lines after the current run's `Log started at` sentinel are evaluated (see FR-002)
6. **Given** SMAPI skipped the mod (for example because the installed SMAPI is older than the mod's `MinimumApiVersion`), **When** the script runs, **Then** the script reports a mod-load failure with SMAPI's stated reason (see FR-003)

---

### User Story 2 - Mod data persistence verification (Priority: P2, Deferred)

As the maintainer, I want the script to verify that the mod's data files appear in SMAPI's mod-data folder after the game loads with a save, so that I can confirm the mod's persistence layer works in the real game.

**Why this priority**: Loading without errors is necessary but not sufficient — the mod must also persist data correctly. This is the second half of the smoke test.

**Status**: Deferred. The automated script cannot load a save (SMAPI has no command-line save selection, and the mod is purely reactive). The title screen is the expected state. This user story will be implemented after the basic smoke test (User Story 1) works and the team has real usage data.

**Independent Test**: Can be fully tested by running the script and checking that SMAPI's mod-data folder for the mod (`~/.config/StardewValley/.smapi/mod-data/lfgranja.LivingRoots/`) contains the expected JSON files (`soil_health_data_*.json`, `composting_bins_*.json`). Delivers value by confirming the mod's persistence pipeline works end-to-end.

**Acceptance Scenarios**:

1. **Given** the game has a save file loaded with the mod active, **When** the script completes its check, **Then** SMAPI's mod-data folder for the mod contains at least one file matching the mod's data prefix
2. **Given** the mod failed to persist data files, **When** the script completes its check, **Then** the script reports the missing data files and exits with a non-zero code

### Edge Cases

- What happens when the game crashes during launch? The script should detect the crash (non-zero process exit or SMAPI-crash.txt) and report failure.
- What happens when the mods path is incorrect? The script should detect that the mod was not loaded (the mod's name is absent from SMAPI's `Loaded N mods:` block, or it appears in the `Skipped mods` section) and report failure.
- What happens when the save file does not exist yet? The save check is deferred (see FR-004). The title screen is the expected state in the automated script.
- What happens when the game takes longer than expected to load? The script should have a configurable timeout and report a timeout failure if the game does not produce a log within the expected window.
- What happens when the display (Xvfb) is not available? The script should detect this and report a clear error message.
- What happens when the game is already running? The script detects the existing process (via `pgrep`) and aborts with a descriptive error by default. An explicit `--force` flag kills the existing instance (SIGTERM then SIGKILL) before launching.
- What happens when another smoke test instance is already running? The script fails to acquire the `flock` and exits immediately with a descriptive error.
- What happens when a prerequisite is missing (game not installed, SMAPI not found, Xvfb not available)? The pre-flight phase detects it and emits an actionable error ("What → Where → How to fix") with a distinct exit code per failure category.
- What happens when the script is interrupted (Ctrl+C) during execution? The EXIT trap runs cleanup: game process killed, Xvfb killed, X11 locks removed, temp files cleaned. The script exits with code 130 (SIGINT) or 143 (SIGTERM).
- What happens when a previous run left a `SMAPI-latest.txt` that already contains the mod's success signal? The script MUST ignore every log line preceding the current run's `Log started at` sentinel (see FR-002), so a stale log can never produce a false pass.
- What happens when the mod build deployed into the mods directory is stale (older than the current source)? The digest assertion in FR-016 MUST fail the run before the game is launched, and the failure message MUST name both the built and the deployed SHA-256 digests.
- What happens when the game fails to create a graphics device (no usable OpenGL under Xvfb)? The script MUST report this as a graphics/environment failure (exit code `3`), not as a timeout or a mod-load failure. The pre-flight's `glxinfo` probe is expected to catch this condition before launch.
- What happens when the game process exits with status `0` but no log was produced? The script MUST report failure. This occurs when SMAPI re-asserts its dependency manifest after a game update and asks the user to relaunch.
- What happens when a leftover `SMAPI-crash.txt` is present from an earlier crash? The pre-flight MUST remove it before launch (see FR-012 item 6), because SMAPI's handling of a leftover crash marker performs a blocking keypress read that would hang the headless run.
- What happens when the resolved mods directory contains a stale copy of the mod while a current copy exists elsewhere? The script tests only the directory it resolved and passed to SMAPI via `--mods-path` (see FR-017); it does not search for other copies.
- What happens when a required host tool is missing? The pre-flight fails closed with exit code `9`, naming the tool and the package that provides it. A tool that is installed but *unusable* — for example a graphics stack with no software OpenGL — exits `3` instead, because the two conditions have different remediations.
- What happens when the script itself hits an unexpected error? The ERR trap reports the script name, failing line, enclosing function and exit code, and the script exits `13` — never with the raw status of the failing command, which under `set -e` would otherwise masquerade as a domain failure (`dotnet build` exits `1`, an unset variable exits `1`, a syntax error exits `2`).
- What happens when the mod fails to build, or when the deployed assembly does not match the fresh build? The run aborts before the game is launched with exit code `12`, naming the build error or both SHA-256 digests.

## Requirements

### Functional Requirements

- **FR-001**: The script MUST launch the Stardew Valley game via SMAPI with the mod installed, using a virtual display (Xvfb) for headless operation. The launch MUST run SMAPI's native apphost `./StardewModdingAPI --no-terminal` from the game directory (`--game-path`), which MUST be the process working directory — SMAPI resolves its dependencies, the `Mods/` folder, and the log directory relative to that directory, and a relocated copy of the launcher aborts with SIGABRT (exit 134). The script uses SMAPI's officially supported automation env vars: `SMAPI_NO_TERMINAL=true`, `SMAPI_USE_CURRENT_SHELL=true`, and `SMAPI_DEVELOPER_MODE=true`. `SMAPI_DEVELOPER_MODE` gates **console** verbosity only — SMAPI writes TRACE-level entries to the log file unconditionally, so TRACE-level diagnostics are available without it; it is retained because it makes the launch console output usable for debugging. The script MUST additionally export `LIBGL_ALWAYS_SOFTWARE=1` and `GALLIUM_DRIVER=llvmpipe` to force Mesa software rendering, and MUST set `SDL_VIDEODRIVER=x11` (never `wayland`) because the game bundles `libSDL2` and Wayland cannot be used against an Xvfb display. Xvfb MUST be started with `-nolisten tcp` on a non-default display (e.g., `:99`).
- **FR-002**: The script MUST wait for the game to initialize and produce a SMAPI log file **that belongs to the current run** before performing checks. The SMAPI log path defaults to `~/.config/StardewValley/ErrorLogs/SMAPI-latest.txt` (Linux convention) and MAY be overridden via `--smapi-log`. Before launching, the script acquires an exclusive `flock` on a dedicated lock file (non-blocking) to prevent concurrent executions. If the lock cannot be acquired, the script exits immediately with a descriptive error.

  **Lock file (MUST).** The lock file MUST live at a **stable, per-user, predictable path** — `${XDG_RUNTIME_DIR}/livingroots-smoke.lock`, falling back to `${XDG_STATE_HOME:-$HOME/.local/state}/livingroots-smoke/livingroots-smoke.lock` when `$XDG_RUNTIME_DIR` is unset — inside a directory with mode `0700` owned by the current user. The path MUST NOT be inside a per-run `mktemp -d` directory: a unique directory per run means two concurrent instances lock *different inodes* and mutual exclusion is zero. The lock file MUST be opened with `exec 9<>"$lockfile"` (read-write, create-if-absent) and **not** `exec 9>"$lockfile"`, because `>` truncates and follows symlinks while `<>` neither truncates nor destroys a symlink target. The lock MUST be acquired with `flock -n 9`. The lock file MUST **not** be removed at exit: the kernel releases the lock when the descriptor closes (or the process dies), whereas removing the file detaches the name from the locked inode and re-opens the race window that a second instance would exploit. The lock path MUST be on a local filesystem — `flock` is unreliable on NFS and CIFS.

  **Log freshness (MUST).** SMAPI unlinks `SMAPI-latest.txt` at startup and creates a new file, and writes an in-band per-run sentinel line `Log started at {UTC timestamp} UTC` near the top of every log. The script MUST therefore: (1) record the UTC launch timestamp `T0` before starting the game; (2) wait for a `Log started at` sentinel whose timestamp is **not older than `T0`**; and (3) evaluate every success and failure signal **only against log lines that follow that sentinel line**. Signals appearing before the sentinel belong to a previous run and MUST be ignored. This ordering requirement is what prevents a stale log left by an earlier successful run from producing a false pass. As a belt-and-braces assertion, the script MUST record the log file's inode (`stat -c %i`) before launch and verify it changed once the log is (re)created.

  **Pre-launch cleanup (MUST).** The script MUST remove a pre-existing `SMAPI-latest.txt` and `SMAPI-crash.txt` before launching. Removing the crash file is required because SMAPI's startup handling of a leftover crash marker performs a blocking `Console.ReadKey()`, which can hang a headless launch indefinitely.

  **Readiness vs. exit (MUST).** If the game process exits **without** producing a log — including an exit status of `0` — the script MUST report failure, not success. SMAPI's dependency-assertion routine exits with status `0` and the message "Please exit this window and re-launch SMAPI to play" after a game update, which would otherwise be mistaken for a successful run.
- **FR-003**: The script MUST parse the SMAPI log file for errors attributable to the mod (LivingRoots). Log entries follow the format `[HH:mm:ss LEVEL SOURCE] message` — the level field is padded to **5** characters (SMAPI renders it with `PadRight(Monitor.MaxLevelLength)`, and `MaxLevelLength` is the length of the longest public `LogLevel` name — `Trace`/`Debug`/`Error`/`Alert` = 5) followed by a single separator space, the source column carries the mod's manifest name for mod-originated entries, and lines are CRLF-terminated, so matching MUST be substring-based (`grep -F`) with any trailing carriage return stripped before an exact comparison. A real mod-scoped line therefore reads `[14:32:02 ERROR Stardew Valley - Living Roots] …`. The level is **inside** the bracket group — there is no `[ERROR]` token — so an Error/Alert entry MUST be matched on the **level column**, never as a literal `[ERROR]` substring. Per-line timestamps carry no date and MUST NOT be used to identify a run. Only Error and Alert level entries are failure markers. WARN-level entries (if ever added to the mod) are logged but do not fail the smoke test. Trace-level entries are written to the log file by SMAPI unconditionally and are captured for diagnostic purposes only — they do not fail the test but provide exception type and HResult information in failure reports. The success marker match is case-sensitive and exact.

  **Success gate (MUST).** The success gate is computed from SMAPI's own mod-resolution output, not from the mod's self-reported marker: (1) SMAPI MUST have emitted a `Loaded N mods:` block, (2) the mod's manifest name (`Stardew Valley - Living Roots`) MUST appear within one of that block's per-mod entry lines, and (3) the mod MUST NOT appear in SMAPI's `Skipped mods` section. SMAPI renders each loaded mod as `   <Name> <Version> by <Author>`; because the mod's name contains spaces, the match MUST be a substring match of the **full** manifest name against the entry line rather than a first-token comparison. The mod's own marker line (`The 'Stardew Valley - Living Roots' mod was loaded successfully!`) MUST still be detected and reported, but it does **not** gate success: it is emitted by the mod from its `GameLaunched` handler (`ModController.cs:959`), which runs only after the game has reached the title screen, so gating on it would couple the smoke test to a working graphics device and would report a graphics failure as a timeout rather than as the environment problem it is.
- **FR-004**: The script SHOULD verify that the mod's data files are present in SMAPI's mod-data folder for the mod (`~/.config/StardewValley/.smapi/mod-data/lfgranja.LivingRoots/`) after the game has run with a save loaded — checking for `soil_health_data_*.json` and `composting_bins_*.json`. In the current implementation the save check is always skipped (with a `SKIPPED:` warning) because the automated script cannot load a save (SMAPI has no command-line save selection, and the mod is purely reactive — it only responds to SMAPI events after a save is loaded via the title screen UI). The title screen is the expected state. The save check is deferred until the basic smoke test works and the team has real usage data; it does not gate success (see FR-006).
- **FR-005**: The script MUST terminate the game process immediately after the log check passes, without leaving orphaned processes. The script launches the game in its own process group and sends SIGTERM to the entire group first, waits a configurable grace period (default 15s, via `--grace-period`) for graceful exit, and escalates to SIGKILL only if the process is unresponsive. The own-process-group requirement is satisfied by enabling bash job control (`set -m`) around the launch only: job control gives the game a process group whose ID equals the game's PID, so `$!` is simultaneously the game's PID and its process-group ID and `kill -- -$!` signals exactly that group and nothing else. Before any group signal the script MUST assert that the process-group ID it is about to signal differs from the script's own process-group ID and from `1` — signalling the script's own group would terminate the script itself instead of the game. Because job control moves the game out of the terminal's foreground process group, the game no longer receives terminal-generated signals and the script's own signal-forwarding trap becomes the only path to the game. Both children (game and Xvfb) MUST be launched with `&`, with their stdin redirected from `/dev/null` and their stdout/stderr redirected to the run log, and MUST be waited on with `wait -f` — a background job that touches the controlling terminal is suspended by SIGTTIN/SIGTTOU, and bash defers a trapped signal until the *foreground* command completes, so a foreground launch would delay the signal handler until the game exits. The script does NOT wait for the `Saved` event — the mod emits no observable log marker on `Saved`, making it impossible to detect externally.

  **Trap design (MUST).** The `EXIT` trap is registered **exactly once**, in the top-level shell, and is the single cleanup path: bash resets caught traps to their inherited values in subshells, so an inherited `EXIT` trap does not fire there and a subshell that owns a child process MUST clean that child up itself before exiting; no subshell may register its own `EXIT` trap (that would double-clean the shared resources). The cleanup function MUST capture `$?` as its very first statement and MUST end with `exit "$rc"`. The `INT`, `TERM` and `HUP` handlers MUST forward the signal to the child process groups and then **reset their own trap and re-raise the signal on the script itself** (`trap - SIG; kill -SIG $$`) — the script MUST die *from* the signal so the caller observes `128+N` as a genuine signal death, which is observably different from `exit 128+N` (a plain exit status; the caller cannot tell the two apart). The script MUST NOT use `trap '' INT TERM` to make cleanup uninterruptible: bash already does not re-enter a handler for the same signal, and ignoring those signals permanently would (a) make the script un-killable by SIGTERM and (b) cause every child spawned afterwards to inherit the ignored disposition across `execve`. Cleanup MUST instead be idempotent (guarded by an `in_cleanup` flag) and time-bounded. `trap - EXIT` inside the cleanup function is permitted as belt-and-braces: POSIX specifies that `exit` inside an `EXIT` trap exits immediately without recursing, but leaves the "a new `EXIT` trap is set during the `EXIT` trap" case unspecified.
- **FR-006**: The script MUST report success (exit code 0) when the log check passes. The log check uses an AND conjunction: success requires the mod to be listed in SMAPI's `Loaded N mods:` block AND the mod to be absent from SMAPI's `Skipped mods` section AND no Error/Alert entries from the mod. All three signals MUST be evaluated against log lines that follow the current run's `Log started at` sentinel (see FR-002). The mod's own success marker, when present, MUST be reported in the result output as a secondary signal but does not gate the verdict. The save check is deferred (see FR-004) and does not gate success in the current implementation. The success message MUST be exactly `SUCCESS: Mod loaded without errors.`
- **FR-007**: The script MUST report failure (non-zero exit code) with a descriptive message when any check fails. Failure messages MUST follow the "What → Where → How to fix" pattern: identify the failed component, the specific error, relevant log context (last 20-30 lines of the SMAPI log including Trace-level entries that follow any Error entry), and an actionable remediation hint. Exit codes MUST assign a distinct code per failure category: `1` = game installation not found, `2` = SMAPI not found or not functional, `3` = graphics environment present but unusable, `4` = timeout, `5` = mod load failure, `6` = lock contention, `7` = process conflict, `9` = missing host tool or runtime dependency, `10` = display conflict, `11` = Steam API prerequisite missing, `12` = build or artifact-identity failure, `13` = internal script error, plus the POSIX `128+N` interruption codes (`130` = SIGINT, `143` = SIGTERM) and `0` = success. This is a bespoke, sysexits-*style* scheme — one code per failure class — and is NOT the `sysexits.h` numbering, which begins at `EX__BASE` = 64; the phrase "sysexits.h convention" MUST NOT be used to describe these values, and codes are allocated **additively** (an existing code MUST NOT be re-assigned; a new category takes the next unused low value).

**No subprocess-specific status may ever become the script's final code.** Every child status MUST be translated into one of the categories above before the script exits, using this table: `0` → `0`; `timeout`'s native `124` → `4`; `timeout`'s `125` (the timeout utility itself failed) → `13`; `126` (found but not executable) → `9`; `127` (not found) → `9`; `134` (SIGABRT — for example a relocated SMAPI launcher that cannot resolve its dependencies) → `2`; `137` (SIGKILL) → `5` when it is the game process and `13` otherwise; `128+N` for SIGINT/SIGTERM delivered to the script itself → `128+N`, unchanged; any other non-zero status → `13`. A pre-flight probe that fails is translated by the **category of the probe**, not by the raw status the probe happened to return. An unhandled error caught by the ERR trap exits `13`; a failed mod build or a build/artifact digest mismatch exits `12` (see FR-016).
- **FR-008**: The script MUST be idempotent — running it multiple times in sequence produces the same result
- **FR-009**: The script MUST accept a configurable timeout for game launch and initialization via command-line argument, with a 120-second default. The script polls the log continuously (no wasted time), and the timeout only matters for failure cases.
- **FR-011**: The script MUST detect an existing Stardew Valley/SMAPI process before launching. By default, the script aborts with a descriptive error listing the conflicting PIDs. An explicit `--force` flag kills existing instances (SIGTERM → SIGKILL escalation) before launching. This is a correctness requirement: the mod has no cross-process data file locking, so concurrent instances would corrupt data and truncate the SMAPI log. Identification MUST be **by executable path, not by process-name matching**: a candidate PID qualifies only when `/proc/$PID/exe` resolves to an executable under the resolved game directory — the `StardewModdingAPI` apphost or the `StardewValley` game binary. `pgrep -x` MUST NOT be used for the apphost: the kernel's process name (`comm`) is truncated to 15 characters and `StardewModdingAPI` is 17, so an exact-name match can never succeed and would silently never match. `pidof` matches on the untruncated name and on `/proc/$PID/exe` and is the acceptable alternative. A PID the script itself spawned needs no identity check — an unreaped child stays a zombie and the kernel does not recycle a zombie PID — but **any PID discovered by scanning the process table MUST be verified before it is signalled**.
- **FR-012**: The script MUST include a pre-flight phase before launching that validates: (1) the game installation exists at the expected path (configurable via `--game-path`, default `~/.steam/steam/steamapps/common/Stardew Valley/`) and contains the game assembly (`Stardew Valley.dll`) and SMAPI's launcher (`StardewModdingAPI`); (2) SMAPI is installed and functional — this means the main assembly `StardewModdingAPI.dll` is present and its version can be parsed, the dependency assemblies `smapi-internal/SMAPI.Toolkit.dll` and `smapi-internal/SMAPI.Toolkit.CoreInterfaces.dll` are present, and the `StardewModdingAPI` apphost is executable for the host architecture. No SMAPI release ships a file named `smapi-internal/SMAPI.dll`; probing for that path produces a false negative on a correct installation, so the check MUST use the paths listed here; (3) Xvfb is available and runnable (`command -v Xvfb` plus a version probe) — an absent `Xvfb` binary is a **missing host tool** and exits `9` (see item 8), not `3`; (4) software OpenGL rendering is genuinely usable — the script MUST start the virtual display, confirm with `xdpyinfo` that the `GLX` and `RANDR` extensions are present, and confirm that `glxinfo -B` under `LIBGL_ALWAYS_SOFTWARE=1` exits successfully and reports a software renderer (`llvmpipe` or `softpipe`); the mere presence of `libGL.so` does NOT satisfy this check — a failure of this probe, **with `Xvfb`, `xdpyinfo` and `glxinfo` all present**, is a graphics environment that is present but unusable and exits `3`; (5) no orphaned Xvfb on the chosen display or stale X11 lock files remain from a previous crashed run — a lock file whose owning PID is no longer alive is stale and MUST be removed with logging, while a lock file owned by a live process MUST abort the run with exit code `10` and MUST NOT be removed. The liveness test MUST mirror xorg-server's `LockServer()` semantics (`os/utils.c`): the lock file has a fixed 11-byte format (`"%10lu\n"` — the PID is right-aligned and padded with leading spaces, so a naive `pid=$(cat "$lock")` yields leading spaces that MUST be stripped), the PID is probed with `kill -0` (so `ESRCH` means stale and `EPERM` means live), and a lock file whose length is not 11 bytes is bogus and MUST be treated as stale; (6) any pre-existing `SMAPI-crash.txt` is removed to avoid false positives, and to avoid SMAPI's blocking keypress prompt hanging a headless launch; and (7) a Unicode normalizer is available (`python3`, or `uconv` as fallback) for NFC path normalization and symlink-safe file opens (`O_NOFOLLOW`). The pre-flight phase MUST fail closed when the normalizer is absent, with the same "What → Where → How to fix" pattern and exit code `9`. A missing host tool or an unresolvable runtime MUST fail closed with exit code `9`; (8) every required host tool is present. The required set is: `bash` (4+), `Xvfb`, `xdpyinfo`, `glxinfo`, `python3` (or `uconv`), `flock`, `timeout`, `mktemp`, `stat`, `realpath`, `pgrep` (or `pidof`), `sha256sum`, and `dotnet` (required by FR-016's rebuild). Each MUST be verified with `command -v`; a missing one MUST fail closed with exit code `9` and name the tool. A required tool that is present but **unusable** is a different category — for example an `Xvfb` that is installed but whose display stack cannot provide software OpenGL exits `3`, not `9`.
- **FR-010**: The script MUST clean up temporary resources on exit, including on failure and interruption. Cleanup includes: (1) kill game process (SIGTERM → SIGKILL escalation), (2) kill Xvfb process, (3) remove X11 lock files (`/tmp/.X{n}-lock` and `/tmp/.X11-unix/X{n}`) — but ONLY for the display this script allocated (`{n}` = the script's own display), and, for the lock file, ONLY when its owning PID is no longer alive; a lock file owned by a live process MUST be left in place and logged, never removed. The socket carries no ownership information, so it is governed by the display scope alone. (Xvfb removes both files itself on SIGTERM/SIGINT and on a fatal error, so this step is a no-op on the normal path and load-bearing only after a SIGKILL escalation), (4) remove temp files/directories, (5) the flock is auto-released by the kernel on process death — the lock **file** is deliberately **not** removed, because removing the name detaches it from the locked inode and re-opens the race window for a second instance (see FR-002). Each cleanup step MUST be isolated (guarded with `|| true`) so one failure does not prevent others. The cleanup order is reverse of allocation: game first, then Xvfb, then locks and temp files.

- **FR-013**: The script MUST remain local-first: no CI integration and no machine-parseable (`--json`) output mode in the current scope. Proper exit codes (0/non-zero) are retained so future CI integration is straightforward.
- **FR-014**: The script MUST log every process lifecycle event with a timestamp and level prefix — spawn (game, Xvfb), every signal sent (including the PID and the signal), the grace period, the escalation to SIGKILL, and the observed exit — so that a failed run can be reconstructed from the run log alone. On any unhandled error, the ERR trap MUST report the script name, the failing line number, the enclosing function name, and the exit code.

  **Run log (MUST).** The script's own diagnostic output is the **run log**, and it is distinct from the SMAPI log. The run log MUST be written to a file at `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/<run-id>.log`, in a directory created with mode `0700`. Each run MUST write its own file (no shared append-only file) so that concurrent runs cannot interleave. The run log MUST contain every line the script emits at any level, including the lifecycle events above.

  **Run ID and version (MUST).** The script MUST generate a run ID of the form `<UTC timestamp>-<PID>` (e.g. `20261019T183302Z-48213`) and MUST stamp it on every run-log line, in the stdout summary, in every error message, and in the path of the run log file. The script MUST define a `VERSION` constant (first release `0.1.0`) and MUST report it in the stdout summary, in the run-log header, and in the `--help` output. The run ID and `VERSION` are the correlation keys required by the escalation evidence bundle.

  **Streams (MUST).** The verdict and the `--help`/`--version` output go to stdout; all level-prefixed diagnostics and error messages go to stderr. The exit code remains the sole machine-readable signal (see FR-013).
- **FR-015**: The script's `--help` output MUST document the automation environment variables it sets (`SMAPI_NO_TERMINAL=true`, `SMAPI_USE_CURRENT_SHELL=true`, `SMAPI_DEVELOPER_MODE=true`, `LIBGL_ALWAYS_SOFTWARE=1`, `GALLIUM_DRIVER=llvmpipe`, `SDL_VIDEODRIVER=x11`, and `DISPLAY`) in a dedicated "Environment (set automatically)" section, stating explicitly that they are managed by the script and are not user-configurable. The `--help` output MUST also document the `--mods-path` option (see FR-017), the run-log location, the run ID format, the script `VERSION`, and every exit code.
- **FR-016**: The script MUST ensure that the mod build under test is the build produced from the current source tree, and MUST abort before launching the game if it cannot. The script MUST build the mod with `dotnet build --configuration Release --no-incremental` after removing the deploy target directory, MUST abort with a non-zero exit status if the build fails, and MUST then assert that the deployed `Mods/<ModFolderName>/<EntryDll>` is byte-identical to the freshly built assembly by comparing SHA-256 digests. Comparing digests rather than modification times is required because the mod carries no build identity: `manifest.json` declares a fixed `Version` that is never bumped, the assembly declares a fixed `AssemblyVersion`, and no commit identifier is embedded. The deployed manifest version alone MUST NOT be used as the freshness assertion, because it is invariant across builds.
- **FR-017**: The script MUST resolve the mods directory explicitly and MUST NOT depend on SMAPI's implicit default. The mods directory MUST be configurable via `--mods-path`, defaulting to `<game-path>/Mods`. The script MUST pass the resolved directory to SMAPI using the `--mods-path` argument (equivalently `SMAPI_MODS_PATH`), and the pre-flight MUST verify that the resolved directory exists and contains the mod folder (`Mods/<ModFolderName>/manifest.json` with a matching `UniqueID`). A relative `--mods-path` value MUST be resolved against the game directory, matching SMAPI's own semantics.
### Key Entities

- **SMAPI Log**: The log file produced by SMAPI at `~/.config/StardewValley/ErrorLogs/SMAPI-latest.txt` (Linux). Entries follow the `[HH:mm:ss LEVEL SOURCE] message` format — the level field is padded to 5 characters followed by a single separator space, the source column carries the mod's manifest name for mod-originated entries, and lines are CRLF-terminated. Six levels are recognized (TRACE, DEBUG, INFO, WARN, ERROR, ALERT). The script parses this to (a) detect SMAPI's mod-resolution output (`Loaded N mods:` block and `Skipped mods` section), (b) detect the mod's own success marker ("The 'Stardew Valley - Living Roots' mod was loaded successfully!" — emitted by the mod, not by SMAPI), and (c) detect any Error/Alert entries attributable to the mod. The log begins with a per-run sentinel line `Log started at {UTC timestamp} UTC`; only lines after that sentinel belong to the current run. `SMAPI-crash.txt` (if present) overrides `SMAPI-latest.txt` and indicates failure.
- **Loaded Mods Manifest**: SMAPI's own report of the mods it resolved, emitted in the log as a `Loaded N mods:` block with one `   <Name> <Version> by <Author>` line per mod, followed by an optional `Skipped mods` section naming the reason for each skip (for example "because it needs SMAPI X or later"). This is the authoritative signal for whether the mod was loaded, and it is available without the game having reached the title screen. The same log also records the resolved mods directory (`Mods go here: <path>`) and the SMAPI version banner (`SMAPI <version> with Stardew Valley <version> on <os>`).
- **Mod Build Artifact**: The compiled mod assembly `LivingRoots.dll` and its manifest, deployed by the build into the resolved mods directory (`<mods-path>/LivingRoots/`). The assembly carries no build identity — `manifest.json` declares a fixed `Version` (`0.0.1`), the assembly declares a fixed `AssemblyVersion` (`1.0.0.0`), and no commit identifier is embedded — so freshness MUST be established by comparing the SHA-256 digest of the deployed assembly with the digest of the assembly produced by the current build (see FR-016). Two copies of this artifact may coexist in the workspace (a repository-local `.gamepath/Mods/` copy and the copy in the game installation); only the copy in the resolved mods path is under test.
- **Mod Data Files**: The mod persists data as JSON sidecar files written through SMAPI's `IModHelper.Data.WriteJsonFile`, which resolves relative names against SMAPI's mod-data directory — `~/.config/StardewValley/.smapi/mod-data/<UniqueID>/` (here `<UniqueID>` = `lfgranja.LivingRoots`). The files are named `soil_health_data_<sanitizedSaveId>.json`, `composting_bins_<sanitizedSaveId>.json`, and `visualization_config_<sanitizedSaveId>.json`. The saveId is SMAPI's active save folder name (`Constants.SaveFolderName`), sanitized via Unicode normalization and filename sanitization. The mod does **not** write into a `data/` folder inside its own mod folder — that location is not used by SMAPI's helper API. When no save is loaded (fresh install/title screen), zero data files is the expected valid state.
- **Game Process**: The Stardew Valley process launched via SMAPI. The script manages this process lifecycle (launch, wait, terminate). Termination happens immediately after the log check passes. The script sends SIGTERM first, waits a brief grace period for graceful exit, and escalates to SIGKILL only if the process is unresponsive. The script does NOT wait for the `Saved` event — the mod emits no observable log marker on `Saved` (`ModController.cs:1089-1102`), making it impossible to detect externally.
- **Virtual Display**: The Xvfb display buffer that allows the graphical game to run headless. The script manages this resource lifecycle.
- **Run Log**: The script's own diagnostic output, written per run to `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/<run-id>.log` (see FR-014). It records every lifecycle event with a timestamp, level prefix, and run ID. It is distinct from the SMAPI Log and survives the run, so a failure can be reconstructed afterwards.

The following were resolved directly from evidence and required no decision.

- Evidence-resolved: bash does **not** propagate an inherited `EXIT` trap into subshells. Verified empirically on bash 5.3.9: command substitution, a parenthesised subshell, a background job, a pipeline stage, and a function invoked inside a subshell all completed without firing the parent's `EXIT` trap — only the parent fired it, exactly once. A trap set *inside* a subshell does fire when that subshell exits; only `set -E` propagates the `ERR` trap. Consequently the `EXIT` trap is the single cleanup path and no subshell registers one (FR-005). This replaces the earlier, unsupported claim that the design uses "no subshells" — a single-file script still uses command substitution, pipelines and background jobs; what the design forbids is a *second* `EXIT` trap.
- Evidence-resolved: `research.md` §5 still listed the superseded `8 (interrupted)` exit code and omitted codes 9/10/11. It now matches FR-007 and the canonical table in `data-model.md`.
- Evidence-resolved: `SMAPI_DEVELOPER_MODE` gates console verbosity only — SMAPI writes TRACE-level entries to the log file unconditionally (recorded at spec.md:227). `checklists/smapi-integration.md` item 1.3 now states this accurately instead of implying the log-file TRACE entries depend on the variable.
- Evidence-resolved: the minimal Xvfb posture recorded below (Clarifications → "Session 2026-10-19 (checklist review)") is now reflected consistently in `checklists/security-safety.md` — the Anti-Patterns table no longer prescribes xauth/MIT-MAGIC-COOKIE-1, and item 9.4 is recorded as vacuous under the accepted posture. The accepted residual risk is stated in Assumptions.
- Evidence-resolved: FR-012 item 5 now pins the X11 lock file's exact format and liveness semantics, taken from xorg-server 21.1.24 `os/utils.c` (`LockServer()`): the lock is 11 bytes (`"%10lu\n"`, PID right-aligned and space-padded, so a naive `pid=$(cat "$lock")` leaves leading spaces), the PID is probed with `kill -0` (`ESRCH` = stale, `EPERM` = live), and a lock whose length is not 11 bytes is bogus and therefore stale. Verified empirically against the real Fedora `Xvfb` 21.1.24 binary: `Xvfb` removes both `/tmp/.X{n}-lock` and `/tmp/.X11-unix/X{n}` on SIGTERM/SIGINT and on a fatal error, and only a SIGKILL leaves them behind — so the EXIT trap's lock removal is a no-op on the normal path and load-bearing only on the SIGKILL escalation path.
- Evidence-resolved: the interruption clarification cited `BashFAQ/062` as the canonical pattern for signal handling and the EXIT trap. `BashFAQ/062` is *"How do I create a temporary file in a secure manner?"* — the correct citation is `BashFAQ/047` (*"How do I trap signals in a shell script?"*) together with the Bash Beginners Guide §12.2 *Traps* (which `checklists/script-reliability.md` already cites correctly). The decision itself is unchanged.

### Session 2026-10-19 (checklist review — round 6, user decisions)

Five questions were raised as a batch after the round-5 checklist review, each backed by a dedicated research agent (6 external evidence agents: exit-code taxonomy, exit-code overlap disambiguation, unmapped exit-status handling, bash trap & process-group semantics, X11 lock lifecycle, PID identity verification). **All five recommendations were accepted by the user.**

- Q: When a required pre-flight dependency is absent, should the script exit `3` or `9`? → A: `9` = **any** required host tool is missing (Xvfb, glxinfo, xdpyinfo, the Unicode normalizer, flock, timeout, mktemp, stat, realpath, pgrep/pidof, sha256sum, dotnet, bash); `3` = the graphics stack is **present but unusable** (no `GLX`/`RANDR`, no software renderer). The two categories are disjoint by condition — "binary absent" vs "binary present but its stack unusable" — mirroring Docker's and GNU `timeout`'s `127` (not found) vs `126` (found, cannot be invoked). The required-tool set is now enumerated in FR-012 item 8 and verified with `command -v`. (Supersedes the round-2 clarification "Mesa/OpenGL pre-flight failure exit code? → Reuse exit code 3" for the *missing-binary* case only; a present-but-unusable stack still exits `3`.)
- Q: Which code covers "the script itself broke" and "the build failed", and is the scheme really sysexits? → A: It is **not** sysexits — `sysexits.h` defines only 64–78 and two of three BSDs have deprecated it; the scheme is a bespoke sysexits-*style* one-code-per-class taxonomy, and the phrase "sysexits.h convention" is withdrawn from FR-007, `data-model.md` and the checklists. Two codes are added **additively**: `12` = build or artifact-identity failure (FR-016) and `13` = internal script error. FR-007 now states the general rule it previously applied only to `timeout`'s `124`: **no subprocess-specific status may ever become the script's final code**, with an explicit translation table (124→4, 125→13, 126→9, 127→9, 134→2, 137→5/13, 128+N unchanged, everything else→13).
- Q: How does the game get into its own process group? → A: bash job control (`set -m`) around the launch only — it gives the game a process group whose ID equals its PID, so `$!` is both the game PID and the group ID and `kill -- -$!` is safe. No new dependency. A mandatory assertion precedes every group signal: the group ID to be signalled MUST differ from the script's own group ID and from `1`. (Measured: a plain `cmd &` leaves the child in the script's own group, so `kill -- -$PGID` terminates the script itself.)
- Q: Under what condition may the cleanup remove the X11 lock files? → A: only for the display **the script itself allocated**, and — for the lock file — only when its owning PID is dead. A live-owned lock is left in place and logged. The socket has no ownership information and is governed by the display scope alone. (Xvfb removes both files itself on SIGTERM/SIGINT, so the cleanup step is a no-op on the normal path and load-bearing only after a SIGKILL escalation.)
- Q: Which identity rule applies before `--force` signals a game instance the script did not spawn? → A: **executable path**, not process name. A candidate qualifies only when `/proc/$PID/exe` resolves under the resolved game directory (`StardewModdingAPI` or `StardewValley`); `pidof` is the acceptable stock tool. `pgrep -x` MUST NOT be used for the apphost — `comm` is truncated to 15 characters and `StardewModdingAPI` is 17, so an exact-name match can never succeed. The script's own spawned PID needs no check (an unreaped child stays a zombie and its PID is not recycled), but any process-table-discovered PID MUST be verified before it is signalled.

Five checklists were re-verified against the current artifacts by five parallel review agents. All 360 items were re-checked; the round found **stale citations, factually wrong claims, unsatisfiable requirements, and mutually exclusive rules**. The items that could not be resolved from evidence are carried to the user as a batch of questions.

The following were resolved directly from evidence and required no decision:

- Evidence-resolved: the SMAPI log line format is `[HH:mm:ss LEVEL SOURCE] message` with the level field padded to **5** characters (SMAPI's `Monitor.MaxLevelLength` is the length of the longest public `LogLevel` name) followed by one separator space — **not** 8, which contradicted the worked examples already in `data-model.md`. Consequently there is no `[ERROR]` token: the level lives *inside* the bracket group, so Error/Alert entries must be matched on the **level column**. FR-003 and the Key Entities entry were corrected.
- Evidence-resolved: SMAPI's blocking `Console.ReadKey()` on a leftover crash is gated by `smapi-internal/StardewModdingAPI.crash.marker` (and `smapi-internal/StardewModdingAPI.update.marker`), **not** by `SMAPI-crash.txt` — the crash log is only a copy of the log file. Verified against the installed SMAPI 4.5.2 binary (the three literals are present). Removing only `SMAPI-crash.txt` therefore leaves the marker in place and does **not** prevent the headless hang the spec claims to prevent. The pre-launch cleanup requirement is amended accordingly (FR-002) — the exact file set is settled in the round-7 batch question.
- Evidence-resolved: a relocated SMAPI apphost does **not** abort with SIGABRT (134). Measured against the installed 4.5.2 apphost: a copy without its `.dll` exits **154** ("The application to execute does not exist"); with the `.dll` but no runtime it exits **131** ("You must install .NET to run this application"); with the runtime but no game files it exits **137** ("Failed to create CoreCLR"). FR-007's translation table had no entry for 154 or 131, so a broken SMAPI installation was reported as `13` ("the script itself broke") instead of `2` ("SMAPI not found or not functional"). FR-001's supporting rationale — that SMAPI resolves its dependencies, the `Mods/` folder and the log directory relative to the game directory — is also wrong: the apphost resolves its runtime relative to its own path, `Constants.GamePath` is the directory of `StardewModdingAPI.dll`, and the log directory is `$XDG_CONFIG_HOME`/`~/.config` + `/StardewValley/ErrorLogs`. The *requirement* (launch in place, from the game directory) is unchanged; its rationale is corrected.
- Evidence-resolved: `SMAPI_USE_CURRENT_SHELL` does not exist in SMAPI 4.5.2. The only `SMAPI_*` literals in `StardewModdingAPI.dll` are `SMAPI_NO_TERMINAL`, `SMAPI_MODS_PATH` and `SMAPI_DEVELOPER_MODE`; upstream `Program.cs` reads exactly those three. The variable is read only by SMAPI's installer wrapper, which this design bypasses by launching the apphost directly, so it is a no-op here. Its rationale ("prevents SMAPI from spawning a new shell") was also wrong — SMAPI 4 runs the game **in-process**, so the script's `&`-spawned PID *is* the game PID, which is exactly what FR-005's `set -m` design assumes. Whether FR-001/FR-015 should still list it is settled in the round-7 batch question.
- Evidence-resolved: `Mods go here: <path>` is **tilde-anonymised** by SMAPI (`PathUtilities.AnonymizePathForDisplay` replaces `$HOME` with `~`), so a literal comparison against the absolute resolved `--mods-path` fails. The version banner and the `Mods go here:` line are also written **before** the `Log started at` sentinel, so FR-002's "evaluate every signal only after the sentinel" rule forbids reading them. Both are settled in the round-7 batch question.
- Evidence-resolved: `Loaded N mods:` is followed by a **period** (`Loaded 0 mods.`) when zero mods load, so the block cannot be anchored on the colon form alone; per-mod entries carry an optional ` | <Description>` suffix; and `Skipped mods` entries are indented **six** spaces, not three. `data-model.md`'s canonical table was corrected.
- Evidence-resolved: the canonical trap design is now pinned (FR-005). Signal handlers **reset their own trap and re-raise** (`trap - SIG; kill -SIG $$`) so the script dies *from* the signal — `exit 128+N` yields the same printed number but `WIFSIGNALED == 0`, i.e. a plain exit the caller cannot distinguish from a normal one. `trap '' INT TERM` inside cleanup is **prohibited**: it makes the script un-killable by SIGTERM and causes every child spawned afterwards to inherit the ignored disposition across `execve`. Cleanup is instead made idempotent (an `in_cleanup` guard) and time-bounded. Children MUST be launched with `&` and waited on with `wait -f`, because bash defers a trapped signal until the *foreground* command completes — a foreground launch would delay the handler until the game exits — and their stdin MUST come from `/dev/null` so a terminal-touching child is not suspended by SIGTTIN/SIGTTOU. `trap - EXIT` inside cleanup is kept as belt-and-braces (POSIX leaves "a new `EXIT` trap set during the `EXIT` trap" unspecified).
- Evidence-resolved: the lock file MUST live at a **stable** path, not inside a per-run `mktemp -d` directory — a unique directory per run means two concurrent instances lock different inodes and mutual exclusion is zero, which would make SC-008 and TC-5 unreachable. FR-002 now pins `${XDG_RUNTIME_DIR}/livingroots-smoke.lock` (falling back to `${XDG_STATE_HOME:-$HOME/.local/state}/livingroots-smoke/`) in a `0700` directory, opened with `exec 9<>` rather than `exec 9>` (which truncates and follows symlinks), never removed at exit, and on a local filesystem (`flock` is unreliable on NFS/CIFS).
- Evidence-resolved: `research.md` carried four statements that contradicted the normative artifacts — `SMAPI_DEVELOPER_MODE` "enables TRACE-level logging" (it gates console verbosity only), `pgrep` with "exact process name matching" (FR-011 forbids `pgrep -x`), `BashFAQ/062` as the trap citation (`BashFAQ/047` is correct), and "written to the mod's own data folder" (SMAPI's mod-data directory). All four are corrected. A `--save` option that no requirement defines was also removed from `research-bash-security.md`.

## Assumptions

- The game (Stardew Valley) is installed via Steam on Linux at `~/.steam/steam/steamapps/common/Stardew Valley/`
- SMAPI 4.5.2 is installed and functional in the game directory. The installation is a **self-contained** .NET 6 `linux-x64` deployment — `libcoreclr.so`, `libhostfxr.so`, `libhostpolicy.so`, and `System.Private.CoreLib.dll` all ship in the game directory — so no system .NET or Mono runtime is required or probed. Mono is not involved: SMAPI 4.x targets .NET 6, not .NET Framework.
- SMAPI's launcher `StardewModdingAPI` is a native ELF apphost and MUST be invoked from the game directory
- The game ships `steam_appid.txt` (`413150`), so **no running Steam client is required**; Steam only disables achievements, logging "Oops! Steam achievements won't work because Steam isn't loaded." at Error level from SMAPI core (not from the mod, so it does not affect the mod-scoped Error/Alert gate)
- `Xvfb` MUST be installed (`xorg-x11-server-Xvfb` / `xvfb`) — it is **not** present by default, and the pre-flight MUST fail closed with exit code `9` when it is missing (a missing binary is a missing host tool; `3` is reserved for a graphics stack that is present but unusable). `mesa-utils` (`glxinfo`, `xdpyinfo`) and Mesa's `libgallium`/`libGL` are also required. The .NET **SDK** (`dotnet`) is required on the host because the script rebuilds the mod before every run (FR-016), even though the game itself needs no host .NET runtime

The X11 Unix socket therefore carries Xorg's default permissions, and any local user could attach to the display. `-nolisten tcp` removes the network exposure. This residual risk is **accepted** on the grounds that the script runs on a single-user maintainer machine (plan.md → Target Platform); it is recorded here so the risk is explicit rather than implicit.
- The mod is deployed into the resolved mods directory (default `<game-path>/Mods`) by the build; the script rebuilds and redeploys it before each run (FR-016). The repository-local `.gamepath/Mods/` copy is a build-output artifact and is **not** the copy under test

This directory has **never** contained an `SMAPI-latest.txt` on the maintainer's machine — the mod has never been executed in the real game — so the path is a documented convention rather than an observed artefact, and `--smapi-log` remains available as an override
