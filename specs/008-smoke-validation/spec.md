# Feature Specification: Smoke Validation Script

**Feature Branch**: `008-smoke-validation`

**Created**: 2026-10-19

**Status**: Draft

**Input**: Assessment `automate-ingame-testing` (intake + research + define + shape + decision, verdict: go, Option A)

## Scope

### In scope

- A single local, maintainer-run bash script (`scripts/smoke-validation.sh`) that launches Stardew Valley via SMAPI under a headless Xvfb display and reports whether the Living Roots mod loaded without errors.
- The FR-007 exit-code contract as the **sole** machine-readable signal (no `--json` mode).
- A per-run diagnostic log under `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/`.
- A pre-run rebuild of the mod and a **deploy-effectiveness** assertion on the deployed assembly (FR-016).
- An explicit, script-resolved mods directory passed to SMAPI (FR-017).

### Out of scope

- **Loading a save, and every consequence of it** — the save-data persistence check (FR-004, US2). The title screen is the expected state.
- **CI integration** and any machine-parseable output mode (FR-013).
- **Gameplay validation** — soil health, composting, growth, harvest. This feature validates *loading*, not mechanics.
- **Multiplayer** (roadmap D1).
- **Container / PID-1 signal semantics** — the script is not an entrypoint.
- **Parallel runs, configuration files, environment-variable configuration** — CLI arguments with documented defaults only.
- **Provenance stamping of the assembly** (embedding the commit id). The assembly carries no build identity today, and adding it would require changing `LivingRoots.csproj` — out of scope for a script-only feature. FR-016 asserts deploy effectiveness instead.

### Declared side effects

The script is not read-only. This list is **exhaustive**: every behaviour of the script that mutates state outside the script's own process MUST appear here, and any new requirement that mutates state MUST update this list in the same change. The script MUST be understood to:

- **delete** the mod's deploy directory `<mods-path>/LivingRoots/` and **recreate** it on every run (FR-016 (b)) — so a manual deployment into that directory is not required, and is not preserved;
- **write** the build output into the repository tree at `LivingRoots/bin/` and `LivingRoots/obj/`, and the NuGet restore output into the user's NuGet cache (FR-016 (b)) — the build also emits a release archive (`LivingRoots <version>.zip`) into `LivingRoots/bin/` on every run, because the mod's `ModBuildConfig` enables `EnableModZip`;
- **write** the deployed assembly, manifest, `i18n/` and `Assets/` into `<mods-path>/LivingRoots/` (FR-016 (c));
- **remove** a stale `SMAPI-latest.txt` and `SMAPI-crash.txt` from the SMAPI log directory (`~/.config/StardewValley/ErrorLogs/`) **and** SMAPI's leftover crash **and** update **markers** from the **game** directory (`<game-path>/smapi-internal/StardewModdingAPI.crash.marker` and `…/StardewModdingAPI.update.marker`) — the markers live beside the game's SMAPI assemblies, **not** in the log directory, so removing them is a write to the game installation (FR-012 item 6);
- **destroy** the user's previous SMAPI log — the script removes the stale log before launch and SMAPI then unlinks and recreates it (`PurgeNormalLogs`), so the previous run's log is not preserved (FR-002);
- **create** the X11 socket `/tmp/.X11-unix/X{n}` for the display the script allocates, and **remove** it on cleanup — only for that display; the script neither creates nor removes `/tmp/.X{n}-lock` files (FR-010 item 3, FR-012 item 5);
- **create** a `0700` temporary directory under `$TMPDIR` and **remove** it on exit, including on failure and interruption (FR-010 item 4);
- **create** a run-log file (mode `0600`) and `0700` state directories under `$XDG_STATE_HOME` (FR-014) — and, as a consequence of the script's `umask 077`, the `dotnet build` output, the deployed mod tree and the SMAPI log the game writes are created owner-only as well;
- **create** a lock file at a stable per-user path (FR-002) and **leave it in place** afterwards;
- **terminate** a Stardew Valley/SMAPI process that the script did **not** start, when `--force` is given — SIGTERM to the identified PID, then a `--grace-period` wait, then SIGKILL; the victim's PID, executable path and start time MUST be recorded in the run log before the first signal (FR-011). The signal MUST be sent to the **identified PID only**, never to a process group the script did not create — a game started from the user's shell shares that shell's process group, and a group signal would kill the user's shell.
- **let the launched game mutate the game installation** — SMAPI itself refreshes `smapi-internal/blacklist-updated.json` and creates a `save-backups/` directory under the game directory as a side effect of being launched. These are **indirect** effects of the launch, not actions the script performs, but they are writes to the game installation and are therefore declared here.

The pre-flight MUST **not** kill Xvfb processes the script did not start; it only detects and reports them (FR-012 item 10).

## User Scenarios & Testing

### User Story 1 - Automated smoke validation of mod loading (Priority: P1)

As the maintainer, I want a script that launches the game with the mod installed and reports whether the mod loaded without errors, so that I can verify the mod works in the real game without manual play-through.

**Why this priority**: This is the immediate blocker — the mod has never been executed in the real game. Without this, no gameplay-affecting feature (spec 005 growth, quality, extra harvest) can be activated with confidence.

**Independent Test**: Can be fully tested by running the script and checking its exit code (0 = mod loaded without errors, non-zero = errors found). Delivers value by providing a repeatable, auditable signal that the mod loads correctly in the game. The save check (User Story 2) is deferred — see FR-004.

**Acceptance Scenarios**:

1. **Given** the game is installed and the mod is deployed in the mods folder, **When** the script runs, **Then** the script launches the game with SMAPI + mod, waits for initialization, checks the SMAPI log for errors, and exits with code 0 if no errors are found. The script terminates the game immediately after the log check passes (see FR-005).
2. **Given** the mod has a runtime error during load, **When** the script runs, **Then** the script detects the error in the SMAPI log and exits with a non-zero code and a descriptive message
3. **Given** the script has run successfully once, **When** the script runs again, **Then** it produces the same result (idempotent)
4. **Given** the assembly deployed into the mods directory is not the one produced by the current build, **When** the script runs, **Then** it fails before launching the game with a non-zero code and a message naming both SHA-256 digests (see FR-016)
5. **Given** a previous run left a `SMAPI-latest.txt` that already contains the mod's success marker, **When** the script runs, **Then** the stale content is not used to decide the verdict — only log lines after the current run's `Log started at` sentinel are evaluated (see FR-002)
6. **Given** SMAPI skipped the mod (for example because the installed SMAPI is older than the mod's `MinimumApiVersion`), **When** the script runs, **Then** the script reports a mod-load failure with SMAPI's stated reason (see FR-003)

---

### User Story 2 - Mod data persistence verification (Priority: P2, Deferred)

As the maintainer, I want the script to verify that the mod's data files appear in SMAPI's mod-data folder after the game loads with a save, so that I can confirm the mod's persistence layer works in the real game.

**Why this priority**: Loading without errors is necessary but not sufficient — the mod must also persist data correctly. This is the second half of the smoke test.

**Status**: Deferred. The automated script cannot load a save (SMAPI has no command-line save selection, and the mod is purely reactive). The title screen is the expected state. This user story will be implemented after the basic smoke test (User Story 1) works and the team has real usage data.

**Independent Test**: Can be fully tested by running the script and checking that SMAPI's mod-data folder for the mod (`~/.config/StardewValley/.smapi/mod-data/lfgranja.LivingRoots/`) contains the expected JSON files (`soil_health_data_*.json`, `composting_bins_*.json`). Delivers value by confirming the mod's persistence pipeline works end-to-end.

**Acceptance Scenarios**:

**Deferred scenarios — NOT implemented in this release.** These describe the behaviour of a *future* save check and are stated as future-state on purpose: the present implementation always skips the save check (FR-004), so a present-tense reading of these would contradict FR-004 and FR-006.

1. **Given** the game has a save file loaded with the mod active, **When** the save check runs, **Then** SMAPI's mod-data folder for the mod contains at least one file matching the mod's data prefix
2. **Given** the mod failed to persist data files, **When** the save check runs, **Then** the script reports the missing data files and exits with a non-zero code

### Edge Cases

- What happens when the game crashes during launch? The script should detect the crash (non-zero process exit or SMAPI-crash.txt) and report failure.
- What happens when the mods path is incorrect? The script should detect that the mod was not loaded (the mod's name is absent from SMAPI's `Loaded N mods:` block, or it appears in the `Skipped mods` section) and report failure.
- What happens when the save file does not exist yet? The save check is deferred (see FR-004). The title screen is the expected state in the automated script.
- What happens when the game takes longer than expected to load? The script should have a configurable timeout and report a timeout failure if the game does not produce a log within the expected window.
- What happens when the display (Xvfb) is not available? The script should detect this and report a clear error message.
- What happens when the game is already running? The script detects the existing process (via `pgrep`) and aborts with a descriptive error by default. An explicit `--force` flag kills the existing instance (SIGTERM then SIGKILL) before launching.
- What happens when another smoke test instance is already running? The script fails to acquire the `flock` and exits immediately with a descriptive error.
- What happens when a prerequisite is missing (game not installed, SMAPI not found, Xvfb not available)? The pre-flight phase detects it and emits an actionable error ("What → Where → How to fix") with a distinct exit code per failure category.
- What happens when the script is interrupted (Ctrl+C) during execution? The EXIT trap runs cleanup: game process killed, Xvfb killed, the socket of the display this script allocated removed, temp files cleaned. The script exits with code 130 (SIGINT) or 143 (SIGTERM).
- What happens when a previous run left a `SMAPI-latest.txt` that already contains the mod's success signal? The script MUST ignore every log line preceding the current run's `Log started at` sentinel (see FR-002), so a stale log can never produce a false pass.
- What happens when the mod build deployed into the mods directory is stale (older than the current source)? The digest assertion in FR-016 MUST fail the run before the game is launched, and the failure message MUST name both the built and the deployed SHA-256 digests.
- What happens when the game fails to create a graphics device (no usable OpenGL under Xvfb)? The script MUST report this as a graphics/environment failure (exit code `3`), not as a timeout or a mod-load failure. The pre-flight's `glxinfo` probe is expected to catch this condition before launch. **This classification MUST come from the log and the observed exit status, never from the absence of the loaded-mods block alone**: SMAPI creates the graphics device *before* it resolves any mod (`SCore.LoadMods()` runs from `InitializeBeforeFirstAssetLoaded()`), so a graphics failure means the `Loaded N mods:` block is never written and a script that classified on block-absence alone would wait out the deadline and report `4` — the very misclassification this edge case forbids. A game that exits before the verdict, whose log or exit status shows a graphics-device failure, MUST be reported as `3`. (Note that SMAPI's own "press any key to exit" path calls `Console.ReadKey()`, which throws on the `/dev/null` stdin FR-005 mandates and kills the process with `134` — a status FR-007 maps to `2`. So the graphics classification can only be reached by inspecting the log, not by branching on the status.)
- What happens when the game process exits with status `0` but no log was produced? The script MUST report failure. This occurs when SMAPI re-asserts its dependency manifest after a game update and asks the user to relaunch.
- What happens when a leftover `SMAPI-crash.txt` is present from an earlier crash? The pre-flight MUST remove it **and** SMAPI's leftover crash marker before launch (see FR-012 item 6), because SMAPI's handling of a leftover crash marker performs a keypress read that aborts the headless launch before mod resolution — and the marker is not self-clearing on that path, so every later run would fail identically.
- What happens when the resolved mods directory contains a stale copy of the mod while a current copy exists elsewhere? The script tests only the directory it resolved and passed to SMAPI via `--mods-path` (see FR-017); it does not search for other copies.
- What happens when a required host tool is missing? The pre-flight fails closed with exit code `9`, naming the tool and the package that provides it. A tool that is installed but *unusable* — for example a graphics stack with no software OpenGL — exits `3` instead, because the two conditions have different remediations.
- What happens when the script itself hits an unexpected error? The ERR trap reports the script name, failing line, enclosing function and exit code, and the script exits `13` — never with the raw status of the failing command, which under `set -e` would otherwise masquerade as a domain failure (`dotnet build` exits `1`, an unset variable exits `1`, a syntax error exits `2`).
- What happens when the mod fails to build, or when the deployed assembly does not match the fresh build? The run aborts before the game is launched with exit code `12`, naming the build error or both SHA-256 digests.

## Requirements

### Functional Requirements

- **FR-001**: The script MUST launch the Stardew Valley game via SMAPI with the mod installed, using a virtual display (Xvfb) for headless operation. The launch MUST run SMAPI's native apphost `./StardewModdingAPI --no-terminal` from the game directory (`--game-path`), which MUST be the process working directory. The rationale for running in place is that the apphost resolves its .NET runtime **relative to its own path**, and SMAPI's `Constants.GamePath` is the directory containing `StardewModdingAPI.dll` — a relocated copy of the launcher therefore fails in one of four measured ways, and the run's exit status is the only signal that distinguishes them: **154** ("The application to execute does not exist" — no `.dll` beside the apphost), **131** ("You must install .NET to run this application" — no runtime), **135** ("Could not resolve CoreCLR path" — a partial runtime), or **134** (SIGABRT — the runtime is present but the game files are not, so SMAPI's `AssertGamePresent()` calls `PressAnyKeyToExit()`, and its `Console.ReadKey()` throws `InvalidOperationException` on the `/dev/null` stdin that FR-005 mandates, producing an unhandled exception). All four are translated by FR-007's table (`134` → `2`, `135` → `13`, `131` → `2`, `154` → `2`), so a broken SMAPI installation is reported as `2` ("SMAPI not found or not functional") rather than as an internal error. The script uses SMAPI's officially supported automation env vars: `SMAPI_NO_TERMINAL=true` and `SMAPI_DEVELOPER_MODE=true`. (`SMAPI_USE_CURRENT_SHELL` is **not** used — it is read only by SMAPI's *installer wrapper*, never by `StardewModdingAPI.dll`, so it is inert when the apphost is launched directly; verified against the installed binary, whose only `SMAPI_*` literals are `SMAPI_NO_TERMINAL`, `SMAPI_MODS_PATH` and `SMAPI_DEVELOPER_MODE`.) `SMAPI_DEVELOPER_MODE` gates **console** verbosity only — SMAPI writes TRACE-level entries to the log file unconditionally, so TRACE-level diagnostics are available without it; it is retained because it makes the launch console output usable for debugging. The script MUST additionally export `LIBGL_ALWAYS_SOFTWARE=1` and `GALLIUM_DRIVER=llvmpipe` to force Mesa software rendering, and MUST set `SDL_VIDEODRIVER=x11` (never `wayland`) because the game bundles `libSDL2` and Wayland cannot be used against an Xvfb display. The script MUST also export `SDL_AUDIODRIVER=dummy` and `ALSOFT_DRIVERS=null`, to **mute the game**. Xvfb virtualizes the **display** only — it does **not** virtualize the audio device — so without these the game would open the host's real sound device (the game bundles `libSDL2-2.0.so.0`, which honours `SDL_AUDIODRIVER`, and `libopenal.so.1`, OpenAL Soft, which honours `ALSOFT_DRIVERS`) and the smoke run would play the title-screen music through the maintainer's speakers. Both variables are set together so the mute holds whichever of the two audio stacks the game initialises. Xvfb MUST be started with `-nolisten tcp` and with `-displayfd`, so that the X server itself allocates a free display (see FR-012 item 5).
- **FR-002**: The script MUST wait for the game to initialize and produce a SMAPI log file **that belongs to the current run** before performing checks. The SMAPI log path defaults to `~/.config/StardewValley/ErrorLogs/SMAPI-latest.txt` (Linux convention) and MAY be overridden via `--smapi-log`. Before launching, the script acquires an exclusive `flock` on a dedicated lock file (non-blocking) to prevent concurrent executions. If the lock cannot be acquired, the script exits immediately with a descriptive error.

  **Lock file (MUST).** The lock file MUST live at a **stable, per-user, predictable path** — `${XDG_RUNTIME_DIR}/livingroots-smoke.lock`, falling back to `${XDG_STATE_HOME:-$HOME/.local/state}/livingroots-smoke/livingroots-smoke.lock` when `$XDG_RUNTIME_DIR` is unset — inside a directory with mode `0700` owned by the current user. The path MUST NOT be inside a per-run `mktemp -d` directory: a unique directory per run means two concurrent instances lock *different inodes* and mutual exclusion is zero. The lock file MUST be opened with `exec 9<>"$lockfile"` (read-write, create-if-absent) and **not** `exec 9>"$lockfile"`, because `>` truncates and follows symlinks while `<>` neither truncates nor destroys a symlink target. The lock MUST be acquired with `flock -n 9`. The lock file MUST **not** be removed at exit: the kernel releases the lock when the descriptor closes (or the process dies), whereas removing the file detaches the name from the locked inode and re-opens the race window that a second instance would exploit. **The lock descriptor is inherited by the script's children**, so the lock is released only once the game and Xvfb have also exited — which FR-010's cleanup order (game, then Xvfb) guarantees, and which is why the cleanup MUST NOT remove the lock file while a child still holds the descriptor. The lock path MUST be on a local filesystem — `flock` is unreliable on NFS and CIFS.

  **Lock file permissions (MUST).** The lock file MUST have mode `0600`, and the directory that contains it MUST have mode `0700` and be owned by the current user. The script MUST NOT rely on the process umask alone to establish the file's mode: `exec 9<>` creates the file with mode `0666` masked by the umask, and the umask is **not** applied to a file that already exists — so the script MUST set `umask 077` (FR-014 "Umask (MUST)") before the file is created and MUST then enforce the mode with `chmod 0600 /proc/self/fd/9` — on the **open descriptor**, not on the path: a path-based `chmod` follows symlinks and can therefore act on an inode other than the one `flock` holds. The enforcement MUST use `chmod` and MUST NOT use `install -m 0600` or any write-and-replace operation: replacing the file detaches the lock from the inode the kernel is locking and re-opens the very race window this requirement closes. When the containing directory is `$XDG_RUNTIME_DIR`, the XDG Base Directory Specification already guarantees mode `0700` and sole ownership, and the script MUST NOT change that directory's permissions — the same specification requires that an already-existing destination directory's permissions are left alone. When the fallback `${XDG_STATE_HOME:-$HOME/.local/state}/livingroots-smoke/` is used, the script MUST create it with mode `0700` and MUST enforce `0700` on it with `chmod 0700`.

  **Log freshness (MUST).** SMAPI **unlinks and recreates** `SMAPI-latest.txt` at startup, so the new log has a **new inode**: the `SCore` constructor calls `PurgeNormalLogs()` (`SCore.cs:2560`), which deletes every `SMAPI-*` file in the log directory **except** the crash log (`SMAPI-crash.txt` is explicitly skipped, `SCore.cs:2573`), and only then does `LogFileManager` create the new file. SMAPI also writes an in-band per-run sentinel line near the top of every log. The sentinel's exact form MUST be `Log started at {UTC timestamp} UTC`, where the timestamp is `DateTime.UtcNow` rendered with the round-trip sortable pattern `s` — i.e. `Log started at 2026-10-19T21:01:38 UTC` (no offset, no `Z`). The script MUST therefore: (1) record the UTC launch timestamp `T0` before starting the game; (2) wait for a `Log started at` sentinel whose timestamp is **not older than `T0`**, comparing the two as UTC — the sentinel carries no offset, so the comparison MUST treat it as UTC explicitly (append `Z` when parsing, or compare as UTC epoch seconds) and MUST NOT parse it as local time, which would shift the comparison by the local UTC offset; and (3) evaluate every success and failure signal **only against log lines that follow that sentinel line**. Signals appearing before the sentinel belong to a previous run and MUST be ignored. This ordering requirement is what prevents a stale log left by an earlier successful run from producing a false pass. The sentinel is a **TRACE**-level record with source `SMAPI` (`Monitor.Log` defaults to `LogLevel.Trace`), so a parser that reads only `INFO`-and-above records would never find the run boundary; its shape is `[<ts> TRACE SMAPI] Log started at 2026-10-19T21:01:38 UTC`. **The normative freshness control is the sentinel** — the script MUST remove the stale log before launch and MUST assert that it is **absent** immediately afterwards (a failed removal MUST abort the run), because a file present at the log path when the game starts is what would allow a stale signal to be read. As a belt-and-braces assertion the script MUST record the log file's inode (`stat -c %i`) **before** the stale log is removed and verify it changed once the log is recreated — **the order of these two steps is normative**, because recording the inode after the removal would make the baseline "absent" and the assertion vacuous. The inode check is what detects SMAPI's `player-N` fallback: `GetLogPath()` writes to `SMAPI-latest.player-{n}.txt` when the default file still exists, which happens when `PurgeNormalLogs` silently swallows an `IOException` — in that case the default path still holds the **stale** log, the sentinel is absent from it, and the unchanged inode is the only signal that the purge failed.

  **Header region (MUST).** SMAPI writes the version banner and the `Mods go here:` line **before** the sentinel (`LogManager.LogIntro` order: banner → `Mods go here:` → sentinel). Those two lines are therefore **exempt** from the "only after the sentinel" rule: they MAY be read for context (reporting the installed SMAPI version and the resolved mods directory) but MUST **never** gate the verdict. Every signal that *does* gate — the `Loaded N mods:` block, the `Skipped mods` section, mod-scoped Error/Alert entries, and the crash-file override — MUST be evaluated strictly after the sentinel. The `Mods go here:` path is **tilde-anonymised** by SMAPI (`PathUtilities.AnonymizePathForDisplay` replaces the `$HOME` prefix with `~`), so any comparison against the resolved `--mods-path` MUST compare the home-relative form (`$HOME` → `~`) rather than the absolute path — **and both sides MUST be `realpath`-canonicalised before the comparison**, because SMAPI reports the *canonical* path while the script's default `--game-path` traverses the `~/.steam/steam` symlink (a real Steam install links `~/.steam/steam` → `~/.local/share/Steam`), so an un-canonicalised comparison silently never matches.

  **Pre-launch cleanup (MUST).** The script MUST remove a pre-existing `SMAPI-latest.txt` and `SMAPI-crash.txt` from the SMAPI log directory (`~/.config/StardewValley/ErrorLogs/`) before launching, and MUST also remove **both** of SMAPI's **marker** files from the **game** directory at `<game-path>/smapi-internal/`: `StardewModdingAPI.crash.marker` and `StardewModdingAPI.update.marker`. The markers are built from `Constants.InternalFilesPath` = `Path.Combine(EarlyConstants.GamePath, "smapi-internal")`, where `EarlyConstants.GamePath` is the directory containing `StardewModdingAPI.dll` — so they are **CWD-independent** and are **not** in the log directory.

  The **crash marker** is the load-bearing one: `LogManager.HandleMarkerFiles()` tests for its presence and, when present, performs a blocking `Console.ReadKey()` **before** deleting the crash log and the marker — so deleting `SMAPI-crash.txt` alone does **not** prevent the failure, and the marker is **not** self-clearing on that path. The **update marker** is load-bearing only on a **prerelease** SMAPI build (`Constants.ApiVersion.IsPrerelease()` gates its own keypress read); on the installed release 4.5.2 it is deleted silently and never prompts. It is removed anyway, so that the run does not depend on which SMAPI build happens to be installed. The script MUST log the path of every marker it removed, together with the update marker's content, so nothing is silently discarded.

  Because the script launches the game with stdin redirected from `/dev/null` (FR-005), the keypress read does **not** block: `Console.ReadKey()` throws `InvalidOperationException` when console input is redirected, and SMAPI then aborts with status `1`. The failure is therefore an **abort, not an infinite hang** — but the abort happens **before mod resolution**, so the log carries the run sentinel and **no `Loaded N mods:` block**, and the marker survives the abort and makes **every subsequent run fail identically** until it is removed. The pre-flight removal is what makes the run deterministic. (With a *terminal* stdin the read does block indefinitely, which is why the script must never give the game one.)

  **Readiness vs. exit (MUST).** If the game process exits **without** producing a log — including an exit status of `0` — the script MUST report failure, not success, with exit code `15` (FR-007). SMAPI's dependency-assertion routine exits with status `0` and the message "Please exit this window and re-launch SMAPI to play" after a game update, which would otherwise be mistaken for a successful run.

  **Two-phase wait (MUST).** The wait has two distinct phases, and conflating them makes the primary success path unreachable:
  - **Phase 1 — readiness.** The **sentinel alone** establishes that SMAPI has started and is writing the log. Nothing beyond it gates readiness, and polling for "the mod is listed" is NOT part of this phase.
  - **Phase 2 — verdict availability.** The sentinel is written by `LogManager.LogIntro()` inside the `SCore` **constructor**, while the mod-resolution output is written later, by `LogManager.LogModInfo()` from `LoadMods()` — which runs only from `InitializeBeforeFirstAssetLoaded()`, i.e. **after** the graphics device has been created. Measured on the installed 4.5.2 build, the sentinel is the third line of the log about a second after launch, but the loaded-mods block arrives **tens of seconds later** (≈14 s unloaded; 28–42 s under host load; later still when a leftover marker adds its ~20 s delay). A script that stopped waiting at the sentinel would therefore evaluate the gate **before the block exists** and report a missing `Loaded` header on every run — the success path would be unreachable.

  The script MUST therefore, after seeing the sentinel, **continue polling for the mod-resolution header** — `Loaded <N> mods:` or `Loaded 0 mods.` — **within the same deadline** (FR-009), and MUST then evaluate the gate (FR-003). The two outcomes are distinguished exactly as the round-7 decision intended:
  - the header **appears** → the gate is evaluated against it: the mod missing from the block, or present in the skipped-mods section, is a **mod-load failure** (`5`), reported with SMAPI's stated reason;
  - the header **never appears** before the deadline → a **timeout** (`4`), because SMAPI never resolved any mod at all.

  This preserves the round-7 rule — a mod-load failure is reported as a mod-load failure and not as a timeout — because the header's *presence* is what distinguishes "SMAPI resolved the mods and the mod was not among them" from "SMAPI never got that far".
- **FR-003**: The script MUST parse the SMAPI log file for errors attributable to the mod (LivingRoots).

  **Record shape (MUST).** A SMAPI log *record* is one physical line beginning with a record prefix, optionally followed by **continuation lines** that carry no prefix. The prefix is `[HH:mm:ss LEVEL SOURCE] ` — a bracket group containing a local timestamp, a **level token** and a **source**, followed by exactly one separator space, then the message. SMAPI applies the prefix **once** to the whole message (`Monitor.LogImpl`: `fullMessage = $"{prefix} {message}"`), so **the message's own leading whitespace sits after the prefix**, not at the start of the line: the skipped-mods header appears on the wire as `[<ts> ERROR SMAPI]    Skipped mods`, and an anchor of the form `^   Skipped mods` matches **nothing**.

  **The level token is variable width (MUST).** SMAPI pads it with `PadRight(Monitor.MaxLevelLength)`, where `MaxLevelLength` = 5 (the longest **public** `LogLevel` name). The six public levels therefore render as `TRACE`, `DEBUG`, `INFO `, `WARN `, `ERROR`, `ALERT` — five characters each, `INFO`/`WARN` carrying a trailing pad space, so the raw line shows `INFO  SMAPI`. The **internal** `ConsoleLogLevel` enum also contains `Critical` and `Success`, and `PadRight(5)` is a **no-op** on them, so SMAPI core can render **`CRITICAL` (8 characters)** via `Monitor.LogFatal` — which shifts the source column by three and silently mis-slices a fixed-width parse. The level MUST therefore be bound **by label, not by column**: the script MUST NOT assume a 5-character level field and MUST NOT derive the source column from a fixed offset.

  **Source (MUST).** The source is the **remainder of the bracket group** and may contain spaces. For mod-originated entries it is the mod's manifest `Name` (`Stardew Valley - Living Roots`); SMAPI falls back to the mod's relative folder path when the manifest has no `Name`. In split-screen mode a `screen_<n>` token precedes the source. Records whose source is `SMAPI` or `game` are **outside** the mod-scoped gate — this matters because SMAPI writes the skipped-mods section, the mod-update list and the Steam-achievements notice at `ERROR`/`ALERT` level from source `SMAPI`.

  **Continuation lines and line endings (MUST).** SMAPI writes a record as a single string and terminates it with **CRLF** (`LogFileManager` writes `message + "\r\n"`), while newlines **inside** the message are **bare LF** — so the log file is **mixed CRLF/LF**, and a multi-line record (an exception summary with a stack trace) is one prefixed line followed by unprefixed continuation lines. A line that does not begin with a record prefix is a continuation of the preceding record and MUST NOT be treated as a new record; it inherits no level and no source. Empty lines are **truly empty** (no prefix). Before any matching the script MUST strip the trailing carriage return into a working copy (`sed 's/\r$//'`), because GNU `grep` does **not** strip the CR on Linux and therefore **any pattern ending in `$` never matches a CRLF-terminated line** (verified).

  **Normalised record stream (MUST).** The script MUST normalise the log into a record stream of `<level>\t<source>\t<text>`, one line per physical line, with the level and source fields **empty for continuation lines**. The level and source MUST be extracted from the bracket group by label. All three gates read this stream, never the raw file. A conforming implementation uses only `sed`/`awk`/`grep` and no dependency beyond FR-012 item 8.

  **Failure markers (MUST).** Only records whose **level label** is `ERROR` or `ALERT` **and** whose **source label** equals the mod's manifest name are failure markers. The level lives **inside** the bracket group — there is no `[ERROR]` token — and MUST be compared as a label, never as a literal `[ERROR]` substring and never as a fixed-width column slice. `WARN` never fails. `TRACE` and `DEBUG` are diagnostic only.

  **Trace diagnostics (MUST).** Trace-level records from the mod are captured for diagnostics only and never fail the test. The exception **type and HResult** in a failure report come from the **mod's own** Trace records (e.g. `RegisterEvents exception type: System.InvalidOperationException (HResult: 0x80131509)`) — **not** from SMAPI: SMAPI's `ExceptionHelper.GetLogSummary` is `Exception.ToString()` and contains no HResult. Per-line timestamps carry no date and MUST NOT be used to identify a run. The mod's own success marker match is case-sensitive and exact.

  **The success gate (MUST).** The success gate is computed from SMAPI's own mod-resolution output, not from the mod's self-reported marker:
  1. **The mod MUST be listed in the loaded-mods block.** The block header is the record whose message is `Loaded <N> mods:` — **or** `Loaded 0 mods.` (**period**) when no mod loaded, because SMAPI renders `"Loaded " + count + " mods" + (count > 0 ? ":" : ".")` (`LogManager.cs:303`). Its per-mod entries are the following records whose message begins with **three** spaces (`   <Name> <Version> by <Author>`, optionally ` | <Description>`). The block ends at the first record that is not such an indented entry. The mod's manifest name MUST be matched as a **substring of the entry line** (it contains spaces) and MUST be required to be followed by a space or the end of the line. A `Loaded 0 mods.` header is a **legitimate empty block** and MUST be reported as a mod-load failure (`5`) — not as a malformed log (`13`) — so that a total mod-load failure is reported as a mod-load failure instead of being discovered only at the deadline (FR-009). A **missing** `Loaded` header entirely indicates a foreign or truncated log and MUST be reported as `13`. The separate `Loaded <N> content packs:` block MUST NOT be confused with the mods block.
  2. **The mod MUST NOT appear in the skipped-mods section.** The section header is the record whose message is **three spaces followed by** `Skipped mods` (SMAPI writes it at `ERROR` level, source `SMAPI`). The section's entries are the records whose message begins with **six** spaces followed by `- `, in the form `      - <Name> <Version> because <reason>`. The section is open from the header until the first record whose message is neither empty nor indented by at least three spaces. The ` because ` suffix MUST be required to identify a skip entry, because SMAPI's mod-warning groups write entries with the **identical** `      - <label>` shape but no `because` suffix. The skip reason is the text after ` because ` and MUST be reported verbatim.
  3. **No mod-scoped `ERROR`/`ALERT` record**, per the failure-marker rule above.

  **The manifest name MUST NOT be searched for across the whole log.** SMAPI's skip entry (`      - <Name> … because …`) and the content-pack entry's ` | for <ModID>` suffix both contain the mod's name, so an unscoped search makes a **skipped** mod satisfy leg 1 — a demonstrated **false pass** — and a mod that crashed on entry satisfy it too. Each leg MUST be evaluated only against its own section's records.

  The mod's own marker line (`The 'Stardew Valley - Living Roots' mod was loaded successfully!`) MUST still be detected and reported, but it does **not** gate success: it is emitted by the mod from its `GameLaunched` handler (`ModController.cs:959`), which runs only after the game has reached the title screen, so gating on it would couple the smoke test to a working graphics device and would report a graphics failure as a timeout rather than as the environment problem it is.
- **FR-004**: The script SHOULD verify that the mod's data files are present in SMAPI's mod-data folder for the mod (`~/.config/StardewValley/.smapi/mod-data/lfgranja.LivingRoots/`) after the game has run with a save loaded — checking for `soil_health_data_*.json` and `composting_bins_*.json`. In the current implementation the save check is always skipped (with a `SKIPPED:` warning) because the automated script cannot load a save (SMAPI has no command-line save selection, and the mod is purely reactive — it only responds to SMAPI events after a save is loaded via the title screen UI). The title screen is the expected state. The save check is deferred until the basic smoke test works and the team has real usage data; it does not gate success (see FR-006).
- **FR-005**: The script MUST terminate the game process immediately after the log check passes, without leaving orphaned processes. The script launches **each** child — the game **and** Xvfb — in its own process group and sends SIGTERM to the entire group first, waits a configurable grace period (default 15s, via `--grace-period`) for graceful exit, and escalates to SIGKILL only if the process is unresponsive. The own-process-group requirement is satisfied by enabling bash job control (`set -m`) around **each** child launch: job control gives the child a process group whose ID equals the child's PID, so `$!` is simultaneously the child's PID and its process-group ID and `kill -- -$!` signals exactly that group and nothing else. **`set -m` applies to a launch, not to the script: it MUST be enabled immediately before each child launch and disabled again immediately afterwards.** Enabling it for the whole script would make the script leave the terminal's foreground process group, so a terminal-generated SIGINT would reach the poll loop's foreground `sleep` instead of the script — the `INT` handler the trap design below requires would never run, and the script would exit `130` as a plain exit rather than dying from SIGINT (measured on bash 5.3.9 under a pty). Before any group signal the script MUST assert that the process-group ID it is about to signal differs from the script's own process-group ID and from `1` — signalling the script's own group would terminate the script itself instead of the target child. **The assertion applies to every group signal, for both children.** Because a failed assertion is a hard failure (exit `13`, with no fallback to a single-PID signal) and a child launched without `set -m` shares the script's own process group, the script MUST enable `set -m` around the Xvfb launch as well: without it the Xvfb group signal would either abort the run with `13` before Xvfb is killed — leaving it orphaned — or, if the target group were resolved from the process table, signal the script's own group and terminate the script itself. Because job control moves the child out of the terminal's foreground process group, the child no longer receives terminal-generated signals and the script's own signal-forwarding trap becomes the only path to the child. Both children MUST be launched with `&`, with their stdin redirected from `/dev/null` and their stdout/stderr redirected to the run log, and MUST be waited on with `wait -f` — a background job that touches the controlling terminal is suspended by SIGTTIN/SIGTTOU, and bash defers a trapped signal until the *foreground* command completes, so a foreground launch would delay the signal handler until the game exits. `wait -f` is used with an **explicit pid** (`wait -f "$pid"`), which blocks until that child terminates; the modifier is inert in the no-argument form, where `wait` also returns on a mere state change (measured: both forms return in milliseconds on a *stopped* job). Because FR-005 also requires `set -m` to be disabled again immediately after each launch, `-f` is inert in the prescribed design and the substantive reason to use `wait` rather than `sleep` is the deferred-trap behaviour just described. The script does NOT wait for the `Saved` event — the mod emits no observable log marker on `Saved`, making it impossible to detect externally.

  **Trap design (MUST).** The `EXIT` trap is registered **exactly once**, in the top-level shell, and is the single cleanup path: bash resets caught traps to their inherited values in subshells, so an inherited `EXIT` trap does not fire there and a subshell that owns a child process MUST clean that child up itself before exiting; no subshell may register its own `EXIT` trap (that would double-clean the shared resources). The cleanup function MUST capture `$?` as its very first statement and MUST end with `exit "$rc"`. The `INT`, `TERM` and `HUP` handlers MUST forward the signal to the child process groups and then **reset their own trap and re-raise the signal on the script itself** (`trap - SIG; kill -SIG $$`) — the script MUST die *from* the signal so the caller observes `128+N` as a genuine signal death, which is observably different from `exit 128+N` (a plain exit status; the caller cannot tell the two apart). The script MUST NOT use `trap '' INT TERM` to make cleanup uninterruptible: bash already does not re-enter a handler for the same signal, and ignoring those signals permanently would (a) make the script un-killable by SIGTERM and (b) cause every child spawned afterwards to inherit the ignored disposition across `execve`. Cleanup MUST instead be idempotent (guarded by an `in_cleanup` flag) and time-bounded. `trap - EXIT` inside the cleanup function is permitted as belt-and-braces: POSIX specifies that `exit` inside an `EXIT` trap exits immediately without recursing, but leaves the "a new `EXIT` trap is set during the `EXIT` trap" case unspecified. If the mandatory process-group assertion fails, the script MUST abort immediately with exit code `13` and a message naming both process-group IDs — it MUST NOT fall back to signalling a single PID.
- **FR-006**: The script MUST report success (exit code 0) when the log check passes. The log check uses an AND conjunction over the three legs of FR-003's success gate: **(1)** the mod is listed in SMAPI's loaded-mods block, **(2)** the mod is absent from SMAPI's skipped-mods section, and **(3)** no `ERROR`/`ALERT` record whose source is the mod. All three legs MUST be evaluated against the normalised record stream (FR-003) and against records that follow the current run's `Log started at` sentinel (see FR-002); the version banner and the `Mods go here:` line precede the sentinel and are context only (FR-002 "Header region (MUST)"). The mod's own success marker, when present, MUST be reported in the result output as a secondary signal but does not gate the verdict. The save check is deferred (see FR-004) and does not gate success in the current implementation. The success message MUST be exactly `SUCCESS: Mod loaded without errors.`
- **FR-007**: The script MUST report failure (non-zero exit code) with a descriptive message when any check fails. Failure messages MUST follow the "What → Where → How to fix" pattern: identify the failed component, the specific error, relevant log context, and an actionable remediation, emitted as a trailing `Fix:` line. **Log context (MUST).** The reported context MUST be the **matched failure record together with its continuation lines** — the record's message plus every continuation line that follows it, up to (but excluding) the next record that carries a prefix — and MUST include every mod Trace record that follows a failure record, because those carry the exception type and HResult (FR-003). A fixed `tail -N` window MUST **not** be used: a .NET stack trace is routinely 20–40 lines long, so such a window can consist entirely of stack frames while omitting the record that names the failure. When no record matched, the context MUST be the trailing **records** of the normalised stream, capped at 30 records. The context MUST be emitted from the normalised record stream (FR-003), so the trailing carriage return is not rendered as control noise. Exit codes MUST assign a distinct code per failure category: `1` = game installation not found, `2` = SMAPI not found or not functional, `3` = graphics environment present but unusable, `4` = timeout, `5` = mod load failure, `6` = lock contention, `7` = process conflict, `9` = missing host tool or runtime dependency, `10` = virtual display could not be allocated or started, `11` = Steam API prerequisite missing, `12` = build or artifact-identity failure, `13` = internal script error, `14` = usage or CLI-argument error, `15` = the game produced no SMAPI log, `16` = mods path or mod manifest invalid, plus the POSIX `128+N` interruption codes (`130` = SIGINT, `143` = SIGTERM, and `129` = SIGHUP) and `0` = success. This is a bespoke, one-code-per-failure-class scheme — it is NOT the `sysexits.h` numbering, which begins at `EX__BASE` = 64 and has been deprecated by FreeBSD and OpenBSD; the phrase "sysexits.h convention" MUST NOT be used to describe these values.

  **Allocation rule (MUST).** Codes are allocated **additively** and permanently: a **published code MUST NOT be re-assigned** to a different failure class, and a **retired code MUST NOT be reused**. A new category takes the **next value above the highest published code** — not the next numerically unused value — so the retired value `8` can never be handed out again. The retired set is: `8` (retired in round 2, superseded by the POSIX `128+N` interruption codes; never reused). The remaining published codes are `1`–`7` and `9`–`16`.

  **No subprocess-specific status may ever become the script's final code.** Every child status MUST be translated into one of the categories above before the script exits, using this table: `0` → `0`; `timeout`'s native `124` → `4`; `timeout`'s `125` (the timeout utility itself failed) → `13`; `126` (found but not executable) → `9`; `127` (not found) → `9`; `131` (the .NET runtime could not be started by the SMAPI apphost) → `2`; `134` (SIGABRT) → `2`; `137` (SIGKILL) → `5` when it is the game process, `2` when it is the SMAPI apphost and `13` otherwise; `154` (the SMAPI apphost cannot find its own assembly) → `2`; `128+N` for SIGINT/SIGTERM/SIGHUP delivered to the script itself → `128+N`, unchanged; any other non-zero status → `13`. A pre-flight probe that fails is translated by the **category of the probe**, not by the raw status the probe happened to return. An unhandled error caught by the ERR trap exits `13`; a failed mod build or a build/artifact digest mismatch exits `12` (see FR-016); a failed PGID assertion exits `13` (see FR-005).
- **FR-008**: The script MUST be idempotent — running it multiple times in sequence produces the same result
- **FR-009**: The script MUST accept a configurable timeout for the **game-launch-to-verdict window** via command-line argument (`--timeout`), with a 120-second default. The timeout MUST be measured **from the instant the game process is launched** — the timestamp recorded at launch, **not** the script's start time — and it MUST bound **the whole two-phase wait** (FR-002): the wait for the run sentinel and the subsequent wait for the mod-resolution header. The script MUST NOT count the pre-flight or the rebuild-and-verify phase against this budget; those phases are bounded separately (FR-016). The script MUST NOT treat the timeout as a whole-script deadline and MUST NOT report a phase overrun as a timeout. The script polls the log continuously (no wasted time), and the timeout only matters for failure cases. The timeout MUST be enforced by a **deadline poll loop** over the SMAPI log (`deadline=$(( $(date +%s) + timeout ))`), which MUST check the deadline before each iteration and MUST exit with `4` when it expires. The `timeout` utility MAY be used to bound the poll as a belt-and-braces wrapper, but it MUST **not** wrap the game launch: the game MUST be a direct background child of the script, so that `$!` is simultaneously the game's PID and its process-group ID (FR-005).
- **FR-011**: The script MUST detect an existing Stardew Valley/SMAPI process before launching. By default, the script aborts with a descriptive error listing the conflicting PIDs. An explicit `--force` flag kills existing instances (SIGTERM → SIGKILL escalation) before launching. **The signal MUST be sent to the identified PID only**, never to a process group the script did not create: a game started from the user's shell shares that shell's process group, so a group signal would terminate the user's shell. The victim's PID, executable path and start time MUST be recorded in the run log before the first signal. This is a correctness requirement: the mod has no cross-process data file locking, so concurrent instances would corrupt data and truncate the SMAPI log. Identification MUST be **by executable path, not by process-name matching**: a candidate PID qualifies only when `/proc/$PID/exe` resolves to an executable under the resolved game directory — the `StardewModdingAPI` apphost or the `StardewValley` game binary. **The comparison MUST use the canonicalized game directory on both sides**: bash's `$PWD` is *logical*, while `/proc/$PID/exe` and `/proc/$PID/cwd` are always *physical*, and the Steam installation is commonly a symlink chain (`~/.steam/steam` → `~/.local/share/Steam`), so comparing `/proc/$PID/exe` against the raw `--game-path` string or against `$PWD` would silently never match — and the concurrent-instance corruption this requirement exists to prevent would go undetected. `pgrep -x` MUST NOT be used for the apphost: the kernel's process name (`comm`) is truncated to 15 characters and `StardewModdingAPI` is 17, so an exact-name match can never succeed and would silently never match. `pidof` matches on the untruncated name and on `/proc/$PID/exe` and is the acceptable alternative. A PID the script itself spawned needs no identity check — an unreaped child stays a zombie and the kernel does not recycle a zombie PID — but **any PID discovered by scanning the process table MUST be verified before it is signalled**.
- **FR-012**: The script MUST include a pre-flight phase before launching that validates, **in this order** — the cheapest, most dependency-free checks first, and no check that depends on a tool or resource before that tool or resource has been verified present.

  **(0) Order (MUST).** (a) required-host-tool presence (item 8); (b) game installation and SMAPI markers (items 1–2); (c) Steam prerequisite (item 9); (d) crash-marker removal (item 6); (e) start the virtual display and probe software OpenGL (items 4–5). The build-and-verify step (FR-016) then runs, then the flock, then the existing-process check, then the log baseline, then the game launch. No check may run before the tools it needs are verified present, and the display MUST NOT be started before the tool sweep has confirmed `Xvfb`, `xdpyinfo` and `glxinfo` are installed.

  (1) the game installation exists at the expected path (configurable via `--game-path`, default `~/.steam/steam/steamapps/common/Stardew Valley/`) and contains the game assembly (`Stardew Valley.dll`) and SMAPI's launcher (`StardewModdingAPI`); (2) SMAPI is installed and functional — this means the main assembly `StardewModdingAPI.dll` is present and its version can be parsed, the dependency assemblies `smapi-internal/SMAPI.Toolkit.dll` and `smapi-internal/SMAPI.Toolkit.CoreInterfaces.dll` are present, and the `StardewModdingAPI` apphost is executable for the host architecture. No SMAPI release ships a file named `smapi-internal/SMAPI.dll`; probing for that path produces a false negative on a correct installation, so the check MUST use the paths listed here; (3) Xvfb is available and runnable (`command -v Xvfb` plus a version probe) — an absent `Xvfb` binary is a **missing host tool** and exits `9` (see item 8), not `3`; (4) software OpenGL rendering is genuinely usable — the probe is **layered**: (4a) `xdpyinfo` exits `0` and its output contains the `GLX` and `RANDR` extensions; (4b) `glxinfo -B` under `LIBGL_ALWAYS_SOFTWARE=1` exits **`0`** — note that `glxinfo` exits **255** on failure, not `1`, so the probe MUST branch on "exit 0" and never on a specific status — a zero exit is the proof that a real GLX context could be created; (4c) the `OpenGL renderer string` reported by `glxinfo -B` MUST match `llvmpipe` or `softpipe` — the mere presence of `libGL.so` does NOT satisfy this check, and neither does a hardware or `zink` renderer; (4d) **the game-specific capability MUST also be asserted**: full `glxinfo` (or `glxinfo -s`) MUST report `GL_ARB_framebuffer_object` or `GL_EXT_framebuffer_object`, or the `OpenGL version string` MUST be ≥ 3.0. This layer is load-bearing: the game's graphics backend (MonoGame) throws `PlatformNotSupportedException: MonoGame requires either ARB_framebuffer_object or EXT_framebuffer_object` when a context lacks FBOs, and `glxinfo -B` prints **no extension list**, so it cannot detect that failure class. A failure of this probe, **with `Xvfb`, `xdpyinfo` and `glxinfo` all present**, is a graphics environment that is present but unusable and exits `3`; (5) **the virtual display MUST be allocated by the X server itself**, using `Xvfb -displayfd` — the script MUST NOT choose a display number, MUST NOT probe, create or remove `/tmp/.X{n}-lock` files, and MUST NOT implement the lock liveness protocol. Rationale: `-displayfd` makes the server bind the first free display **atomically** (its `CreateWellKnownSockets()` loop) and it **disables the server lock** entirely — parsing `-displayfd` sets `nolock = TRUE`, so `LockServer()` returns without writing any `/tmp/.X{n}-lock` file — so no lock file exists to manage; a harness-created lock file is at best useless and at worst a local denial-of-service vector (the server installs its own lock atomically via `link()` from `/tmp/.tX{n}-lock`). The script MUST read the allocated display number back from the descriptor and record it for the cleanup phase. If Xvfb fails to start, or reports no display number, the run MUST abort with exit code `10`; (6) **crash- and update-marker removal** — the script MUST delete `<game-path>/smapi-internal/StardewModdingAPI.crash.marker` and `<game-path>/smapi-internal/StardewModdingAPI.update.marker` if present, and MUST log each removal (with the update marker's content, if any). These are SMAPI's prompt-for-a-keypress markers: their presence makes SMAPI call `Console.ReadKey()` during startup, which with stdin redirected from `/dev/null` aborts the launch with status `1` (and with a terminal stdin blocks indefinitely). The markers live in the game's `smapi-internal/` folder, **not** in the SMAPI log directory, and deleting `SMAPI-crash.txt` alone does not suffice. The pre-flight MUST also verify that the SMAPI log directory is **writable**, because SMAPI aborts in its constructor if it cannot purge the previous log (the exact exit status in that case is **not** measured and MUST NOT be assumed — the script classifies it from the log and the observed status, not from a predicted code); (7) **every path the script constructs is validated**: it MUST be canonicalized with `realpath` — **`-e` (`--canonicalize-existing`) where the path must already exist, `-m` (`--canonicalize-missing`) where it need not**, because the default `-E` requires every component but the last to exist and therefore fails on exactly the paths the script mutates (the deploy target FR-016 (b) deletes, the crash marker FR-012 item 6 deletes, and a clean machine's `--mods-path`) — and MUST satisfy a **component-boundary** prefix test against the intended base (`case "$real" in "$base"/*`) — a reject-on-`..` test after canonicalization is dead code, because `realpath()`'s definition excludes `..` by construction. **The base used in the prefix test MUST itself be canonicalized and MUST NOT carry a trailing slash**, because a base that keeps one produces the pattern `…/Stardew Valley//*`, which never matches. **Any character-class test MUST use a negated glob class (`*[!A-Za-z0-9._-]*`) or an extended regular expression (`[[ … =~ … ]]`) and MUST NOT use a positive `case` class**: in `case`, `[A-Za-z0-9._/-]` is a *character class* matched against the first character, so `case "/etc/passwd" in [A-Za-z0-9._/-]*)` matches every path — the check would accept everything (verified). User-supplied roots (`--game-path`, `--mods-path`, `--smapi-log`) are **their own bases**: they MUST be resolved with `realpath -e` for existence (bare `realpath` defaults to `-E`, which does **not** verify the final component and exits `0` for a missing or dangling one), but MUST NOT be prefix-checked against the game directory — an absolute `--mods-path` outside the game directory is legal (FR-017). Path components MUST match the allowlist `[A-Za-z0-9._/-]+`. **No Unicode normalization is performed and no normalizer dependency is required** — NFC is a provable no-op for ASCII paths (UAX #15: "Text exclusively containing ASCII characters is left unaffected by all of the Normalization Forms") and is not a homoglyph defence (that requires UTS #39); the ASCII allowlist is strictly stronger and dependency-free; (8) every required host tool is present. The required set is: `bash` (4+), `Xvfb`, `xdpyinfo`, `glxinfo`, `flock`, `timeout`, `mktemp`, `stat`, `realpath`, `pgrep` (or `pidof`), `sha256sum`, `date`, `grep`, and `dotnet` (required by FR-016's rebuild). Each MUST be verified with `command -v`; a missing one MUST fail closed with exit code `9` and name the tool. A required tool that is present but **unusable** is a different category — for example an `Xvfb` that is installed but whose display stack cannot provide software OpenGL exits `3`, not `9`; (9) the Steam prerequisite is satisfied — `<game-path>/steam_appid.txt` MUST exist and contain the app id `413150`; its absence or a wrong id MUST fail closed with exit code `11`, and this is the only condition that can raise that code; (10) **orphaned displays are detected, not cleaned (MUST).** The pre-flight MUST **detect** Xvfb processes other than the one this run starts, and MUST **report** them (PID, `/proc/$PID/exe` path, `/proc/$PID/stat` start time, owning UID) in the run log and on stderr. It MUST **not** signal them. The script **cannot** prove ownership of a foreign X server: under `Xvfb -displayfd` the server sets `nolock = TRUE` (xorg-server `os/utils.c`) and `LockServer()` returns without writing `/tmp/.X{n}-lock`, so no filesystem record of display ownership exists; and the display number is allocated by the server, so the script never chose it. Signalling a PID discovered by scanning the process table also violates FR-011's identity rule, which no foreign Xvfb can satisfy. This item supersedes the round-2 clarification "Clean up orphaned resources from prior crashed runs? → Yes, pre-flight cleanup with logging", whose rationale — a fixed `:99` display that an orphan would block — no longer holds now that the server allocates the display atomically.
- **FR-010**: The script MUST clean up temporary resources on exit, including on failure and interruption. Cleanup includes: (1) kill the **game process group** (SIGTERM → SIGKILL escalation), (2) kill the **Xvfb process group** (SIGTERM → SIGKILL escalation) — **both by group signal, because both children are launched under `set -m` and therefore each has a process group whose ID equals its PID (FR-005); the same mandatory PGID assertion applies to each of the two group signals, and a failure of either assertion aborts the run with `13` rather than falling back to a single-PID signal**, (3) remove the virtual display's socket (`/tmp/.X11-unix/X{n}`) — but ONLY for the display this script allocated (`{n}` = the number reported by `Xvfb -displayfd`). The script MUST NOT create or remove `/tmp/.X{n}-lock` files: under `-displayfd` the server writes no lock file at all (parsing `-displayfd` sets `nolock = TRUE`, so `LockServer()` returns without writing one), and the server installs any lock it does write atomically via `link()` from `/tmp/.X{n}-lock`'s staging file, so a harness-managed lock is at best useless and at worst a local denial-of-service vector. (Xvfb removes its own artifacts on SIGTERM/SIGINT and on a fatal error, so this step is a no-op on the normal path and load-bearing only after a SIGKILL escalation), (4) remove temp files/directories, (5) the flock is auto-released by the kernel on process death — the lock **file** is deliberately **not** removed, because removing the name detaches it from the locked inode and re-opens the race window for a second instance (see FR-002). Each cleanup step MUST be isolated (guarded with `|| true`) so one failure does not prevent others. The cleanup order is reverse of allocation: game first, then Xvfb, then the socket and temp files. **Neither group signal may be skipped on the grounds that the child is "obviously" still running: an omitted Xvfb group signal is exactly the orphan the cleanup exists to prevent.**

- **FR-013**: The script MUST remain local-first: no CI integration and no machine-parseable (`--json`) output mode in the current scope. Proper exit codes (0/non-zero) are retained so future CI integration is straightforward.
- **FR-014**: The script MUST log every process lifecycle event with a timestamp and level prefix — spawn (game, Xvfb), every signal sent (including the PID and the signal), the grace period, the escalation to SIGKILL, and the observed exit — so that a failed run can be reconstructed from the run log alone. On any unhandled error, the ERR trap MUST report the script name, the failing line number, the enclosing function name, and the exit code.

  **Shell options (MUST).** The script MUST run under `set -Eeuo pipefail`. The `-E` (`errtrace`) is load-bearing and not optional: without it the `ERR` trap is **not inherited by shell functions**, so the trap could not report the enclosing function name that the paragraph above requires. The `-e` supplies the automatic exit that the trap's `13` contract relies on (`set +e` still fires the `ERR` trap, but nothing then aborts the script). `-u` forbids unset-variable reads, `-o pipefail` forbids a pipeline from reporting the status of its last element alone, and job control (`set -m`) is enabled separately and only around the launch (FR-005).

  **Umask (MUST).** The script MUST set `umask 077` before it creates any file or directory. The umask is inherited by every child process (`umask(2)`: "A child process created via fork(2) inherits its parent's umask"), so this also constrains the `dotnet build` output, the deployed mod tree and the SMAPI log the game writes — all created by the same user and all remaining readable by that user. The umask is a **default, not a guarantee**: it does not change the mode of a file or directory that already exists, and `mkdir -p` does not chmod an existing directory, so every artifact the script creates MUST additionally have its mode enforced explicitly with `chmod` (FR-002, FR-014).

  **Run log (MUST).** The script's own diagnostic output is the **run log**, and it is distinct from the SMAPI log. The run log MUST be written to a file at `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/<run-id>.log`, in a directory created with mode `0700`. Each run MUST write its own file (no shared append-only file) so that concurrent runs cannot interleave. The run log MUST contain every line the script emits at any level, including the lifecycle events above.

  **Run log permissions (MUST).** The run log file MUST have mode `0600`, and **every** directory level of the run-log path below the XDG base — `living-roots-smoke/` **and** `runs/`, not only the leaf — MUST have mode `0700` and be owned by the current user. A directory's mode is **not** inherited by the files inside it: a shell redirection creates the file with mode `0666` masked by the umask, so under the default umask `022` the log file would be `0644` even inside a `0700` directory. The script MUST set `umask 077` (FR-014 "Umask (MUST)") before creating the run-log path, MUST enforce `0700` on each directory level it creates with `chmod 0700` — because `mkdir -p` does not change the mode of an already-existing directory, and `mkdir -p -m 0700` applies the mode to the **final path component only**, leaving the intermediate level world-traversable — and MUST enforce `0600` on the log file with `chmod 0600` after it is opened. The XDG Base Directory Specification pins the mode of `$XDG_RUNTIME_DIR` but **not** of `$XDG_STATE_HOME`, so the script — not the environment — is responsible for the run-log path's mode.

  **Phase timings (MUST).** The run log MUST record, for each phase — pre-flight, rebuild-and-verify, launch, readiness wait, verdict, termination, cleanup — the start timestamp, the end timestamp and the elapsed seconds, and the stdout summary MUST print the total wall time and each phase's duration. This makes the configured budgets auditable after the fact.

  **Run ID and version (MUST).** The script MUST generate a run ID of the form `<UTC timestamp>-<PID>` (e.g. `20261019T183302Z-48213`) and MUST stamp it on every run-log line, in the stdout summary, in every error message, and in the path of the run log file. The script MUST define a `VERSION` constant (first release `0.1.0`) and MUST report it in the stdout summary, in the run-log header, and in the `--help` output. The run ID and `VERSION` are the correlation keys required by the escalation evidence bundle.

  **Streams (MUST).** The verdict and the `--help`/`--version` output go to stdout; all level-prefixed diagnostics and error messages go to stderr. The exit code remains the sole machine-readable signal (see FR-013).
- **FR-015**: The script's `--help` output MUST document the automation environment variables it sets (`SMAPI_NO_TERMINAL=true`, `SMAPI_DEVELOPER_MODE=true`, `LIBGL_ALWAYS_SOFTWARE=1`, `GALLIUM_DRIVER=llvmpipe`, `SDL_VIDEODRIVER=x11`, `SDL_AUDIODRIVER=dummy`, `ALSOFT_DRIVERS=null`, and `DISPLAY`) in a dedicated "Environment (set automatically)" section, stating explicitly that they are managed by the script and are not user-configurable. The `--help` output MUST also document the `--mods-path` option (see FR-017), the `--mod-project` option (see FR-016), the run-log location, the run ID format, the script `VERSION`, and every exit code. It MUST also provide `--version` (printing `<name> <VERSION>` to stdout and exiting `0`) and MUST accept `-h` as an alias for `--help` — GNU Coding Standards §4.8: "All programs should support two standard options: `--version` and `--help`", both on stdout and exiting successfully.
- **FR-016**: The script MUST ensure that the mod build under test is the build it just produced, and MUST abort before launching the game if it cannot. This is a **deploy-effectiveness** assertion, not a source-correspondence claim: the mod assembly carries no build identity — `manifest.json` declares a fixed `Version` (`0.0.1`), the assembly declares a fixed `AssemblyVersion` (`1.0.0.0`), no commit identifier is embedded, and `SourceRevisionId` is inert because the project sets `GenerateAssemblyInfo=false` — so no digest of the assembly can prove *which* source tree produced it. What the script CAN prove, and MUST, is that **the assembly the game will load is byte-identical to the assembly this run just built**.

  **(a) Locate the project (MUST).** The mod project MUST be configurable via `--mod-project`, defaulting to `<repo-root>/LivingRoots/LivingRoots.csproj`, where `<repo-root>` is derived from the script's own location (`SCRIPT_DIR/..`). The path MUST be resolved with `realpath` and MUST satisfy the component-boundary prefix test of FR-012 item 7 against the repository root.

  **(b) Build (MUST).** The script MUST run `dotnet build --configuration Release --no-incremental` in the project directory, MUST remove the deploy target directory `<mods-path>/<ModFolderName>/` **before** the build, and MUST abort with exit code `12` if the build fails. **The build MUST itself be bounded** by a configurable `--build-timeout` (default: 300 seconds), enforced the same way as the readiness wait (a deadline poll loop, or GNU `timeout` around the `dotnet build` invocation); expiry MUST abort the run with exit code `12` and a message naming the elapsed time. The build timeout is **independent** of `--timeout` and MUST NOT be consumed from it — the rebuild is currently unbounded, so a hung NuGet restore would hang the run forever. The removal is required because `Pathoschild.Stardew.ModBuildConfig`'s deploy task copies but never deletes, so a stale file from a previous build could otherwise survive. **The removal MUST use the form `rm -rf -- "$target"` with no trailing slash**: a trailing slash makes `rm` follow a symlinked final component and delete the *target's contents* rather than the link itself (verified). The target's parent MUST be re-canonicalized immediately before the removal (FR-012 item 7).

  **(c) Pin the deploy target (MUST).** The build MUST be invoked with `-p:GameModsPath="<resolved mods-path>"`, so that `ModBuildConfig` deploys into exactly the directory the script resolved — and therefore into the directory SMAPI will load from. Without this, `GameModsPath` defaults to `$(GamePath)/Mods` where `GamePath` is **auto-detected** from ~15 candidate locations, the build deploys somewhere the script may not be able to name, and the comparison in (d) is against an unrelated copy.

  **(d) Compare (MUST).** After the build the script MUST compute the SHA-256 digest of the freshly built assembly (`<mod-project-dir>/bin/<EntryDll>` — the project sets `OutputPath=bin/` with `AppendTargetFrameworkToOutputPath=false`, so the output is `bin/LivingRoots.dll`, not `bin/Release/net6.0/`) and the SHA-256 digest of the deployed assembly (`<mods-path>/<ModFolderName>/<EntryDll>`), and MUST abort with exit code `12` — naming **both** digests — if they differ, if either is missing, or if the deployed file is **strictly** older than the build. (The comparison MUST be *strictly* older: MSBuild's copy preserves the source modification time, so in the happy path the two timestamps are identical and a non-strict "older" test would compare equal; the digest comparison does the real work.) This is the standard within-run "did the deploy take effect?" assertion (the file-integrity-monitoring / SLSA subject-digest pattern); a digest is NEVER compared across runs, because the .NET compiler's deterministic content hash — and therefore the PE timestamp and the module version id — is a function of the absolute source path, so two builds of identical source at different paths legitimately differ.

  The deployed manifest version alone MUST NOT be used as the freshness assertion, because it is invariant across builds.
- **FR-017**: The script MUST resolve the mods directory explicitly and MUST NOT depend on SMAPI's implicit default. The mods directory MUST be configurable via `--mods-path`, defaulting to `<game-path>/Mods`. The script MUST pass the resolved directory to SMAPI using the `--mods-path` argument (equivalently `SMAPI_MODS_PATH`); the CLI argument is **normative** and takes precedence over the environment variable, matching SMAPI's own behaviour (upstream reads the argument first and consults the environment variable only when the argument is empty). A relative `--mods-path` value MUST be resolved against the game directory, matching SMAPI's own semantics; an absolute one is accepted as-is and is its own base (FR-012 item 7). The resolved directory MUST be passed to the build as `-p:GameModsPath` so that the build deploys into exactly the directory SMAPI loads from (FR-016 (c)). **Verification of the mod folder (MUST).** The check that the resolved directory contains the mod folder (`<ModFolderName>/manifest.json` with a matching `UniqueID`) MUST run **after** the build-and-verify step (FR-016), not before it: FR-016 removes and recreates the deploy target, so a check placed before the build would fail on a clean machine. A failure of this check — missing directory, missing `manifest.json`, malformed manifest, or `UniqueID` mismatch — exits with code `16`.
### Key Entities

- **SMAPI Log**: The log file produced by SMAPI at `~/.config/StardewValley/ErrorLogs/SMAPI-latest.txt` (Linux). Entries follow a **record** shape: one physical line beginning with the prefix `[HH:mm:ss LEVEL SOURCE] ` followed by the message, optionally followed by **continuation lines** that carry no prefix. The level is a **variable-width label** (the six public levels render 5 characters wide; SMAPI core can also render `CRITICAL`, 8 characters), the source is the remainder of the bracket group and may contain spaces, records are terminated with **CRLF** while newlines *inside* a message are **bare LF** (so the file is mixed CRLF/LF), and the script MUST normalise the file and bind the level and source **by label** — see FR-003's record-shape contract. The script parses this to (a) detect SMAPI's mod-resolution output (the loaded-mods block and the `   Skipped mods` section — the skipped-mods header carries **three** leading spaces and its entries **six**), (b) detect the mod's own success marker ("The 'Stardew Valley - Living Roots' mod was loaded successfully!" — emitted by the mod, not by SMAPI), and (c) detect any Error/Alert entries attributable to the mod. The log begins with a per-run sentinel line `Log started at {UTC timestamp} UTC` — a **TRACE**-level record, so a parser that reads only `INFO`-and-above would never find the run boundary; only lines after that sentinel belong to the current run. `SMAPI-crash.txt` (if present) overrides `SMAPI-latest.txt` and indicates failure.
- **Loaded Mods Manifest**: SMAPI's own report of the mods it resolved, emitted in the log as a `Loaded N mods:` block (or `Loaded 0 mods.` when none loaded) with one `   <Name> <Version> by <Author>` line per mod (optionally suffixed ` | <Description>`), followed by an optional `   Skipped mods` section — the header literal carries **three** leading spaces and each entry is indented **six** — naming the reason for each skip (for example "because it needs SMAPI X or later"). This is the authoritative signal for whether the mod was loaded, and it is available without the game having reached the title screen. The same log also records the resolved mods directory (`Mods go here: <path>`, `~`-anonymised) and the SMAPI version banner (`SMAPI <version> with Stardew Valley <version> on <os>`) — both of which precede the run sentinel and are therefore **context only**, never gating (FR-002 "Header region (MUST)").
- **Mod Build Artifact**: The compiled mod assembly `LivingRoots.dll` and its manifest, deployed by the build into the resolved mods directory (`<mods-path>/LivingRoots/`). The assembly carries no build identity — `manifest.json` declares a fixed `Version` (`0.0.1`), the assembly a fixed `AssemblyVersion` (`1.0.0.0`), and no commit identifier is embedded — so the artifact's freshness is established by the **deploy-effectiveness** assertion of FR-016: the deployed assembly's SHA-256 digest MUST equal the digest of the assembly produced by the current build, with the deploy target pinned to the resolved mods path. Two copies of this artifact may coexist in the workspace (a repository-local `.gamepath/Mods/` copy and the copy in the game installation); only the copy in the resolved mods path is under test.
- **Mod Data Files**: The mod persists data as JSON sidecar files written through SMAPI's `IModHelper.Data.WriteJsonFile`, which resolves relative names against SMAPI's mod-data directory — `~/.config/StardewValley/.smapi/mod-data/<UniqueID>/` (here `<UniqueID>` = `lfgranja.LivingRoots`). The files are named `soil_health_data_<sanitizedSaveId>.json`, `composting_bins_<sanitizedSaveId>.json`, and `visualization_config_<sanitizedSaveId>.json`. The saveId is SMAPI's active save folder name (`Constants.SaveFolderName`), sanitized via Unicode normalization and filename sanitization. The mod does **not** write into a `data/` folder inside its own mod folder — that location is not used by SMAPI's helper API. When no save is loaded (fresh install/title screen), zero data files is the expected valid state.
- **Game Process**: The Stardew Valley process launched via SMAPI. The script manages this process lifecycle (launch, wait, terminate). Termination happens immediately after the log check passes. The script sends SIGTERM first, waits a brief grace period for graceful exit, and escalates to SIGKILL only if the process is unresponsive. The script does NOT wait for the `Saved` event — the mod emits no observable log marker on `Saved` (`ModController.cs:1089-1102`), making it impossible to detect externally.
- **Virtual Display**: The Xvfb display buffer that allows the graphical game to run headless. The script manages this resource lifecycle, but does **not** choose the display number — Xvfb allocates a free display itself via `-displayfd` and reports it back (FR-012 item 5).
- **Run Log**: The script's own diagnostic output, written per run to `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/<run-id>.log` (see FR-014). It records every lifecycle event with a timestamp, level prefix, and run ID. It is distinct from the SMAPI Log and survives the run, so a failure can be reconstructed afterwards.

## Success Criteria

### Measurable Outcomes

- **SC-001**: From a clean state (no prior game process, no Xvfb), the script launches the game and produces a pass/fail verdict **within the configured readiness timeout (default: 120 seconds) measured from the instant the game process is launched**. The timeout bounds **only the wait for the current run's `Log started at` sentinel** (FR-002, FR-009); it does **not** include the pre-flight or the rebuild-and-verify phase, which runs before the launch and is bounded separately by `--build-timeout` (default: 300 seconds, FR-016). The script reports the measured duration of every phase and the total wall time in the run log (FR-014), so both budgets are auditable after the fact.
- **SC-015**: The script is **idempotent** (FR-008): executed twice in sequence from the same starting state, it produces the **same exit code and the same verdict**. This is a **repeat** property and is therefore **not** established by a single run; it is verified by executing the script twice and comparing the two verdicts. The runs MUST use the same inputs (same `--mods-path`, same `--mod-project`, no `--force`).
- **SC-002**: When the mod loads without errors, the script exits with code 0 and reports exactly `SUCCESS: Mod loaded without errors.` — this is the expected baseline after a correct mod build
- **SC-003**: When the mod has a load-time error, the script exits with a non-zero code and reports the specific error message from the SMAPI log
- **SC-004**: *(Deferred — see FR-004. Not gating in this release.)* When the mod loads but does not persist data files to SMAPI's mod-data folder, a future implementation of the save check will exit with a non-zero code and report the missing data files. In the current version the save check is always skipped with a `SKIPPED:` warning and does not gate success; this criterion is therefore **not evaluated** by any run and MUST NOT be read as a failure.
- **SC-005**: *(Deferred — see FR-004. Not gating in this release.)* The mod's **load** half is evaluated by this script: a successful run establishes that the mod resolves and loads in the real game. The mod's **persistence** half is not evaluated at all, because no save is loaded. This criterion therefore covers only the load half; it does **not** discharge, and makes no claim about, any criterion in spec 004 — 004's SC-008 is a manual-playtest *discoverability* criterion that states "No automated task covers this criterion", and is unrelated to persistence.
- **SC-006**: The quickstart guide documents every exit code in the FR-007 taxonomy with its cause and its remediation, lists every required host tool and every CLI option, and provides a troubleshooting ladder that maps every symptom to a check with an explicit expected result. These properties are verifiable by reading `quickstart.md` and are exercised by TC-1…TC-17.
- **SC-007**: When the game is already running, the script detects it and aborts with a descriptive error (or kills it with `--force`)
- **SC-008**: When another smoke test instance is already running, the script fails to acquire the flock and exits immediately
- **SC-009**: When a prerequisite is missing, the pre-flight phase detects it and emits an actionable error with a distinct exit code
- **SC-010**: When the script is interrupted (Ctrl+C), the EXIT trap runs full cleanup (game, Xvfb, the socket of the display this script allocated, temp files) and exits with code 128+N
- **SC-011**: When a previous run left a `SMAPI-latest.txt` containing the mod's success marker, the current run does NOT report success from that stale content — the verdict is derived only from lines following the current run's `Log started at` sentinel
- **SC-012**: When the assembly deployed into the resolved mods directory is missing, is not byte-identical to the assembly produced by the current build, or is older than that build, the script exits with code `12` **before** launching the game, and the failure message names both SHA-256 digests
- **SC-013**: The success verdict is derived from SMAPI's `Loaded N mods:` / `   Skipped mods` output (the skipped-mods header carries three leading spaces — see FR-003 "Exact anchors"); a mod that SMAPI skipped (for example for an unmet `MinimumApiVersion`) is reported as a mod-load failure with SMAPI's stated reason, even though the game itself started successfully
- **SC-014**: Every run produces a retained run log under `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/` containing the run ID, the script `VERSION`, the launch timestamp, and every lifecycle event, such that the run can be reconstructed from that file alone

- Evidence-resolved: `research.md` carried four statements that contradicted the normative artifacts — `SMAPI_DEVELOPER_MODE` "enables TRACE-level logging" (it gates console verbosity only), `pgrep` with "exact process name matching" (FR-011 forbids `pgrep -x`), `BashFAQ/062` as the trap citation (`BashFAQ/047` is correct), and "written to the mod's own data folder" (SMAPI's mod-data directory). FR-005, FR-010 and `plan.md` now require `set -m` around **each** launch, scoped to it.

The X11 Unix socket therefore carries Xorg's default permissions, and any local user could attach to the display. `-nolisten tcp` removes the network exposure. This residual risk is **accepted** on the grounds that the script runs on a single-user maintainer machine (plan.md → Target Platform); it is recorded here so the risk is explicit rather than implicit.
- The mod is deployed into the resolved mods directory (default `<game-path>/Mods`) by the build; the script rebuilds and redeploys it before each run, with the build's deploy target pinned to the resolved mods path via `-p:GameModsPath` (FR-016). The repository-local `.gamepath/Mods/` copy is a build-output artifact and is **not** the copy under test
- The mod assembly carries **no** source-tree identity: `manifest.json` declares a fixed `Version` (`0.0.1`), the assembly a hardcoded `AssemblyVersion` (`1.0.0.0`), no commit identifier is embedded, and `SourceRevisionId` is inert because the project sets `GenerateAssemblyInfo=false`. FR-016 therefore asserts **deploy effectiveness** (the deployed assembly is byte-identical to the one this run built), not source correspondence; the latter would require changing `LivingRoots.csproj` and is out of scope
- The host paths used by the script are expected to be **ASCII**: path components are validated against `[A-Za-z0-9._/-]+` and no Unicode normalization is performed. This is a deliberate trade — NFC normalization is a provable no-op for ASCII paths (UAX #15) and is not a homoglyph defence, so it would have added a `python3`/`uconv` dependency for no benefit
- The SMAPI log location follows the Linux convention: `~/.config/StardewValley/ErrorLogs/` (SMAPI's `Constants.DataPath` + `ErrorLogs`). This directory has **never** contained an `SMAPI-latest.txt` on the maintainer's machine — the mod has never been executed in the real game — so the path is a documented convention rather than an observed artefact, and `--smapi-log` remains available as an override
- The mod persists data through SMAPI's `IModHelper.Data.WriteJsonFile` under `~/.config/StardewValley/.smapi/mod-data/lfgranja.LivingRoots/`, with keys prefixed `soil_health_data_` and `composting_bins_` (per `ModConstants.KeyPrefix` and `CompostingBinKeyPrefix`) and the save folder name sanitized (Unicode FormC + `FileNameSanitizationService`) as part of the filename
- The game can be launched headless via Xvfb with Mesa software rendering. This is **unverified**: the only prior launch attempt on the maintainer's machine failed with "Failed to create graphics device! GPU: Could not detect." The pre-flight's `glxinfo` probe (FR-012 item 4) is the control for this assumption
- The game process can be terminated via SIGTERM/SIGKILL immediately after the log check passes — the script does not wait for the `Saved` event because the mod emits no observable log marker on `Saved`
- The script is intended for local execution by the maintainer, not CI integration (CI may be added later). The script uses proper exit codes (0/non-zero) so future CI integration is straightforward.
