# Feature Specification: Smoke Validation Script

**Feature Branch**: `008-smoke-validation`

**Created**: 2026-10-19

**Status**: Draft

**Input**: Assessment `automate-ingame-testing` (intake + research + define + shape + decision, verdict: go, Option A)

## Scope

### In scope

- A single local, maintainer-run bash script (`scripts/smoke-validation.sh`) that launches Stardew Valley via SMAPI under a headless Xvfb display and reports whether the Living Roots mod loaded without errors.
- The FR-007 exit-code contract as the **sole** machine-readable signal (no `--json` mode).
- A per-run diagnostic log under `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/`.
- A pre-run rebuild of the mod and a **deploy-effectiveness** assertion on the deployed assembly (FR-016).
- An explicit, script-resolved mods directory passed to SMAPI (FR-017).

### Out of scope

- **Loading a save, and every consequence of it** — the save-data persistence check (FR-004, US2). The title screen is the expected state.
- **CI integration** and any machine-parseable output mode (FR-013).
- **Gameplay validation** — soil health, composting, growth, harvest. This feature validates *loading*, not mechanics.
- **Multiplayer** (roadmap D1).
- **Container / PID-1 signal semantics** — the script is not an entrypoint.
- **Parallel runs, configuration files, environment-variable configuration** — CLI arguments with documented defaults only.
- **Provenance stamping of the assembly** (embedding the commit id). The assembly carries no build identity today, and adding it would require changing `LivingRoots.csproj` — out of scope for a script-only feature. FR-016 asserts deploy effectiveness instead.

### Declared side effects

The script is not read-only. It MUST be understood to:

- **delete** the mod's deploy directory `<mods-path>/LivingRoots/` and **recreate** it on every run (FR-016 (b)) — so a manual deployment into that directory is not required, and is not preserved;
- **write** the build output into the repository tree at `LivingRoots/bin/` (FR-016 (b));
- **write** the deployed assembly, manifest, `i18n/` and `Assets/` into `<mods-path>/LivingRoots/` (FR-016 (c));
- **remove** a stale `SMAPI-latest.txt`, `SMAPI-crash.txt` and `smapi-internal/StardewModdingAPI.crash.marker` from the SMAPI log directory (FR-012 item 6);
- **create** a run-log file and a `0700` state directory under `$XDG_STATE_HOME` (FR-014);
- **create** a lock file at a stable per-user path (FR-002) and **leave it in place** afterwards.

## User Scenarios & Testing

### User Story 1 - Automated smoke validation of mod loading (Priority: P1)

As the maintainer, I want a script that launches the game with the mod installed and reports whether the mod loaded without errors, so that I can verify the mod works in the real game without manual play-through.

**Why this priority**: This is the immediate blocker — the mod has never been executed in the real game. Without this, no gameplay-affecting feature (spec 005 growth, quality, extra harvest) can be activated with confidence.

**Independent Test**: Can be fully tested by running the script and checking its exit code (0 = mod loaded without errors, non-zero = errors found). Delivers value by providing a repeatable, auditable signal that the mod loads correctly in the game. The save check (User Story 2) is deferred — see FR-004.

**Acceptance Scenarios**:

1. **Given** the game is installed and the mod is deployed in the mods folder, **When** the script runs, **Then** the script launches the game with SMAPI + mod, waits for initialization, checks the SMAPI log for errors, and exits with code 0 if no errors are found. The script terminates the game immediately after the log check passes (see FR-005).
2. **Given** the mod has a runtime error during load, **When** the script runs, **Then** the script detects the error in the SMAPI log and exits with a non-zero code and a descriptive message
3. **Given** the script has run successfully once, **When** the script runs again, **Then** it produces the same result (idempotent)
4. **Given** the assembly deployed into the mods directory is not the one produced by the current build, **When** the script runs, **Then** it fails before launching the game with a non-zero code and a message naming both SHA-256 digests (see FR-016)
5. **Given** a previous run left a `SMAPI-latest.txt` that already contains the mod's success marker, **When** the script runs, **Then** the stale content is not used to decide the verdict — only log lines after the current run's `Log started at` sentinel are evaluated (see FR-002)
6. **Given** SMAPI skipped the mod (for example because the installed SMAPI is older than the mod's `MinimumApiVersion`), **When** the script runs, **Then** the script reports a mod-load failure with SMAPI's stated reason (see FR-003)

---

### User Story 2 - Mod data persistence verification (Priority: P2, Deferred)

As the maintainer, I want the script to verify that the mod's data files appear in SMAPI's mod-data folder after the game loads with a save, so that I can confirm the mod's persistence layer works in the real game.

**Why this priority**: Loading without errors is necessary but not sufficient — the mod must also persist data correctly. This is the second half of the smoke test.

**Status**: Deferred. The automated script cannot load a save (SMAPI has no command-line save selection, and the mod is purely reactive). The title screen is the expected state. This user story will be implemented after the basic smoke test (User Story 1) works and the team has real usage data.

**Independent Test**: Can be fully tested by running the script and checking that SMAPI's mod-data folder for the mod (`~/.config/StardewValley/.smapi/mod-data/lfgranja.LivingRoots/`) contains the expected JSON files (`soil_health_data_*.json`, `composting_bins_*.json`). Delivers value by confirming the mod's persistence pipeline works end-to-end.

**Acceptance Scenarios**:

**Deferred scenarios — NOT implemented in this release.** These describe the behaviour of a *future* save check and are stated as future-state on purpose: the present implementation always skips the save check (FR-004), so a present-tense reading of these would contradict FR-004 and FR-006.

1. **Given** the game has a save file loaded with the mod active, **When** the save check runs, **Then** SMAPI's mod-data folder for the mod contains at least one file matching the mod's data prefix
2. **Given** the mod failed to persist data files, **When** the save check runs, **Then** the script reports the missing data files and exits with a non-zero code

### Edge Cases

- What happens when the game crashes during launch? The script should detect the crash (non-zero process exit or SMAPI-crash.txt) and report failure.
- What happens when the mods path is incorrect? The script should detect that the mod was not loaded (the mod's name is absent from SMAPI's `Loaded N mods:` block, or it appears in the `Skipped mods` section) and report failure.
- What happens when the save file does not exist yet? The save check is deferred (see FR-004). The title screen is the expected state in the automated script.
- What happens when the game takes longer than expected to load? The script should have a configurable timeout and report a timeout failure if the game does not produce a log within the expected window.
- What happens when the display (Xvfb) is not available? The script should detect this and report a clear error message.
- What happens when the game is already running? The script detects the existing process (via `pgrep`) and aborts with a descriptive error by default. An explicit `--force` flag kills the existing instance (SIGTERM then SIGKILL) before launching.
- What happens when another smoke test instance is already running? The script fails to acquire the `flock` and exits immediately with a descriptive error.
- What happens when a prerequisite is missing (game not installed, SMAPI not found, Xvfb not available)? The pre-flight phase detects it and emits an actionable error ("What → Where → How to fix") with a distinct exit code per failure category.
- What happens when the script is interrupted (Ctrl+C) during execution? The EXIT trap runs cleanup: game process killed, Xvfb killed, X11 locks removed, temp files cleaned. The script exits with code 130 (SIGINT) or 143 (SIGTERM).
- What happens when a previous run left a `SMAPI-latest.txt` that already contains the mod's success signal? The script MUST ignore every log line preceding the current run's `Log started at` sentinel (see FR-002), so a stale log can never produce a false pass.
- What happens when the mod build deployed into the mods directory is stale (older than the current source)? The digest assertion in FR-016 MUST fail the run before the game is launched, and the failure message MUST name both the built and the deployed SHA-256 digests.
- What happens when the game fails to create a graphics device (no usable OpenGL under Xvfb)? The script MUST report this as a graphics/environment failure (exit code `3`), not as a timeout or a mod-load failure. The pre-flight's `glxinfo` probe is expected to catch this condition before launch.
- What happens when the game process exits with status `0` but no log was produced? The script MUST report failure. This occurs when SMAPI re-asserts its dependency manifest after a game update and asks the user to relaunch.
- What happens when a leftover `SMAPI-crash.txt` is present from an earlier crash? The pre-flight MUST remove it before launch (see FR-012 item 6), because SMAPI's handling of a leftover crash marker performs a blocking keypress read that would hang the headless run.
- What happens when the resolved mods directory contains a stale copy of the mod while a current copy exists elsewhere? The script tests only the directory it resolved and passed to SMAPI via `--mods-path` (see FR-017); it does not search for other copies.
- What happens when a required host tool is missing? The pre-flight fails closed with exit code `9`, naming the tool and the package that provides it. A tool that is installed but *unusable* — for example a graphics stack with no software OpenGL — exits `3` instead, because the two conditions have different remediations.
- What happens when the script itself hits an unexpected error? The ERR trap reports the script name, failing line, enclosing function and exit code, and the script exits `13` — never with the raw status of the failing command, which under `set -e` would otherwise masquerade as a domain failure (`dotnet build` exits `1`, an unset variable exits `1`, a syntax error exits `2`).
- What happens when the mod fails to build, or when the deployed assembly does not match the fresh build? The run aborts before the game is launched with exit code `12`, naming the build error or both SHA-256 digests.

## Requirements

### Functional Requirements

- **FR-001**: The script MUST launch the Stardew Valley game via SMAPI with the mod installed, using a virtual display (Xvfb) for headless operation. The launch MUST run SMAPI's native apphost `./StardewModdingAPI --no-terminal` from the game directory (`--game-path`), which MUST be the process working directory. The rationale for running in place is that the apphost resolves its .NET runtime **relative to its own path**, and SMAPI's `Constants.GamePath` is the directory containing `StardewModdingAPI.dll` — a relocated copy of the launcher does **not** abort with SIGABRT: measured against the installed SMAPI 4.5.2 apphost, a relocated copy exits **154** ("The application to execute does not exist"), or **131** ("You must install .NET to run this application"), or **137** ("Failed to create CoreCLR") (see FR-007's translation table). The script uses SMAPI's officially supported automation env vars: `SMAPI_NO_TERMINAL=true` and `SMAPI_DEVELOPER_MODE=true`. (`SMAPI_USE_CURRENT_SHELL` is **not** used — it is read only by SMAPI's *installer wrapper*, never by `StardewModdingAPI.dll`, so it is inert when the apphost is launched directly; verified against the installed binary, whose only `SMAPI_*` literals are `SMAPI_NO_TERMINAL`, `SMAPI_MODS_PATH` and `SMAPI_DEVELOPER_MODE`.) `SMAPI_DEVELOPER_MODE` gates **console** verbosity only — SMAPI writes TRACE-level entries to the log file unconditionally, so TRACE-level diagnostics are available without it; it is retained because it makes the launch console output usable for debugging. The script MUST additionally export `LIBGL_ALWAYS_SOFTWARE=1` and `GALLIUM_DRIVER=llvmpipe` to force Mesa software rendering, and MUST set `SDL_VIDEODRIVER=x11` (never `wayland`) because the game bundles `libSDL2` and Wayland cannot be used against an Xvfb display. Xvfb MUST be started with `-nolisten tcp` and with `-displayfd`, so that the X server itself allocates a free display (see FR-012 item 5).
- **FR-002**: The script MUST wait for the game to initialize and produce a SMAPI log file **that belongs to the current run** before performing checks. The SMAPI log path defaults to `~/.config/StardewValley/ErrorLogs/SMAPI-latest.txt` (Linux convention) and MAY be overridden via `--smapi-log`. Before launching, the script acquires an exclusive `flock` on a dedicated lock file (non-blocking) to prevent concurrent executions. If the lock cannot be acquired, the script exits immediately with a descriptive error.

  **Lock file (MUST).** The lock file MUST live at a **stable, per-user, predictable path** — `${XDG_RUNTIME_DIR}/livingroots-smoke.lock`, falling back to `${XDG_STATE_HOME:-$HOME/.local/state}/livingroots-smoke/livingroots-smoke.lock` when `$XDG_RUNTIME_DIR` is unset — inside a directory with mode `0700` owned by the current user. The path MUST NOT be inside a per-run `mktemp -d` directory: a unique directory per run means two concurrent instances lock *different inodes* and mutual exclusion is zero. The lock file MUST be opened with `exec 9<>"$lockfile"` (read-write, create-if-absent) and **not** `exec 9>"$lockfile"`, because `>` truncates and follows symlinks while `<>` neither truncates nor destroys a symlink target. The lock MUST be acquired with `flock -n 9`. The lock file MUST **not** be removed at exit: the kernel releases the lock when the descriptor closes (or the process dies), whereas removing the file detaches the name from the locked inode and re-opens the race window that a second instance would exploit. The lock path MUST be on a local filesystem — `flock` is unreliable on NFS and CIFS.

  **Log freshness (MUST).** SMAPI unlinks `SMAPI-latest.txt` at startup and creates a new file, and writes an in-band per-run sentinel line near the top of every log. The sentinel's exact form MUST be `Log started at {UTC timestamp} UTC`, where the timestamp is `DateTime.UtcNow` rendered with the round-trip sortable pattern `s` — i.e. `Log started at 2026-10-19T21:01:38 UTC` (no offset, no `Z`). The script MUST therefore: (1) record the UTC launch timestamp `T0` before starting the game; (2) wait for a `Log started at` sentinel whose timestamp is **not older than `T0`**, comparing the two as UTC — the sentinel carries no offset, so the comparison MUST treat it as UTC explicitly (append `Z` when parsing, or compare as UTC epoch seconds) and MUST NOT parse it as local time, which would shift the comparison by the local UTC offset; and (3) evaluate every success and failure signal **only against log lines that follow that sentinel line**. Signals appearing before the sentinel belong to a previous run and MUST be ignored. This ordering requirement is what prevents a stale log left by an earlier successful run from producing a false pass. As a belt-and-braces assertion, the script MUST record the log file's inode (`stat -c %i`) before launch and verify it changed once the log is (re)created. **The order of these two steps is normative**: the inode MUST be recorded *before* the stale log is removed, otherwise the baseline is "absent" and the assertion is vacuous.

  **Header region (MUST).** SMAPI writes the version banner and the `Mods go here:` line **before** the sentinel (`LogManager.LogIntro` order: banner → `Mods go here:` → sentinel). Those two lines are therefore **exempt** from the "only after the sentinel" rule: they MAY be read for context (reporting the installed SMAPI version and the resolved mods directory) but MUST **never** gate the verdict. Every signal that *does* gate — the `Loaded N mods:` block, the `Skipped mods` section, mod-scoped Error/Alert entries, and the crash-file override — MUST be evaluated strictly after the sentinel. The `Mods go here:` path is **tilde-anonymised** by SMAPI (`PathUtilities.AnonymizePathForDisplay` replaces the `$HOME` prefix with `~`), so any comparison against the resolved `--mods-path` MUST compare the home-relative form (`$HOME` → `~`) rather than the absolute path.

  **Pre-launch cleanup (MUST).** The script MUST remove a pre-existing `SMAPI-latest.txt` and `SMAPI-crash.txt` before launching, and MUST also remove SMAPI's leftover crash **marker** (`smapi-internal/StardewModdingAPI.crash.marker`). The **marker**, not the crash log, is what gates SMAPI's blocking `Console.ReadKey()` on a leftover crash: `LogManager.HandleMarkerFiles()` tests for the marker's presence and only then performs the keypress read, which would hang a headless launch indefinitely. Removing `SMAPI-crash.txt` alone leaves the marker in place and therefore does **not** prevent the hang; the crash log stays in the cleanup set only because its presence overrides the log verdict (FR-006).

  **Readiness vs. exit (MUST).** If the game process exits **without** producing a log — including an exit status of `0` — the script MUST report failure, not success, with exit code `15` (FR-007). SMAPI's dependency-assertion routine exits with status `0` and the message "Please exit this window and re-launch SMAPI to play" after a game update, which would otherwise be mistaken for a successful run. **Readiness is the sentinel alone** (FR-002); the mod-resolution signals are the *verdict*, evaluated immediately after the sentinel, and MUST NOT be part of the readiness condition — polling for "the mod is listed" would turn a mod-load failure into a timeout instead of a mod-load failure.
- **FR-003**: The script MUST parse the SMAPI log file for errors attributable to the mod (LivingRoots). Log entries follow the format `[HH:mm:ss LEVEL SOURCE] message` — the level field is padded to **5** characters (SMAPI renders it with `PadRight(Monitor.MaxLevelLength)`, and `MaxLevelLength` is the length of the longest public `LogLevel` name — `Trace`/`Debug`/`Error`/`Alert` = 5) followed by a single separator space, the source column carries the mod's manifest name for mod-originated entries, and lines are CRLF-terminated, so matching MUST be substring-based (`grep -F`) with any trailing carriage return stripped before an exact comparison. A real mod-scoped line therefore reads `[14:32:02 ERROR Stardew Valley - Living Roots] …`. The level is **inside** the bracket group — there is no `[ERROR]` token — so an Error/Alert entry MUST be matched on the **level column**, never as a literal `[ERROR]` substring. Per-line timestamps carry no date and MUST NOT be used to identify a run. Only Error and Alert level entries are failure markers. WARN-level entries (if ever added to the mod) are logged but do not fail the smoke test. Trace-level entries are written to the log file by SMAPI unconditionally and are captured for diagnostic purposes only — they do not fail the test but provide exception type and HResult information in failure reports. The success marker match is case-sensitive and exact.

  **Success gate (MUST).** The success gate is computed from SMAPI's own mod-resolution output, not from the mod's self-reported marker: (1) SMAPI MUST have emitted a `Loaded N mods:` block, (2) the mod's manifest name (`Stardew Valley - Living Roots`) MUST appear within one of that block's per-mod entry lines, and (3) the mod MUST NOT appear in SMAPI's `Skipped mods` section. SMAPI renders each loaded mod as `   <Name> <Version> by <Author>`; because the mod's name contains spaces, the match MUST be a substring match of the **full** manifest name against the entry line rather than a first-token comparison. The mod's own marker line (`The 'Stardew Valley - Living Roots' mod was loaded successfully!`) MUST still be detected and reported, but it does **not** gate success: it is emitted by the mod from its `GameLaunched` handler (`ModController.cs:959`), which runs only after the game has reached the title screen, so gating on it would couple the smoke test to a working graphics device and would report a graphics failure as a timeout rather than as the environment problem it is.
- **FR-004**: The script SHOULD verify that the mod's data files are present in SMAPI's mod-data folder for the mod (`~/.config/StardewValley/.smapi/mod-data/lfgranja.LivingRoots/`) after the game has run with a save loaded — checking for `soil_health_data_*.json` and `composting_bins_*.json`. In the current implementation the save check is always skipped (with a `SKIPPED:` warning) because the automated script cannot load a save (SMAPI has no command-line save selection, and the mod is purely reactive — it only responds to SMAPI events after a save is loaded via the title screen UI). The title screen is the expected state. The save check is deferred until the basic smoke test works and the team has real usage data; it does not gate success (see FR-006).
- **FR-005**: The script MUST terminate the game process immediately after the log check passes, without leaving orphaned processes. The script launches the game in its own process group and sends SIGTERM to the entire group first, waits a configurable grace period (default 15s, via `--grace-period`) for graceful exit, and escalates to SIGKILL only if the process is unresponsive. The own-process-group requirement is satisfied by enabling bash job control (`set -m`) around the launch only: job control gives the game a process group whose ID equals the game's PID, so `$!` is simultaneously the game's PID and its process-group ID and `kill -- -$!` signals exactly that group and nothing else. Before any group signal the script MUST assert that the process-group ID it is about to signal differs from the script's own process-group ID and from `1` — signalling the script's own group would terminate the script itself instead of the game. Because job control moves the game out of the terminal's foreground process group, the game no longer receives terminal-generated signals and the script's own signal-forwarding trap becomes the only path to the game. Both children (game and Xvfb) MUST be launched with `&`, with their stdin redirected from `/dev/null` and their stdout/stderr redirected to the run log, and MUST be waited on with `wait -f` — a background job that touches the controlling terminal is suspended by SIGTTIN/SIGTTOU, and bash defers a trapped signal until the *foreground* command completes, so a foreground launch would delay the signal handler until the game exits. The script does NOT wait for the `Saved` event — the mod emits no observable log marker on `Saved`, making it impossible to detect externally.

  **Trap design (MUST).** The `EXIT` trap is registered **exactly once**, in the top-level shell, and is the single cleanup path: bash resets caught traps to their inherited values in subshells, so an inherited `EXIT` trap does not fire there and a subshell that owns a child process MUST clean that child up itself before exiting; no subshell may register its own `EXIT` trap (that would double-clean the shared resources). The cleanup function MUST capture `$?` as its very first statement and MUST end with `exit "$rc"`. The `INT`, `TERM` and `HUP` handlers MUST forward the signal to the child process groups and then **reset their own trap and re-raise the signal on the script itself** (`trap - SIG; kill -SIG $$`) — the script MUST die *from* the signal so the caller observes `128+N` as a genuine signal death, which is observably different from `exit 128+N` (a plain exit status; the caller cannot tell the two apart). The script MUST NOT use `trap '' INT TERM` to make cleanup uninterruptible: bash already does not re-enter a handler for the same signal, and ignoring those signals permanently would (a) make the script un-killable by SIGTERM and (b) cause every child spawned afterwards to inherit the ignored disposition across `execve`. Cleanup MUST instead be idempotent (guarded by an `in_cleanup` flag) and time-bounded. `trap - EXIT` inside the cleanup function is permitted as belt-and-braces: POSIX specifies that `exit` inside an `EXIT` trap exits immediately without recursing, but leaves the "a new `EXIT` trap is set during the `EXIT` trap" case unspecified. If the mandatory process-group assertion fails, the script MUST abort immediately with exit code `13` and a message naming both process-group IDs — it MUST NOT fall back to signalling a single PID.
- **FR-006**: The script MUST report success (exit code 0) when the log check passes. The log check uses an AND conjunction: success requires the mod to be listed in SMAPI's `Loaded N mods:` block AND the mod to be absent from SMAPI's `Skipped mods` section AND no Error/Alert entries from the mod. All three signals MUST be evaluated against log lines that follow the current run's `Log started at` sentinel (see FR-002); the version banner and the `Mods go here:` line precede the sentinel and are context only (FR-002 "Header region (MUST)"). The mod's own success marker, when present, MUST be reported in the result output as a secondary signal but does not gate the verdict. The save check is deferred (see FR-004) and does not gate success in the current implementation. The success message MUST be exactly `SUCCESS: Mod loaded without errors.`
- **FR-007**: The script MUST report failure (non-zero exit code) with a descriptive message when any check fails. Failure messages MUST follow the "What → Where → How to fix" pattern: identify the failed component, the specific error, relevant log context (last 20-30 lines of the SMAPI log including Trace-level entries that follow any Error entry), and an actionable remediation, emitted as a trailing `Fix:` line. Exit codes MUST assign a distinct code per failure category: `1` = game installation not found, `2` = SMAPI not found or not functional, `3` = graphics environment present but unusable, `4` = timeout, `5` = mod load failure, `6` = lock contention, `7` = process conflict, `9` = missing host tool or runtime dependency, `10` = virtual display could not be allocated or started, `11` = Steam API prerequisite missing, `12` = build or artifact-identity failure, `13` = internal script error, `14` = usage or CLI-argument error, `15` = the game produced no SMAPI log, `16` = mods path or mod manifest invalid, plus the POSIX `128+N` interruption codes (`130` = SIGINT, `143` = SIGTERM, and `129` = SIGHUP) and `0` = success. This is a bespoke, one-code-per-failure-class scheme — it is NOT the `sysexits.h` numbering, which begins at `EX__BASE` = 64 and has been deprecated by FreeBSD and OpenBSD; the phrase "sysexits.h convention" MUST NOT be used to describe these values.

  **Allocation rule (MUST).** Codes are allocated **additively** and permanently: a **published code MUST NOT be re-assigned** to a different failure class, and a **retired code MUST NOT be reused**. A new category takes the **next value above the highest published code** — not the next numerically unused value — so the retired value `8` can never be handed out again. The retired set is: `8` (retired in round 2, superseded by the POSIX `128+N` interruption codes; never reused). The remaining published codes are `1`–`7` and `9`–`16`.

  **No subprocess-specific status may ever become the script's final code.** Every child status MUST be translated into one of the categories above before the script exits, using this table: `0` → `0`; `timeout`'s native `124` → `4`; `timeout`'s `125` (the timeout utility itself failed) → `13`; `126` (found but not executable) → `9`; `127` (not found) → `9`; `131` (the .NET runtime could not be started by the SMAPI apphost) → `2`; `134` (SIGABRT) → `2`; `137` (SIGKILL) → `5` when it is the game process, `2` when it is the SMAPI apphost and `13` otherwise; `154` (the SMAPI apphost cannot find its own assembly) → `2`; `128+N` for SIGINT/SIGTERM/SIGHUP delivered to the script itself → `128+N`, unchanged; any other non-zero status → `13`. A pre-flight probe that fails is translated by the **category of the probe**, not by the raw status the probe happened to return. An unhandled error caught by the ERR trap exits `13`; a failed mod build or a build/artifact digest mismatch exits `12` (see FR-016); a failed PGID assertion exits `13` (see FR-005).
- **FR-008**: The script MUST be idempotent — running it multiple times in sequence produces the same result
- **FR-009**: The script MUST accept a configurable timeout for game launch and initialization via command-line argument, with a 120-second default. The script polls the log continuously (no wasted time), and the timeout only matters for failure cases. The timeout MUST be enforced by a **deadline poll loop** over the SMAPI log (`deadline=$(( $(date +%s) + timeout ))`), which MUST check the deadline before each iteration and MUST exit with `4` when it expires. The `timeout` utility MAY be used to bound the poll as a belt-and-braces wrapper, but it MUST **not** wrap the game launch: the game MUST be a direct background child of the script, so that `$!` is simultaneously the game's PID and its process-group ID (FR-005).
- **FR-011**: The script MUST detect an existing Stardew Valley/SMAPI process before launching. By default, the script aborts with a descriptive error listing the conflicting PIDs. An explicit `--force` flag kills existing instances (SIGTERM → SIGKILL escalation) before launching. This is a correctness requirement: the mod has no cross-process data file locking, so concurrent instances would corrupt data and truncate the SMAPI log. Identification MUST be **by executable path, not by process-name matching**: a candidate PID qualifies only when `/proc/$PID/exe` resolves to an executable under the resolved game directory — the `StardewModdingAPI` apphost or the `StardewValley` game binary. `pgrep -x` MUST NOT be used for the apphost: the kernel's process name (`comm`) is truncated to 15 characters and `StardewModdingAPI` is 17, so an exact-name match can never succeed and would silently never match. `pidof` matches on the untruncated name and on `/proc/$PID/exe` and is the acceptable alternative. A PID the script itself spawned needs no identity check — an unreaped child stays a zombie and the kernel does not recycle a zombie PID — but **any PID discovered by scanning the process table MUST be verified before it is signalled**.
- **FR-012**: The script MUST include a pre-flight phase before launching that validates, **in this order** — the cheapest, most dependency-free checks first, and no check that depends on a tool or resource before that tool or resource has been verified present.

  **(0) Order (MUST).** (a) required-host-tool presence (item 8); (b) game installation and SMAPI markers (items 1–2); (c) Steam prerequisite (item 9); (d) crash-marker removal (item 6); (e) start the virtual display and probe software OpenGL (items 4–5). The build-and-verify step (FR-016) then runs, then the flock, then the existing-process check, then the log baseline, then the game launch. No check may run before the tools it needs are verified present, and the display MUST NOT be started before the tool sweep has confirmed `Xvfb`, `xdpyinfo` and `glxinfo` are installed.

  (1) the game installation exists at the expected path (configurable via `--game-path`, default `~/.steam/steam/steamapps/common/Stardew Valley/`) and contains the game assembly (`Stardew Valley.dll`) and SMAPI's launcher (`StardewModdingAPI`); (2) SMAPI is installed and functional — this means the main assembly `StardewModdingAPI.dll` is present and its version can be parsed, the dependency assemblies `smapi-internal/SMAPI.Toolkit.dll` and `smapi-internal/SMAPI.Toolkit.CoreInterfaces.dll` are present, and the `StardewModdingAPI` apphost is executable for the host architecture. No SMAPI release ships a file named `smapi-internal/SMAPI.dll`; probing for that path produces a false negative on a correct installation, so the check MUST use the paths listed here; (3) Xvfb is available and runnable (`command -v Xvfb` plus a version probe) — an absent `Xvfb` binary is a **missing host tool** and exits `9` (see item 8), not `3`; (4) software OpenGL rendering is genuinely usable — the probe is **layered**: (4a) `xdpyinfo` exits `0` and its output contains the `GLX` and `RANDR` extensions; (4b) `glxinfo -B` under `LIBGL_ALWAYS_SOFTWARE=1` exits **`0`** — note that `glxinfo` exits **255** on failure, not `1`, so the probe MUST branch on "exit 0" and never on a specific status — a zero exit is the proof that a real GLX context could be created; (4c) the `OpenGL renderer string` reported by `glxinfo -B` MUST match `llvmpipe` or `softpipe` — the mere presence of `libGL.so` does NOT satisfy this check, and neither does a hardware or `zink` renderer; (4d) **the game-specific capability MUST also be asserted**: full `glxinfo` (or `glxinfo -s`) MUST report `GL_ARB_framebuffer_object` or `GL_EXT_framebuffer_object`, or the `OpenGL version string` MUST be ≥ 3.0. This layer is load-bearing: the game's graphics backend (MonoGame) throws `PlatformNotSupportedException: MonoGame requires either ARB_framebuffer_object or EXT_framebuffer_object` when a context lacks FBOs, and `glxinfo -B` prints **no extension list**, so it cannot detect that failure class. A failure of this probe, **with `Xvfb`, `xdpyinfo` and `glxinfo` all present**, is a graphics environment that is present but unusable and exits `3`; (5) **the virtual display MUST be allocated by the X server itself**, using `Xvfb -displayfd` — the script MUST NOT choose a display number, MUST NOT probe, create or remove `/tmp/.X{n}-lock` files, and MUST NOT implement the lock liveness protocol. Rationale: `-displayfd` makes the server bind the first free display **atomically** (its `CreateWellKnownSockets()` loop) and it **disables the server lock** entirely (`os/utils.c` → `DisableServerLock()`), so no lock file exists to manage; a harness-created lock file is at best useless and at worst a local denial-of-service vector (the server installs its own lock atomically via `link()` from `/tmp/.tX{n}-lock`). The script MUST read the allocated display number back from the descriptor and record it for the cleanup phase. If Xvfb fails to start, or reports no display number, the run MUST abort with exit code `10`; (6) any pre-existing `SMAPI-crash.txt` **and** SMAPI's leftover crash **marker** (`smapi-internal/StardewModdingAPI.crash.marker`) are removed — the **marker**, not the crash log, is what gates SMAPI's blocking `Console.ReadKey()` on a leftover crash (`LogManager.HandleMarkerFiles()` tests for the marker's presence), so removing only the crash log does **not** prevent the headless hang; (7) **every path the script constructs is validated**: it MUST be canonicalized with `realpath` and MUST satisfy a **component-boundary** prefix test against the intended base (`case "$real" in "$base"/*)`) — a reject-on-`..` test after canonicalization is dead code, because `realpath()`'s definition excludes `..` by construction. User-supplied roots (`--game-path`, `--mods-path`, `--smapi-log`) are **their own bases**: they MUST be resolved with `realpath` for existence, but MUST NOT be prefix-checked against the game directory — an absolute `--mods-path` outside the game directory is legal (FR-017). Path components MUST match the allowlist `[A-Za-z0-9._/-]+`. **No Unicode normalization is performed and no normalizer dependency is required** — NFC is a provable no-op for ASCII paths (UAX #15: "Text exclusively containing ASCII characters is left unaffected by all of the Normalization Forms") and is not a homoglyph defence (that requires UTS #39); the ASCII allowlist is strictly stronger and dependency-free; (8) every required host tool is present. The required set is: `bash` (4+), `Xvfb`, `xdpyinfo`, `glxinfo`, `flock`, `timeout`, `mktemp`, `stat`, `realpath`, `pgrep` (or `pidof`), `sha256sum`, `date`, `grep`, and `dotnet` (required by FR-016's rebuild). Each MUST be verified with `command -v`; a missing one MUST fail closed with exit code `9` and name the tool. A required tool that is present but **unusable** is a different category — for example an `Xvfb` that is installed but whose display stack cannot provide software OpenGL exits `3`, not `9`; (9) the Steam prerequisite is satisfied — `<game-path>/steam_appid.txt` MUST exist and contain the app id `413150`; its absence or a wrong id MUST fail closed with exit code `11`, and this is the only condition that can raise that code.
- **FR-010**: The script MUST clean up temporary resources on exit, including on failure and interruption. Cleanup includes: (1) kill game process (SIGTERM → SIGKILL escalation), (2) kill Xvfb process, (3) remove the virtual display's socket (`/tmp/.X11-unix/X{n}`) — but ONLY for the display this script allocated (`{n}` = the number reported by `Xvfb -displayfd`). The script MUST NOT create or remove `/tmp/.X{n}-lock` files: under `-displayfd` the server writes no lock file at all (`DisableServerLock()`), and the server installs any lock it does write atomically via `link()` from `/tmp/.X{n}-lock`'s staging file, so a harness-managed lock is at best useless and at worst a local denial-of-service vector. (Xvfb removes its own artifacts on SIGTERM/SIGINT and on a fatal error, so this step is a no-op on the normal path and load-bearing only after a SIGKILL escalation), (4) remove temp files/directories, (5) the flock is auto-released by the kernel on process death — the lock **file** is deliberately **not** removed, because removing the name detaches it from the locked inode and re-opens the race window for a second instance (see FR-002). Each cleanup step MUST be isolated (guarded with `|| true`) so one failure does not prevent others. The cleanup order is reverse of allocation: game first, then Xvfb, then the socket and temp files.

- **FR-013**: The script MUST remain local-first: no CI integration and no machine-parseable (`--json`) output mode in the current scope. Proper exit codes (0/non-zero) are retained so future CI integration is straightforward.
- **FR-014**: The script MUST log every process lifecycle event with a timestamp and level prefix — spawn (game, Xvfb), every signal sent (including the PID and the signal), the grace period, the escalation to SIGKILL, and the observed exit — so that a failed run can be reconstructed from the run log alone. On any unhandled error, the ERR trap MUST report the script name, the failing line number, the enclosing function name, and the exit code.

  **Run log (MUST).** The script's own diagnostic output is the **run log**, and it is distinct from the SMAPI log. The run log MUST be written to a file at `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/<run-id>.log`, in a directory created with mode `0700`. Each run MUST write its own file (no shared append-only file) so that concurrent runs cannot interleave. The run log MUST contain every line the script emits at any level, including the lifecycle events above.

  **Run ID and version (MUST).** The script MUST generate a run ID of the form `<UTC timestamp>-<PID>` (e.g. `20261019T183302Z-48213`) and MUST stamp it on every run-log line, in the stdout summary, in every error message, and in the path of the run log file. The script MUST define a `VERSION` constant (first release `0.1.0`) and MUST report it in the stdout summary, in the run-log header, and in the `--help` output. The run ID and `VERSION` are the correlation keys required by the escalation evidence bundle.

  **Streams (MUST).** The verdict and the `--help`/`--version` output go to stdout; all level-prefixed diagnostics and error messages go to stderr. The exit code remains the sole machine-readable signal (see FR-013).
- **FR-015**: The script's `--help` output MUST document the automation environment variables it sets (`SMAPI_NO_TERMINAL=true`, `SMAPI_DEVELOPER_MODE=true`, `LIBGL_ALWAYS_SOFTWARE=1`, `GALLIUM_DRIVER=llvmpipe`, `SDL_VIDEODRIVER=x11`, and `DISPLAY`) in a dedicated "Environment (set automatically)" section, stating explicitly that they are managed by the script and are not user-configurable. The `--help` output MUST also document the `--mods-path` option (see FR-017), the `--mod-project` option (see FR-016), the run-log location, the run ID format, the script `VERSION`, and every exit code. It MUST also provide `--version` (printing `<name> <VERSION>` to stdout and exiting `0`) and MUST accept `-h` as an alias for `--help` — GNU Coding Standards §4.8: "All programs should support two standard options: `--version` and `--help`", both on stdout and exiting successfully.
- **FR-016**: The script MUST ensure that the mod build under test is the build it just produced, and MUST abort before launching the game if it cannot. This is a **deploy-effectiveness** assertion, not a source-correspondence claim: the mod assembly carries no build identity — `manifest.json` declares a fixed `Version` (`0.0.1`), the assembly declares a fixed `AssemblyVersion` (`1.0.0.0`), no commit identifier is embedded, and `SourceRevisionId` is inert because the project sets `GenerateAssemblyInfo=false` — so no digest of the assembly can prove *which* source tree produced it. What the script CAN prove, and MUST, is that **the assembly the game will load is byte-identical to the assembly this run just built**.

  **(a) Locate the project (MUST).** The mod project MUST be configurable via `--mod-project`, defaulting to `<repo-root>/LivingRoots/LivingRoots.csproj`, where `<repo-root>` is derived from the script's own location (`SCRIPT_DIR/..`). The path MUST be resolved with `realpath` and MUST satisfy the component-boundary prefix test of FR-012 item 7 against the repository root.

  **(b) Build (MUST).** The script MUST run `dotnet build --configuration Release --no-incremental` in the project directory, MUST remove the deploy target directory `<mods-path>/<ModFolderName>/` **before** the build, and MUST abort with exit code `12` if the build fails. The removal is required because `Pathoschild.Stardew.ModBuildConfig`'s deploy task copies but never deletes, so a stale file from a previous build could otherwise survive.

  **(c) Pin the deploy target (MUST).** The build MUST be invoked with `-p:GameModsPath="<resolved mods-path>"`, so that `ModBuildConfig` deploys into exactly the directory the script resolved — and therefore into the directory SMAPI will load from. Without this, `GameModsPath` defaults to `$(GamePath)/Mods` where `GamePath` is **auto-detected** from ~15 candidate locations, the build deploys somewhere the script may not be able to name, and the comparison in (d) is against an unrelated copy.

  **(d) Compare (MUST).** After the build the script MUST compute the SHA-256 digest of the freshly built assembly (`<mod-project-dir>/bin/<EntryDll>` — the project sets `OutputPath=bin/` with `AppendTargetFrameworkToOutputPath=false`, so the output is `bin/LivingRoots.dll`, not `bin/Release/net6.0/`) and the SHA-256 digest of the deployed assembly (`<mods-path>/<ModFolderName>/<EntryDll>`), and MUST abort with exit code `12` — naming **both** digests — if they differ, if either is missing, or if the deployed file is older than the build. This is the standard within-run "did the deploy take effect?" assertion (the file-integrity-monitoring / SLSA subject-digest pattern); a digest is NEVER compared across runs, because the .NET compiler's deterministic content hash — and therefore the PE timestamp and the module version id — is a function of the absolute source path, so two builds of identical source at different paths legitimately differ.

  The deployed manifest version alone MUST NOT be used as the freshness assertion, because it is invariant across builds.
- **FR-017**: The script MUST resolve the mods directory explicitly and MUST NOT depend on SMAPI's implicit default. The mods directory MUST be configurable via `--mods-path`, defaulting to `<game-path>/Mods`. The script MUST pass the resolved directory to SMAPI using the `--mods-path` argument (equivalently `SMAPI_MODS_PATH`); the CLI argument is **normative** and takes precedence over the environment variable, matching SMAPI's own behaviour (upstream reads the argument first and consults the environment variable only when the argument is empty). A relative `--mods-path` value MUST be resolved against the game directory, matching SMAPI's own semantics; an absolute one is accepted as-is and is its own base (FR-012 item 7). The resolved directory MUST be passed to the build as `-p:GameModsPath` so that the build deploys into exactly the directory SMAPI loads from (FR-016 (c)). **Verification of the mod folder (MUST).** The check that the resolved directory contains the mod folder (`<ModFolderName>/manifest.json` with a matching `UniqueID`) MUST run **after** the build-and-verify step (FR-016), not before it: FR-016 removes and recreates the deploy target, so a check placed before the build would fail on a clean machine. A failure of this check — missing directory, missing `manifest.json`, malformed manifest, or `UniqueID` mismatch — exits with code `16`.
### Key Entities

- **SMAPI Log**: The log file produced by SMAPI at `~/.config/StardewValley/ErrorLogs/SMAPI-latest.txt` (Linux). Entries follow the `[HH:mm:ss LEVEL SOURCE] message` format — the level field is padded to 5 characters followed by a single separator space, the source column carries the mod's manifest name for mod-originated entries, and lines are CRLF-terminated. Six levels are recognized (TRACE, DEBUG, INFO, WARN, ERROR, ALERT). The script parses this to (a) detect SMAPI's mod-resolution output (`Loaded N mods:` block and `Skipped mods` section), (b) detect the mod's own success marker ("The 'Stardew Valley - Living Roots' mod was loaded successfully!" — emitted by the mod, not by SMAPI), and (c) detect any Error/Alert entries attributable to the mod. The log begins with a per-run sentinel line `Log started at {UTC timestamp} UTC`; only lines after that sentinel belong to the current run. `SMAPI-crash.txt` (if present) overrides `SMAPI-latest.txt` and indicates failure.
- **Loaded Mods Manifest**: SMAPI's own report of the mods it resolved, emitted in the log as a `Loaded N mods:` block with one `   <Name> <Version> by <Author>` line per mod, followed by an optional `Skipped mods` section naming the reason for each skip (for example "because it needs SMAPI X or later"). This is the authoritative signal for whether the mod was loaded, and it is available without the game having reached the title screen. The same log also records the resolved mods directory (`Mods go here: <path>`) and the SMAPI version banner (`SMAPI <version> with Stardew Valley <version> on <os>`).
- **Mod Build Artifact**: The compiled mod assembly `LivingRoots.dll` and its manifest, deployed by the build into the resolved mods directory (`<mods-path>/LivingRoots/`). The assembly carries no build identity — `manifest.json` declares a fixed `Version` (`0.0.1`), the assembly a fixed `AssemblyVersion` (`1.0.0.0`), and no commit identifier is embedded — so the artifact's freshness is established by the **deploy-effectiveness** assertion of FR-016: the deployed assembly's SHA-256 digest MUST equal the digest of the assembly produced by the current build, with the deploy target pinned to the resolved mods path. Two copies of this artifact may coexist in the workspace (a repository-local `.gamepath/Mods/` copy and the copy in the game installation); only the copy in the resolved mods path is under test.
- **Mod Data Files**: The mod persists data as JSON sidecar files written through SMAPI's `IModHelper.Data.WriteJsonFile`, which resolves relative names against SMAPI's mod-data directory — `~/.config/StardewValley/.smapi/mod-data/<UniqueID>/` (here `<UniqueID>` = `lfgranja.LivingRoots`). The files are named `soil_health_data_<sanitizedSaveId>.json`, `composting_bins_<sanitizedSaveId>.json`, and `visualization_config_<sanitizedSaveId>.json`. The saveId is SMAPI's active save folder name (`Constants.SaveFolderName`), sanitized via Unicode normalization and filename sanitization. The mod does **not** write into a `data/` folder inside its own mod folder — that location is not used by SMAPI's helper API. When no save is loaded (fresh install/title screen), zero data files is the expected valid state.
- **Game Process**: The Stardew Valley process launched via SMAPI. The script manages this process lifecycle (launch, wait, terminate). Termination happens immediately after the log check passes. The script sends SIGTERM first, waits a brief grace period for graceful exit, and escalates to SIGKILL only if the process is unresponsive. The script does NOT wait for the `Saved` event — the mod emits no observable log marker on `Saved` (`ModController.cs:1089-1102`), making it impossible to detect externally.
- **Virtual Display**: The Xvfb display buffer that allows the graphical game to run headless. The script manages this resource lifecycle.
- **Run Log**: The script's own diagnostic output, written per run to `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/<run-id>.log` (see FR-014). It records every lifecycle event with a timestamp, level prefix, and run ID. It is distinct from the SMAPI Log and survives the run, so a failure can be reconstructed afterwards.

## Success Criteria

### Measurable Outcomes

- **SC-001**: The script can be executed from a clean state (no prior game process, no Xvfb) and produces a deterministic pass/fail result within a configurable timeout (default: 120 seconds)
- **SC-002**: When the mod loads without errors, the script exits with code 0 and reports exactly `SUCCESS: Mod loaded without errors.` — this is the expected baseline after a correct mod build
- **SC-003**: When the mod has a load-time error, the script exits with a non-zero code and reports the specific error message from the SMAPI log
- **SC-004**: *(Deferred — see FR-004. Not gating in this release.)* When the mod loads but does not persist data files to SMAPI's mod-data folder, a future implementation of the save check will exit with a non-zero code and report the missing data files. In the current version the save check is always skipped with a `SKIPPED:` warning and does not gate success; this criterion is therefore **not evaluated** by any run and MUST NOT be read as a failure.
- **SC-005**: *(Deferred — see FR-004. Not gating in this release.)* The mod's **load** half is evaluated by this script: a successful run establishes that the mod resolves and loads in the real game. The mod's **persistence** half is not evaluated at all, because no save is loaded. This criterion therefore covers only the load half; it does **not** discharge, and makes no claim about, any criterion in spec 004 — 004's SC-008 is a manual-playtest *discoverability* criterion that states "No automated task covers this criterion", and is unrelated to persistence.
- **SC-006**: The quickstart guide documents every exit code in the FR-007 taxonomy with its cause and its remediation, lists every required host tool and every CLI option, and provides a troubleshooting ladder that maps every symptom to a check with an explicit expected result. These properties are verifiable by reading `quickstart.md` and are exercised by TC-1…TC-17.
- **SC-007**: When the game is already running, the script detects it and aborts with a descriptive error (or kills it with `--force`)
- **SC-008**: When another smoke test instance is already running, the script fails to acquire the flock and exits immediately
- **SC-009**: When a prerequisite is missing, the pre-flight phase detects it and emits an actionable error with a distinct exit code
- **SC-010**: When the script is interrupted (Ctrl+C), the EXIT trap runs full cleanup (game, Xvfb, X11 locks, temp files) and exits with code 128+N
- **SC-011**: When a previous run left a `SMAPI-latest.txt` containing the mod's success marker, the current run does NOT report success from that stale content — the verdict is derived only from lines following the current run's `Log started at` sentinel
- **SC-012**: When the assembly deployed into the resolved mods directory is missing, is not byte-identical to the assembly produced by the current build, or is older than that build, the script exits with code `12` **before** launching the game, and the failure message names both SHA-256 digests
- **SC-013**: The success verdict is derived from SMAPI's `Loaded N mods:` / `Skipped mods` output; a mod that SMAPI skipped (for example for an unmet `MinimumApiVersion`) is reported as a mod-load failure with SMAPI's stated reason, even though the game itself started successfully
- **SC-014**: Every run produces a retained run log under `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/` containing the run ID, the script `VERSION`, the launch timestamp, and every lifecycle event, such that the run can be reconstructed from that file alone

- Q: How can the game be terminated safely without corrupting data? → A: The safest termination point is after the `Saved` event fires (all data flushed to disk). The script should send SIGTERM first, wait a grace period (30-60s) for graceful exit, and only escalate to SIGKILL if the process is unresponsive. Never terminate during a save operation (risk of non-atomic JSON write corruption).

- Q: How does the game handle save files and which save should the script check? → A: The mod has no save selection logic — it uses SMAPI's `Constants.SaveFolderName` as the active save identifier. The smoke test validates "mod loads without errors" (log check) unconditionally, and validates "data persistence" (save check) only when a save was loaded. This is the simplest approach and aligns with Option A (smallest thing that could work).

- Q: What is the appropriate timeout value for the game to launch and produce a ready signal? → A: The timeout is configurable via command-line argument with a 120-second default. The script polls the log continuously (no wasted time), and the timeout only matters for failure cases. A configurable timeout allows calibration after the first real run without code changes.

- Q: Is the smoke test script intended for local execution only, or should it be designed for CI integration from the start? → A: Local-first. The script is a simple bash script that runs on the maintainer's machine. CI integration is a separate future effort. The script uses proper exit codes (0/non-zero) so CI integration is straightforward later.

- Q: After the log check passes (mod loaded successfully detected), when should the script terminate the game process? → A: Terminate immediately after the log check passes. The log check establishes that SMAPI resolved and loaded the mod without errors; the mod's own Info-level marker, when present, is reported as a secondary signal. The script sends SIGTERM first, waits a brief grace period for graceful exit, and escalates to SIGKILL only if the process is unresponsive. No waiting for the `Saved` event — the mod emits no observable log marker on `Saved`, making it impossible to detect externally.

- Q: How should the script trigger save loading for the save check, given that SMAPI has no command-line save selection and the mod has no save selection logic? → A: Skip the save check entirely in the automated script. The title screen is the expected state — SMAPI has no `--load-save` argument, the mod is purely reactive, and automating title screen interaction would add significant complexity and fragility for a P2 feature. The save check is deferred until the basic smoke test works and the team has real usage data.

- Q: Should WARN-level log entries from the mod cause the smoke test to fail, or only Error/Alert? → A: Only Error/Alert entries cause failure. WARN-level entries (if ever added to the mod) are logged but do not fail the smoke test. Industry consensus supports binary pass/fail based on errors only (Fowler 2006, Google Testing Blog, Microsoft DevOps, Atlassian). The mod currently emits zero WARN messages; this clarification is future-proofing. The existing spec's "Failure markers include Error/Alert level entries" deliberately excludes WARN.

- Q: Should the script detect and handle an already-running game instance before launching? → A: Yes. The script detects an existing Stardew Valley/SMAPI process and aborts with a descriptive error by default. An explicit `--force` flag kills existing instances (SIGTERM then SIGKILL) before launching. This is a correctness requirement: the mod has no cross-process locking (all locks are process-local), so concurrent instances would corrupt data files (non-atomic JSON writes) and truncate the SMAPI log. (Internal: zero process detection in codebase; Research: Politowski et al. 2022, mc-runtime-test ephemeral pattern, flock gold standard)

- Q: Should the script prevent concurrent executions? → A: Yes. The script uses `flock` on a dedicated lock file to ensure only one instance runs at a time. The kernel automatically releases the lock on process death (even SIGKILL), eliminating stale-lock risk. This aligns with FR-010's "lock files" reference and FR-008's idempotency requirement. (Research: flock kernel-managed atomicity, Debian bug #1095028 xvfb-run 26-40% failure rate, cc-ci production pattern)

- Q: Should the script validate prerequisites before launching the game? → A: Yes. The script includes a pre-flight phase that validates: (1) game installation exists, (2) SMAPI is installed and functional, (3) Xvfb is available. Errors follow the "What → Where → How to fix" pattern with distinct exit codes per failure category (one code per category; see FR-007). This mirrors the existing CI preflight pattern (build_and_test.yml:87-109, 6-assembly check) and scripts/check-protected-paths.sh conventions (set -euo pipefail, table-driven checks, aggregated failure count). (Internal: mod has zero prerequisite self-validation; Research: IEEE 829-2008, xUnit fixture patterns, Meszaros 2007)

(FR-007, FR-012 item 9, FR-017.)
- Q: Which path-hardening controls should survive for a local, single-user script? → A: **A minimal, correctness-oriented posture.** The threat model is "the attacker is the maintainer", who already owns every file the script can reach, so there is no privilege boundary to cross. The percent-encoding clause, the absolute-path rejection, the save-name allowlist, the shell-metacharacter rejection, `printf '%q'` and the ported `sanitize_path_segments()` are all removed — each is either vacuous, contradicts the script's own CLI surface, or has no call site. "Never stat before open" is kept as the load-bearing rule; the symlink check is demoted to a diagnostic, not a gate. Canonicalisation plus a component-boundary prefix test is kept, and it applies only to paths the script *constructs* — user-supplied roots are their own bases. **The `python3`/`uconv` NFC dependency is dropped**: NFC is a provable no-op for ASCII paths (UAX #15) and is not a homoglyph defence; an explicit ASCII allowlist `[A-Za-z0-9._/-]+` replaces it, which is stricter and dependency-free. (FR-012 item 7.)
- Q: How is the X display chosen, and in what order do the pre-flight checks run? → A: **The X server allocates the display.** Xvfb is started with `-displayfd`, so the server binds the first free display atomically; the script reads the number back and records it. The fixed `:99` and the whole `/tmp/.X{n}-lock` → exit-`10` policy are dropped, because `-displayfd` disables the server lock entirely (`DisableServerLock()`) and a harness-created lock file is at best useless and at worst a local denial-of-service vector. Exit `10` is redefined as "the virtual display could not be allocated or started" and is raised when Xvfb fails to start or reports no display number. The pre-flight order is pinned: required-tool presence → game and SMAPI path checks → Steam prerequisite → crash-marker removal → start the display and probe software OpenGL; then build-and-verify, flock, process detection, log baseline, launch. (FR-012 item 0 and item 5, FR-010 item 3, FR-001.)
- Q: Does `timeout` wrap the game launch or the log poll, and what exactly is "readiness"? → A: **The poll only, and the sentinel alone is readiness.** The game is a direct background child of the script, so `$!` is simultaneously its PID and its process-group ID; wrapping the launch in `timeout` would break that. The timeout is enforced by a deadline poll loop over the log; `timeout` may bound the poll as a belt-and-braces wrapper. The `Loaded N mods:` / `Skipped mods` signals are the *verdict*, evaluated immediately after the sentinel, and are never part of the readiness condition — polling for "the mod is listed" would turn a mod-load failure into a timeout. The `--kill-after=30` form is dropped: the escalation window is `--grace-period` (15 s). (FR-002, FR-005, FR-009.)
- Q: Should the spec gain a Scope section, and how should SC-004/SC-005/SC-006 be worded? → A: **Yes — the spec gains an explicit `## Scope` section** with in-scope, out-of-scope and **declared side effects** (the script deletes and recreates `<mods-path>/LivingRoots/`, writes `LivingRoots/bin/`, removes stale SMAPI log artifacts, and creates a lock file it leaves in place). SC-004 and SC-005 are re-worded as explicitly **not evaluated** in this release; SC-005 drops its false cross-reference to spec 004's SC-008, which is a manual-playtest *discoverability* criterion that states "No automated task covers this criterion". SC-006 becomes measurable: it names the concrete properties of the guide. User Story 2's scenarios are re-labelled as **deferred future-state** so they no longer read as present-tense requirements that contradict FR-004 and FR-006. (Scope section, SC-004…SC-006, US2.)
- Q: Should new test cases be added for FR-014, FR-015 and FR-007's translation table? → A: **Yes — three new cases.** TC-15 (the run log exists at the FR-014 path with the run ID, `VERSION` and launch timestamp; the verdict on stdout, the diagnostics on stderr), TC-16 (`--help` completeness — each of the FR-015 obligations present), TC-17 (status translation — a table-driven harness feeding each raw status to the translator and asserting the mapped code). TC-12's title is corrected (it contradicted its own input) and it is given a decidable expected result — exit `15`. (quickstart.md TC table.)
- Q: How deep should the troubleshooting guide go? → A: **An ordered, branching ladder.** The flat symptom→cause→remediation table is converted into a ladder (D-1…D-n) where each step states the exact command, its expected result, the branch when it does not hold, the remediation, and the post-fix expectation; the existing exit-code table is kept as a quick-reference index at the end. The order follows decreasing likelihood with cost as the tiebreak. (quickstart.md Troubleshooting.)
- Q: Should the repository gain a shell lint gate, and does CI integration stay out of scope? → A: **A local pre-commit hook, and CI stays out of scope.** `lefthook.yml` gains a `bash -n` syntax check and a `shellcheck` run over `scripts/*.sh`; no GitHub Actions job is added and no `required_status_checks` entry is created, so the repo's own warning about promoting a dormant job is respected. The exit-code contract remains CI-interpretable by design, and the three YAML-specific checklist items are re-worded to describe script-side properties rather than a pipeline that does not exist. (lefthook.yml; FR-013 unchanged.)
- Q: Should the log header region be exempted from the post-sentinel rule, and should `SMAPI_USE_CURRENT_SHELL` be dropped? → A: **Yes to both.** The version banner and the `Mods go here:` line precede the sentinel and are therefore exempt from the "only after the sentinel" rule — they may be read for context but never gate the verdict. Every gating signal remains strictly post-sentinel. The `Mods go here:` path is `~`-anonymised by SMAPI, so any comparison against the resolved `--mods-path` compares the home-relative form. `SMAPI_USE_CURRENT_SHELL` is **removed** from FR-001, FR-015, the `--help` contract and `research.md`: it is read only by SMAPI's installer wrapper, never by `StardewModdingAPI.dll`, so it is inert when the apphost is launched directly. (FR-002 "Header region (MUST)", FR-001, FR-015, FR-006.)

## Assumptions

- The game (Stardew Valley) is installed via Steam on Linux at `~/.steam/steam/steamapps/common/Stardew Valley/`
- SMAPI 4.5.2 is installed and functional in the game directory. The installation is a **self-contained** .NET 6 `linux-x64` deployment — `libcoreclr.so`, `libhostfxr.so`, `libhostpolicy.so`, and `System.Private.CoreLib.dll` all ship in the game directory — so no system .NET or Mono runtime is required or probed. Mono is not involved: SMAPI 4.x targets .NET 6, not .NET Framework.
- SMAPI's launcher `StardewModdingAPI` is a native ELF apphost and MUST be invoked from the game directory
- The game ships `steam_appid.txt` (`413150`), so **no running Steam client is required**; Steam only disables achievements, logging "Oops! Steam achievements won't work because Steam isn't loaded." at Error level from SMAPI core (not from the mod, so it does not affect the mod-scoped Error/Alert gate)
- `Xvfb` MUST be installed (`xorg-x11-server-Xvfb` / `xvfb`) — it is **not** present by default, and the pre-flight MUST fail closed with exit code `9` when it is missing (a missing binary is a missing host tool; `3` is reserved for a graphics stack that is present but unusable). `mesa-utils` (`glxinfo`, `xdpyinfo`) and Mesa's `libgallium`/`libGL` are also required. The .NET **SDK** (`dotnet`) is required on the host because the script rebuilds the mod before every run (FR-016), even though the game itself needs no host .NET runtime
- The Xvfb display runs under the minimal posture recorded in Clarifications ("Session 2026-10-19 (checklist review)"): `-nolisten tcp` with the display allocated by the server via `-displayfd`, and with **no** MIT-MAGIC-COOKIE-1 / xauth hardening. The X11 Unix socket therefore carries Xorg's default permissions, and any local user could attach to the display. `-nolisten tcp` removes the network exposure. This residual risk is **accepted** on the grounds that the script runs on a single-user maintainer machine (plan.md → Target Platform); it is recorded here so the risk is explicit rather than implicit.
- The mod is deployed into the resolved mods directory (default `<game-path>/Mods`) by the build; the script rebuilds and redeploys it before each run, with the build's deploy target pinned to the resolved mods path via `-p:GameModsPath` (FR-016). The repository-local `.gamepath/Mods/` copy is a build-output artifact and is **not** the copy under test
- The mod assembly carries **no** source-tree identity: `manifest.json` declares a fixed `Version` (`0.0.1`), the assembly a hardcoded `AssemblyVersion` (`1.0.0.0`), no commit identifier is embedded, and `SourceRevisionId` is inert because the project sets `GenerateAssemblyInfo=false`. FR-016 therefore asserts **deploy effectiveness** (the deployed assembly is byte-identical to the one this run built), not source correspondence; the latter would require changing `LivingRoots.csproj` and is out of scope
- The host paths used by the script are expected to be **ASCII**: path components are validated against `[A-Za-z0-9._/-]+` and no Unicode normalization is performed. This is a deliberate trade — NFC normalization is a provable no-op for ASCII paths (UAX #15) and is not a homoglyph defence, so it would have added a `python3`/`uconv` dependency for no benefit
- The SMAPI log location follows the Linux convention: `~/.config/StardewValley/ErrorLogs/` (SMAPI's `Constants.DataPath` + `ErrorLogs`). This directory has **never** contained an `SMAPI-latest.txt` on the maintainer's machine — the mod has never been executed in the real game — so the path is a documented convention rather than an observed artefact, and `--smapi-log` remains available as an override
- The mod persists data through SMAPI's `IModHelper.Data.WriteJsonFile` under `~/.config/StardewValley/.smapi/mod-data/lfgranja.LivingRoots/`, with keys prefixed `soil_health_data_` and `composting_bins_` (per `ModConstants.KeyPrefix` and `CompostingBinKeyPrefix`) and the save folder name sanitized (Unicode FormC + `FileNameSanitizationService`) as part of the filename
- The game can be launched headless via Xvfb with Mesa software rendering. This is **unverified**: the only prior launch attempt on the maintainer's machine failed with "Failed to create graphics device! GPU: Could not detect." The pre-flight's `glxinfo` probe (FR-012 item 4) is the control for this assumption
- The game process can be terminated via SIGTERM/SIGKILL immediately after the log check passes — the script does not wait for the `Saved` event because the mod emits no observable log marker on `Saved`
- The script is intended for local execution by the maintainer, not CI integration (CI may be added later). The script uses proper exit codes (0/non-zero) so future CI integration is straightforward.
