# Feature Specification: Smoke Validation Script

**Feature Branch**: `008-smoke-validation`

**Created**: 2026-10-19

**Status**: Draft

**Input**: Assessment `automate-ingame-testing` (intake + research + define + shape + decision, verdict: go, Option A)

## User Scenarios & Testing

### User Story 1 - Automated smoke validation of mod loading (Priority: P1)

As the maintainer, I want a script that launches the game with the mod installed and reports whether the mod loaded without errors, so that I can verify the mod works in the real game without manual play-through.

**Why this priority**: This is the immediate blocker — the mod has never been executed in the real game. Without this, no gameplay-affecting feature (spec 005 growth, quality, extra harvest) can be activated with confidence.

**Independent Test**: Can be fully tested by running the script and checking its exit code (0 = mod loaded without errors, non-zero = errors found). Delivers value by providing a repeatable, auditable signal that the mod loads correctly in the game. The save check (User Story 2) is deferred — see FR-004.

**Acceptance Scenarios**:

1. **Given** the game is installed and the mod is deployed in the mods folder, **When** the script runs, **Then** the script launches the game with SMAPI + mod, waits for initialization, checks the SMAPI log for errors, and exits with code 0 if no errors are found. The script terminates the game immediately after the log check passes (see FR-005).
2. **Given** the mod has a runtime error during load, **When** the script runs, **Then** the script detects the error in the SMAPI log and exits with a non-zero code and a descriptive message
3. **Given** the script has run successfully once, **When** the script runs again, **Then** it produces the same result (idempotent)
4. **Given** the assembly deployed into the mods directory is not the one produced by the current build, **When** the script runs, **Then** it fails before launching the game with a non-zero code and a message naming both SHA-256 digests (see FR-016)
5. **Given** a previous run left a `SMAPI-latest.txt` that already contains the mod's success marker, **When** the script runs, **Then** the stale content is not used to decide the verdict — only log lines after the current run's `Log started at` sentinel are evaluated (see FR-002)
6. **Given** SMAPI skipped the mod (for example because the installed SMAPI is older than the mod's `MinimumApiVersion`), **When** the script runs, **Then** the script reports a mod-load failure with SMAPI's stated reason (see FR-003)

---

### User Story 2 - Mod data persistence verification (Priority: P2, Deferred)

As the maintainer, I want the script to verify that the mod's data files appear in SMAPI's mod-data folder after the game loads with a save, so that I can confirm the mod's persistence layer works in the real game.

**Why this priority**: Loading without errors is necessary but not sufficient — the mod must also persist data correctly. This is the second half of the smoke test.

**Status**: Deferred. The automated script cannot load a save (SMAPI has no command-line save selection, and the mod is purely reactive). The title screen is the expected state. This user story will be implemented after the basic smoke test (User Story 1) works and the team has real usage data.

**Independent Test**: Can be fully tested by running the script and checking that SMAPI's mod-data folder for the mod (`~/.config/StardewValley/.smapi/mod-data/lfgranja.LivingRoots/`) contains the expected JSON files (`soil_health_data_*.json`, `composting_bins_*.json`). Delivers value by confirming the mod's persistence pipeline works end-to-end.

**Acceptance Scenarios**:

1. **Given** the game has a save file loaded with the mod active, **When** the script completes its check, **Then** SMAPI's mod-data folder for the mod contains at least one file matching the mod's data prefix
2. **Given** the mod failed to persist data files, **When** the script completes its check, **Then** the script reports the missing data files and exits with a non-zero code

### Edge Cases

- What happens when the game crashes during launch? The script should detect the crash (non-zero process exit or SMAPI-crash.txt) and report failure.
- What happens when the mods path is incorrect? The script should detect that the mod was not loaded (the mod's name is absent from SMAPI's `Loaded N mods:` block, or it appears in the `Skipped mods` section) and report failure.
- What happens when the save file does not exist yet? The save check is deferred (see FR-004). The title screen is the expected state in the automated script.
- What happens when the game takes longer than expected to load? The script should have a configurable timeout and report a timeout failure if the game does not produce a log within the expected window.
- What happens when the display (Xvfb) is not available? The script should detect this and report a clear error message.
- What happens when the game is already running? The script detects the existing process (via `pgrep`) and aborts with a descriptive error by default. An explicit `--force` flag kills the existing instance (SIGTERM then SIGKILL) before launching.
- What happens when another smoke test instance is already running? The script fails to acquire the `flock` and exits immediately with a descriptive error.
- What happens when a prerequisite is missing (game not installed, SMAPI not found, Xvfb not available)? The pre-flight phase detects it and emits an actionable error ("What → Where → How to fix") with a distinct exit code per failure category.
- What happens when the script is interrupted (Ctrl+C) during execution? The EXIT trap runs cleanup: game process killed, Xvfb killed, X11 locks removed, temp files cleaned. The script exits with code 130 (SIGINT) or 143 (SIGTERM).
- What happens when a previous run left a `SMAPI-latest.txt` that already contains the mod's success signal? The script MUST ignore every log line preceding the current run's `Log started at` sentinel (see FR-002), so a stale log can never produce a false pass.
- What happens when the mod build deployed into the mods directory is stale (older than the current source)? The digest assertion in FR-016 MUST fail the run before the game is launched, and the failure message MUST name both the built and the deployed SHA-256 digests.
- What happens when the game fails to create a graphics device (no usable OpenGL under Xvfb)? The script MUST report this as a graphics/environment failure (exit code `3`), not as a timeout or a mod-load failure. The pre-flight's `glxinfo` probe is expected to catch this condition before launch.
- What happens when the game process exits with status `0` but no log was produced? The script MUST report failure. This occurs when SMAPI re-asserts its dependency manifest after a game update and asks the user to relaunch.
- What happens when a leftover `SMAPI-crash.txt` is present from an earlier crash? The pre-flight MUST remove it before launch (see FR-012 item 6), because SMAPI's handling of a leftover crash marker performs a blocking keypress read that would hang the headless run.
- What happens when the resolved mods directory contains a stale copy of the mod while a current copy exists elsewhere? The script tests only the directory it resolved and passed to SMAPI via `--mods-path` (see FR-017); it does not search for other copies.

## Requirements

### Functional Requirements

- **FR-001**: The script MUST launch the Stardew Valley game via SMAPI with the mod installed, using a virtual display (Xvfb) for headless operation. The launch MUST run SMAPI's native apphost `./StardewModdingAPI --no-terminal` from the game directory (`--game-path`), which MUST be the process working directory — SMAPI resolves its dependencies, the `Mods/` folder, and the log directory relative to that directory, and a relocated copy of the launcher aborts with SIGABRT (exit 134). The script uses SMAPI's officially supported automation env vars: `SMAPI_NO_TERMINAL=true`, `SMAPI_USE_CURRENT_SHELL=true`, and `SMAPI_DEVELOPER_MODE=true`. `SMAPI_DEVELOPER_MODE` gates **console** verbosity only — SMAPI writes TRACE-level entries to the log file unconditionally, so TRACE-level diagnostics are available without it; it is retained because it makes the launch console output usable for debugging. The script MUST additionally export `LIBGL_ALWAYS_SOFTWARE=1` and `GALLIUM_DRIVER=llvmpipe` to force Mesa software rendering, and MUST set `SDL_VIDEODRIVER=x11` (never `wayland`) because the game bundles `libSDL2` and Wayland cannot be used against an Xvfb display. Xvfb MUST be started with `-nolisten tcp` on a non-default display (e.g., `:99`).
- **FR-002**: The script MUST wait for the game to initialize and produce a SMAPI log file **that belongs to the current run** before performing checks. The SMAPI log path defaults to `~/.config/StardewValley/ErrorLogs/SMAPI-latest.txt` (Linux convention) and MAY be overridden via `--smapi-log`. Before launching, the script acquires an exclusive `flock` on a dedicated lock file (non-blocking) to prevent concurrent executions. If the lock cannot be acquired, the script exits immediately with a descriptive error.

  **Log freshness (MUST).** SMAPI unlinks `SMAPI-latest.txt` at startup and creates a new file, and writes an in-band per-run sentinel line `Log started at {UTC timestamp} UTC` near the top of every log. The script MUST therefore: (1) record the UTC launch timestamp `T0` before starting the game; (2) wait for a `Log started at` sentinel whose timestamp is **not older than `T0`**; and (3) evaluate every success and failure signal **only against log lines that follow that sentinel line**. Signals appearing before the sentinel belong to a previous run and MUST be ignored. This ordering requirement is what prevents a stale log left by an earlier successful run from producing a false pass. As a belt-and-braces assertion, the script MUST record the log file's inode (`stat -c %i`) before launch and verify it changed once the log is (re)created.

  **Pre-launch cleanup (MUST).** The script MUST remove a pre-existing `SMAPI-latest.txt` and `SMAPI-crash.txt` before launching. Removing the crash file is required because SMAPI's startup handling of a leftover crash marker performs a blocking `Console.ReadKey()`, which can hang a headless launch indefinitely.

  **Readiness vs. exit (MUST).** If the game process exits **without** producing a log — including an exit status of `0` — the script MUST report failure, not success. SMAPI's dependency-assertion routine exits with status `0` and the message "Please exit this window and re-launch SMAPI to play" after a game update, which would otherwise be mistaken for a successful run.
- **FR-003**: The script MUST parse the SMAPI log file for errors attributable to the mod (LivingRoots). Log entries follow the format `[HH:mm:ss LEVEL     SOURCE] message` — the level field is padded to 8 characters, the source column carries the mod's manifest name for mod-originated entries, and lines are CRLF-terminated, so matching MUST be substring-based (`grep -F`) with any trailing carriage return stripped before an exact comparison. Per-line timestamps carry no date and MUST NOT be used to identify a run. Only Error and Alert level entries are failure markers. WARN-level entries (if ever added to the mod) are logged but do not fail the smoke test. Trace-level entries are written to the log file by SMAPI unconditionally and are captured for diagnostic purposes only — they do not fail the test but provide exception type and HResult information in failure reports. The success marker match is case-sensitive and exact.

  **Success gate (MUST).** The success gate is computed from SMAPI's own mod-resolution output, not from the mod's self-reported marker: (1) SMAPI MUST have emitted a `Loaded N mods:` block, (2) the mod's manifest name (`Stardew Valley - Living Roots`) MUST appear as a listed entry within that block, and (3) the mod MUST NOT appear in SMAPI's `Skipped mods` section. The mod's own marker line (`The 'Stardew Valley - Living Roots' mod was loaded successfully!`) MUST still be detected and reported, but it does **not** gate success: it is emitted by the mod from its `GameLaunched` handler (`ModController.cs:959`), which runs only after the game has reached the title screen, so gating on it would couple the smoke test to a working graphics device and would report a graphics failure as a timeout rather than as the environment problem it is.
- **FR-004**: The script SHOULD verify that the mod's data files are present in SMAPI's mod-data folder for the mod (`~/.config/StardewValley/.smapi/mod-data/lfgranja.LivingRoots/`) after the game has run with a save loaded — checking for `soil_health_data_*.json` and `composting_bins_*.json`. In the current implementation the save check is always skipped (with a `SKIPPED:` warning) because the automated script cannot load a save (SMAPI has no command-line save selection, and the mod is purely reactive — it only responds to SMAPI events after a save is loaded via the title screen UI). The title screen is the expected state. The save check is deferred until the basic smoke test works and the team has real usage data; it does not gate success (see FR-006).
- **FR-005**: The script MUST terminate the game process immediately after the log check passes, without leaving orphaned processes. The script launches the game in its own process group and sends SIGTERM to the entire group first, waits a configurable grace period (default 15s, via `--grace-period`) for graceful exit, and escalates to SIGKILL only if the process is unresponsive. The script does NOT wait for the `Saved` event — the mod emits no observable log marker on `Saved`, making it impossible to detect externally. The script traps SIGINT and SIGTERM to forward signals to child processes (game + Xvfb) and exits with code 128+N (130 for SIGINT, 143 for SIGTERM). An EXIT trap serves as universal safety net for all termination paths.
- **FR-006**: The script MUST report success (exit code 0) when the log check passes. The log check uses an AND conjunction: success requires the mod to be listed in SMAPI's `Loaded N mods:` block AND the mod to be absent from SMAPI's `Skipped mods` section AND no Error/Alert entries from the mod. All three signals MUST be evaluated against log lines that follow the current run's `Log started at` sentinel (see FR-002). The mod's own success marker, when present, MUST be reported in the result output as a secondary signal but does not gate the verdict. The save check is deferred (see FR-004) and does not gate success in the current implementation. The success message MUST be exactly `SUCCESS: Mod loaded without errors.`
- **FR-007**: The script MUST report failure (non-zero exit code) with a descriptive message when any check fails. Failure messages MUST follow the "What → Where → How to fix" pattern: identify the failed component, the specific error, relevant log context (last 20-30 lines of the SMAPI log including Trace-level entries that follow any Error entry), and an actionable remediation hint. Exit codes MUST follow the sysexits.h convention with distinct codes per failure category (e.g., 1=game not found, 2=SMAPI not found, 3=Xvfb not available, 4=timeout, 5=mod load failure). The timeout category (`4`) is canonical: when the `timeout` utility is used to bound an operation, its native exit status `124` MUST be translated to `4` at the script boundary so that no subprocess-specific status ever becomes the script's final code. The following additional categories are defined: `9` = missing host tool or runtime dependency (a required binary is absent, or the bundled .NET runtime cannot be resolved), `10` = display conflict (the chosen X display is owned by a live server, or a stale X11 lock could not be reclaimed), and `11` = Steam API prerequisite missing (`steam_appid.txt` absent or wrong). Codes `1`–`7` and the POSIX `128+N` interruption codes are unchanged by this addition.
- **FR-008**: The script MUST be idempotent — running it multiple times in sequence produces the same result
- **FR-009**: The script MUST accept a configurable timeout for game launch and initialization via command-line argument, with a 120-second default. The script polls the log continuously (no wasted time), and the timeout only matters for failure cases.
- **FR-011**: The script MUST detect an existing Stardew Valley/SMAPI process before launching. By default, the script aborts with a descriptive error listing the conflicting PIDs. An explicit `--force` flag kills existing instances (SIGTERM → SIGKILL escalation) before launching. This is a correctness requirement: the mod has no cross-process data file locking, so concurrent instances would corrupt data and truncate the SMAPI log.
- **FR-012**: The script MUST include a pre-flight phase before launching that validates: (1) the game installation exists at the expected path (configurable via `--game-path`, default `~/.steam/steam/steamapps/common/Stardew Valley/`) and contains the game assembly (`Stardew Valley.dll`) and SMAPI's launcher (`StardewModdingAPI`); (2) SMAPI is installed and functional — this means the main assembly `StardewModdingAPI.dll` is present and its version can be parsed, the dependency assemblies `smapi-internal/SMAPI.Toolkit.dll` and `smapi-internal/SMAPI.Toolkit.CoreInterfaces.dll` are present, and the `StardewModdingAPI` apphost is executable for the host architecture. No SMAPI release ships a file named `smapi-internal/SMAPI.dll`; probing for that path produces a false negative on a correct installation, so the check MUST use the paths listed here; (3) Xvfb is available and runnable (`command -v Xvfb` plus a version probe); (4) software OpenGL rendering is genuinely usable — the script MUST start the virtual display, confirm with `xdpyinfo` that the `GLX` and `RANDR` extensions are present, and confirm that `glxinfo -B` under `LIBGL_ALWAYS_SOFTWARE=1` exits successfully and reports a software renderer (`llvmpipe` or `softpipe`); the mere presence of `libGL.so` does NOT satisfy this check; (5) no orphaned Xvfb on the chosen display or stale X11 lock files remain from a previous crashed run — a lock file whose owning PID is no longer alive is stale and MUST be removed with logging, while a lock file owned by a live process MUST abort the run with exit code `10` and MUST NOT be removed; (6) any pre-existing `SMAPI-crash.txt` is removed to avoid false positives, and to avoid SMAPI's blocking keypress prompt hanging a headless launch; and (7) a Unicode normalizer is available (`python3`, or `uconv` as fallback) for NFC path normalization and symlink-safe file opens (`O_NOFOLLOW`). The pre-flight phase MUST fail closed when the normalizer is absent, with the same "What → Where → How to fix" pattern and the graphics/environment exit code. A missing host tool or an unresolvable runtime MUST fail closed with exit code `9`.
- **FR-010**: The script MUST clean up temporary resources on exit, including on failure and interruption. Cleanup includes: (1) kill game process (SIGTERM → SIGKILL escalation), (2) kill Xvfb process, (3) remove X11 lock files (`/tmp/.X{n}-lock` and `/tmp/.X11-unix/X{n}`), (4) remove temp files/directories, (5) the flock is auto-released by the kernel on process death. Each cleanup step MUST be isolated (guarded with `|| true`) so one failure does not prevent others. The cleanup order is reverse of allocation: game first, then Xvfb, then locks and temp files.

- **FR-013**: The script MUST remain local-first: no CI integration and no machine-parseable (`--json`) output mode in the current scope. Proper exit codes (0/non-zero) are retained so future CI integration is straightforward.
- **FR-014**: The script MUST log every process lifecycle event with a timestamp and level prefix — spawn (game, Xvfb), every signal sent (including the PID and the signal), the grace period, the escalation to SIGKILL, and the observed exit — so that a failed run can be reconstructed from the run log alone. On any unhandled error, the ERR trap MUST report the script name, the failing line number, the enclosing function name, and the exit code.

  **Run log (MUST).** The script's own diagnostic output is the **run log**, and it is distinct from the SMAPI log. The run log MUST be written to a file at `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/<run-id>.log`, in a directory created with mode `0700`. Each run MUST write its own file (no shared append-only file) so that concurrent runs cannot interleave. The run log MUST contain every line the script emits at any level, including the lifecycle events above.

  **Run ID and version (MUST).** The script MUST generate a run ID of the form `<UTC timestamp>-<PID>` (e.g. `20261019T183302Z-48213`) and MUST stamp it on every run-log line, in the stdout summary, in every error message, and in the path of the run log file. The script MUST define a `VERSION` constant (first release `0.1.0`) and MUST report it in the stdout summary, in the run-log header, and in the `--help` output. The run ID and `VERSION` are the correlation keys required by the escalation evidence bundle.

  **Streams (MUST).** The verdict and the `--help`/`--version` output go to stdout; all level-prefixed diagnostics and error messages go to stderr. The exit code remains the sole machine-readable signal (see FR-013).
- **FR-015**: The script's `--help` output MUST document the automation environment variables it sets (`SMAPI_NO_TERMINAL=true`, `SMAPI_USE_CURRENT_SHELL=true`, `SMAPI_DEVELOPER_MODE=true`, `LIBGL_ALWAYS_SOFTWARE=1`, `GALLIUM_DRIVER=llvmpipe`, `SDL_VIDEODRIVER=x11`, and `DISPLAY`) in a dedicated "Environment (set automatically)" section, stating explicitly that they are managed by the script and are not user-configurable. The `--help` output MUST also document the `--mods-path` option (see FR-017), the run-log location, the run ID format, the script `VERSION`, and every exit code.
- **FR-016**: The script MUST ensure that the mod build under test is the build produced from the current source tree, and MUST abort before launching the game if it cannot. The script MUST build the mod with `dotnet build --configuration Release --no-incremental` after removing the deploy target directory, MUST abort with a non-zero exit status if the build fails, and MUST then assert that the deployed `Mods/<ModFolderName>/<EntryDll>` is byte-identical to the freshly built assembly by comparing SHA-256 digests. Comparing digests rather than modification times is required because the mod carries no build identity: `manifest.json` declares a fixed `Version` that is never bumped, the assembly declares a fixed `AssemblyVersion`, and no commit identifier is embedded. The deployed manifest version alone MUST NOT be used as the freshness assertion, because it is invariant across builds.
- **FR-017**: The script MUST resolve the mods directory explicitly and MUST NOT depend on SMAPI's implicit default. The mods directory MUST be configurable via `--mods-path`, defaulting to `<game-path>/Mods`. The script MUST pass the resolved directory to SMAPI using the `--mods-path` argument (equivalently `SMAPI_MODS_PATH`), and the pre-flight MUST verify that the resolved directory exists and contains the mod folder (`Mods/<ModFolderName>/manifest.json` with a matching `UniqueID`). A relative `--mods-path` value MUST be resolved against the game directory, matching SMAPI's own semantics.
### Key Entities

- **SMAPI Log**: The log file produced by SMAPI at `~/.config/StardewValley/ErrorLogs/SMAPI-latest.txt` (Linux). Entries follow the `[HH:mm:ss LEVEL     SOURCE] message` format — the level field is padded to 8 characters, the source column carries the mod's manifest name for mod-originated entries, and lines are CRLF-terminated. Six levels are recognized (TRACE, DEBUG, INFO, WARN, ERROR, ALERT). The script parses this to (a) detect SMAPI's mod-resolution output (`Loaded N mods:` block and `Skipped mods` section), (b) detect the mod's own success marker ("The 'Stardew Valley - Living Roots' mod was loaded successfully!" — emitted by the mod, not by SMAPI), and (c) detect any Error/Alert entries attributable to the mod. The log begins with a per-run sentinel line `Log started at {UTC timestamp} UTC`; only lines after that sentinel belong to the current run. `SMAPI-crash.txt` (if present) overrides `SMAPI-latest.txt` and indicates failure.
- **Loaded Mods Manifest**: SMAPI's own report of the mods it resolved, emitted in the log as a `Loaded N mods:` block with one `   <Name> <Version> by <Author>` line per mod, followed by an optional `Skipped mods` section naming the reason for each skip (for example "because it needs SMAPI X or later"). This is the authoritative signal for whether the mod was loaded, and it is available without the game having reached the title screen. The same log also records the resolved mods directory (`Mods go here: <path>`) and the SMAPI version banner (`SMAPI <version> with Stardew Valley <version> on <os>`).
- **Mod Build Artifact**: The compiled mod assembly `LivingRoots.dll` and its manifest, deployed by the build into the resolved mods directory (`<mods-path>/LivingRoots/`). The assembly carries no build identity — `manifest.json` declares a fixed `Version` (`0.0.1`), the assembly declares a fixed `AssemblyVersion` (`1.0.0.0`), and no commit identifier is embedded — so freshness MUST be established by comparing the SHA-256 digest of the deployed assembly with the digest of the assembly produced by the current build (see FR-016). Two copies of this artifact may coexist in the workspace (a repository-local `.gamepath/Mods/` copy and the copy in the game installation); only the copy in the resolved mods path is under test.
- **Mod Data Files**: The mod persists data as JSON sidecar files written through SMAPI's `IModHelper.Data.WriteJsonFile`, which resolves relative names against SMAPI's mod-data directory — `~/.config/StardewValley/.smapi/mod-data/<UniqueID>/` (here `<UniqueID>` = `lfgranja.LivingRoots`). The files are named `soil_health_data_<sanitizedSaveId>.json`, `composting_bins_<sanitizedSaveId>.json`, and `visualization_config_<sanitizedSaveId>.json`. The saveId is SMAPI's active save folder name (`Constants.SaveFolderName`), sanitized via Unicode normalization and filename sanitization. The mod does **not** write into a `data/` folder inside its own mod folder — that location is not used by SMAPI's helper API. When no save is loaded (fresh install/title screen), zero data files is the expected valid state.
- **Game Process**: The Stardew Valley process launched via SMAPI. The script manages this process lifecycle (launch, wait, terminate). Termination happens immediately after the log check passes. The script sends SIGTERM first, waits a brief grace period for graceful exit, and escalates to SIGKILL only if the process is unresponsive. The script does NOT wait for the `Saved` event — the mod emits no observable log marker on `Saved` (`ModController.cs:1089-1102`), making it impossible to detect externally.
- **Virtual Display**: The Xvfb display buffer that allows the graphical game to run headless. The script manages this resource lifecycle.
- **Run Log**: The script's own diagnostic output, written per run to `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/<run-id>.log` (see FR-014). It records every lifecycle event with a timestamp, level prefix, and run ID. It is distinct from the SMAPI Log and survives the run, so a failure can be reconstructed afterwards.

## Success Criteria

### Measurable Outcomes

- **SC-001**: The script can be executed from a clean state (no prior game process, no Xvfb) and produces a deterministic pass/fail result within a configurable timeout (default: 120 seconds)
- **SC-002**: When the mod loads without errors, the script exits with code 0 and reports exactly `SUCCESS: Mod loaded without errors.` — this is the expected baseline after a correct mod build
- **SC-003**: When the mod has a load-time error, the script exits with a non-zero code and reports the specific error message from the SMAPI log
- **SC-004**: *(Deferred — see FR-004.)* When the mod loads but does not persist data files to SMAPI's mod-data folder, the script exits with a non-zero code and reports the missing data files. Not implemented in the current version; the save check is always skipped with a `SKIPPED:` warning and does not gate success.
- **SC-005**: *(Deferred — see FR-004.)* The gate SC-008 (from spec 004) can be evaluated based on the script's result — a successful script run satisfies the "mod loads and persists data" portion of SC-008. In the current version only the "mod loads" portion is satisfied; the "persists data" portion remains unevaluated until the save check is implemented.
- **SC-006**: The script is documented with clear instructions for local execution and troubleshooting
- **SC-007**: When the game is already running, the script detects it and aborts with a descriptive error (or kills it with `--force`)
- **SC-008**: When another smoke test instance is already running, the script fails to acquire the flock and exits immediately
- **SC-009**: When a prerequisite is missing, the pre-flight phase detects it and emits an actionable error with a distinct exit code
- **SC-010**: When the script is interrupted (Ctrl+C), the EXIT trap runs full cleanup (game, Xvfb, X11 locks, temp files) and exits with code 128+N
- **SC-011**: When a previous run left a `SMAPI-latest.txt` containing the mod's success marker, the current run does NOT report success from that stale content — the verdict is derived only from lines following the current run's `Log started at` sentinel
- **SC-012**: When the assembly deployed into the mods directory differs from the assembly produced by the current build, the script exits non-zero **before** launching the game, and the failure message names both SHA-256 digests
- **SC-013**: The success verdict is derived from SMAPI's `Loaded N mods:` / `Skipped mods` output; a mod that SMAPI skipped (for example for an unmet `MinimumApiVersion`) is reported as a mod-load failure with SMAPI's stated reason, even though the game itself started successfully
- **SC-014**: Every run produces a retained run log under `${XDG_STATE_HOME:-$HOME/.local/state}/living-roots-smoke/runs/` containing the run ID, the script `VERSION`, the launch timestamp, and every lifecycle event, such that the run can be reconstructed from that file alone
