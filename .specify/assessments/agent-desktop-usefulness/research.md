# Idea Research: agent-desktop for the headless verification runner (spec 010)

- **Slug**: agent-desktop-usefulness
- **Created**: 2026-11-04
- **Evidence confidence (overall)**: high

**Idea under research**: whether `vercel-labs/agent-desktop` — a computer-use CLI that drives desktop apps through the OS accessibility tree — is useful for the functionality specified in `specs/010-headless-verification-runner/` (unattended Stardew Valley gameplay verification under Xvfb + SMAPI).

## Users & Demand

- The demand is internal and specific: the maintainer needs Gate 3 `machine-pass` for feature 004 without playing the game by hand; spec 010 exists to provide it. — [source: `specs/010-headless-verification-runner/spec.md` §Plain-Language Summary, US1] (confidence: high, cited)
- The concrete pain is currently T137: a real-host run produces `partial` with `signalsComplete=false`, so promotion to `machine-pass` (T146) cannot happen. — [source: `specs/010-headless-verification-runner/verification/real-host.log`; `evidence-bundle-run-20261104T225246Z-4399/verdict.json`] (confidence: high, cited)
- No external user, issue, or roadmap item in this repository asks for desktop computer-use or accessibility-tree automation. The idea entered through a one-off question, not through observed demand. — [source: repo search for `agent-desktop`/`AT-SPI`/`computer use`; `.specify/assessments/agent-desktop-usefulness/intake.md`] (confidence: high, cited)
- What the spec actually asks for is deterministic, reproducible, non-interactive injection: SMAPI macros, save seeding, and custom console commands; input simulation is explicitly excluded. — [source: `specs/010-headless-verification-runner/spec.md` FR-006 and Clarifications 2026-10-26] (confidence: high, cited)

## Prior Art

- **Dedicated-server mods (Stardew Valley)**: established projects run the real game under `xvfb-run` and load/host a save through SMAPI mod code, with no GUI automation. This is the same architectural family as `LivingRoots.Verification`, which calls `SaveGame.Load(saveId)` directly from a mod event. — [source: `github.com/ObjectManagerManager/SMAPIDedicatedServerMod` README; `github.com/stardew-valley-dedicated-server/server` README; `LivingRoots.Verification/ModEntry.cs`] (confidence: high, cited)
- **Stardew Access**: a mature screen-reader/keyboard-only mod that narrates menus and world state. Its existence is evidence that the base game does not expose a usable OS accessibility tree; the mod reads game state through SMAPI and speaks through Tolk/libspeechdwrapper/libspeak, not AT-SPI. — [source: `github.com/stardew-access/stardew-access` README/docs; search-index excerpt] (confidence: high, cited)
- **Spec 010's own prior research**: input simulation (`xdotool`) was considered and rejected as fragile/non-deterministic; screenshots/OCR were scoped to supporting evidence only, because software GL rendering is not a correctness oracle. — [source: `specs/010-headless-verification-runner/research.md` alternative decisions; `spec.md` Clarifications 2026-10-26] (confidence: high, cited)
- **agent-desktop's own model**: it reads the OS accessibility tree and acts on a ref per element; it is explicitly not a pixel/coordinate tool, and apps that do not expose a tree are outside its reach. — [source: `github.com/vercel-labs/agent-desktop` README; `skills/agent-desktop-linux/SKILL.md`] (confidence: high, cited)
- **Existing verification harness**: spec 010 already ships `LivingRoots.Verification`, a dev-only SMAPI mod that consumes a file queue, loads the milestone save, advances days, dumps crop/soil state, and acknowledges each generation. No GUI driver is part of that design. — [source: `LivingRoots.Verification/ModEntry.cs`; `scripts/lib/injection.sh`] (confidence: high, cited)

## Market & Context

- `agent-desktop` is very new: Vercel Labs, Apache-2.0, announced around 2026-10-31, ~15k stars, ~1k forks, ~330 commits; the Linux adapter is part of the initial 1.0.x line. Maturity and API stability are therefore low compared with the runner's other dependencies. — [source: `github.com/vercel-labs/agent-desktop` repository page; search-index excerpts] (confidence: high for stars/license/age, medium for exact release version)
- Its Linux target is narrow: Ubuntu 24.04+ with GNOME 46 as the measured desktop, glibc ≥ 2.35, a running AT-SPI bus, a graphical session, and a window manager. The local host is Fedora 44 KDE on Wayland, with no `at-spi2-core` and no window manager installed. — [source: `skills/agent-desktop-linux/SKILL.md`; local `rpm -qa`, `command -v`, `lsb_release`] (confidence: high, cited)
- Alternatives already available and cheaper: X11 screenshot/window tools (`xwd`, ImageMagick `import`), SMAPI console commands, and the existing queue. These cover the only plausible diagnostic uses (a failure screenshot or a window listing) without a new runtime. — [source: `spec.md` screenshot policy; local tool inventory] (confidence: medium, cited/assumption)
- Cost of doing nothing is not created by the missing tool: T137 is blocked by a save-load failure inside the current design, which a desktop-automation tool cannot repair. — [source: full SMAPI log, see Evidence Against] (confidence: high, cited)

## Data & Constraints

- **The runner deliberately disables the accessibility bridge for the game**: `scripts/lib/launch.sh` exports `NO_AT_BRIDGE=1`, along with `SDL_VIDEODRIVER=x11`, `SDL_AUDIODRIVER=dummy`, `LIBGL_ALWAYS_SOFTWARE=1`, and `GALLIUM_DRIVER=llvmpipe`. Adopting agent-desktop would require reversing that choice and adding an AT-SPI bus to the game's environment. — [source: `scripts/lib/launch.sh`] (confidence: high, cited)
- **`list-apps` only shows apps registered on the accessibility bus.** SDL2/MonoGame games do not register an AT-SPI application; the game's dependency set includes `MonoGame.Framework.dll`, and the render loop is canvas-style. No refs means no `click @ref`, no `snapshot`, no semantic `type`. — [source: `skills/agent-desktop-linux/SKILL.md`; `gamepath.lock.json` assembly list; `github.com/stardew-access/stardew-access`] (confidence: high for the mechanism, medium for the specific SDL/AT-SPI registration claim)
- **Headed actions need a window manager.** The Linux skill documents that a window the WM never activated ends `activation_not_granted`; the runner's Xvfb starts without a WM (`openbox` is absent on this host). — [source: `skills/agent-desktop-linux/SKILL.md`; local `command -v openbox`] (confidence: high, cited)
- **The game did not stop after `LoadContent`.** The full SMAPI log shows it reached the title screen (`setGameMode('titleScreenGameMode (0)')`), attempted `getLoadEnumerator('farm-year1-day5')`, then logged `DebugOutput: File does not exist` and returned to title; the process stayed alive and kept rendering for minutes. The `artifacts/smapi-log.txt` in the bundle has only two lines because `signals_smapi_log_excerpt` greps for `elapsed|DayEnding|not main player`, not because the game stopped. — [source: `/tmp/tmp.EcGeZjLK6n/lr-save-BqbJ6l/xdg/config/StardewValley/ErrorLogs/SMAPI-latest.txt` lines 59–80; `scripts/lib/signals.sh:86`] (confidence: high, cited)
- **Likely root cause of T137**: the isolated save folder is `Saves/farm-year1-day5/`, but the main save file inside it is `Agroeco_421179919`, not `farm-year1-day5`. The loader's `File does not exist` is consistent with looking for `Saves/<name>/<name>`; the folder/inner-file name mismatch would make `SaveGame.Load('farm-year1-day5')` fail. This is inferred from the log plus the directory listing, not from a controlled experiment. — [source: `/tmp/tmp.EcGeZjLK6n/.../Saves/farm-year1-day5/` listing; SMAPI log lines 71–80] (confidence: high for the failure, medium for the exact lookup rule)
- **`verified` is human-only.** Even a perfect GUI driver could only produce runtime evidence (honesty level R); T148 reserves the E attestation for a maintainer. — [source: `spec.md` FR-016/FR-017; `tasks.md` T148] (confidence: high, cited)
- **Security/trust surface**: agent-desktop is an external native binary that reads snapshots, screenshots, clipboard, and window contents; the spec's integrity model pins game assets and bundle digests but has no slot for this dependency. Adding it would widen the trust boundary of the verification harness. — [source: agent-desktop README privacy note; `spec.md` FR-024–FR-027] (confidence: high, cited)
- **Dependency shape**: agent-desktop ships as an npm package with native binaries and helpers, plus an optional MCP server and a C FFI library. The runner currently depends on bash, Python, jq, Xvfb, `gh`/`curl`, and .NET; a Node/native toolchain would be a new class of dependency. — [source: agent-desktop README; `quickstart.md` Prerequisites] (confidence: high, cited)

## Evidence Against the Idea

1. **The core value is unavailable for this target.** agent-desktop's advantage is the accessibility tree; a canvas-rendered SDL2/MonoGame game exposes no AT-SPI tree, so there are no snapshot refs to act on. The tool's own docs describe game-like/canvas interfaces as outside the semantic path. All that remains is blind pointer/keyboard injection, which is the capability the spec explicitly rejected. — [source: `skills/agent-desktop-linux/SKILL.md`; `spec.md` FR-006] (confidence: high, cited)
2. **The T137 failure is a save-loading bug, not an input gap.** The game reached the title screen and called `SaveGame.Load`; the load failed with `File does not exist` because the save folder and the inner save file disagree (`farm-year1-day5` vs `Agroeco_421179919`). No amount of clicking, focus, or window management fixes a missing file. — [source: full SMAPI log; save directory listing] (confidence: high, cited)
3. **The premise "the game stalls without human input" is not supported by the full log.** The earlier diagnosis came from a two-line filtered excerpt. The game stayed alive at the title screen for minutes and rendered continuously; what it lacked was a loadable save, not a click. — [source: full SMAPI log; `scripts/lib/signals.sh:86`] (confidence: high, cited)
4. **It contradicts the spec's determinism contract.** FR-006 excludes input simulation as fragile and non-deterministic; agent-desktop's `press`, `mouse-click`, and `--headed` paths are the same class of physical input, just wrapped in a nicer CLI. A run driven that way would be harder to defend as `machine-pass`, not easier. — [source: `spec.md` FR-006 and Clarifications] (confidence: high, cited)
5. **The headless environment is hostile to it.** No window manager, no AT-SPI bus, `NO_AT_BRIDGE=1`, Fedora/KDE rather than the measured Ubuntu/GNOME target. Making it work would mean changing the environment under test and adding moving parts to the very harness whose job is to be reproducible. — [source: `scripts/lib/launch.sh`; `skills/agent-desktop-linux/SKILL.md`; local host inventory] (confidence: high, cited)
6. **It cannot raise the claim level.** The runner may write `machine-pass` only; `verified` requires a human E attestation (T148). A GUI automation tool changes neither the three-signal requirement nor the honesty ladder. — [source: `spec.md` FR-016; `tasks.md` T148] (confidence: high, cited)
7. **Marginal diagnostic value at real cost.** A failure screenshot or window listing is the only plausible use, and X11 tools already do that without a new native binary, MCP server, or clipboard-capable process in the trust boundary. — [source: `spec.md` screenshot policy; agent-desktop README] (confidence: medium, partly assumption)
8. **Maturity risk.** Linux support is days old at the time of this research (1.0.x, ~330 commits, 62 open issues, 101 open PRs). Pinning it would add upgrade and compatibility work to a verification gate that should change rarely. — [source: agent-desktop repository page] (confidence: medium, cited)

## Gaps & Open Questions

- [NEEDS CLARIFICATION: Is there a *separate* desktop-automation need outside spec 010 — e.g., a future mod manager, installer, or Steam/SMAPI GUI flow? The intake's "essa funcionalidade" is now clarified as spec 010, but the original question may have been broader.]
- [NEEDS CLARIFICATION: Does the maintainer want an agent-driven aid for the *human* Gate 3 session (T148), accepting that the attestation is still human E? If so, the value is convenience, not verification.]
- [NEEDS CLARIFICATION: Would adding a window manager and an AT-SPI session to the runner's Xvfb be acceptable if a future feature genuinely needs GUI automation? Today it would change the environment under test.]
- [NEEDS CLARIFICATION: Should the runner capture the *full* SMAPI log in the evidence bundle instead of the grep-filtered excerpt? The current excerpt caused a multi-day misdiagnosis of T137 and is arguably a bundle-quality bug independent of this idea.]
- Unverified by direct experiment: whether an SDL2 window ever appears in agent-desktop's `list-apps`/`list-windows` on a real AT-SPI session. The docs and the game's toolkit strongly suggest no, but a 30-minute spike would settle it. The save-load bug makes that spike irrelevant to T137 either way.
