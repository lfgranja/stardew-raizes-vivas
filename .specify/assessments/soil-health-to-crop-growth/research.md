- **Code-constraint relevant to the idea**: `CheckForOverflowUnderflow=true` project-wide; `Interlocked.CompareExchange` permitted for atomic flags; `Interlocked` is already used for the `FirstWins` lock (`HostAtomicLockService`); `volatile` fields exist. A growth roll on a tile must be computed once (`IsMainPlayer`) and persisted in save; clients read, never roll. `ModController.TryApplyCompostWithLock` (`:871-872`, `farmerId = Game1.player?.UniqueMultiplayerID ?? 0L`) and the `message.compost.action-conflict` refusal message show the concurrency model already exists.

## Evidence Against the Idea

The strongest counter-evidence comes from the repo itself, not from competitors:

- **The idea is not missing — it has never been attempted.** No internal spec, plan, or task for "soil health → crop growth" exists (`.specify/assessments/` has only `next-feature-80-20`; `specs/` has 001/002/003/004; 004 stops at the compost loop). The idea is not a rejected design — it is an un-started one.
- **The only verification mechanism is manual play-through.** With no SMAPI log and no save with mod data, any growth-change can only be validated by eye, not by automated test. Changing `Crop` state introduces a failure mode (wrong phase, wrong quality, double-dip with vanilla) that cannot be caught by `dotnet test`. The risk is not of wrong code — it is of **untested interaction with a live game**.
- **The competitive product delivers the claim with less documentation debt.** `ReGen Valley` already has the per-tile tracking, growth boost, quality/yield effects, and multiplayer handling — and ships. The idea's value is not the mechanism (already done) but the coherence of the framing (agroecology, multiplayer, honest documentation). That is a valid reason, but it is **not** a reason for urgency.
- **The agronomic claims need restraint to stay honest.** Teaching "Three Sisters improve soil together" or "insect hotels reduce pests" as facts is wrong (peer-reviewed evidence shows otherwise). If the mod teaches these sincerely and gets corrected by players, it loses credibility; if it teaches them skeptically ("traditional claim — evidence mixed"), it needs a design for that, which does not exist in any briefing.
- **The filesystem / git / CI state is broken enough that committing a feature change is risky.** The index/group-write failure on `btrfs` (`statvfs` reports 0 inodes free despite 24 GiB of blocks) and the 7 proprietary DLLs in `origin/dev` mean a feature branch could easily compound a licensing or build issue. The environment must be repaired first (see below).
- **No external user signal exists for this idea.** All demand is inferred from the assessment pipeline; no support ticket, no forum post, no Nexus comment was found asking for "soil health to crop growth" specifically.
